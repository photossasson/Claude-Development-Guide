עבודה עם Legacy Code

קוד Legacy הוא לא קוד ישן; הוא קוד שאי אפשר לשנות בביטחון. אין לו בדיקות, אין מי שזוכר למה הוא כתוב כך, והוא עובד, בערך, ב-Production. Claude Code הוא כלי חזק במיוחד בסביבה כזאת, כי הוא קורא מהר, מסביר בסבלנות ולא נבהל מ-400 שורות בפונקציה אחת. אבל הוא גם מסוכן במיוחד בה: הוא ינחש בביטחון, והניחוש שלו יישמע כמו ידיעה. הפרק מלמד שיטת עבודה: יום ראשון לקריאה בלבד, מפת ארכיטקטורה ומרשם סיכונים, בדיקות אפיון מהתנהגות נצפית ולא מהנחות, איתור בדיקות חסרות ו-Coupling נסתר, טיפול ב-Dependencies מיושנים, מודרניזציה מדורגת עם תנאי עצירה, הוכחת שימור התנהגות, מחיקה בטוחה, שחזור תיעוד, ותרחיש מלא על מודול ייצוא דוחות דמיוני מגרסה ותיקה של TaskFlow.

מה הופך קוד ל-Legacy

ההגדרה שנעבוד איתה, בעקבות הספרות המקובלת בתחום: קוד Legacy הוא קוד ללא בדיקות שמאפשרות לשנות אותו בביטחון. גיל אינו הקריטריון; יש קוד בן שבועיים שהוא Legacy וקוד בן עשור שאינו. סימני ההיכר בשטח:

  • אין רשת ביטחון: אין בדיקות, או שיש בדיקות שאיש לא מריץ כי חצי מהן אדומות.
  • אין זיכרון ארגוני: מי שכתב עזב; ההערות מתארות גרסה קודמת של הקוד; ה-Commit Messages אומרות "fix".
  • Coupling נסתר: מודולים תלויים זה בזה דרך משתנים גלובליים, סדר Imports, קבצים על הדיסק או טבלה משותפת בבסיס הנתונים.
  • פחד: הסימן החשוב ביותר. אם הצוות אומר "אל תיגע בזה", זה Legacy.

מה Claude Code נותן כאן: קריאה מהירה של כמויות גדולות של קוד, הסבר של מה הקוד עושה בפועל (להבדיל ממה שההערות טוענות), הצעות לנקודות תפר (Seams), וכתיבה מהירה של בדיקות אפיון. מה הוא לא נותן: ידיעה. כל טענה שלו על קוד שאין לו בדיקות היא השערה עד שאימתתם אותה בהרצה. הפרק כולו הוא, במובן מסוים, שיטה להפוך השערות של המודל לעובדות שנבדקו.

מתי להשתמש בשיטות של הפרק: כשנכנסים ל-Codebase לא מוכר, כשמקבלים בעלות על מודול שאיש לא מתחזק, ולפני כל Migration (פרק 35) על קוד בלי בדיקות. מתי לא: קוד עם חבילת בדיקות אמינה, גם אם הוא מכוער; שם עוברים ישר לפרק 12.

פרק 6 (קריאת Repository), פרק 7 (Plan Mode), פרק 11 (Testing), פרק 12 (Refactoring) ו-פרק 35 (Strangler, חוזה תאימות, תנאי עצירה). כלים: pytest, וכלי כיסוי כמו coverage אם תרצו לאמת טענות על בדיקות חסרות.

בדיקות אפיון (Golden Master): מהתנהגות, לא מהנחות

בדיקת אפיון מתעדת מה הקוד עושה היום, נכון או לא. היא לא שואלת "מה הוא צריך לעשות". ההבדל קריטי בעבודה עם מודל: אם תבקשו "write tests for exporter.py", Claude יקרא את הקוד, יסיק מה הוא אמור לעשות, ויכתוב בדיקות להסקה. הן יעברו (או שהוא "יתקן" את הקוד כדי שיעברו), ולא ילמדו אתכם כלום. הדרך הנכונה: להריץ את הקוד על קלטים מייצגים, ללכוד את הפלט כפי שהוא, ולהפוך אותו ל-Golden Master.

Prompt 5 (default mode)
Create characterization tests for app/reports/exporter.py using a
golden-master approach. Do NOT infer expected values from reading
the code. Instead: (1) write a small harness that seeds a temp DB
with a fixed set of tasks (fixed ids, titles with unicode and
commas, all statuses, fixed created_at values); (2) run each public
export function (csv, html) and SAVE the actual output to
tests/golden/<name>.txt; (3) write tests that re-run and compare
byte-for-byte to the saved files. Freeze time and any randomness.
If output differs between runs, report why instead of hiding it.

backend/tests/test_exporter_golden.py (המחשה)
from pathlib import Path

from app.reports import exporter

GOLDEN = Path(__file__).parent / "golden"


def test_csv_export_matches_golden(seeded_db, frozen_time):
    actual = exporter.export_csv()
    expected = (GOLDEN / "tasks.csv").read_text(encoding="utf-8")
    assert actual == expected


def test_html_export_matches_golden(seeded_db, frozen_time):
    actual = exporter.export_html()
    expected = (GOLDEN / "tasks.html").read_text(encoding="utf-8")
    assert actual == expected

כמה קלטים?

מעט קלטים שנבחרו היטב עדיפים על הרבה אקראיים: משימה עם פסיק וגרשיים בכותרת, כותרת ב-Unicode, תיאור ריק, כל ערך Status, ורשומה אחת ותיקה מאוד. בקשו מ-Claude להציע את "הקלטים המשונים ביותר שהקוד עלול לפגוש", ואז אשרו את הרשימה. את הבדיקות המבוססות-הנחות (מה הקוד צריך לעשות) תכתבו אחר כך, כשתבינו ותחליטו.

עוד נקודה שכדאי להבין: Golden Master הוא רשת ביטחון זמנית, לא חבילת הבדיקות הסופית. הוא נוקשה במכוון (כל שינוי בפלט מפיל אותו), ולכן הוא מצוין לתקופת ה-Refactoring ומעצבן אחריה. כשמסיימים לייצב את המודול, מחליפים אותו בהדרגה בבדיקות ממוקדות שמבטאות כוונה ("ייצוא CSV מצטט כותרת עם פסיק"), ואז אפשר למחוק את קבצי ה-Golden או להשאיר אחד כבדיקת עשן. גם ההחלפה הזאת נעשית ב-Commits קטנים, וגם בה שואלים את Claude להציע ואתם מאשרים.

איתור בדיקות חסרות ו-Coupling נסתר

עכשיו, עם רשת ביטחון ראשונית, מרחיבים אותה בכיוון הנכון: איפה אין כיסוי, ואיפה מודולים קשורים בדרכים שלא רואים.

איך מאמתים: טענת "לא מכוסה" מאומתת בדוח הכיסוי עצמו (coverage report -m מציג את השורות החסרות); אל תסתפקו בסיכום של Claude, בקשו את שורות הדוח הרלוונטיות. טענת "Coupling נסתר" מאומתת ב-grep: grep -rn "os.environ" backend/app, grep -rn "^_[a-z_]* = " backend/app למשתני מודול. הרעיון קבוע: הטענה של המודל היא Hypothesis, והפקודה היא ה-Test. על Testing שיטתי ראו פרק 11.

Dependencies מיושנים: טריאז' עם אבטחה קודם

ב-Codebase ותיק תמצאו Dependencies נעולים לגרסאות בנות שנים. הפיתוי הוא "לשדרג הכול"; זה מתכון לשבירה. הסדר הנכון:

  1. מלאי: רשימת התלויות הישירות והעקיפות, גרסה נוכחית, גרסה עדכנית, האם עדיין מתוחזקת.
  2. אבטחה קודם: הריצו את כלי הביקורת של האקוסיסטם (למשל pip-audit ל-Python או npm audit ל-Node.js) והפרידו פגיעויות ידועות מהכול. אלה מטופלות ראשונות, אחת אחת, כל אחת ב-Commit עם הרצת בדיקות האפיון.
  3. סוף חיים: ספרייה שאינה מתוחזקת היא סיכון גם בלי CVE. מתכננים החלפה (פרק 35, תרחיש 1 או 2), לא שדרוג.
  4. כל השאר: נשאר נעול עד שיש סיבה. יציבות היא ערך.

תסמיןאבחון וטיפול
בדיקת ה-Golden לא יציבה: עוברת ונכשלת לסירוגיןיש בפלט זמן, סדר לא מובטח, מזהים אקראיים או נתיבים מוחלטים. הקפיאו זמן ואקראיות בהרנס, הוסיפו ORDER BY בהרנס (לא בקוד), ונרמלו נתיבים. אל "תרככו" את ההשוואה

הרצת הקוד הישן בסביבת בדיקה נכשלת (חסר משתנה סביבה, קובץ, שירות)זו תגלית של Coupling נסתר. רשמו במרשם הסיכונים; פתחו Seam (פרמטר) במקום לחקות את הסביבה כולה
כלי הכיסוי או הביקורת לא מצליח לרוץודאו שהותקן ב-venv הנכון, ושה-Sandbox וההרשאות מאפשרים גישת רשת למאגר הפגיעויות (פרק 20). אם אין רשת, הריצו את הביקורת מחוץ ל-Session והדביקו את הפלט
הרצת Side by Side מראה הבדל שאינו מוסברעצרו את ההחלפה. בקשו מ-Claude לצמצם לקלט המינימלי שמייצר את ההבדל, הוסיפו אותו ל-Golden, והחליטו במודע מי צודק

Security

  • קוד Legacy הוא לרוב המקום עם הפגיעויות: SQL משורשר, Templating ללא Escaping, סודות בקוד. הסקירה הראשונה היא סקירת אבטחה, גם לפני ה-Refactoring; /security-review ו-Subagent ייעודי (פרק 34) עובדים גם על קוד קיים כשמבקשים סקירה של נתיב ולא של Diff.
  • נתוני Production בבדיקות: הרצת Side by Side נעשית על עותק מנוקה ממידע אישי; המודל לא מקבל גישה לנתונים אמיתיים.
  • Dependencies: ביקורת פגיעויות עם כלי עדכני, לא מזיכרון המודל.
  • מחיקה: אף פעם לא על סמך טענת המודל בלבד; ראיות סטטיות ודינמיות.

עלות ו-Context

קוד Legacy "אוכל" Context: קבצים ארוכים, הרבה קריאה, מעט כתיבה. שלושה הרגלים: האצלת קריאה ל-Subagents (מפת תלויות, מלאי, כיסוי); שמירת כל תוצר לקובץ (מפה, מרשם, Golden, תיעוד) כך שה-Session הבא מתחיל מקבצים ולא משיחה; ומודל חזק ו-Effort גבוה דווקא ביום הראשון ובניתוח הסיכונים, מודל מהיר יותר לכתיבת ההרנס והבדיקות. ראו פרק 30.

Best Practices

  • יום ראשון לקריאה בלבד, ב-Plan Mode, עם דרישה לראיה ולרמת ביטחון על כל טענה.
  • מרשם סיכונים ומפת ארכיטקטורה כקבצים ב-docs/, לא כשיחה.
  • Golden Master מהתנהגות נצפית; בדיקת מוטציה ידנית לפני שסומכים עליו.
  • אימות מדגמי של כל טענת "אין בדיקות", "קוד מת", "לא בשימוש" בפקודה אחת.
  • אבטחה קודם ב-Dependencies; השאר נשאר נעול עד שיש סיבה.
  • שינוי אחד ל-Commit: Seam, תיקון אבטחה, מחיקה, ניקיון, כל אחד לבד.
  • תיעוד מסומן "נצפה" או "מוסק", ו-CLAUDE.md שמשקף את מה שגיליתם.

Anti-patterns

  • השכתוב הגדול: "הקוד הזה נורא, תכתוב אותו מחדש". בלי Golden Master אין דרך לדעת מה אבד.
  • בדיקות מהנחות: בדיקות שנכתבו ממה שהמודל חושב שהקוד צריך לעשות.
  • ניקיון בזמן אפיון: "תיקנתי גם כמה דברים קטנים בדרך" בזמן שכותבים את רשת הביטחון.
  • מחיקה על סמך grep אחד: בלי ראיה דינמית או היסטורית.
  • תיעוד מהזיכרון: מסמך יפה שמתאר את מה שהמודל שיער, בלי סימון.

מה מבדיל פתרון טוב: (1) ביום הראשון אין אף Commit של קוד; יש שלושה קבצי docs/ ו-CLAUDE.md. (2) קבצי ה-Golden נוצרו מהרצה, וההוכחה היא שהם מכילים את הזמן המקומי "השגוי", כי כך הקוד מתנהג. (3) בדיקת המוטציה תועדה (פלט אדום, ואז החזרה). (4) תיקון ה-SQL המשורשר הוא Commit לבד, עם בדיקה שלילית של גרש בכותרת, וה-Golden ירוק לפניו ואחריו. (5) ה-Seam נפתח בלי לשנות התנהגות ברירת מחדל. (6) המחיקה של export_xml לא בוצעה בפועל ב-PR הזה; יש בו רק שורת Log ורשימת ראיות. (7) התיעוד מסמן [observed] ו-[inferred], ויש בו "שאלות פתוחות".

מלכודות טיפוסיות: Claude "מתקן" את התאריכים ל-UTC תוך כדי האפיון (דחו; רשמו במרשם); בדיקת HTML לא יציבה בגלל חותמת זמן (הקפאת זמן בהרנס); ו-grep על export_xml שמפספס קריאה במחרוזת ב-Template ישן (בדקו גם קבצים שאינם Python). אם ה-PR שלכם קטן ומשעמם, עשיתם את זה נכון.
