Plan לפני Implementation

הדרך המהירה ביותר לקבל קוד גרוע היא לבקש קוד מיד. בפרק הזה נלמד את Plan Mode: מצב שבו Claude Code חוקר ומציע תוכנית מפורטת בלי לגעת בקבצים, עד שאתם מאשרים. נראה איך נכנסים, מה מותר ומה חסום, איך נראה מסך אישור התוכנית ואיך עורכים תוכנית לפני ביצוע. נלמד לבקש חלופות ולהשוות Trade-offs, לתכנן שינויים שאינם שוברים, להעריך השפעה על Architecture, נתונים, API, אבטחה, ביצועים ובדיקות, ולהגדיר תנאי עצירה. בסוף נתכנן יחד, מקצה לקצה, פיצ'ר אמיתי ב-TaskFlow: תאריכי יעד למשימות.

מה זה Plan Mode ואיזו בעיה הוא פותר

Plan Mode הוא אחד ממצבי ההרשאות (Permission Modes) של Claude Code. כשהוא פעיל, Claude מונחה לחקור ולהציע שינויים בלי לבצע אותם: הוא קורא קבצים, מריץ פקודות חקירה, ומנסח תוכנית כתובה. עריכת קוד המקור חסומה עד שאתם מאשרים את התוכנית במסך אישור ייעודי. שורת הסטטוס מציגה plan mode on כשהמצב פעיל.

הבעיה שהמצב פותר מנוסחת בתיעוד הרשמי במשפט אחד: לתת ל-Claude לקפוץ ישר לקוד עלול להפיק קוד שפותר את הבעיה הלא נכונה. תוכנית כתובה, שאתם קוראים לפני שנכתבת שורת קוד, תופסת אי הבנות בשלב שבו תיקון עולה משפט אחד במקום Refactoring שלם. זה גם משנה את חוויית העבודה: במקום לפקח על עריכות בזמן אמת, אתם מבצעים Review אחד מרוכז על הכוונה, ואז משחררים את הביצוע.

העיקרון שמאחורי המצב נקרא בתיעוד "Explore, plan, code": קודם חקירה (כמו שלמדנו בפרק 6), אחר כך תוכנית, ורק אז מימוש, ולבסוף Commit. ארבעה שלבים, שני מצבים: השניים הראשונים ב-Plan Mode, השניים האחרונים אחרי האישור.

מתי להשתמש ומתי לא

מתי כן: התיעוד מגדיר זאת במדויק. תכנון משתלם כשאינכם בטוחים בגישה, כשהשינוי נוגע בכמה קבצים, או כשאתם לא מכירים את הקוד שמשתנה. כמו כן: שינויים ב-Schema של נתונים, שינויי API שמשפיעים על צרכנים, עבודה על קוד רגיש, וכל משימה שאתם מתכוונים לשחרר לריצה ארוכה בלי פיקוח צמוד.

מתי לא: התיעוד מזהיר במפורש ש-Plan Mode מוסיף תקורה. תיקון כתיב, הוספת שורת Log, שינוי שם משתנה: כלל האצבע הרשמי הוא שאם אתם יכולים לתאר את ה-Diff במשפט אחד, דלגו על התכנון ובקשו את השינוי ישירות.

מה מותר ומה חסום בזמן תכנון

  • מותר: קריאת קבצים, חיפוש, וכתיבת התוכנית עצמה. פקודות Shell מהסט המובנה של פקודות קריאה בלבד רצות חופשי.
  • מבוקר: פקודות מחוץ לסט הקריאה. כש-Auto Mode זמין בחשבונכם (וההגדרה useAutoModeDuringPlan פעילה, כברירת מחדל), מודל מסווג בודק את הפקודה ברקע: פקודות שאושרו רצות, והשאר נחסמות. בלי Auto Mode, כל פקודה כזו עוצרת לבקשת אישור רגילה.
  • חסום: עריכת קובצי קוד המקור. העריכות ממתינות עד לאישור התוכנית.
חריג שחשוב להכיר

ב-Sessions שהופעלו עם Bypass Permissions (למשל --dangerously-skip-permissions), התיעוד מציין שהחסימות של Plan Mode אינן נאכפות: Claude עדיין מונחה לתכנן בלי לערוך, אבל עריכה שהוא ינסה תרוץ בלי בקשת אישור. אל תסמכו על Plan Mode כמנגנון בטיחות בסביבה כזו. על מצבי ההרשאות במלואם: פרק 18.

מסך אישור התוכנית

כשהתוכנית מוכנה, Claude מציג אותה ושואל איך להמשיך. לפי התיעוד, אלו האפשרויות:

אפשרותמה היא עושה
Yes, and use auto modeמאשר את התוכנית ועובר לביצוע ב-Auto Mode (בדיקות בטיחות ברקע במקום בקשות אישור). כש-Auto Mode אינו זמין, האפשרות מופיעה כ-Yes, auto-accept edits, שמאשרת עריכות אוטומטית; ב-Session עם Bypass Permissions מופיע Yes, and bypass permissions
Yes, manually approve editsמאשר את התוכנית, וכל עריכה בביצוע תבקש אישור פרטני. הבחירה השמרנית והמומלצת למתחילים
No, refine with Ultraplan on Claude Code on the webשולח את התוכנית ל-Ultraplan, ממשק עידון תוכניות בדפדפן ב-Claude Code on the web
No, keep planningנשאר במצב תכנון; אתם כותבים מה לשנות בתוכנית

שלושה פרטים חשובים סביב האישור:

  • עריכה ישירה של התוכנית: לחיצה על Ctrl+G פותחת את התוכנית המוצעת בעורך הטקסט המוגדר במערכת שלכם. אתם עורכים, שומרים, ו-Claude ממשיך עם הגרסה שלכם. זה הכלי החזק ביותר לתיקונים כירורגיים בתוכנית.
  • אישור מחליף מצב: אישור תוכנית יוצא ממצב התכנון ומעביר את ה-Session למצב ההרשאות שהאפשרות שבחרתם מתארת. כדי לתכנן שוב, חוזרים עם Shift+Tab או /plan.
  • שם אוטומטי: אישור תוכנית גם מעניק ל-Session שם שנגזר מתוכן התוכנית (אלא אם כבר קבעתם שם עם /rename או --name), מה שמקל לאתר אותו אחר כך ב-/resume.
הגדרה שימושית לתוכניות ארוכות

ההגדרה showClearContextOnPlanAccept מוסיפה למסך האישור אפשרות ראשונה שמאשרת את התוכנית ומנקה את הקשר התכנון, כך שהביצוע מתחיל עם Context נקי שמכיל את התוכנית בלבד. שימושי כשהחקירה הייתה ארוכה במיוחד.

לבקש חלופות ולהשוות Trade-offs

תוכנית אחת היא הצעה; שתי תוכניות הן החלטה. אחד השימושים החזקים ב-Plan Mode הוא לדרוש חלופות מנומקות לפני בחירת כיוון:

Prompt (בתוך Plan Mode)
propose two alternative approaches for this feature. for each: the files
that change, effort estimate, risks, performance implications, and how hard
it would be to reverse later. then recommend one and justify the choice

דרשו שההשוואה תהיה קונקרטית: שמות קבצים, לא כותרות. "גישה א' משנה שלושה קבצים והפיכה ב-Commit אחד; גישה ב' דורשת Migration בלתי הפיך" זו השוואה שאפשר להחליט לפיה. אם ההמלצה של Claude לא משכנעת, אתם המחליטים: כתבו go with approach B, but keep the API surface of approach A והמשיכו בתכנון.

תכנון שינויים שאינם שוברים

שינוי שאינו שובר (Non-breaking) הוא שינוי שקוד קיים, נתונים קיימים וצרכני API קיימים ממשיכים לעבוד אחריו בלי התאמה. זו דרישה שצריך לכתוב ב-Prompt במפורש, כי בלעדיה Claude רשאי להציע גם מהלכים הורסים. תבניות מנוסחות היטב:

  • the change must be backward compatible: existing rows, existing API clients and existing tests must keep working unchanged
  • additive changes only: new optional fields and new endpoints are fine, changing or removing existing ones is not
  • if a breaking change is unavoidable, stop and present it as a separate decision instead of including it in the plan

בפועל, ב-Backend טיפוסי זה מתורגם ל: עמודות חדשות עם NULL או ערך ברירת מחדל במקום שינוי עמודות קיימות, שדות אופציונליים במודלים במקום שדות חובה, ו-Endpoints חדשים במקום שינוי חוזה של קיימים. את התבנית הזו נראה חיה בדוגמת ה-TaskFlow בהמשך.

רשימת בדיקה: הערכת השפעה בשישה ממדים

לפני שמאשרים תוכנית, עברו עליה עם הרשימה הזאת. תוכנית טובה עונה על כל שאלה; אם ממד חסר, זו בדיוק הסיבה לבחור "No, keep planning" ולבקש השלמה:

  • Architecture: אילו שכבות ורכיבים משתנים? האם השינוי מכבד את הגבולות הקיימים או יוצר תלות חדשה בין שכבות?
  • Data: האם ה-Schema משתנה? מה קורה לנתונים קיימים? האם נדרש Migration, והאם הוא הפיך?
  • API: אילו חוזים משתנים? האם צרכן קיים יכול להישבר? האם השינוי תוספתי בלבד?
  • Security: האם נוסף קלט משתמש חדש, ומי מבצע עליו Validation? האם משתנים הרשאות, Secrets או משטח תקיפה?
  • Performance: האם נוספות שאילתות, לולאות או קריאות רשת במסלולים חמים? מה קורה בנפחי נתונים גדולים?
  • Tests: אילו בדיקות חדשות נוספות? אילו קיימות צריכות עדכון? ומה פקודת האימות שמוכיחה שהכול עובד?

תנאי עצירה: לקבוע מראש מתי Claude עוצר

תוכנית טובה כוללת לא רק מה ייעשה, אלא מתי עוצרים לבדיקה. הגדירו זאת ב-Prompt התכנון, כדי שתנאי העצירה ייכנסו לתוכנית עצמה ויחייבו את שלב הביצוע:

Prompt: דוגמאות לתנאי עצירה
structure the plan in phases. at the end of each phase, run the tests
and stop for my review before starting the next phase.

stop immediately and ask me if: a test that passed before now fails,
the change requires touching a file outside backend/ and frontend/,
or you discover the schema change cannot be made backward compatible

שימו לב להבחנה: תנאי עצירה ב-Prompt הם הנחיה למודל, חזקים אך לא אכיפה קשיחה. שכבת האכיפה נשארת מצב ההרשאות: אם בחרתם "Yes, manually approve edits", כל עריכה ממילא עוברת דרככם. השילוב של שניהם, תוכנית עם שלבים ועצירות ועליה אישור עריכות ידני, הוא המסגרת הבטוחה ביותר לשינוי גדול. גבולות שאמרתם בשיחה ("אל תעשה Push עד שאבדוק") נלקחים ברצינות גם על ידי מנגנון ה-Auto Mode, שמתייחס אליהם כאות חסימה, אבל לערובה קשיחה השתמשו בחוקי deny שנלמד בפרק 18.

opusplan: מודל חזק לתכנון, חסכוני לביצוע

מכיוון שתכנון הוא שלב החשיבה הכבד, יש היגיון לתכנן עם מודל חזק ולבצע עם מודל מהיר וזול יותר. בדיוק לשם כך קיים ה-Model Alias בשם opusplan: לפי תיעוד תצורת המודלים, במצב תכנון הוא משתמש ב-opus לחשיבה מורכבת והחלטות ארכיטקטוניות, ובמעבר לביצוע הוא עובר אוטומטית ל-sonnet לכתיבת הקוד. מפעילים אותו כמו כל בחירת מודל:

$ claude --permission-mode plan --model opusplan

או מתוך ה-Session עם /model opusplan. זו דוגמה מצוינת להתאמת עלות למשימה; על משפחת המודלים, ה-Aliases והשיקולים לבחירה נרחיב בפרק 8.

דוגמה מציאותית מקצה לקצה: תכנון Due Dates ב-TaskFlow

נתכנן פיצ'ר אמיתי: תאריך יעד (Due Date) אופציונלי לכל משימה. זה פיצ'ר מייצג כי הוא חוצה את כל השכבות שמיפינו בפרק 6: Schema, מודלים, API, טיפוסים ו-UI. פתחו את ה-Session במצב תכנון:

$ claude --permission-mode plan

צעד 1: חקירה ממוקדת

Prompt
read the backend (app/models.py, app/database.py, app/routers/tasks.py),
the frontend (src/types.ts, src/api.ts, src/App.tsx) and the tests.
summarize how a task field flows through the system today,
and what it takes to add a new optional field end to end

מה קורה: Claude קורא את הקבצים (פעולות קריאה, בלי בקשות אישור) ומסכם: שדה חדש נוגע ב-Schema ב-database.py, בשלושת מודלי ה-Pydantic ב-models.py, בהרכבת ה-Task ב-_row_to_task, בטיפוסי ה-Frontend ב-types.ts, וב-UI. זו בדיוק תשתית הידע שהתוכנית תיבנה עליה.

צעד 2: בקשת התוכנית, עם אילוצים ותנאי עצירה

Prompt
create a detailed plan for adding an optional due_date to tasks.
requirements:
- backward compatible: existing rows, clients and tests keep working
- consider two storage options (ISO-8601 TEXT vs epoch INTEGER),
  compare and pick one
- include validation, tests, and impact on architecture, data, API,
  security, performance
- structure the work in phases: backend first, then frontend.
  plan a stop for my review after the backend phase

מה קורה: Claude מעבד את הדרישות ומציג תוכנית. הנה דוגמה מציאותית (מקוצרת) לתוכנית סבירה שתקבלו; הניסוח אצלכם יהיה שונה, המבנה צריך להיות דומה:

תוכנית לדוגמה (כפי ש-Claude מציג אותה)
# Plan: optional due_date for tasks

## Storage decision
ISO-8601 TEXT (e.g. "2026-08-15"), matching created_at which is
already TEXT via datetime('now'). Sorts correctly as a string,
human readable in SQLite. Epoch INTEGER rejected: saves little,
inconsistent with existing conventions.

## Phase 1: backend
1. database.py: add "due_date TEXT" (nullable) to CREATE TABLE.
   For existing databases add a startup migration:
   ALTER TABLE tasks ADD COLUMN due_date TEXT
   (guarded, runs only if the column is missing).
2. models.py: TaskCreate/TaskUpdate get optional due_date with
   date-format validation; Task gets due_date: Optional[str].
3. routers/tasks.py: include due_date in INSERT and _row_to_task.
   PATCH needs no change (model_dump(exclude_none=True)).
4. tests: create with/without due_date, invalid format 422,
   update due_date, old payloads still work.
Verification: cd backend && pytest -q
== STOP for user review ==

## Phase 2: frontend
5. types.ts: due_date?: string | null on Task and TaskCreate.
6. App.tsx: date input in the add form; show due date on items.
   api.ts needs no change (createTask passes the payload through).
Verification: cd frontend && npm run typecheck

## Impact summary
Architecture: no new layers or dependencies. Data: additive nullable
column, reversible. API: additive only, old clients unaffected.
Security: new input validated by Pydantic before SQL; parameterized
INSERT unchanged. Performance: negligible (no new queries).
Tests: 4 new backend tests; frontend covered by typecheck only.

צעד 3: ביקורת ותיקון התוכנית

עברו על התוכנית עם רשימת ששת הממדים. נניח ששמתם לב לפער אמיתי: התוכנית מוסיפה Validation לפורמט תאריך אבל לא מגדירה מה קורה עם תאריך בעבר. אל תאשרו; בחרו "No, keep planning" וכתבו:

Prompt
revise the plan: due dates in the past are allowed (importing old data
must work), but add a test that documents this decision explicitly.
also spell out the exact guard for the ALTER TABLE migration

Claude מעדכן את התוכנית ומציג אותה שוב לאישור. לחלופין, לתיקונים קטנים, לחצו Ctrl+G וערכו את הטקסט ישירות בעורך שלכם. שני המסלולים לגיטימיים; כתיבה חופשית מתאימה לשינויי כיוון, ועריכה ישירה לליטוש.

צעד 4: אישור ומעבר לביצוע

כשהתוכנית משקפת בדיוק את מה שאתם רוצים, בחרו "Yes, manually approve edits". ה-Session יוצא ממצב תכנון, Claude מתחיל לממש את שלב 1, וכל עריכה עוברת דרך בקשת אישור שבה אתם רואים את ה-Diff. בזכות תנאי העצירה שבתוכנית, אחרי ששלב ה-Backend עובר את הבדיקות Claude יעצור לביקורת שלכם לפני ה-Frontend. את מלאכת הביצוע המבוקר עצמה נעמיק בפרק 9.

Best Practice: תוכנית ששורדת

במשימות ארוכות, בקשו בסוף התכנון: save this plan to PLAN.md before implementing (שמירת הקובץ תבקש אישור, או תתבצע אחרי היציאה ממצב התכנון). התיעוד ממליץ על כך במיוחד בשינויים חוצי חבילות: שיחה ארוכה עוברת Compaction, וקובץ תוכנית שמור מחזיק מעמד גם כשהיסטוריית השיחה מסוכמת. בהמשך אפשר לבקש מ-Subagent לבדוק את ה-Diff מול PLAN.md.

שגיאות נפוצות

  • לאשר תוכנית אחרי קריאה ברפרוף. התוכנית היא ה-Review החשוב ביותר בתהליך. קראו אותה כמו Pull Request: כל קובץ שמוזכר, כל החלטה, כל מה שחסר.
  • לתכנן בלי אילוצים. "plan adding due dates" בלי דרישת תאימות לאחור, בלי חלופות ובלי תנאי עצירה מחזיר תוכנית גנרית. האילוצים הם המקום שבו המומחיות שלכם נכנסת לתהליך.
  • לתקן תוכנית דרך אישור וביטול. אם התוכנית לא טובה, אל תאשרו "כדי לראות מה יקרה". בחרו "No, keep planning"; תיקון מילולי בשלב התכנון זול פי כמה מ-Rewind אחרי ביצוע שגוי.
  • Plan Mode לכל דבר. תקורה של תכנון על תיקון של שורה היא בזבוז. זכרו את כלל ה-Diff במשפט אחד.
  • לשכוח שהאישור מחליף מצב. אחרי אישור עם "Yes, and use auto mode" אתם כבר לא במצב ברירת המחדל. שימו לב לשורת הסטטוס, וחזרו למצב המתאים עם Shift+Tab כשמתחילים משימה חדשה.
  • לבלבל בין תוכנית לבין ביצוע מובטח. תוכנית מאושרת אינה ערובה: הביצוע יכול לסטות כשמתגלות הפתעות. תנאי העצירה והבדיקות בכל שלב הם מה שמחזיר סטיות אליכם.

Troubleshooting

  • לא מוצאים את מצב התכנון: לחצו Shift+Tab כמה פעמים ועקבו אחרי שורת הסטטוס עד שמופיע plan mode on. אם המקש לא מגיב בטרמינל שלכם (קורה בחלק מסביבות Windows), התיעוד מציין את Alt+M כקיצור חלופי, ותמיד אפשר לפתוח עם claude --permission-mode plan.
  • Claude ביצע פעולה בזמן תכנון: בדקו מה בדיוק רץ ב-Ctrl+O. פקודות קריאה ופקודות שאושרו על ידי המסווג הן חלק מהתנהגות המצב המתועדת. אם נערך קובץ מקור, בדקו אם ה-Session הופעל עם Bypass Permissions (החריג שתואר למעלה).
  • Ctrl+G לא פותח עורך: הקיצור פותח את עורך ברירת המחדל של המערכת. ודאו שמשתנה הסביבה EDITOR (או VISUAL) מוגדר בטרמינל שלכם, למשל export EDITOR="code --wait".
  • התוכנית שטחית מדי: סימן שהחקירה הייתה רזה. חזרו לצעד החקירה ובקשו קריאה מפורשת של הקבצים הרלוונטיים לפני בקשת תוכנית מחודשת, או דרשו: the plan must name every file and function it touches.
  • אישרתם בטעות: Esc עוצר את הביצוע מיד. אם כבר בוצעו עריכות, /rewind משחזר את מצב הקבצים ל-Checkpoint שלפני (פרק 3, ובהרחבה בפרק 19).

Security

תכנון כשכבת הגנה, לא כתחליף לה

שלב התוכנית הוא נקודת הביקורת הטובה ביותר לתפוס פעולות מסוכנות לפני שהן קורות: מחיקות, Migrations הרסניים, שינויי הרשאות, פקודות רשת. חפשו אותן בתוכנית באופן אקטיבי. אבל זכרו שלוש מגבלות: התוכנית היא טקסט, והביצוע יכול לסטות ממנה; ב-Sessions עם Bypass Permissions חסימות המצב אינן נאכפות; וגם בזמן תכנון Claude קורא קבצים, כך שאזהרת ה-Prompt Injection מפרק 6 תקפה גם כאן, כולל האפשרות שתוכן עוין ינסה להשפיע על התוכנית עצמה. בקוד לא מהימן, תכננו במצב תכנון, בצעו עם אישור ידני, והשאירו את חוקי ה-deny פעילים. הרחבה: פרק 20.

שיקולי Cost ו-Context

כמה עולה תוכנית

תכנון צורך Tokens פעמיים: חקירה שממלאת את ה-Context בקריאות קבצים, וניסוח התוכנית עצמה. זו עלות שמחזירה את עצמה במשימות מורכבות (ביצוע שגוי עולה יותר), אבל היא בדיוק הסיבה שלא מתכננים תיקוני שורה. עם opusplan שלב התכנון רץ על opus, מודל יקר יותר, והביצוע חוזר ל-sonnet; קחו זאת בחשבון בתקציב. כלים לניהול: /context לבדיקת מצב, שמירת התוכנית לקובץ כדי שתשרוד Compaction, וההגדרה showClearContextOnPlanAccept שמתחילה את הביצוע עם הקשר נקי. הרחבה: פרק 14 ופרק 30.

Best Practices

  • עבדו בארבעת השלבים הרשמיים: Explore, ואז Plan, ואז Implement, ואז Commit. אל תדלגו מחקירה ישר לקוד במשימות מורכבות.
  • פתחו משימות גדולות עם claude --permission-mode plan, כך שהמחקר והתכנון מוגנים מהרגע הראשון.
  • כתבו את האילוצים בתוך בקשת התכנון: תאימות לאחור, חלופות, ממדי השפעה, תנאי עצירה.
  • העבירו כל תוכנית דרך רשימת ששת הממדים: Architecture, Data, API, Security, Performance, Tests.
  • דרשו שכל תוכנית תסתיים בצעד אימות מוכח: פקודת בדיקות ותוצאה צפויה.
  • תקנו תוכניות במילים ("No, keep planning") או ב-Ctrl+G; אשרו רק כשהייתם חותמים על זה כ-Reviewer.
  • במשימות ארוכות, שמרו את התוכנית ל-PLAN.md ובדקו את הביצוע מולה בסוף.
  • שקלו /model opusplan כשהתכנון הוא החלק הקשה של המשימה.

Anti-patterns

  • תכנון טקסי: להיכנס ל-Plan Mode כי "ככה נכון" ולאשר כל תוכנית תוך שניות. אם אינכם מתכוונים לקרוא את התוכנית, חסכתם לכולם זמן בלי המצב הזה.
  • תוכנית ענק אחת: תוכנית של עשרות צעדים בלי עצירות ביניים היא הימור אחד גדול. פרקו לשלבים עם אימות אחרי כל אחד.
  • לתכנן את מה שלא נחקר: בקשת תוכנית בלי שלב חקירה קודם מייצרת תוכנית מנותקת מהקוד. קודם קריאה, אחר כך תכנון.
  • יישור אוטומטי עם ההמלצה: לקבל תמיד את החלופה ש-Claude ממליץ עליה בלי לקרוא את הנימוקים. ההשוואה קיימת בשביל שאתם תחליטו.
  • שימוש ב-Plan Mode כ-Sandbox אבטחה: להריץ קוד לא מהימן "כי אנחנו רק בתכנון". המצב מגביל עריכות, הוא אינו סביבה מבודדת.

תרגיל

תרגיל 7.1: תכנון פיצ'ר סינון וחיפוש

תכננו ב-TaskFlow, בלי לממש, פיצ'ר חדש: סינון משימות לפי סטטוס וחיפוש טקסט חופשי בכותרת, דרך פרמטרים ב-GET /tasks (למשל ?status=todo&q=docs).

  1. פתחו Session עם claude --permission-mode plan והריצו חקירה ממוקדת של הקבצים הרלוונטיים.
  2. בקשו תוכנית עם הדרישות: תאימות לאחור מלאה, שתי חלופות למימוש הסינון (ב-SQL מול סינון בזיכרון ב-Python) עם השוואה והמלצה, כיסוי ששת ממדי ההשפעה, ותנאי עצירה אחרי ה-Backend.
  3. מצאו בתוכנית לפחות דבר אחד לתקן (רמז: מה קורה עם ערך status לא חוקי בפרמטר? והאם החיפוש משתמש בפרמטרים של SQL?), ותקנו עם "No, keep planning" או Ctrl+G.
  4. צאו ממצב התכנון עם Shift+Tab בלי לאשר, וודאו עם !git status ששום קובץ לא השתנה.
פתרון מוסבר

(1) חקירה טובה תקרא את routers/tasks.py, models.py ו-api.ts, ותזהה ש-list_tasks היום מחזירה הכול בלי פרמטרים. (2) תוכנית סבירה תמליץ על סינון ב-SQL עם WHERE ופרמטרים (?): הוא מנצל את בסיס הנתונים, נשאר יעיל כשהטבלה גדלה, ועקבי עם המוסכמה הקיימת של שאילתות עם פרמטרים. סינון בזיכרון פשוט יותר אך אינו מתרחב יפה. תאימות לאחור מובטחת כי שני הפרמטרים אופציונליים ו-GET /tasks בלי פרמטרים מתנהג בדיוק כמו היום. (3) שני התיקונים המתבקשים: status לא חוקי צריך להידחות עם 422 (למשל על ידי טיפוס TaskStatus בפרמטר) ולא להיכשל בשקט או להחזיר רשימה ריקה בלי הסבר; והחיפוש חייב לרוץ כ-LIKE עם פרמטר קשור ולא בשרשור מחרוזת לשאילתה, כדי לא לפתוח דלת ל-SQL Injection ראשונה בפרויקט. תוכנית שכוללת בדיקות לשני המקרים האלה היא תוכנית שעברה את ממד ה-Security וה-Tests באמת. (4) git status נקי מדגים את הנקודה המרכזית של הפרק: תכנון שלם, עם ביקורת ותיקונים, בלי ששורת קוד אחת השתנתה.

סיכום

Plan Mode הופך את סדר העבודה הנכון, קודם להבין ולתכנן ורק אז לכתוב, ממשמעת אישית למנגנון של הכלי. למדתם להיכנס (Shift+Tab, /plan, --permission-mode plan), מה מותר בזמן תכנון ומה חסום, ואיך עובד מסך האישור על ארבע אפשרויותיו, כולל עריכת תוכנית ישירה עם Ctrl+G. למדתם לבקש חלופות עם Trade-offs, לדרוש שינויים שאינם שוברים, להעריך השפעה בשישה ממדים, להגדיר תנאי עצירה, ולנצל את opusplan לחלוקת עבודה חכמה בין מודלים. ותרגלתם את כל זה על פיצ'ר אמיתי ב-TaskFlow בלי לשנות קובץ אחד. בפרק הבא נכיר מקרוב את המודלים עצמם: מתי Sonnet, מתי Opus, ואיך בוחרים נכון.
