Automation מקצועית

בפרק 32 בנינו סוכן עם ה-SDK. בפרק הזה נשלים את התמונה מהצד השני: הפעלת Claude Code עצמו כרכיב אוטומציה, בלי אדם מול המסך. נצלול לעומק מצב claude -p על כל הדגלים שלו, נלמד לנתח stream-json עם jq, נבנה תבניות ל-CI, למשימות מתוזמנות ולעיבוד אצווה על הרבה Repositories, נכיר את סוכני הרקע (--bg), ונסיים בדוגמה עבודה מלאה: משימת לילה שממיינת Issues חדשים של TaskFlow לדוח מסודר. ובאמצע, החלק החשוב מכולם: גבולות הבטיחות של אוטומציה ללא השגחה.

מה זה מצב לא אינטראקטיבי ואיזו בעיה הוא פותר

הדגל -p (או --print) הופך את claude מממשק שיחה לפקודת Unix רגילה: קלט נכנס (ארגומנט או stdin), הסוכן רץ את הלולאה המלאה שלו עם כלים, פלט יוצא ל-stdout, וקוד היציאה מדווח הצלחה או כישלון. זה מה שמאפשר לשלב את Claude Code בכל מקום שסקריפט יכול לרוץ בו: CI, cron, Git Hooks, סקריפטים של Build. התיעוד הרשמי מגדיר את זה כדרך להשתמש ב-Agent SDK "דרך ה-CLI", וזו גם הדרך הרשמית להפעיל את הלולאה מכל שפה שאינה Python או TypeScript.

מתי להשתמש: משימות חד-כיווניות שאפשר לנסח מראש (סיכום, סיווג, בדיקה, דוח). מתי לא: כשנדרשת שיחה אמיתית עם החלטות תלויות-תשובה (לכו ל-SDK, פרק 31), או כשנדרש אישור אנושי בזמן אמת (אין מי שיאשר). ההבדל בין claude -p לבין ה-SDK אינו ביכולות (אותו מנוע), אלא בנוחות: הסקריפט נותן לכם טקסט או JSON וקוד יציאה; ה-SDK נותן אובייקטי הודעה מוקלדים, Callbacks להרשאות ושליטה עדינה יותר. לרוב האוטומציות של צוות פיתוח, -p מספיק ומהיר יותר לכתיבה.

דרישות מוקדמות

Claude Code מותקן (פרק 2), היכרות עם כללי ההרשאות (פרק 4) ועם Hooks (פרק על Hooks), הכלים jq ו-gh מותקנים לדוגמאות, ומפתח ANTHROPIC_API_KEY לריצות במצב --bare.

צלילה לעומק: claude -p והדגלים שלו

הבסיס וצינורות

$ claude -p "What does the auth module do?" $ cat build-error.txt | claude -p 'concisely explain the root cause of this build error' > output.txt

מצב -p קורא stdin, כך שאפשר להזרים אליו נתונים כמו לכל כלי שורת פקודה. מגבלה מתועדת: קלט מוזרם מוגבל ל-10MB; מעבר לזה התהליך יוצא עם שגיאה ברורה וקוד יציאה שונה מאפס. לקבצים גדולים, כתבו לקובץ ותנו ל-Claude את הנתיב ב-Prompt. עוד דוגמה מהתיעוד שממחישה את הרעיון "Claude כפקודת Unix": סקריפט npm שמזרים git diff main ל-Claude כ-Linter של שגיאות כתיב, בלי לתת לו שום הרשאת Bash, כי ה-Diff כבר הגיע דרך הצינור.

הדגלים המרכזיים, אחד אחד

דגלמה הוא עושההערות מהתיעוד
--output-formatפורמט הפלט: text (ברירת מחדל), json (תוצאה + מטא-נתונים: מזהה Session, שימוש, עלות), stream-json (שורת JSON לכל אירוע, בזמן אמת)ב-json הטקסט נמצא בשדה result; העלות ב-total_cost_usd היא אומדן צד-לקוח
--json-schemaפלט מובנה: JSON שאומת מול הסכמה שסיפקתם, בשדה structured_outputעובד עם --output-format json; סכמה לא תקינה מפילה את הריצה עם שגיאה מפורשת (מאז v2.1.205)
--include-partial-messagesמוסיף אירועי Streaming חלקיים (Token אחרי Token) לזרםדורש --print וגם --output-format stream-json (ועל פי דוגמאות התיעוד גם --verbose)
--max-turnsתקרת סבבי כלים; חריגה מסתיימת בשגיאהמצב print בלבד; אין מגבלה כברירת מחדל
--max-budget-usdתקרת הוצאה משוערת לריצהמצב print בלבד; הוצאות Subagents נספרות, ומ-v2.1.217 חציית התקרה גם עוצרת Subagents פעילים
--bareמצב מינימלי: בלי טעינת Hooks, Skills, Plugins, שרתי MCP, זיכרון אוטומטי ו-CLAUDE.mdמומלץ רשמית לסקריפטים ול-CI; מהיר יותר וצפוי יותר (אותה תוצאה בכל מכונה). לא קורא אישורי OAuth, ולכן דורש ANTHROPIC_API_KEY. מתועד שיהפוך לברירת המחדל של -p בגרסה עתידית
--allowedTools / --disallowedToolsכללי Allow ו-Deny בתחביר כללי ההרשאותהבסיס להרצה ללא השגחה; ראו סעיף הבטיחות
--permission-modeמצב הרשאות בסיסי לריצה: dontAsk לריצות נעולות, acceptEdits לעריכות בלי שאלות, plan לתכנון בלבדב-acceptEdits פקודות Shell שאינן פעולות מערכת קבצים עדיין דורשות Allow, אחרת הריצה נעצרת כשמנסים אותן
--append-system-promptמוסיף הוראות ל-System Prompt בלי להחליף את ברירת המחדלב---bare זו הדרך להזרים "פרסונה" (למשל: סוקר אבטחה) בלי CLAUDE.md
--continue / --resumeהמשך השיחה האחרונה, או שיחה ספציפית לפי מזההאת המזהה שולפים מפלט json: jq -r '.session_id'

ב---bare Claude מקבל את כלי ה-Bash, קריאת הקבצים ועריכת הקבצים; כל הקשר נוסף (הגדרות, שרתי MCP, Agents מותאמים, Plugin) מזריקים במפורש בדגלים: --settings, --mcp-config, --agents, --plugin-dir. זה בדיוק ההיפך מהמצב האינטראקטיבי, שבו הכול נטען אוטומטית מהתיקייה ומ-~/.claude, וזה מה שהופך את הריצה לניתנת לשחזור.

התנהגות יציאה וזמנים: מה שסקריפטים חייבים לדעת

  • קודי יציאה: 0 בהצלחה, שונה מאפס בכישלון, כך שאפשר להתנות עליהם (if claude -p ... ; then). דגל לא תקין מדווח ל-stderr לפני הריצה; כשל בתוך הריצה (למשל בעיית אימות) מודפס כתוצאה ב-stdout.
  • עצירה מבחוץ: SIGTERM (למשל kill או Supervisor) קוטע את התור, מסיים את עץ התהליכים של פקודות Bash רצות, מריץ Hooks מסוג SessionEnd, ויוצא עם קוד 143.
  • משימות רקע בסיום: תהליך רקע ש-Claude פתח (כמו שרת פיתוח) מסתיים כחמש שניות אחרי התוצאה הסופית. Subagents ברקע מחריגים: הריצה ממתינה להם, עם תקרה של עשר דקות כברירת מחדל (משתנה CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS).
  • Timeouts של API: אין "timeout כולל" מובנה לריצה; שולטים בהתנהגות מול ה-API עם משתני סביבה מתועדים כמו API_TIMEOUT_MS (ברירת מחדל 600000 מילישניות לבקשה) ו-CLAUDE_CODE_MAX_RETRIES. תקרת זמן כוללת לסקריפט אוכפים בכלי המערכת, למשל timeout 20m claude -p ....
  • ניסיונות חוזרים ב-API: בזרם stream-json מופיע אירוע system/api_retry לפני כל ניסיון חוזר, עם מספר הניסיון, ההשהיה וקטגוריית השגיאה (rate_limit, overloaded, server_error ועוד). שימושי להצגת התקדמות או ללוגיקת Backoff משלכם.

ניתוח stream-json עם jq

ב-stream-json כל שורה היא אובייקט JSON: אירוע system/init עם מטא-נתונים, הודעות assistant ו-user (תוצאות כלים), אירועי stream_event חלקיים אם ביקשתם, ולבסוף שורת result. הדוגמה הרשמית להצגת הטקסט בלבד, Token אחרי Token:

Bash
claude -p "Write a poem" --output-format stream-json --verbose --include-partial-messages | \
  jq -rj 'select(.type == "stream_event" and .event.delta.type? == "text_delta") | .event.delta.text'

הדגל -r מדפיס מחרוזות גולמיות בלי מירכאות ו--j מדביק בלי שורות חדשות, כך שהטקסט זורם ברצף. אם הצרכן קורא לאט, Claude Code ממתין לריקון התור לפני היציאה (עד 30 שניות), כך שסוף התשובה לא נחתך. הודעות של Subagents מופיעות בזרם עם parent_tool_use_id שמצביע על קריאת ה-Agent שיצרה אותן, ובברירת מחדל רק בלוקי הכלים שלהם נשלחים; הדגל --forward-subagent-text מוסיף גם את הטקסט שלהם לשחזור תמליל מלא. עוד שני שימושים מעשיים ב-jq על פלט json רגיל:

Bash
# שליפת הטקסט בלבד
claude -p "Summarize this project" --output-format json | jq -r '.result'

# שליפת עלות משוערת ומזהה Session לרישום
claude -p "..." --output-format json | jq '{cost: .total_cost_usd, session: .session_id}'

תבניות CI כלליות

בפרק 28 ראינו את האינטגרציה הייעודית ל-GitHub Actions. התבנית הכללית, לכל מערכת CI (GitLab CI, Jenkins, Buildkite וכדומה), היא Job שמריץ claude -p עם ברירות מחדל בטוחות:

ci-review.sh (תבנית Job גנרית ל-CI)
#!/usr/bin/env bash
set -euo pipefail

# סוקר Diff ב-CI: קריאה בלבד, מצב bare, תקציב ותקרות קשיחים.
# דורש: ANTHROPIC_API_KEY כסוד של מערכת ה-CI (לעולם לא בקוד).

git diff origin/main...HEAD | claude --bare -p \
  "You are a code reviewer. List concrete problems in this diff: bugs, security issues, missing tests. If none, reply exactly: LGTM" \
  --allowedTools "Read,Grep,Glob" \
  --permission-mode dontAsk \
  --max-turns 15 \
  --max-budget-usd 0.50 \
  --output-format json > review.json

jq -r '.result' review.json
# שער איכות אופציונלי: הפלת ה-Job כשיש ממצאים
if ! jq -er '.result | test("^LGTM$")' review.json > /dev/null; then
  echo "Review findings detected" >&2
  exit 1
fi

הרכיבים שהופכים את זה לבטוח וצפוי: --bare מנתק את הריצה מהגדרות מקומיות של המכונה (Hook של מישהו ב-~/.claude לא ירוץ ב-CI שלכם); --permission-mode dontAsk דוחה בשקט כל מה שלא אושר במקום להיתקע על שאלה שאין מי שיענה עליה; רשימת --allowedTools היא קריאה בלבד; והצינור (git diff | ...) מזרים את ה-Diff פנימה כך ש-Claude לא צריך בכלל הרשאת Bash כדי לקרוא אותו. שימו לב גם לתקציב: ב-CI שרץ על כל Push, חצי דולר לריצה הם ההבדל בין ניסוי לחשבון מפתיע בסוף החודש.

שתי הערות על העברת הסקריפט למערכות CI שונות: ב-GitLab CI ה-Job מקבל את המפתח כ-CI/CD Variable מסומן Masked, וה-Runner צריך את claude ו-jq ב-Image (או שלב התקנה); ב-Jenkins משתמשים ב-withCredentials כדי לחשוף את המפתח רק לשלב הרלוונטי. בכל מערכת, זכרו ש-git diff origin/main...HEAD דורש שה-Checkout יכלול את ההיסטוריה של main (Fetch Depth מלא או לפחות ה-Branch הראשי), אחרת ה-Diff יהיה ריק והסוקר יענה "LGTM" על כלום.

Best Practice

בזרימת stream-json ב-CI אפשר גם לתפוס תקלות טעינה: אירוע ה-system/init כולל שדות plugin_errors ו-mcp_server_errors (כשהם לא ריקים), והתיעוד מציע להפיל את ה-Job כשהם קיימים, כדי ש-Plugin או שרת MCP שלא נטען לא יהפוך ל"עבר בשקט".

משימות מתוזמנות: cron + claude -p

לתזמון קבוע משתמשים בכלי התזמון של מערכת ההפעלה. התבנית: סקריפט עטיפה שמגדיר סביבה, מריץ claude -p עם גבולות, ושומר פלט ולוג עם חותמת זמן. שורת crontab טיפוסית להרצה לילית ב-02:30:

crontab -e
30 2 * * * /home/dev/automation/nightly-triage.sh >> /home/dev/automation/triage.log 2>&1

שלוש מלכודות של cron שכדאי להכיר: הסביבה של cron מינימלית (אין את ה-PATH וה-Aliases שלכם, אז נתיבים מלאים ומשתני סביבה מפורשים בתוך הסקריפט); אין טרמינל (בדיוק בשביל זה קיימים -p ו-dontAsk); ואין מי שיקרא שגיאות בזמן אמת (לכן הפניית הפלט ללוג היא חובה, לא קישוט). ב-Windows המקבילה היא Task Scheduler עם סקריפט PowerShell, ואותם עקרונות חלים. את הדוגמה המלאה של סקריפט הלילה תראו בסוף הפרק.

ומה עם תזמון מתוך Claude עצמו?

קיימים גם כלים מובנים לתזמון (CronCreate, CronList, CronDelete ברשימת ה-Tools הרשמית) ומשימות מתוזמנות באפליקציות Claude. הם שייכים לעולם ה-Sessions האינטראקטיביים והמוצרים האחרים, ואינם תחליף ל-cron של מערכת ההפעלה כשמדובר בסקריפט -p על שרת. לאוטומציית שרת, cron (או המקבילה בקונטיינר) נשאר הכלי הנכון.

עיבוד אצווה על הרבה Repositories

כשאותה משימה צריכה לרוץ על עשרות פרויקטים (סריקת חבילות פגיעות, איתור TODO ישנים, בדיקת עמידה בסטנדרט), התבנית היא לולאה עם תקציב כפול: תקציב לכל Repository ותקציב כולל לאצווה, בדיוק כמו שעשינו ב-SDK בפרק 32. מימוש ה-TypeScript המלא של התבנית הזאת נמצא בחבילת המדריך בקובץ agent-sdk/typescript/02-automation.ts (עבר בדיקת טיפוסים עם tsc מול גרסת ה-SDK הנוכחית); הנה אותה תבנית כ-Bash טהור:

batch-scan.sh (קטע)
#!/usr/bin/env bash
set -euo pipefail
TOTAL_BUDGET=5.00
SPENT=0

for repo in ~/work/repos/*/ ; do
  # עצירת האצווה כשהתקציב הכולל נגמר
  if awk "BEGIN {exit !($SPENT >= $TOTAL_BUDGET)}"; then
    echo "batch budget reached (~\$$SPENT); stopping" >&2
    break
  fi
  out=$(cd "$repo" && claude --bare -p \
    "Count TODO/FIXME comments and list files with none of their functions tested. Reply as a short report." \
    --allowedTools "Read,Grep,Glob" \
    --permission-mode dontAsk \
    --max-turns 10 --max-budget-usd 0.25 \
    --output-format json) || { echo "FAILED: $repo" >&2 ; continue ; }
  cost=$(jq -r '.total_cost_usd // 0' <<< "$out")
  SPENT=$(awk "BEGIN {printf \"%.4f\", $SPENT + $cost}")
  jq -r '.result' <<< "$out" > "reports/$(basename "$repo").md"
done

שימו לב ל-|| { ...; continue; }: כשל ב-Repository אחד לא מפיל את האצווה, אבל כן נרשם. ריצה סדרתית היא בכוונה: היא מפזרת עומס, מכבדת מגבלות קצב, ומשאירה את חשבון הTokens קריא. אם צריך מקבול, הריצו קבוצות קטנות והשוו עלויות קודם. ובאותו הקשר, אם אצווה של עשרות Repositories צריכה גם לכתוב (למשל תיקון אוטומטי של קובץ תצורה), הפכו כל שינוי ל-Branch ול-PR נפרד; אצווה שכותבת ישירות ל-main היא בדיוק סוג האוטומציה שהסעיף הבא אוסר.

סוכני רקע: --bg, claude agents ו-daemon

לצד -p הסינכרוני, ל-Claude Code יש מנגנון מתועד לסוכנים ברקע על המכונה שלכם:

פקודהמה היא עושה
claude --bg "task"מפעיל את המשימה כ-Session רקע וחוזר מיד, עם הדפסת מזהה ה-Session ופקודות הניהול. לא ניתן לשילוב עם -p. עם --exec מריץ פקודת Shell כ-Job רקע, ועם --agent מריץ Subagent מוגדר
claude agentsפותח את תצוגת הסוכנים (Agent View) למעקב ושליחת משימות; --json מדפיס את ה-Sessions הפעילים כמערך JSON לסקריפטים, ו---json --all כולל גם Sessions שהסתיימו
claude daemon statusמדפיס את מצב תהליך ה-Supervisor שמארח את סוכני הרקע (גרסה, Socket, מספר Workers); קוד יציאה 1 אם אינו רץ
claude daemon stop --anyעוצר את ה-Supervisor ואת ה-Sessions שהוא מארח; עם --keep-workers משאיר את סוכני הרקע רצים לחיבור מחדש

ההבחנה החשובה: --bg נועד למשימות שאתם משגרים מהטרמינל וממשיכים לעבוד לידן (והן עדיין תחת מערכת ההרשאות הרגילה), בעוד -p נועד לאוטומציה סקריפטואלית. אל תערבבו: תזמון לילי בונים על -p, לא על --bg.

גבולות בטיחות לאוטומציה

מה לעולם לא מריצים ללא השגחה

סוכן אוטומטי טועה לפעמים, ובלי אדם בלולאה הטעות מבוצעת עד הסוף. לכן, ללא קשר לכמה ה-Prompt "בטוח", אל תתנו לריצה לא מושגחת יכולת לבצע: Deploy ל-Production, מיגרציות Database, git push --force (או בכלל push ישיר ל-main), מחיקות רחבות, שינויי הרשאות והוצאת סודות. הכלל המנחה: פעולה שאי אפשר לבטל בקלות דורשת אדם. והדגל --dangerously-skip-permissions שמור אך ורק לסביבות מבודדות (קונטיינר ללא רשת וללא סודות), כפי שהוזהר בפרקים 4 ו-24.

שערי אישור אנושיים הם הדרך לקבל גם אוטומציה וגם שליטה:

  • הפרדת תכנון מביצוע: ריצה אוטומטית עם --permission-mode plan מפיקה תוכנית בלי לגעת בקבצים; אדם קורא את הפלט ומריץ את הביצוע בנפרד. זו גרסת ה-CLI לשער האישור שבנינו בפרק 32.
  • זרימה מבוססת PR: האוטומציה רשאית לערוך רק ב-Branch ולפתוח Pull Request; ה-Merge נשאר אנושי, עם כל הגנות ה-Branch הרגילות. כך גם טעות של סוכן היא רק PR שנדחה.
  • Hooks כשערים: Hook מסוג PreToolUse רץ לפני כל קריאת כלי, בכל מצב הרשאות כולל bypassPermissions, ולכן הוא השער האמין ביותר לחסימת פקודות אסורות (ראו ה-Hook החוסם שבנינו בפרק על Hooks). שימו לב: ב---bare Hooks לא נטענים אוטומטית, אז מזריקים אותם דרך --settings אם הם חלק מהמעקות.

הרשאה מינימלית בדגלים: תמיד --allowedTools עם רשימה מפורשת וצרה (עדיף כללים עם תבנית, כמו "Bash(git diff *)", מאשר "Bash" גורף), --disallowedTools לכל מה שאסור שיהיה קיים בכלל, ו---permission-mode dontAsk כדי שכל השאר יידחה בשקט. בסביבות רגישות מוסיפים בידוד ברמת מערכת ההפעלה: קונטיינר ייעודי, משתמש מוגבל, ו-Sandboxing של Claude Code (פרק 24) לצמצום גישת קבצים ורשת. וכלל אחרון, מהניסיון: אוטומציה שכותבת צריכה Repository נקי בתחילת הריצה ו-git diff נשמר בסופה; כך תמיד אפשר לענות "מה בדיוק הסוכן שינה", וזו השאלה הראשונה שנשאלת כשמשהו משתבש.

דוגמה עבודה מלאה: טריאז' לילי ל-Issues של TaskFlow

נחבר הכול: משימת לילה שאוספת את ה-Issues הפתוחים החדשים של פרויקט TaskFlow מ-GitHub, נותנת ל-Claude לסווג כל אחד (סוג, דחיפות, קבצים רלוונטיים בקוד) בעזרת חקירת ה-Repository בקריאה בלבד, ומפיקה דוח Markdown שממתין לצוות בבוקר. הסקריפט המלא:

automation/nightly-triage.sh
#!/usr/bin/env bash
# Nightly triage of new TaskFlow issues into a Markdown report.
# Requirements: claude, gh (authenticated), jq. ANTHROPIC_API_KEY must be set
# (cron runs with a minimal environment, so we load it explicitly).
set -euo pipefail

REPO_DIR="$HOME/projects/taskflow"
OUT_DIR="$HOME/automation/reports"
STAMP="$(date +%Y-%m-%d)"
REPORT="$OUT_DIR/triage-$STAMP.md"
export PATH="/usr/local/bin:/usr/bin:/bin:$HOME/.local/bin"
# shellcheck source=/dev/null
source "$HOME/automation/secrets.env"   # מכיל: export ANTHROPIC_API_KEY=...

mkdir -p "$OUT_DIR"
cd "$REPO_DIR"

# 1. איסוף Issues פתוחים מהיממה האחרונה (gh מחזיר JSON מובנה)
since="$(date -u -d 'yesterday' +%Y-%m-%dT%H:%M:%SZ)"
gh issue list --state open --search "created:>$since" \
  --json number,title,body,labels > /tmp/new-issues.json

count="$(jq 'length' /tmp/new-issues.json)"
if [ "$count" -eq 0 ]; then
  echo "# TaskFlow triage $STAMP" > "$REPORT"
  echo "No new issues in the last 24 hours." >> "$REPORT"
  exit 0
fi

# 2. סכמת הפלט: סיווג לכל Issue
schema='{
  "type": "object",
  "properties": {
    "triage": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "issue_number": {"type": "number"},
          "category": {"type": "string", "enum": ["bug", "feature", "question", "docs"]},
          "priority": {"type": "string", "enum": ["high", "medium", "low"]},
          "relevant_files": {"type": "array", "items": {"type": "string"}},
          "suggested_next_step": {"type": "string"}
        },
        "required": ["issue_number", "category", "priority", "suggested_next_step"]
      }
    }
  },
  "required": ["triage"]
}'

# 3. הרצת הטריאז': קריאה בלבד, bare, תקציב ותקרות קשיחים
cat /tmp/new-issues.json | timeout 20m claude --bare -p \
  "These are new GitHub issues for this repository (JSON on stdin). For each issue: categorize it, set priority, locate the most relevant source files by exploring the repository, and suggest a concrete next step." \
  --allowedTools "Read,Grep,Glob" \
  --permission-mode dontAsk \
  --max-turns 30 \
  --max-budget-usd 1.00 \
  --output-format json \
  --json-schema "$schema" > /tmp/triage-result.json

# 4. כשל => דוח שגיאה במקום דוח ריק שקט
if ! jq -e '.structured_output.triage' /tmp/triage-result.json > /dev/null; then
  {
    echo "# TaskFlow triage $STAMP: FAILED"
    echo '```'
    jq -r '.result // "no result field"' /tmp/triage-result.json
    echo '```'
  } > "$REPORT"
  exit 1
fi

# 5. בניית דוח Markdown מהפלט המובנה
{
  echo "# TaskFlow triage $STAMP ($count new issues)"
  echo
  jq -r '.structured_output.triage[] |
    "## Issue #\(.issue_number): \(.category) / \(.priority)\n" +
    "- Next step: \(.suggested_next_step)\n" +
    "- Files: \((.relevant_files // []) | join(", "))\n"' /tmp/triage-result.json
  cost="$(jq -r '.total_cost_usd // 0' /tmp/triage-result.json)"
  echo "---"
  echo "Estimated cost: \$$cost (client-side estimate)"
} > "$REPORT"

echo "Report written to $REPORT"

נעבור על ההחלטות: ה-Issues נאספים עם gh ומוזרמים ב-stdin, כך שלסוכן אין שום הרשאת רשת או gh משלו; הכלים המאושרים הם קריאה בלבד, בדיוק מה שנדרש כדי לאתר קבצים רלוונטיים; --json-schema מבטיח שהדוח נבנה מנתונים מובנים ולא מניתוח טקסט שביר; timeout 20m נותן תקרת זמן כוללת; וכשל מפיק דוח שגיאה גלוי במקום כלום. חיברו את הסקריפט לשורת ה-crontab מהסעיף הקודם, וזהו: טריאז' אוטומטי, מוגבל תקציב, ללא יכולת כתיבה.

תוצאה צפויה: קובץ triage-2026-07-29.md (לפי התאריך) עם כותרת לכל Issue, קטגוריה ודחיפות, צעד מומלץ ורשימת קבצים, ובסופו שורת עלות. אימות: הריצו את הסקריפט ידנית פעם אחת לפני שמחברים אותו ל-cron (bash -x nightly-triage.sh מציג כל פקודה), פתחו את הדוח שנוצר, ובדקו שהקבצים שהסוכן ציין אכן קיימים ב-Repository. אם הדוח מסומן FAILED, הטקסט הגולמי של Claude בתוכו יסביר למה, לרוב סכמה שלא סופקה או תקציב שנגמר על יותר מדי Issues.

מה אומת

תחביר הסקריפט אומת עם bash -n ומבנה שאילתות ה-jq נבדק על נתוני דמה בסביבת העבודה של המדריך. הרצה מלאה מקצה לקצה דורשת מפתח API ו-gh מאומת, שאינם זמינים בסביבת הכתיבה; ההתנהגות מתוארת לפי התיעוד הרשמי של הדגלים.

שיקולי Cost ו-Context

  • אוטומציה מכפילה עלויות בשקט: ריצה של 0.30 דולר פעם בשעה היא בערך 216 דולר בחודש. תמיד --max-budget-usd לריצה, ורישום total_cost_usd מכל ריצה ללוג מרכזי (זכרו: אומדן, לא חיוב; לנתוני אמת ראו פרק 30).
  • --bare חוסך גם Context: בלי CLAUDE.md, Skills ו-MCP שאינם רלוונטיים למשימה, ה-Prompt קטן והתוצאה יציבה יותר בין מכונות.
  • משימות ליליות הן מקום טבעי למודל קטן יותר: הוסיפו --model haiku (או כינוי מודל אחר זמין) למשימות סיווג פשוטות, ושמרו את המודל הגדול למשימות הסקה כבדות.
  • הזרמת הנתונים ב-stdin במקום לתת לסוכן "ללכת להביא" אותם חוסכת גם Turns וגם הרשאות: פחות קריאות כלים, פחות Tokens, ומשטח תקיפה קטן יותר.

רשימת בדיקה: לפני שהאוטומציה רצה לבד

  • כל הרצה לא-אינטראקטיבית מוגבלת בשלושה צירים: --max-turns, --max-budget-usd ו-Timeout של ה-Job או ה-cron.
  • סט הכלים מצומצם במפורש (--allowedTools או --permission-mode dontAsk עם חוקי allow), ואין --dangerously-skip-permissions מחוץ למכולה מבודדת.
  • האישורים הם מפתח או Token ייעודי לאוטומציה, שאפשר לבטל בלי לפגוע במפתחים, ונשמרים ב-Secrets של פלטפורמת ה-CI.
  • הפלט נאסף כ-JSON (--output-format json) ונבדק תוכניתית, כולל קוד היציאה; כישלון שקט אינו אפשרות.
  • כל תוצר שהסוכן מייצר (PR, תגובה, דוח) עובר דרך אדם לפני שהוא משפיע על אחרים.
  • יש נתיב עצירה ידני מתועד: claude stop לסוכני רקע, ביטול ה-Workflow, או הסרת ה-cron.

תרגיל

תרגיל 33.1: שער איכות שבועי ל-Dependencies

כתבו סקריפט weekly-deps.sh שרץ כל יום ראשון ב-06:00 ועושה: (1) קורא את backend/requirements.txt של TaskFlow; (2) מריץ claude --bare -p שמסווג כל תלות לפי סיכון עדכון (outdated_major / outdated_minor / current / unknown) על סמך מה שידוע לו, עם פלט מובנה; (3) כותב דוח Markdown; (4) יוצא עם קוד 1 אם יש תלות בסיווג outdated_major, כדי שמערכת ניטור תתריע. דרישות בטיחות: קריאה בלבד, dontAsk, תקציב 0.20 דולר, ו-timeout כולל של 10 דקות. כתבו גם את שורת ה-crontab.

פתרון מוסבר
automation/weekly-deps.sh
#!/usr/bin/env bash
set -euo pipefail
REPO_DIR="$HOME/projects/taskflow"
REPORT="$HOME/automation/reports/deps-$(date +%Y-%m-%d).md"
export PATH="/usr/local/bin:/usr/bin:/bin"
source "$HOME/automation/secrets.env"
cd "$REPO_DIR"

schema='{
  "type": "object",
  "properties": {
    "dependencies": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": {"type": "string"},
          "status": {"type": "string",
            "enum": ["outdated_major", "outdated_minor", "current", "unknown"]},
          "note": {"type": "string"}
        },
        "required": ["name", "status"]
      }
    }
  },
  "required": ["dependencies"]
}'

cat backend/requirements.txt | timeout 10m claude --bare -p \
  "Classify each Python dependency on stdin by update risk based on your knowledge. If you are not sure, use unknown." \
  --allowedTools "Read" \
  --permission-mode dontAsk \
  --max-turns 5 \
  --max-budget-usd 0.20 \
  --output-format json \
  --json-schema "$schema" > /tmp/deps.json

jq -e '.structured_output.dependencies' /tmp/deps.json > /dev/null

{
  echo "# Dependency risk report $(date +%Y-%m-%d)"
  jq -r '.structured_output.dependencies[] |
    "- **\(.name)**: \(.status) \(.note // "")"' /tmp/deps.json
} > "$REPORT"

# קוד יציאה 1 אם קיימת תלות עם פער גרסה ראשי
if jq -e '.structured_output.dependencies[] |
    select(.status == "outdated_major")' /tmp/deps.json > /dev/null; then
  echo "Major-version gaps found; see $REPORT" >&2
  exit 1
fi
crontab -e
0 6 * * 0 /home/dev/automation/weekly-deps.sh >> /home/dev/automation/deps.log 2>&1

נקודות המפתח: הקובץ מוזרם ב-stdin כך שגם הרשאת Read כמעט מיותרת (נשארה למקרה שהסוכן ירצה להציץ ב-pyproject.toml וכדומה); הסכמה כוללת unknown כי למודל אין גישה לרשת כאן, וסיווג "לא בטוח" עדיף על ניחוש בטוח; ו-jq -e עם select הוא שער האיכות שהופך דוח לסטטוס יציאה שמערכת ניטור מבינה. שורת ה-cron משתמשת ב-0 (יום ראשון) בשדה היום-בשבוע. גם כאן: תחביר הסקריפט ניתן לאימות עם bash -n; ההרצה המלאה דורשת מפתח API.

סיכום

  • claude -p הופך את Claude Code לפקודת Unix: stdin נכנס, stdout יוצא, קוד יציאה מדווח, וכל דגלי השליטה (--output-format, --json-schema, --max-turns, --max-budget-usd) זמינים.
  • --bare הוא ברירת המחדל הנכונה לסקריפטים ול-CI: מהיר, צפוי, ומנותק מהגדרות מקומיות.
  • הרביעייה הבטוחה לריצה ללא השגחה: --bare + --allowedTools צר + --permission-mode dontAsk + תקציב, ועל זה שערי אישור אנושיים (Plan, PR, Hooks) לכל פעולה בלתי הפיכה.
  • stream-json עם jq נותן שליטה מלאה בזרם האירועים, כולל תפיסת שגיאות טעינה של Plugins ו-MCP ב-CI.
  • אצוות בונים כלולאה עם תקציב כפול והמשך-על-כשל; רקע אינטראקטיבי מנהלים עם --bg, claude agents ופקודות ה-daemon; ו-Channels (Research Preview) דוחף אירועים לתוך Session חי.
  • מה שלא בוטל בקליק אחד לא רץ בלי אדם: Deploys, מיגרציות ו-force-push נשארים מחוץ לאוטומציה.

בפרק הבא נעזוב את התשתיות ונחזור לפיתוח עצמו: פרויקט מסכם שבו נבנה Feature מורכב מקצה לקצה עם כל הכלים שנאספו לאורך המדריך.
