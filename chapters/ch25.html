Subagents

בפרק הזה נלמד להאציל עבודה: Subagent הוא עוזר ממוקד שרץ בתוך ה-Session שלכם, עם Context Window נפרד, System Prompt משלו והרשאות מוגבלות משלו. נבין את מנגנון בידוד ה-Context, נכיר את ה-Subagents המובנים, נעבור על כל שדות ההגדרה המתועדים, ונבנה חמישה Subagents מקצועיים לפרויקט TaskFlow: סוקר ארכיטקטורה, סוקר אבטחה, מומחה בדיקות, מומחה תיעוד וסוקר Database.

מה זה Subagent ואיזו בעיה הוא פותר

Subagent הוא סוכן AI ייעודי ש-Claude מפעיל מתוך השיחה הראשית כדי לטפל במשימת צד. לכל Subagent יש שלושה מאפיינים מגדירים, לפי התיעוד הרשמי:

  • Context Window נפרד. ה-Subagent עובד בהקשר משלו; החיפושים, הלוגים ותוכן הקבצים שהוא קורא לא נכנסים לשיחה הראשית. רק הסיכום הסופי חוזר אליה.
  • System Prompt מותאם. גוף קובץ ההגדרה הופך להנחיה הקבועה של הסוכן, במקום ה-System Prompt המלא של Claude Code.
  • גישה מבוקרת לכלים ולהרשאות. אפשר להגביל אילו כלים מותר לו להפעיל, באיזה Permission Mode הוא רץ ואיזה מודל ישרת אותו.

הבעיה שהמנגנון פותר היא בעיקר כלכלת Context: הרצת חבילת בדיקות, סריקת Codebase גדול או ניתוח לוגים מייצרים אלפי שורות פלט שאתם לא תקראו שוב, אבל הן ממשיכות לתפוס מקום בחלון ההקשר ולדחוף החוצה מידע חשוב. האצלה ל-Subagent משאירה את הרעש אצלו, ומחזירה לשיחה הראשית רק את השורה התחתונה. בנוסף, המנגנון מאפשר אכיפת מגבלות (סוקר שאינו יכול לכתוב קבצים), שימוש חוזר (הגדרה אחת שמשרתת את כל הפרויקטים) ושליטה בעלויות (ניתוב משימות פשוטות למודל זול כמו Haiku).

גבולות מוצר

שלוש יכולות דומות ונבדלות: Subagents רצים בתוך Session אחד ומדווחים חזרה אליו; Background Sessions שמנוהלים דרך claude agents (Agent View) הם Sessions עצמאיים לגמרי; ו-Agent Teams Experimental הם קבוצת Sessions שמתקשרים זה עם זה (סעיף בהמשך, והרחבה בפרק 38).

איך זה עובד: בידוד Context

כל הפעלה של Subagent פותחת חלון הקשר טרי ומבודד. ה-Subagent לא רואה את היסטוריית השיחה שלכם, לא את הקבצים ש-Claude כבר קרא ולא את ה-Skills שכבר הופעלו. במקום זאת, Claude מנסח עבורו הודעת האצלה שמסכמת את המשימה. לפי התיעוד, ההקשר ההתחלתי של Subagent רגיל (שאינו Fork) מכיל:

  • System Prompt: ההנחיה מגוף קובץ ההגדרה, בתוספת פרטי סביבה בסיסיים כמו תיקיית העבודה. לא ה-System Prompt המלא של Claude Code.
  • הודעת המשימה: ה-Prompt ש-Claude כותב כשהוא מאציל את העבודה.
  • קובצי CLAUDE.md: כל היררכיית ה-CLAUDE.md שהשיחה הראשית טוענת. יוצאי הדופן: הסוכנים המובנים Explore ו-Plan מדלגים עליה כדי להישאר מהירים וזולים.
  • מצב Git: תמונת מצב שנלקחה בתחילת ה-Session של ההורה. Explore ו-Plan מדלגים גם עליה.
  • Skills שנטענו מראש: התוכן המלא של כל Skill שמופיע בשדה skills של ההגדרה.

מה לא מגיע אליו: ה-Output Style של השיחה הראשית, ה-Auto Memory שלה, וגודל חלון ההקשר שלה (חלון ה-Subagent נקבע לפי המודל שלו עצמו). בסיום העבודה חוזר לשיחה הראשית רק הדוח הסופי של ה-Subagent, ולא אף תוצר ביניים. זה בדיוק מקור החיסכון, וגם מקור הסיכון של "הרעבת הקשר" שנטפל בו ב-Troubleshooting: מה שלא כתבתם בהודעת ההאצלה, ה-Subagent פשוט לא יודע.

ה-Subagents המובנים

Claude Code מגיע עם כמה Subagents מובנים, שכולם יורשים את הרשאות השיחה הראשית עם הגבלות כלים נוספות:

Exploreיורש מהשיחה הראשית (ב-Claude API מוגבל עד Opus)קריאה בלבד; Write ו-Edit חסומיםחיפוש קבצים, חיפוש קוד וחקירת Codebase בלי לשנות דבר. Claude מציין רמת יסודיות: quick, medium או very thorough

חשוב להכיר את החריגות של Explore ו-Plan: הם היחידים שלא טוענים CLAUDE.md ולא מצב Git, והם חד-פעמיים (One-shot): הם לא מחזירים Agent ID ולכן אי אפשר להמשיך אותם ב-Resume. אם כלל מ-CLAUDE.md חייב להגיע אליהם (למשל "להתעלם מתיקיית vendor/"), חזרו עליו בהודעת ההאצלה. הגדרה מקומית בשם Explore דורסת את המובנה ושומרת על שדה ה-model שלה, כך שאפשר להצמיד את החקירה ל-Haiku ולחסוך.

רוצים לכבות? שלוש דרכים מתועדות: חסימת סוג ספציפי עם "deny": ["Agent(Explore)"] בהגדרות ההרשאות; חסימת כלי ה-Agent כולו כדי למנוע כל האצלה; או משתנה הסביבה CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1 שמסיר רק את Explore ו-Plan (מגרסה 2.1.198). במצב לא אינטראקטיבי וב-Agent SDK קיים גם CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1.

הגדרת Subagents מותאמים אישית

Subagent מותאם הוא קובץ Markdown עם YAML Frontmatter. מיקום הקובץ קובע למי הוא זמין, וכשכמה הגדרות חולקות שם, המיקום בעל העדיפות הגבוהה מנצח:

מיקוםהיקףעדיפות
Managed settingsכלל ארגוני, נפרס על ידי מנהלי מערכת1 (הגבוהה ביותר)
--agents (דגל CLI)ה-Session הנוכחי בלבד, לא נשמר לדיסק2
.claude/agents/הפרויקט הנוכחי; מומלץ להכניס ל-Version Control3
~/.claude/agents/כל הפרויקטים שלכם4
תיקיית agents/ של Pluginהיכן שה-Plugin מופעל5 (הנמוכה ביותר)

הסריקה של .claude/agents/ ושל ~/.claude/agents/ היא רקורסיבית, כך שמותר לארגן קבצים בתתי-תיקיות כמו agents/review/. הזהות נקבעת אך ורק לפי שדה ה-name ב-Frontmatter (שם הקובץ לא חייב להתאים), ולכן חובה לשמור על שמות ייחודיים: שני קבצים עם אותו name באותו עץ יגרמו לטעינת אחד מהם בלבד, וה-Setup Checkup של /doctor מדווח על כפילויות כאלה. אצל Plugins תת-התיקייה כן נכנסת למזהה: קובץ ב-agents/review/security.md של Plugin בשם my-plugin נרשם כ-my-plugin:review:security.

מבנה הקובץ, על פי התיעוד:

.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

Claude Code עוקב אחרי שתי התיקיות: קובץ שנוסף או נערך נקלט תוך שניות בודדות, בלי הפעלה מחדש. שני מקרים כן דורשים הפעלה מחדש: כשתיקיית agents נוצרה לראשונה אחרי שה-Session כבר התחיל, ו-Sessions שהופעלו עם --disable-slash-commands.

הפקודה /agents והדגלים בשורת הפקודה

שימו לב לשינוי התנהגות מתועד: מגרסה 2.1.198 הפקודה /agents כבר לא פותחת אשף יצירה אינטראקטיבי. הרצתה מדפיסה תזכורת לבקש מ-Claude ליצור או לנהל Subagents, או לערוך ישירות את .claude/agents/ ואת ~/.claude/agents/. בגרסאות 2.1.197 ומטה הפקודה פתחה ממשק ניהול מלא. הדרך המומלצת היום היא פשוט לבקש:

Prompt
Create a project subagent in .claude/agents/ named security-reviewer that
audits code for vulnerabilities. Make it read-only.

להגדרה זמנית ל-Session יחיד משמש הדגל --agents, שמקבל JSON עם אותם שדות כמו ה-Frontmatter, בתוספת שדה prompt שמחליף את גוף ה-Markdown:

Bash (macOS / Linux / WSL)
claude --agents '{
  "code-reviewer": {
    "description": "Expert code reviewer. Use proactively after code changes.",
    "prompt": "You are a senior code reviewer. Focus on quality and security.",
    "tools": ["Read", "Grep", "Glob", "Bash"],
    "model": "sonnet"
  }
}'

דגל נפרד ושונה הוא --agent <name> (ביחיד): הוא מפעיל Session שלם שבו השיחה הראשית עצמה מאמצת את ה-System Prompt, הגבלות הכלים והמודל של אותו Subagent. אפשר לקבוע זאת כברירת מחדל לפרויקט עם ההגדרה "agent" ב-.claude/settings.json. במצב לא אינטראקטיבי קיים גם --append-subagent-system-prompt (מגרסה 2.1.205) שמוסיף טקסט לסוף ה-System Prompt של כל Subagent.

רק name ו-description הם שדות חובה. אלה כל השדות המתועדים:

לגבי בחירת מודל, סדר ההכרעה המתועד הוא: משתנה הסביבה CLAUDE_CODE_SUBAGENT_MODEL, אחריו פרמטר model שהועבר בהפעלה הספציפית, אחריו שדה ה-model ב-Frontmatter, ולבסוף המודל של השיחה הראשית. מגרסה 2.1.198 ה-Subagents יורשים גם את הגדרת ה-Extended Thinking של השיחה הראשית; אין הגדרת חשיבה נפרדת לסוכן.

הגבלת כלים וירושת הרשאות

Subagent יורש את הכלים המובנים וכלי ה-MCP שזמינים בשיחה הראשית, אחרי שני מסננים מתועדים. המסנן הראשון מסיר מכל Subagent רשימה קצרה של כלים "שיחתיים" (בהם AskUserQuestion, EnterPlanMode ו-ExitPlanMode, אלא אם הסוכן ב-permissionMode: plan). המסנן השני חל על סוכנים שרצים ברקע (ברירת המחדל): הם שומרים על כל כלי ה-MCP אבל רק על קבוצה מוגדרת של כלים מובנים, ובהם Read, Grep, Glob, Bash, Edit, Write, WebFetch ו-WebSearch. המשמעות המעשית: אותה הגדרה יכולה להתפרש לכלים שונים ב-Foreground וב-Background.

מעל הירושה הזאת פועלות שתי הרשימות שלכם: tools כרשימת היתר ו-disallowedTools כרשימת חסימה. אם שתיהן מוגדרות, החסימה מוחלת קודם. שתיהן מקבלות גם תבניות ברמת שרת MCP: mcp__github או mcp__github__* לכל הכלים של שרת מסוים, ו-mcp__* בתוך disallowedTools להסרת כל כלי ה-MCP. אם אף ערך ברשימת tools לא מתורגם לכלי קיים (למשל בגלל שגיאת כתיב), הסוכן בדרך כלל מסרב לעלות עם שגיאה שמונה את הערכים הבעייתיים (מגרסה 2.1.208).

הרשאות: ה-Subagent יורש את הקשר ההרשאות של השיחה הראשית ויכול לעקוף את המצב עם permissionMode, עם שלושה סייגים מתועדים: אם ההורה רץ ב-bypassPermissions או acceptEdits, מצב ההורה גובר ואי אפשר לעקוף אותו; ואם ההורה ב-Auto Mode, הסוכן יורש אותו וה-permissionMode שבקובץ מנוטרל. בקשות אישור של סוכן רקע צצות בשיחה הראשית שלכם עם שם הסוכן המבקש (מגרסה 2.1.186); אישור מאפשר לו להמשיך, ו-Esc דוחה את הקריאה הבודדת בלי לעצור אותו.

אזהרה

permissionMode: bypassPermissions מדלג על בקשות האישור של הסוכן, כולל כתיבה לתיקיות רגישות כמו .git ו-.claude. השתמשו בו רק בסביבות מבודדות. חוקי ask מפורשים ומחיקות שורש עדיין עוצרים לאישור.

לשליטה עדינה יותר מרשימת כלים משתמשים ב-Hooks: PreToolUse בתוך ה-Frontmatter יכול לבדוק כל פקודה לפני ריצה ולחסום אותה עם קוד יציאה 2. נראה את זה חי אצל database-reviewer. בנוסף, Hooks כלל-מערכתיים מ-settings.json חלים גם בתוך Subagents, והאירועים SubagentStart ו-SubagentStop מאפשרים להגיב להפעלה ולסיום שלהם.

Skills וזיכרון מתמשך

שדה skills מזריק את התוכן המלא של Skills נבחרים להקשר הסוכן כבר בהפעלה, כך שהוא מתחיל עם ידע התחום בלי לחפש אותו. גם בלי השדה, הסוכן יכול להפעיל Skills של פרויקט, משתמש ו-Plugins דרך כלי ה-Skill; כדי למנוע זאת מסירים את Skill מרשימת הכלים. אי אפשר לטעון מראש Skills שמוגדרים עם disable-model-invocation: true.

שדה memory מעניק לסוכן תיקיית זיכרון שנשמרת בין שיחות, בשלושה היקפים: user (~/.claude/agent-memory/<name>/, לכל הפרויקטים), project (.claude/agent-memory/<name>/, משותף דרך Version Control; ההיקף המומלץ בתיעוד) ו-local (.claude/agent-memory-local/<name>/, פרויקטלי אך לא נכנס ל-Repository). כשהזיכרון פעיל, ה-System Prompt של הסוכן מקבל הוראות ניהול זיכרון ואת תחילת קובץ MEMORY.md (עד 200 שורות או 25KB), והכלים Read, Write ו-Edit מופעלים אוטומטית כדי שיוכל לתחזק את קובצי הזיכרון שלו. שימו לב: הזיכרון הוא חלק מ-Auto Memory; אם כיביתם את Auto Memory, השדה לא עושה דבר.

Foreground מול Background

מגרסה 2.1.198 Subagents רצים ברקע כברירת מחדל: אתם ממשיכים לעבוד, והם עובדים במקביל. Claude מריץ סוכן ב-Foreground (חוסם את השיחה עד סיום) רק כשהוא צריך את התוצאה מיד. תוצאת סוכן רקע מגיעה ל-Claude כהתראת סיום בתור מאוחר יותר, ואם תשאלו על ההתקדמות לפני כן, הוא ידווח שהסוכן עדיין רץ. השליטה בידיים שלכם:

  • בקשו במפורש ריצה ברקע או ב-Foreground בתוך ה-Prompt.
  • לחצו Ctrl+B כדי להעביר משימה רצה לרקע.
  • קבעו background: true ב-Frontmatter לסוכן שתמיד ירוץ ברקע.
  • /tasks מציג את עבודות הרקע של ה-Session, כולל Subagents שסיימו (סוכן שהסתיים נשאר ברשימה מסומן כ-Done, מגרסה 2.1.208). פאנל הסוכנים מתחת לשורת הקלט מציג את עץ הריצה.
  • CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 מכבה את כל מנגנון הרקע.

אל תתבלבלו בין זה לבין claude agents: הפקודה הזאת פותחת את Agent View, מסך ניהול ל-Background Sessions עצמאיים (עם פקודות אחיות כמו claude attach, claude logs ו-claude stop). אלה Sessions נפרדים לגמרי, לא Subagents של השיחה הנוכחית, אם כי אפשר לשגר מהם משימה לסוכן מותאם עם תחילית @<agent-name>.

המשך עבודה: Resume ל-Subagent

כל הפעלה של Subagent יוצרת מופע חדש עם הקשר טרי. כדי להמשיך עבודה קיימת במקום להתחיל מאפס, בקשו מ-Claude להמשיך את הסוכן: הוא משתמש בכלי SendMessage עם השם או ה-Agent ID של הסוכן, והסוכן מתעורר עם מלוא ההיסטוריה שלו, כולל כל קריאות הכלים והנימוקים הקודמים:

Prompt
Use the security-reviewer subagent to audit the authentication module
[הסוכן מסיים ומחזיר דוח]

Continue that security review and now cover the authorization logic too

ה-Transcripts של סוכנים נשמרים בנפרד מהשיחה הראשית, בקבצים agent-{agentId}.jsonl תחת ~/.claude/projects/{project}/{sessionId}/subagents/. הם שורדים Compaction של השיחה הראשית, נשמרים עם ה-Session (כך שאפשר להמשיך סוכן גם אחרי הפעלה מחדש דרך המשכת אותו Session), ומנוקים לפי cleanupPeriodDays (ברירת מחדל: 30 יום). Subagents גם עוברים Auto-compaction באותו מנגנון של השיחה הראשית. זכרו: Explore ו-Plan חד-פעמיים ולא ניתנים להמשכה; לעבודה מתמשכת בחרו general-purpose או סוכן מותאם.

דפוסי האצלה

האצלה אוטומטית

Claude מחליט להאציל לפי תיאור המשימה שביקשתם, שדה ה-description של כל סוכן וההקשר הנוכחי. לכן ה-description הוא שדה קריטי: כתבו בו מתי להשתמש בסוכן, לא רק מה הוא. התיעוד ממליץ לכלול ניסוח כמו "use proactively" כדי לעודד האצלה יזומה.

הפעלה מפורשת

שלושה דפוסים מתועדים, מהרך לקשיח:

  • שפה טבעית: נקבו בשם הסוכן ב-Prompt (Use the test-specialist subagent to fix failing tests); Claude בדרך כלל יאציל.
  • אזכור עם @: הקלידו @ ובחרו את הסוכן מההשלמה האוטומטית, או כתבו ידנית @agent-<name> (ל-Plugins: @agent-my-plugin:code-reviewer). זה מבטיח שהסוכן הספציפי ירוץ; Claude עדיין מנסח את הודעת המשימה שלו.
  • כל ה-Session: claude --agent code-reviewer מפעיל את השיחה הראשית עצמה עם ההגדרה של הסוכן, או הגדרת "agent" ב-settings.json כברירת מחדל פרויקטלית.

מניפת מחקר מקבילית ושרשור

לחקירות בלתי תלויות, בקשו כמה סוכנים במקביל:

Prompt
Research the authentication, database, and API modules in parallel
using separate subagents

כל סוכן חוקר את אזורו בנפרד, ו-Claude מסנתז את הממצאים. לזרימות רב-שלביות אפשר לשרשר: Use the code-reviewer subagent to find performance issues, then use the optimizer subagent to fix them. כברירת מחדל סוכן יכול גם להוליד סוכנים משלו עד שלוש שכבות מתחת לשיחה הראשית (ניתן לשינוי עם CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, מגרסה 2.1.217). שתי מגבלות נוספות: עד 200 סוכנים ל-Session (CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION) ועד 20 רצים בו-זמנית (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS); /clear מאפס את מונה ה-Session.

אזהרה

התוצאות של כל הסוכנים חוזרות לשיחה הראשית. מניפה של סוכנים רבים שכל אחד מחזיר דוח מפורט יכולה לצרוך הרבה Context בעצמה. בקשו מכל סוכן להחזיר סיכום קצר וממוקד.

מתי Subagent, מתי בשיחה, מתי Session חדש

מסגרת החלטה לפי התיעוד:

  • הישארו בשיחה הראשית כשצריך דו-שיח צמוד ותיקונים חוזרים, כשכמה שלבים חולקים הקשר משמעותי (תכנון, מימוש ובדיקות של אותו פיצ'ר), כשהשינוי קטן וממוקד, או כשהזמן קריטי: סוכן מתחיל מאפס וצריך זמן לאסוף הקשר.
  • האצילו ל-Subagent כשהמשימה מייצרת פלט מפורט שאין לכם צורך בו בהקשר הראשי, כשרוצים לאכוף הגבלות כלים והרשאות, או כשהעבודה עומדת בפני עצמה ויכולה לחזור כסיכום.
  • לשאלת צד קטנה על משהו שכבר בשיחה, השתמשו ב-/btw: הוא רואה את מלוא ההקשר, בלי גישה לכלים, והתשובה לא מצטרפת להיסטוריה.
  • Session חדש (או Background Session דרך claude agents) מתאים כשהמשימה החדשה לא קשורה לנוכחית בכלל; אין סיבה לגרור את ההקשר הקיים.
  • Skill עדיף כשרוצים הנחיות עבודה לשימוש חוזר שרצות דווקא בתוך ההקשר הראשי (פרק 21).

עלות ו-Context

כל Subagent הוא שיחת מודל עצמאית: הוא צורך Tokens משלו על ה-System Prompt, על קובצי CLAUDE.md שנטענים אליו, ועל כל קריאת כלים שלו, בנפרד מהשיחה הראשית ובנוסף לה. המשמעות: האצלה אינה "בחינם"; היא ממירה עומס הקשר בעלות Tokens נוספת. כמה עובדות מתועדות שכדאי לתמחר:

  • סוכן בשם (Named) מתחיל עם Prompt Cache נפרד, בעוד Fork של השיחה (דרך /subtask) חולק את ה-Cache עם ההורה ולכן זול יותר להפעלה כשצריך את מלוא ההקשר. שימו לב שהולדת Forks על ידי Claude עצמו מסומנת בתיעוד כ-Experimental.
  • ניתוב משימות מכניות למודל זול (model: haiku) הוא כלי החיסכון המרכזי; כך עשינו ב-documentation-specialist.
  • Explore ו-Plan חוסכים בכך שהם מדלגים על CLAUDE.md ועל מצב Git.
  • maxTurns שם תקרה על סוכן שנכנס ללולאה ושורף Tokens.

חמשת ה-Subagents של המדריך

נבנה עכשיו ערכת סוקרים ומומחים מלאה לפרויקט TaskFlow. הקבצים נמצאים בחבילת המדריך בתיקייה subagents/; העתיקו אותם אל .claude/agents/ בשורש הפרויקט (או אל ~/.claude/agents/ אם תרצו אותם בכל הפרויקטים):

$ mkdir -p .claude/agents scripts $ cp /path/to/guide/subagents/*.md .claude/agents/ $ cp /path/to/guide/subagents/scripts/validate-readonly-query.sh scripts/ $ chmod +x scripts/validate-readonly-query.sh

1. architecture-reviewer: סוקר הארכיטקטורה

.claude/agents/architecture-reviewer.md
---
name: architecture-reviewer
description: Reviews code structure, layering, dependencies, and design decisions without modifying files. Use proactively after adding new modules, changing interfaces between components, or refactoring across more than one file.
tools: Read, Grep, Glob
model: inherit
memory: project
color: blue
---

You are a senior software architect performing read-only architecture reviews.

When invoked:
1. Map the affected area: entry points, modules, and the interfaces between them.
2. Read the changed files and every module that depends on them.
3. Review structure before style: boundaries, layering, and data flow come first.

Review checklist:
- Separation of concerns: each module has one clear responsibility
- Dependency direction: high-level code does not depend on low-level details
- No circular imports or hidden coupling between layers
- Public interfaces are minimal, explicit, and consistent
- Errors cross boundaries in a controlled, well-defined way
- New code follows the existing patterns of the project, or documents why not

Report findings ordered by impact:
- Blocking: structural problems that will be expensive to undo later
- Should fix: coupling or duplication that raises maintenance cost
- Consider: reasonable alternatives worth discussing

For each finding, name the files involved, explain the consequence of leaving
it as is, and propose the smallest change that fixes the structure. You never
modify project files; you only report.

Update your agent memory with architectural decisions, module boundaries, and
recurring patterns you discover, so future reviews start from established
knowledge.

הרציונל לכלים: סוקר טהור. Read, Grep ו-Glob מספיקים לניווט ולקריאה, ואין Bash בכלל: ארכיטקטורה סוקרים מקוד המקור. memory: project מצטבר לידע ארכיטקטוני ב-.claude/agent-memory/architecture-reviewer/ שמשותף לצוות דרך Git. שימו לב לניואנס מתועד: הפעלת memory מוסיפה אוטומטית Read, Write ו-Edit כדי שהסוכן יתחזק את קובצי הזיכרון שלו; ההנחיה בגוף הקובץ מגדירה שהוא לא נוגע בקובצי הפרויקט.

הפעלה על TaskFlow: Use the architecture-reviewer subagent to review the boundary between the routers and the database layer in backend/app. תוצאה צפויה: דוח מדורג שיצביע, למשל, על כך ש-routers/tasks.py ניגש ישירות ל-SQLite בלי שכבת שירות, עם הצעת מבנה מינימלית. מקרה כשל: אם תבקשו ממנו "לתקן את המבנה", הוא לא יכול: אין לו Edit לקובצי פרויקט. זו התנהגות רצויה; את התיקון מבצעים בשיחה הראשית לפי הדוח.

2. security-reviewer: סוקר האבטחה

.claude/agents/security-reviewer.md
---
name: security-reviewer
description: Audits code for security vulnerabilities such as injection, broken authentication, exposed secrets, and unsafe dependencies. Read-only. Use proactively after changes to authentication, input handling, API endpoints, or dependency files.
tools: Read, Grep, Glob, Bash
model: inherit
color: red
---

You are an application security reviewer. You audit code and configuration;
you never modify files.

When invoked:
1. Run git diff to focus on recent changes; widen scope only when the changes
   touch trust boundaries such as authentication or input parsing.
2. Trace every external input to where it is parsed, stored, or executed.
3. Check dependency and configuration files for known-risk patterns.

Audit checklist:
- Injection: SQL, command, path traversal, template, and header injection
- Authentication and sessions: token storage, expiry, logout, privilege
  checks on every route
- Secrets: hardcoded keys, tokens, or passwords in code or configuration
- Input validation and output encoding at every boundary
- Insecure defaults: permissive CORS, debug mode, verbose errors in production
- Dependencies: unpinned versions and known-vulnerable packages

Use Bash for read-only inspection only: git diff, git log, and dependency
audit tools. Do not run commands that change state.

Report each finding with severity (Critical / High / Medium / Low), the exact
file and line, evidence, the attack scenario, and a concrete fix. If you find
no issues, state explicitly what you checked and what you could not verify.

הרציונל לכלים: כמו הסוקר הקודם, בלי Write ו-Edit, אבל עם Bash: ביקורת אבטחה אמיתית צריכה git diff וכלי בדיקת תלויות כמו pip-audit או npm audit. ההנחיה מגבילה את Bash לפקודות קריאה, ומעליה ממשיכות לחול ההרשאות הרגילות של ה-Session: פקודה שדורשת אישור תקפיץ בקשה בשיחה הראשית.

הפעלה על TaskFlow: Use the security-reviewer subagent to audit the task creation endpoint and the database access in backend/app. תוצאה צפויה: ממצאים מדורגי חומרה עם קובץ ושורה, למשל SQL שנבנה בשרשור מחרוזות ב-High והיעדר הגבלת אורך לקלט ב-Medium, כל אחד עם תרחיש תקיפה ותיקון. מקרה כשל: להתייחס לדוח "לא נמצאו ממצאים" כהוכחת בטיחות. סוקר AI הוא שכבת הגנה אחת, לא תחליף ל-Penetration Testing; לכן ההנחיה מחייבת אותו לפרט מה בדק ומה לא הצליח לאמת.

3. test-specialist: מומחה הבדיקות

---
name: test-specialist
description: Writes, repairs, and runs automated tests. Use proactively when tests fail, when new code lacks coverage, or when asked to add unit or integration tests.
tools: Read, Grep, Glob, Bash, Edit, Write
model: inherit
maxTurns: 50
color: green
---

You are a test specialist. You write, repair, and run automated tests.

When invoked:
1. Discover the test framework, runner, and conventions from existing tests
   and configuration files.
2. Run the relevant test suite first to establish a baseline.
3. Make the smallest change that achieves the goal: a new test, a fixed
   assertion, or a missing fixture.
4. Re-run the suite and report before and after results.

pass and fail counts.

5. database-reviewer: סוקר ה-Database

.claude/agents/database-reviewer.md
---
name: database-reviewer
description: Reviews database schemas, migrations, and SQL queries for correctness, performance, and safety. Read-only. Use proactively when migrations, ORM models, or raw SQL change.
tools: Read, Grep, Glob, Bash
color: purple
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-readonly-query.sh"
---

You are a database reviewer specializing in schemas, migrations, and query
safety. You are read-only: report, never modify.

When invoked:
1. Read the schema definitions, ORM models, and pending migrations.
2. Trace each query from the application code to the tables and indexes it
   touches.
3. You may run read-only SELECT queries through Bash to inspect real data
   shapes; a hook blocks any write statement.

Review checklist:
- Migrations: reversible, lock-aware, safe on large tables, no destructive
  change without a backfill plan
- Schema: correct types, NOT NULL and UNIQUE constraints, foreign keys,
  sensible defaults
- Queries: indexes match the WHERE and ORDER BY clauses, no N+1 patterns,
  no unbounded result sets
- Integrity: transactions around multi-step writes, race conditions on
  unique values
- Safety: no string-built SQL, parameterized queries everywhere,
  least-privilege connection settings

Report findings by severity with the exact file and line, the scenario in
which it breaks, and the smallest safe fix. Flag any migration you would not
run in production as Blocking.

הסוכן מסתמך על סקריפט אימות (מבוסס על הדוגמה בתיעוד הרשמי) שחוסם כל פקודת כתיבה ב-SQL עם קוד יציאה 2:

scripts/validate-readonly-query.sh
#!/bin/bash
# Blocks SQL write operations, allows SELECT queries.
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')
if [ -z "$COMMAND" ]; then
  exit 0
fi
if echo "$COMMAND" | grep -iE '\b(INSERT|UPDATE|DELETE|DROP|CREATE|ALTER|TRUNCATE|REPLACE|MERGE)\b' > /dev/null; then
  echo "Blocked: Write operations not allowed. Use SELECT queries only." >&2
  exit 2
fi
exit 0

הרציונל לכלים: סוקר Database טוב חייב להציץ בנתונים אמיתיים (sqlite3 taskflow.db "SELECT ..."), ולכן יש לו Bash; אבל רשימת כלים לבדה לא מבדילה בין SELECT ל-DROP. כאן נכנס ה-Hook: PreToolUse בודק כל פקודת Bash לפני ריצה וחוסם כתיבה. זה הדפוס המתועד לשליטה מותנית, עדין יותר מהיתר או חסימה גורפים.

הפעלה על TaskFlow: Use the database-reviewer subagent to review the tasks table schema and the queries in backend/app/database.py. תוצאה צפויה: דוח שמצביע, למשל, על היעדר Index לעמודת הסטטוס שמסוננת בכל בקשה, ועל שאילתה שנבנית בשרשור מחרוזות כממצא Blocking. מקרה כשל: אם שכחתם להעתיק את הסקריפט או לתת לו הרשאת ריצה, כל קריאת Bash של הסוכן תיכשל בשגיאת ה-Hook. וגם להפך: הסקריפט חוסם לפי מילות מפתח, ולכן פקודת קריאה לגיטימית שמכילה את המילה CREATE (למשל SELECT sql FROM sqlite_master שמחזירה הגדרות CREATE TABLE בפלט זה בסדר, אבל grep CREATE migrations/ תיחסם) עלולה להיעצר בטעות. זו דוגמה טובה למחיר של False Positives באכיפה מבוססת תבניות.

Agent Teams בקצרה Experimental

Agent Teams הם השלב הבא בסולם ההקבלה: במקום סוכני עזר שמדווחים רק חזרה לשיחה הראשית, מוקם צוות של מופעי Claude Code מלאים, עם Session מוביל (Team Lead), רשימת משימות משותפת ותקשורת ישירה בין חברי הצוות. היכולת ניסיונית וכבויה כברירת מחדל: בלי המשתנה CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 (בסביבה או ב-settings.json) לא מוקם צוות, ו-Claude לא מציע ולא מוליד חברי צוות. ההבדל המהותי מ-Subagents: חברי צוות מתקשרים זה עם זה ומתאמים עבודה בעצמם, וכל אחד מהם הוא מופע Claude נפרד, ולכן צריכת ה-Tokens גבוהה משמעותית. נקודת חיבור נחמדה לפרק הזה: אפשר להשתמש בהגדרות ה-Subagents שבניתם כתבניות תפקיד לחברי צוות (Spawn a teammate using the security-reviewer agent type); חבר הצוות מכבד את רשימת ה-tools ואת ה-model, וגוף ההגדרה מצורף ל-System Prompt שלו. צלילה מלאה, כולל מצבי תצוגה, אישור תוכניות ומגבלות ידועות: פרק 38.

שגיאות נפוצות

  • סוקר עם כלי כתיבה. אם ל-code-reviewer יש Edit, יום אחד הוא "יתקן תוך כדי" ותקבלו סקירה שמערבבת שינויים. סוקרים מקבלים כלי קריאה בלבד; את התיקון מבצע גורם אחר.
  • description עמום. "Helps with code" לא נותן למנגנון ההאצלה האוטומטית שום דבר להיאחז בו. כתבו מתי להפעיל, על אילו קבצים ובאיזה טריגר, והוסיפו "use proactively" כשמתאים.
  • שגיאת כתיב ברשימת tools. ערכים שלא מתורגמים לכלים גורמים לסוכן לסרב לעלות עם שגיאת "zero tools". בדקו איות מדויק של שמות כלים.
  • ציפייה שהסוכן "יזכור" את השיחה. הוא מתחיל מהקשר טרי. כל פרט חיוני צריך להופיע בהודעת ההאצלה או בקובץ ההגדרה.
  • בלבול בין --agents (הגדרת סוכנים ב-JSON ל-Session) לבין --agent (הפעלת ה-Session כולו כסוכן מסוים).

Troubleshooting

  • Claude לא בוחר בסוכן שלכם. קודם ודאו שהוא בכלל נטען: אם תיקיית agents נוצרה אחרי תחילת ה-Session, נדרשת הפעלה מחדש. אחר כך שפרו את ה-description (טריגרים קונקרטיים), בדקו כפילות שמות עם /doctor, וכפו ריצה עם אזכור @agent-<name> כדי לבודד את הבעיה.
  • "הרעבת הקשר": הסוכן חוזר עם תשובה שטחית או לא רלוונטית. זכרו מה הוא לא מקבל: את היסטוריית השיחה. נסחו האצלה עשירה (קבצים, סימפטומים, מה כבר נוסה), טענו ידע קבוע דרך skills, או השתמשו ב-Fork (/subtask) כשנדרש מלוא ההקשר.
  • שגיאת "Agent would be spawned with zero tools". אף ערך ב-tools לא הפך לכלי זמין. בדקו איות, וזכרו שסוכן רקע מקבל סט כלים מובנים מצומצם: כלי שקיים ב-Foreground יכול להיעלם ב-Background.
  • הסוכן נעצר עם "Subagent spawn limit reached" או "Concurrent subagent limit reached". נגעתם במגבלות (200 ל-Session, 20 במקביל). /clear מאפס את מונה ה-Session, ומשתני הסביבה שהוזכרו מעלים את התקרות.
  • סוכן רקע "נתקע" בלי תוצאה. ייתכן שהוא ממתין לאישור הרשאה שצץ בשיחה הראשית ולא שמתם לב, או שנפל על שגיאת API. בדקו את /tasks; מגרסה 2.1.199 כשל API מדווח ל-Claude ככשל, כולל הפלט החלקי, ואפשר לבקש Resume אחרי שהתקלה חלפה.

אבטחה

Subagents יורשים את גבולות האמון של ה-Session: הם פועלים תחת אותה מערכת הרשאות, ואישור שנתתם לשיחה הראשית משרת גם אותם (ולהפך, Bypass של ההורה גובר על כל הגדרה שלהם). כמה נקודות מתועדות שחשוב להפנים:

  • סוכן אינו משתמש. שום הודעה מסוכן אחר לא נחשבת לאישור הרשאות מטעמכם, ואינה יכולה לשנות הגדרות הרשאה, CLAUDE.md או תצורה. רק מערכת ההרשאות או אתם מאשרים.
  • סריקת פלט (מגרסה 2.1.210). Claude Code סורק את הדוח הסופי של כל סוכן לפני ש-Claude קורא אותו, ומנטרל טקסט שמתחזה לפלט מערכת (כמו תגיות system-reminder מזויפות) על ידי הוספת לוכסן וסימון שורת אזהרה. הסריקה לא שופטת זדוניות ואינה תחליף להגבלת כלים: תוכן שסוכן קרא מקובץ או מדף אינטרנט עדיין יכול לנסות לכוון את השיחה הראשית (Prompt Injection).
  • סוכני סקירה כשכבת בטיחות. ערכת הסוקרים שבנינו היא בקרה מפצה זולה: security-reviewer קורא כל שינוי רגיש לפני Merge, ו-database-reviewer עוצר Migration מסוכן. אבל אלה בקרות הסתברותיות; אל תוותרו בגללן על Code Review אנושי ו-CI.
  • Plugins מוגבלים בכוונה. סוכן שמגיע מ-Plugin לא יכול להביא איתו hooks, mcpServers או permissionMode; השדות מנוטרלים. כדי להשתמש בהם, העתיקו את הקובץ ל-.claude/agents/ אחרי שבחנתם אותו.
  • הגבילו לפי עיקרון ההרשאה המינימלית. כל כלי שאינו נחוץ לתפקיד הוא שטח תקיפה מיותר. סוקר לא צריך Write; מתעד לא צריך Bash.

Best Practices

  • סוכן אחד, אחריות אחת. עדיף חמישה מומחים צרים על "עוזר-על" אחד.
  • כתבו description ממוקד טריגרים, עם "use proactively" כשההפעלה צריכה להיות יזומה.
  • העניקו רק את הכלים הנחוצים לתפקיד; לסוקרים כלי קריאה בלבד.
  • הכניסו את .claude/agents/ ל-Version Control כדי שהצוות ישתפר יחד.
  • בקשו מכל סוכן דוח בפורמט קבוע וקצר; מה שחוזר לשיחה הראשית עולה Context.
  • נתבו משימות מכניות ל-model: haiku ושמרו את המודל החזק לשיחה הראשית.
  • השתמשו ב-memory: project אצל סוקרים קבועים כדי לצבור ידע מוסדי בין שיחות.
  • אמתו הגדרה חדשה מיד: @agent-<name> עם משימה קטנה, ובדקו שהדוח בפורמט שציפיתם לו.

Anti-patterns

  • האצלה של הכול. משימה קטנה עם דו-שיח צמוד ב-Subagent רק מוסיפה עלות והשהיה. סוכן מצדיק את עצמו כשהפלט הביניים גדול או כשנדרשת אכיפת מגבלות.
  • מניפת ענק שמחזירה דוחות ענק. עשרה סוכנים שכל אחד מחזיר 2,000 מילים יחנקו את השיחה הראשית שניסיתם להגן עליה.
  • עקיפת הרשאות גורפת. permissionMode: bypassPermissions בקובץ סוכן שנכנס ל-Repository משותף הוא מתנה לתוקף עתידי.
  • שכפול סוכנים כמעט זהים. אם שלושה סוכנים חולקים 90% מההנחיה, אחדו אותם ושימו את הידע המשותף ב-Skill שנטען דרך skills.
  • שימוש בסוכן כתחליף ל-/clear. אם ההקשר הראשי התלכלך, נקו אותו; אל תבנו סביבו פיגומים.

תרגיל: בונים performance-reviewer

תרגיל 25.1

בנו Subagent חמישי-פלוס לערכה: performance-reviewer שסוקר קוד לבעיות ביצועים (לולאות מיותרות, שאילתות בתוך לולאה, מבני נתונים לא מתאימים, עבודת I/O חוזרת). דרישות: קריאה בלבד עם יכולת להריץ מדידות לא הרסניות; description שמפעיל אותו אוטומטית אחרי שינויים בנתיבי קוד חמים; דוח בפורמט קבוע שמדרג ממצאים לפי השפעה משוערת. שמרו אותו ב-.claude/agents/, ודאו שנקלט, והפעילו אותו על backend/app/routers/tasks.py ב-TaskFlow.

פתרון מוסבר

ההגדרה המלאה:

.claude/agents/performance-reviewer.md
---
name: performance-reviewer
description: Reviews code for performance problems such as N+1 queries, redundant loops, repeated I/O, and inefficient data structures. Read-only. Use proactively after changes to request handlers, database access, or loops over large collections.
tools: Read, Grep, Glob, Bash
model: inherit
color: orange
---

You are a performance reviewer. You analyze code for efficiency; you never
modify files.

When invoked:
1. Read the changed code and identify the hot paths: request handlers,
   loops, and database access.
2. Trace the cost of each hot path: how many queries, allocations, and I/O
   operations run per request.
3. You may run non-destructive measurements through Bash (timing a test run,
   EXPLAIN on a query). Never run load tests against shared environments.

Look for:
- N+1 queries and queries inside loops
- Work repeated inside loops that could be hoisted or cached
- Inefficient data structures (linear scans where a set or dict fits)
- Unbounded result sets and missing pagination
- Repeated file or network I/O that could be batched

Report findings ordered by estimated impact. For each: file and line, why it
is slow, expected effect at scale, and the smallest fix. State clearly which
findings are measured and which are estimated from reading the code.

נקודות המפתח: הכלים זהים לפרופיל של security-reviewer (קריאה בתוספת Bash למדידות), ה-description מונה טריגרים קונקרטיים כדי שההאצלה האוטומטית תעבוד, וההנחיה מחייבת הפרדה בין ממצא מדוד לממצא משוער, הרגל שמונע דוחות ביצועים מנופחים. מכיוון שהקובץ נכתב לתיקייה קיימת בזמן שה-Session רץ, הוא נקלט תוך שניות בלי הפעלה מחדש (אם התיקייה נוצרה רק עכשיו, הפעילו מחדש). אימות: @agent-performance-reviewer review backend/app/routers/tasks.py, ובדקו בדוח שהוא מזהה, למשל, שליפת משימות בלי Pagination.

אימות מסכם לפרק: ודאו שחמשת הקבצים יושבים ב-.claude/agents/, הריצו /doctor לבדיקת כפילויות שמות, הקלידו @ ובדקו שכל החמישה מופיעים בהשלמה האוטומטית, והפעילו סוכן אחד לפחות על TaskFlow ובדקו ב-/tasks שהוא רץ והסתיים.

סיכום

Subagents הם כלי ההאצלה הפנימי של Claude Code: הקשר מבודד, הנחיה ממוקדת, כלים והרשאות תפורים לתפקיד, ותוצאה שחוזרת כסיכום נקי. למדנו את שלושת המובנים המרכזיים (Explore, Plan, general-purpose), את כל שדות ה-Frontmatter ואת סדר העדיפויות בין מיקומי ההגדרה, את ברירת המחדל של ריצה ברקע ואת מנגנון ה-Resume, ובנינו ערכה של חמישה מומחים לפרויקט אמיתי. הכלל המנחה: האצילו כשהפלט רועש או כשצריך אכיפת מגבלות, הישארו בשיחה כשההקשר המשותף הוא הנכס, וזכרו שכל סוכן משלם Tokens משלו. בפרק הבא נראה איך אורזים סוכנים, Skills ו-Hooks לחבילה אחת ניתנת להפצה: Plugins.
