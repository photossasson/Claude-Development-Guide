Refactoring

Refactoring הוא שינוי מבנה הקוד בלי שינוי התנהגות, וזו בדיוק הנקודה שבה מודל שמייצר קוד "טוב יותר" בקלות הופך מסוכן: קל לקבל קוד יפה יותר שמתנהג קצת אחרת. בפרק הזה נבנה את שרשרת הביטחון המלאה: Characterization Tests שמקבעים את ההתנהגות הקיימת, צעדים קטנים ומבוקרים, פירוק קבצים גדולים, הסרת קוד מת עם הוכחה, שמירת תאימות API ו-Schema, והוכחת שימור התנהגות. נסיים בדוגמה מלאה: חילוץ שכבת אחסון מה-Routers של TaskFlow.

מהו Refactoring, ולמה עם Claude זה שונה

ההגדרה המחייבת: שינוי במבנה הפנימי של הקוד שמשאיר את ההתנהגות הנצפית זהה. אותם קלטים, אותם פלטים, אותם קודי שגיאה, אותן תופעות לוואי. כל דבר אחר הוא לא Refactoring אלא שינוי התנהגות, וצריך להיות מנוהל ככזה: בנפרד, עם בדיקות משלו.

הבעיה שהפרק פותר: קוד חי צובר חוב מבני. קובץ Router שמערבב HTTP עם SQL, פונקציה של 300 שורות, קוד מת שאיש לא מעז למחוק. Claude מוריד דרמטית את עלות העבודה המכנית של השינוי, אבל לא את הסיכון שבו. להפך, שני מאפיינים שלו מגדילים את הסיכון אם לא מרסנים אותם:

  • נטייה לשכתב במקום להזיז. כשמבקשים "לשפר" קוד, מודל עלול לייצר גרסה חדשה ודומה במקום להעביר את הקוד הקיים כמו שהוא. גרסה "דומה" היא בדיוק המקום שבו התנהגות משתנה בשקט: תנאי גבול, סדר פעולות, ערך ברירת מחדל.
  • יוזמה מעבר לבקשה. "תוך כדי" תיקון שמות, שינוי הודעות שגיאה, "שיפור" ולידציה. כל אחד מאלה הוא שינוי התנהגות שמוסתר בתוך Diff גדול.

לכן ההמלצה הרשמית בתיעוד היא לבצע Refactoring בצעדים קטנים וניתנים לבדיקה, לבקש שמירת תאימות במפורש, ולאמת עם הרצת בדיקות אחרי כל שינוי. כל הפרק הוא פירוט של שלושת הכללים האלה.

דרישות מוקדמות

הפרק נשען ישירות על פרק 11 (Testing): בלי חבילת בדיקות ירוקה אין Refactoring בטוח. נדרש גם Git בסיסי (Commit לכל צעד); את זרימת העבודה המלאה מול Git נראה בפרק 13.

שלב ראשון תמיד: Characterization Tests

Characterization Test היא בדיקה שמקבעת את ההתנהגות הקיימת של הקוד, כפי שהיא, כולל המוזרויות שלה. בניגוד לבדיקה רגילה, היא לא שואלת "מה הקוד אמור לעשות?" אלא "מה הקוד עושה בפועל?". זו רשת הביטחון שמאפשרת לשנות מבנה בלב שקט: אם אחרי השינוי כל בדיקות האפיון ירוקות, ההתנהגות נשמרה, לפחות בכל מה שקיבעתם.

נדגים על ה-Endpoint שנשנה בהמשך הפרק: PATCH /tasks/{task_id} ב-backend/app/routers/tasks.py. לפני שנוגעים בו, מבקשים מ-Claude לאפיין אותו:

Prompt
I am about to restructure the update endpoint in app/routers/tasks.py.
before any change: write characterization tests in
backend/tests/test_characterize_update.py that pin its CURRENT behavior,
including quirks. probe edge cases through the HTTP API only: empty
payload, null fields, unknown fields, invalid status on a missing id,
partial updates. document surprises as comments. run the tests, make
sure they are green against the current code, and do not touch app/.

תוצר אופייני, אחרי הרצה ירוקה. שימו לב כמה התנהגות לא מובנת מאליה מסתתרת ב-Endpoint אחד קטן:

backend/tests/test_characterize_update.py
"""Characterization tests for PATCH /tasks/{task_id}.

They pin what the code DOES today, not what it should do.
If one fails after a refactor, behavior changed.
"""


def test_empty_payload_is_400_not_422(client, task):
    # A quirk worth pinning: the endpoint itself rejects {} with 400,
    # while Pydantic validation errors return 422.
    res = client.patch(f"/tasks/{task['id']}", json={})
    assert res.status_code == 400
    assert res.json()["detail"] == "No fields to update"


def test_explicit_nulls_count_as_missing(client, task):
    # model_dump(exclude_none=True) drops nulls, so {"title": null}
    # behaves exactly like {}.
    res = client.patch(f"/tasks/{task['id']}", json={"title": None})
    assert res.status_code == 400


def test_validation_beats_existence_check(client):
    # Surprise: invalid body on a MISSING id returns 422, not 404.
    # Validation runs before the handler ever queries the database.
    res = client.patch("/tasks/999999", json={"status": "bad"})
    assert res.status_code == 422


def test_unknown_fields_silently_ignored(client, task):
    res = client.patch(
        f"/tasks/{task['id']}", json={"title": "t", "due_date": "2026-01-01"}
    )
    assert res.status_code == 200


def test_partial_update_preserves_other_fields(client, task):
    res = client.patch(f"/tasks/{task['id']}", json={"status": "done"})
    assert res.json()["title"] == task["title"]
    assert res.json()["description"] == task["description"]

שלוש נקודות על התוצר: ראשית, בדיקת סדר הבדיקות (ולידציה לפני קיום) היא זהב: זה בדיוק סוג ההתנהגות ש-Refactoring תמים משנה בלי כוונה, למשל אם מזיזים את שליפת המשימה לפני הולידציה. שנית, גם אם התנהגות נראית לכם שגויה (אולי 422 על {} היה "נכון" יותr מ-400?), מקבעים אותה כמו שהיא: תיקון התנהגות הוא משימה נפרדת, אחרי ה-Refactoring, לעולם לא בתוכו. שלישית, כאן מותר וכדאי לקבע גם את נוסח הודעת השגיאה: בזמן Refactoring אתם רוצים לדעת על כל שינוי נצפה, גם בניסוח. אחרי שהשינוי הושלם אפשר לרכך את ה-Assertion חזרה לקוד סטטוס בלבד.

צעדים קטנים, מבוקרים, הפיכים

היחידה הבסיסית של Refactoring בטוח היא צעד אחד קטן: טרנספורמציה אחת (חילוץ פונקציה, העברת קובץ, שינוי שם), ואחריה מיד הרצת בדיקות ו-Commit. המחזור:

  1. ירוק לפני: pytest -q עובר במלואו. אם לא, קודם מתקנים או מבודדים; אסור להתחיל מבסיס אדום, כי לא תוכלו להבחין בין כישלון ישן לכישלון שיצרתם.
  2. צעד אחד: הנחיה שמגדירה טרנספורמציה אחת, עם איסור מפורש על שינויים נלווים.
  3. ירוק אחרי + סקירת Diff: הרצת הבדיקות וקריאת ה-Diff המלא.
  4. Commit: נקודת שמירה שמאפשרת חזרה מדויקת.

ניסוח הנחיה של צעד, עם המגבלות בגוף הבקשה:

Prompt
extract the row-to-model conversion from app/routers/tasks.py into a
separate module. move the existing code as-is: do not rename fields, do
not change error handling, do not "improve" anything else. run
cd backend && pytest -q after the change and show the result.

אם צעד השתבש, יש שתי דרכי נסיגה: git checkout ל-Commit האחרון, או תפריט ה-Rewind של Claude Code (Esc Esc או /rewind) שמשחזר גם את הקבצים וגם את השיחה ל-Checkpoint קודם. זכרו את הגבול המתועד של Checkpoints: הם עוקבים רק אחרי עריכות שנעשו דרך כלי העריכה של Claude, לא אחרי שינויים מפקודות Bash או מכלים חיצוניים. לכן ב-Refactoring ה-Commit הוא רשת הביטחון הראשית, וה-Rewind תוספת נוחה.

Best Practice

לצעדים גדולים (פירוק קובץ, החלפת תלות) התחילו ב-Plan Mode (Shift+Tab): Claude קורא ומתכנן בלי לגעת בקבצים, אתם מאשרים את התוכנית, ורק אז עוברים לביצוע. לצעד זעיר ומוגדר היטב, כמו שינוי שם משתנה, התוכנית מיותרת: בקשו ישירות.

פירוק קובץ גדול: תוכנית, ואז לולאת העבר-ואמת

קובץ של אלף שורות הוא המקרה שבו הפיתוי "תפצל לי את זה" הכי מסוכן: פיצול בבת אחת מייצר Diff ענק שאי אפשר לסקור. השיטה הבטוחה בנויה משני שלבים:

שלב א: תוכנית פיצול

Prompt (ב-Plan Mode)
app/routers/tasks.py mixes HTTP handling with SQL. propose a split plan:
which units move to which new files, in what order, and what stays.
order the moves from least to most entangled. for each move list the
imports that change. do not write code yet.

מהתוכנית אתם דורשים שלושה דברים: יעד לכל יחידה, סדר העברות מהקל אל הסבוך, ורשימת ה-Imports שמושפעים בכל צעד. שמרו את התוכנית המאושרת בקובץ (למשל REFACTOR_PLAN.md): היא תשמש אתכם גם אם ה-Session יתחלף באמצע, כפי שנראה בסעיף ה-Cost/Context.

שלב ב: לולאת העבר-ואמת

כל איטרציה מעבירה יחידה אחת מהתוכנית: העברת הקוד כמו שהוא, עדכון Imports, הרצת בדיקות, סקירת Diff, Commit עם הודעה שמפנה לצעד בתוכנית ("step 2 of REFACTOR_PLAN"). היתרון המצטבר: בכל רגע נתון הקוד עובד, ואפשר לעצור באמצע ולהמשיך מחר. Refactoring שאפשר לעצור באמצעו הוא הסימן שהצעדים בגודל נכון.

היפוך תלות בעזרת Claude

Dependency Inversion הוא הצעד שאחרי הפירוק: במקום שקוד עסקי יידע על מימוש קונקרטי (למשל: ה-Router יודע ש-SQLite קיים), הוא תלוי בהפשטה, והמימוש מוזרק מבחוץ. ב-Python ההפשטה הטבעית היא Protocol:

backend/app/storage/base.py (סקיצה)
from typing import Optional, Protocol

from app.models import Task


class TaskStore(Protocol):
    def list_tasks(self) -> list[Task]: ...
    def get_task(self, task_id: int) -> Optional[Task]: ...

מתי זה שווה את המורכבות? כשיש לפחות שני מימושים אמיתיים באופק (למשל: SQLite היום, PostgreSQL מחר), או כשרוצים להחליף את המימוש בבדיקות. ב-TaskFlow, שבו הבדיקות רצות מצוין מול SQLite אמיתי, נסתפק בדוגמה המלאה בהמשך בחילוץ מודול אחסון פשוט בלי Protocol: הפשטה מוסיפים כשיש לה צרכן שני, לא "ליתר ביטחון". זה בדיוק סוג ההחלטה שכדאי לברר עם Claude לפני שמבצעים: we have one storage backend and no plans for another. is introducing a TaskStore protocol justified now? argue both sides.

הסרת קוד מת: איך מוכיחים שהוא באמת מת

קוד מת הוא קוד שאין אליו שום הפניה חיה. הבעיה: "לא מצאתי הפניה" אינו "אין הפניה". לפני מחיקה, דרשו מ-Claude תיק ראיות:

  1. חיפוש טקסטואלי מלא על השם, כולל מחרוזות: קוד שנקרא דרך getattr, קובצי תצורה, Templates ו-Frontend לא יופיעו כ-Import.
  2. גבולות ציבוריים: פונקציה שלא נקראת בתוך ה-Repository עדיין יכולה להיות חוזה ציבורי: Endpoint של API, Export של חבילה, Hook שנרשם חיצונית. ב-TaskFlow, אף אחד בקוד לא "קורא" ל-delete_task של ה-Router, ובכל זאת הוא חי מאוד: ה-Frontend וכל צרכן HTTP אחר תלויים בו.
  3. היסטוריה: git log על הקובץ: מתי נגעו בזה לאחרונה ולמה. התיעוד הרשמי ממליץ במפורש להפנות את Claude להיסטוריית Git כשחוקרים "למה הקוד הזה קיים".
  4. ראיות זמן ריצה כשיש: לוגים, Metrics, נתוני Coverage מסביבה אמיתית.
Prompt
is anything in app/database.py dead code? for each candidate produce
evidence: grep results (including string references and the frontend),
whether it is part of a public contract, and last-touched history.
conclude keep or delete per item. do not delete anything yet.

את המחיקה עצמה עושים ב-Commit נפרד ונקי, בלי שום שינוי אחר, כך שאם מתברר שהקוד היה חי, ההחזרה היא git revert אחד.

תאימות API ו-Schema בזמן Refactoring

תאימות API: Deprecation Shims

כשמשנים שם או חתימה של קוד שיש לו צרכנים (מודול ציבורי, Endpoint), לא מוחקים את הישן: משאירים Shim, מעטפת דקה שמפנה מהישן אל החדש ומכריזה על הוצאה משימוש:

דוגמת Shim ב-Python
import warnings


def old_name(*args, **kwargs):
    warnings.warn(
        "old_name is deprecated, use new_name",
        DeprecationWarning,
        stacklevel=2,
    )
    return new_name(*args, **kwargs)

ב-API חיצוני העיקרון זהה בכלים אחרים: הנתיב הישן ממשיך לענות (מפנה פנימית לחדש), התגובה שומרת על כל השדות הקיימים, והסרה נעשית רק אחרי חלון זמן והודעה לצרכנים. כלל אצבע להנחיות: הוסיפו תמיד maintain backward compatibility כשזה נדרש, וזה בדיוק אחד הניסוחים שהתיעוד הרשמי ממליץ עליהם ב-Refactoring.

תאימות Schema: שינויים תוספתיים תחילה

ב-Database הכלל הוא "תוספתי קודם" (additive first): כל שינוי מפורק לרצף של צעדים שכל אחד מהם תאים לאחור. למשל, שינוי שם עמודה לא נעשה כ-RENAME אחד אלא כרצף: הוספת עמודה חדשה, כתיבה כפולה לשתיהן, העתקת נתונים קיימים (backfill), העברת הקריאה לעמודה החדשה, ורק בסוף, אחרי שהכול יציב, הסרת הישנה. בכל שלב ביניים גם הקוד הישן וגם החדש עובדים, ולכן אפשר לפרוס ולחזור אחורה בבטחה.

דוגמה מ-TaskFlow: נניח שרוצים לשנות את ערך הסטטוס in_progress ל-active. זה נוגע בשלושה מקומות שחייבים לנוע יחד: אילוץ ה-CHECK בטבלה (database.py), הטיפוס TaskStatus במודלים, והטיפוס המקביל ב-Frontend. המסלול הבטוח: להרחיב את האילוץ ואת הטיפוסים כך שיקבלו את שני הערכים, להסב את הנתונים, לעדכן את הצרכנים, ורק בסוף לצמצם חזרה לערך החדש בלבד. שימו לב לאילוץ מעשי של SQLite: שינוי אילוץ CHECK מחייב בנייה מחדש של הטבלה, עוד סיבה לתכנן את הצעדים מראש ולא לאלתר.

הוכחת שימור התנהגות

איך יודעים שבאמת לא שיניתם התנהגות? שלוש שכבות, מצטברות:

  • חבילה ירוקה לפני ואחרי. תנאי הכרחי אך לא מספיק: הוא מוכיח שימור רק של מה שהבדיקות מכסות. לכן שכבת האפיון קודמת: ודאו שבדיקות ה-Characterization מכסות את הקוד שאתם נוגעים בו, כולל מקרי הקצה והשגיאות, לא רק את המסלול המאושר.
  • משמעת סקירת Diff. קוראים את כל ה-Diff, ושואלים על כל שינוי: האם זו הזזה או שינוי? טכניקה יעילה היא לבקש מ-Claude דוח על ה-Diff של עצמו: summarize the current git diff. list anything that is NOT a pure move or rename: any changed condition, default, message, or order of operations. זה לא תחליף לקריאה שלכם, זה זרקור שמכוון אותה.
  • סוקר עצמאי. ההטיה המתועדת: מודל נוטה לאשר קוד שהוא עצמו כתב. לכן ביקורת אפקטיבית רצה ב-Context נקי: פקודת /code-review המובנית מריצה סקירת Bugs על ה-Diff הנוכחי ב-Subagent טרי, ואפשר גם לנסח סוקר ייעודי: use a subagent to review the diff against REFACTOR_PLAN.md: verify it is behavior-preserving and nothing outside the plan changed.

אימות לכל Refactoring, לפני ה-Commit האחרון:

  • בדיקות האפיון נכתבו לפני השינוי והיו ירוקות על הקוד הישן.
  • pytest -q ירוק אחרי, בלי שום שינוי בקובצי הבדיקות עצמם.
  • ה-Diff נסקר במלואו ואין בו שינוי התנהגות שלא הוכרז.
  • סוקר עצמאי (/code-review או Subagent) עבר על ה-Diff.
  • כל צעד יושב ב-Commit משלו וניתן להחזרה בנפרד.
אזהרה

אם בדיקה נכשלה אחרי צעד Refactoring, הבדיקה כמעט תמיד צודקת. האינסטינקט "נעדכן את הבדיקה שתתאים לקוד החדש" הופך את רשת הביטחון לנייר טואלט: כך מקבעים שינוי התנהגות בלי לשים לב. קודם מבינים מה השתנה, ורק אם השינוי מכוון ומוצהר, מעדכנים בדיקה, ב-Commit נפרד עם הסבר.

מתי לא לעשות Refactoring

  • בלי רשת ביטחון ואין זמן לבנות אחת. קוד ללא בדיקות משנים רק אחרי אפיון. אם אין תקציב לאפיון, אין תקציב ל-Refactoring.
  • קוד שעומד להימחק או להיכתב מחדש ממילא בקרוב. שיפוץ של בניין מיועד להריסה.
  • קוד שאתם עדיין לא מבינים. קודם חקירה (פרק 6) ואפיון; ה-Refactoring יחכה.
  • באמצע פיתוח Feature. ערבוב שינוי מבנה ושינוי התנהגות ב-Diff אחד הוא ה-Anti-pattern המרכזי של הפרק. סיימו את ה-Feature, ואז שפצו, או להפך.
  • ערב Release או תיקון דחוף. שינוי מבנה מרחיב את שטח הסיכון בדיוק כשסובלנות הסיכון נמוכה.
  • "יופי" בלי תועלת. אם אף אחד לא נכווה מהמבנה הנוכחי ואין תוכנית שהוא חוסם, העלות ודאית והתועלת ספקולטיבית.

ספריית Prompts ל-Refactoring

תבניות לניסוחים שחוזרים שוב ושוב. התאימו שמות קבצים ופקודות לפרויקט שלכם:

1. אפיון לפני שינוי
before I restructure <file>, write characterization tests that pin its
current behavior including quirks and error paths. green against current
code. do not touch the code itself.
2. חילוץ יחידה, בלי שיפורים
extract <unit> from <file> into <new file>. move code as-is: no renames,
no logic changes, no "improvements". update imports, run <test command>,
show the diff summary.
3. שינוי שם חוצה-פרויקט
rename <old> to <new> across the codebase, including strings, docs and
config. list every file you changed. keep a deprecation shim at the old
name that warns and delegates.
4. תוכנית פירוק לקובץ גדול
(plan mode) propose a split plan for <file>: target file per unit, move
order from least to most entangled, affected imports per step. no code.
5. קוד מת עם ראיות
find dead code candidates in <scope>. for each: grep evidence including
string references, public-contract check, git history. keep/delete
verdict per item. no deletions yet.
6. דוח שימור התנהגות על ה-Diff
summarize the current git diff. list anything that is not a pure move
or rename: changed conditions, defaults, messages, ordering, error
handling. if the list is empty, say so explicitly.
7. שדרוג דפוס עם שמירת התנהגות
refactor <file> to use <modern pattern> while maintaining the same
behavior and backward compatibility. work in small steps, run
<test command> after each step.

דוגמה מלאה: חילוץ שכבת אחסון ב-TaskFlow

ה-Router של TaskFlow (app/routers/tasks.py) מערבב שתי אחריויות: טיפול ב-HTTP (קודי סטטוס, HTTPException) וגישה לנתונים (SQL, המרת שורות למודלים). נחלץ את שכבת האחסון, צעד אחר צעד.

רצף הצעדים

  1. אפיון: בדיקות ה-Characterization מתחילת הפרק כבר ירוקות, לצד החבילה הקיימת. Commit.
  2. תכנון: ב-Plan Mode, תוכנית פיצול (תבנית 4). ההחלטה המרכזית שעולה בתכנון: איפה עובר הגבול? ה-HTTPException נשאר ב-Router (זו שפת HTTP), והאחסון מסמן "לא נמצא" בהחזרת None. גם בדיקת "גוף ריק" נשארת ב-Router: זה חוק של החוזה, לא של האחסון.
  3. צעד 1: יצירת storage/tasks_store.py והעברת פעולות הקריאה בלבד (list, get) יחד עם _row_to_task. ה-Router נהיה צרכן. בדיקות, Diff, Commit.
  4. צעד 2: העברת create, update, delete. בדיקות, Diff, Commit.
  5. סקירה עצמאית: /code-review על ה-Diff המצטבר, ותיקון ממצאים אם יש.

הקוד אחרי (הקטעים המרכזיים)

backend/app/storage/tasks_store.py
"""Data access for tasks. No HTTP concerns here."""
from typing import Optional

from app.database import get_conn
from app.models import Task


def _row_to_task(row) -> Task:
    return Task(
        id=row["id"],
        title=row["title"],
        description=row["description"],
        status=row["status"],
        created_at=row["created_at"],
    )


def get_task(task_id: int) -> Optional[Task]:
    with get_conn() as conn:
        row = conn.execute(
            "SELECT * FROM tasks WHERE id = ?", (task_id,)
        ).fetchone()
    return _row_to_task(row) if row else None


def update_task(task_id: int, fields: dict) -> Optional[Task]:
    sets = ", ".join(f"{k} = ?" for k in fields)
    with get_conn() as conn:
        cur = conn.execute(
            f"UPDATE tasks SET {sets} WHERE id = ?",
            (*fields.values(), task_id),
        )
        if cur.rowcount == 0:
            return None
        row = conn.execute(
            "SELECT * FROM tasks WHERE id = ?", (task_id,)
        ).fetchone()
    return _row_to_task(row)
backend/app/routers/tasks.py (אחרי, הפונקציה המרכזית)
@router.patch("/{task_id}", response_model=Task)
def update_task(task_id: int, payload: TaskUpdate) -> Task:
    fields = payload.model_dump(exclude_none=True)
    if not fields:
        raise HTTPException(status_code=400, detail="No fields to update")
    task = tasks_store.update_task(task_id, fields)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    return task

שימו לב מה השתמר בקפידה: סדר הבדיקות (גוף ריק לפני גישה לנתונים), קודי הסטטוס, נוסחי השגיאות, והעובדה שהעדכון מחזיר את השורה הטרייה מה-Database. בדיקות האפיון הן שמוכיחות זאת: הן רצות אחרי כל צעד בלי שנגענו בהן. שימו לב גם למה שלא עשינו: לא הוספנו Protocol, לא Class, לא Dependency Injection. חילוץ המודול לבדו כבר נתן את ההפרדה; את ההפשטה נוסיף כשיהיה לה צרכן שני.

שגיאות נפוצות

  • "תשפר את הקובץ הזה" כהנחיית Refactoring. "שיפור" מזמין שינויי התנהגות. בקשו טרנספורמציה מוגדרת עם איסור מפורש על כל שינוי אחר.
  • להתחיל מחבילה אדומה. אי אפשר להבחין בין כישלון ירושה לכישלון שנגרם עכשיו.
  • לעדכן בדיקות שנכשלו כדי "להתאים לקוד החדש". ראו האזהרה למעלה: זו הדרך המהירה לקבע Regression.
  • Diff ענק אחד. אם אי אפשר לסקור את הצעד בכמה דקות, הצעד גדול מדי.
  • מחיקת "קוד מת" לפי תחושה. בלי תיק ראיות, במיוחד סביב גבולות ציבוריים ורפלקציה.
  • Refactoring ו-Feature באותו Commit. הסוקר (אנושי או Claude) לא יכול להפריד בין הזזה לשינוי.

אבטחה

  • אל תזיזו קוד אבטחה, תאפיינו אותו קודם. ולידציה, אימות, הרשאות והגבלות קצב הם המקומות שבהם "הזזה תמימה" מסוכנת: שינוי סדר (כמו ולידציה מול שליפה, שקיבענו באפיון) יכול לפתוח חור. כתבו בדיקות אפיון על מסלולי הדחייה, לא רק על ההצלחה.
  • קוד מת של אבטחה הוא לא קוד מת. Header שנראה מיותר, בדיקת קלט "כפולה": לפני שמוחקים, בררו בהיסטוריה למה זה נוסף. לפעמים זו הגנה מאירוע אמת.
  • ה-Shim יורש את שטח התקיפה. נתיב ישן שהושארו לתאימות חייב לעבור את אותן בדיקות הרשאה כמו החדש, אחרת יצרתם מעקף.
  • שימו לב לזליגת SQL דינמי. בחילוץ שעשינו, בניית ה-SET הדינמית עברה למודול האחסון. ודאו שהקריאה אליה נשארת רק מ-Pydantic שמסנן שדות; חשיפת update_task(fields) לקלט לא מסונן תהיה פרצת SQL Injection. בדיקת ה-Security מפרק 11 שומרת גם כאן.

עלות ו-Context: אסטרטגיית Session ל-Refactoring גדול

Refactoring רחב הוא ממלא Context אגרסיבי: קריאת קבצים גדולים, Diffs ארוכים, הרצות בדיקה חוזרות. העקרונות:

  • התוכנית חיה בקובץ, לא בשיחה. REFACTOR_PLAN.md עם סימון צעדים שהושלמו הוא הזיכרון החיצוני: כל Session חדש נפתח ב"קרא את התוכנית והמשך מהצעד הבא", בלי לשחזר הקשר.
  • Session לכל מקטע. אחרי כמה צעדים, או כשה-Context מתמלא, /clear ופתיחה מהתוכנית. עדיף על Session אחד ארוך שמתחיל לשכוח את ההנחיות. לחלופין /compact עם הנחיה ממוקדת ("שמור את רשימת הקבצים שהושלמו ואת הצעד הנוכחי").
  • חקירה ב-Subagents. מיפוי תלויות ("מי משתמש במודול הזה?") צורך המון קריאות קבצים; הריצו אותו ב-Subagent שמחזיר סיכום בלבד.
  • הרצות בדיקה ממוקדות, כמו בפרק 11: קובץ אחד בכל איטרציה, החבילה המלאה בסוף כל צעד.

לניהול המעמיק של Sessions ו-Context ראו פרק 14; ל-Refactoring בקנה מידה של Codebase שלם, כולל עבודה מקבילית ו-Fan-out, ראו פרק 35.

Best Practices

  • אפיון לפני שינוי: ההתנהגות הקיימת מקובעת בבדיקות, כולל המוזרויות ומסלולי השגיאה.
  • צעד אחד, בדיקות, סקירת Diff, Commit. אם אי אפשר לעצור באמצע, הצעדים גדולים מדי.
  • כל הנחיה כוללת "העבר כמו שהוא" ואיסור על שיפורים נלווים; Plan Mode לצעדים מורכבים.
  • שינוי התנהגות, אם נדרש, נעשה לפני או אחרי, לעולם לא בתוך ה-Refactoring, וב-Commit נפרד.
  • תאימות כברירת מחדל: Shims לצרכני קוד, שינויים תוספתיים ל-Schema.
  • סוקר עצמאי על ה-Diff לפני סיום: /code-review או Subagent עם קריטריונים.

תרגיל: פישוט שנראה זהה, ואינו

תרגיל 12.1

ב-backend/app/database.py של TaskFlow יש כפילות לכאורה:

backend/app/database.py (קטע)
DEFAULT_DB_PATH = os.environ.get("TASKFLOW_DB", "taskflow.db")


def get_db_path() -> str:
    return os.environ.get("TASKFLOW_DB", DEFAULT_DB_PATH)

מוצע "פישוט": למחוק את DEFAULT_DB_PATH ולהחזיר os.environ.get("TASKFLOW_DB", "taskflow.db") ישירות. ענו, בעזרת Claude או בלעדיה: (1) האם DEFAULT_DB_PATH הוא קוד מת? (2) האם הפישוט משמר התנהגות בכל תרחיש? (3) האם חבילת הבדיקות הקיימת תתפוס הבדל אם יש? (4) החליטו: לבצע או לא, ואיך.

פתרון מוסבר

(1) לא מת: DEFAULT_DB_PATH משמש כערך ברירת המחדל בתוך get_db_path. חיפוש הפניות מוכיח זאת מיד.

(2) לא בדיוק: יש הבדל התנהגות דק. DEFAULT_DB_PATH מקובע בזמן טעינת המודול: אם TASKFLOW_DB היה מוגדר בזמן ה-import ונמחק מהסביבה אחר כך, הקוד הישן ימשיך להחזיר את הערך שנלכד בטעינה, והקוד "המפושט" יחזור פתאום ל-taskflow.db. פישוט שנראה זהה לחלוטין משנה התנהגות בתרחיש קצה. זה בדיוק השיעור: "אותו דבר בערך" אינו "אותו דבר".

(3) לא: הבדיקות מגדירות את TASKFLOW_DB לפני ה-import ולא מוחקות אותו, כך שכל החבילה ירוקה בשתי הגרסאות. זו הדגמה חיה של הגבול מסעיף הוכחת השימור: חבילה ירוקה מוכיחה שימור רק של מה שמכוסה, ולכן סקירת ה-Diff והחשיבה על תרחישים הן שכבה שאין לוותר עליה.

(4) החלטה סבירה: לבצע, כי התרחיש (מחיקת משתנה סביבה באמצע ריצה) אינו נתמך ואינו מתועד, אבל לבצע במודע: Commit נפרד עם הודעה שמצהירה על ההבדל ההתנהגותי הדק. החלטה סבירה לא פחות: להשאיר, כי אין כאב אמיתי. מה שפסול הוא לבצע בלי לדעת שההבדל קיים. נסו למסור ל-Claude את ההנחיה is this simplification behavior-preserving? think about import-time versus call-time environment reads וראו אם הוא מזהה את ההבדל בעצמו.

סיכום

  • Refactoring משנה מבנה ומשמר התנהגות; כל השאר הוא שינוי התנהגות שמנוהל בנפרד.
  • הסדר הקבוע: אפיון, תוכנית, צעדים קטנים עם בדיקות ו-Commit לכל צעד, סוקר עצמאי בסוף.
  • Characterization Tests מקבעים את מה שיש, כולל מוזרויות ומסלולי שגיאה; בדיקה שנכשלת אחרי צעד היא כמעט תמיד צודקת.
  • קוד מת מוסר רק עם תיק ראיות; תאימות נשמרת עם Shims ושינויי Schema תוספתיים.
  • חבילה ירוקה היא תנאי הכרחי ולא מספיק: סקירת Diff ומודעות לפערי כיסוי משלימות את ההוכחה.
  • ב-Refactoring גדול, התוכנית חיה בקובץ וה-Sessions מתחלפים סביבה; בפרק הבא נחבר את הצעדים האלה לזרימת Git ו-Pull Requests מסודרת.
