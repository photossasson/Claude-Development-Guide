ביצוע שינוי קוד מבוקר

זהו הפרק המרכזי של חלק ב: תהליך עבודה מלא בן 15 שלבים לביצוע שינוי קוד עם Claude Code, מהבנת הדרישה ועד Pull Request. נדגים אותו מקצה לקצה על פרויקט הדוגמה TaskFlow, עם Feature אמיתי: הוספת שדה priority למשימות, כולל Backend, Frontend, בדיקות, תיעוד ו-PR. בכל שלב תראו את ה-Prompt המדויק, את התוצאה הצפויה, איך מאמתים, ומה עושים כשמשהו נכשל.

למה תהליך מבוקר, ולמה צעדים קטנים

הפיתוי הגדול ביותר בעבודה עם Agent חזק הוא ה-Prompt הכוללני: "תוסיף שדה עדיפות למשימות, בכל השכבות, עם בדיקות, ותפתח PR". לפעמים זה אפילו יעבוד. אבל כשהוא נכשל, הוא נכשל ביוקר: מקבלים Diff ענק שנוגע בעשרה קבצים, שאי אפשר באמת לסקור, עם באג חבוי באחת הפינות, ואין דרך לדעת איזה חלק תקין ואיזה לא. התהליך המבוקר הופך את המשימה לסדרת צעדים קטנים, שכל אחד מהם ניתן לאימות בנפרד.

שלוש סיבות מעשיות להעדיף צעדים קטנים על פני Prompt אחד גדול:

  • אימות מקומי: אחרי כל צעד יש בדיקה שאפשר להריץ (בדיקות, Type Check, /diff). התיעוד הרשמי מדגיש בדיוק את זה: תנו ל-Claude דרך לאמת את עבודתו, אחרת אתם הופכים בעצמכם ללולאת האימות היחידה. ההמלצה הרשמית לגבי Refactoring מנוסחת במפורש: לעבוד ב-Increments קטנים וניתנים לבדיקה.
  • Diff קריא: אדם יכול לסקור ברצינות Diff של 30 שורות. הוא לא יכול לסקור ברצינות 800 שורות. סקירה אמיתית של השינוי היא שכבת ההגנה המרכזית שלכם.
  • כשל זול: אם צעד קטן נכשל, חוזרים צעד אחד אחורה. אם Prompt ענק נכשל, לעיתים קרובות זורקים הכול ומתחילים מחדש, אחרי ששרפתם זמן, Tokens ו-Context.

מתי להשתמש בתהליך המלא: כל שינוי שנוגע ביותר מקובץ אחד או שניים, כל שינוי שמשנה התנהגות חיצונית (API, סכמת נתונים, ממשק משתמש), וכל עבודה על קוד שאינכם מכירים לעומק. מתי לא: תיקון הקלדה, הוספת שורת Log, שינוי חד משורתי שאתם יכולים לתאר במשפט אחד. במקרים כאלה, לפי התיעוד הרשמי, תכנון מוקדם הוא תקורה מיותרת: בקשו את השינוי ישירות. חלק מהשלבים גם מתכווצים באופן טבעי בפרויקטים קטנים; הנקודה היא לוותר עליהם בכוונה, לא מתוך שכחה.

דרישות מוקדמות

הפרק מניח שעברתם את פרק 3 (עבודה בסיסית ב-Session), פרק 6 (קריאת Repository) ו-פרק 7 (Plan Mode), ושיש לכם עותק עבודה של TaskFlow עם Git מאותחל, כפי שהכנו בפרק 3. נדרשים גם Python 3.12, Node.js ו-pytest מותקנים.

ה-Feature שנבנה, ומצבי ההרשאות לאורך הדרך

הדרישה שנממש: לכל משימה תהיה עדיפות (low, medium או high), עם ברירת מחדל medium. העדיפות תיקבע ביצירה, תהיה ניתנת לעדכון, תוחזר בכל תשובות ה-API, ותוצג ברשימת המשימות ב-Frontend. זה Feature אמיתי וטיפוסי: הוא חוצה את כל השכבות (מודל, בסיס נתונים, API, טיפוסים, ממשק), אבל כל שכבה בו קטנה.

שלב 1: הבנת הדרישה

לפני שנוגעים בקוד, מוודאים שהדרישה חד-משמעית. עברו ל-Plan Mode עם Shift+Tab (או פתחו את ה-Session עם claude --permission-mode plan), ונסחו את הדרישה בעצמכם, כולל מה שמחוץ לתחום:

Prompt (Plan Mode)
We want to add a priority field to tasks in this project.
Requirements: values low / medium / high, default medium,
set on create, editable via update, returned by the API,
shown in the task list UI. Out of scope: sorting or
filtering by priority.
Before we plan anything: restate the requirement in your own
words and ask me about anything ambiguous or risky.

מה קורה: Claude מנסח מחדש את הדרישה ושואל שאלות הבהרה. בהרצה שלנו הוא שאל שתי שאלות מצוינות: מה יקרה למשימות קיימות בבסיס הנתונים (תשובה: יקבלו medium), והאם ערך עדיפות לא חוקי צריך להחזיר 422 (תשובה: כן, כמו שאר ה-Validation בפרויקט). ניסוח "מה מחוץ לתחום" חשוב לא פחות מהדרישה עצמה: הוא מונע מהמודל "לשפר" מעבר למה שביקשתם. לבקשות גדולות באמת יש טכניקה חזקה עוד יותר, ראיון יזום דרך AskUserQuestion, שראינו בפרק 5.

אימות: אתם יכולים לענות בביטחון על שלוש שאלות: מה נבנה, מה לא נבנה, ומה קורה לנתונים קיימים. אם לא, המשיכו לשאול. כישלון כאן הוא הזול ביותר בכל התהליך.

שלב 2: מחקר הקוד

עדיין ב-Plan Mode. עכשיו בודקים איך התכונות הקיימות עובדות, כדי שהשדה החדש יתיישר עם הדפוסים הקיימים:

Prompt (Plan Mode)
Research how the existing status field flows through the system,
end to end: model validation, database schema, SQL in the router,
API responses, frontend types and UI. Don't propose changes yet,
just explain the current mechanics and conventions.

מה קורה: Claude קורא את models.py, database.py, routers/tasks.py, types.ts ו-App.tsx, ומסביר את השרשרת: TaskStatus מוגדר כ-Literal של Pydantic, בסיס הנתונים אוכף אותם ערכים עם CHECK Constraint, וה-Frontend משכפל אותם כ-Union Type ב-TypeScript. זה בדיוק הדפוס שנחקה עבור priority. למה לחקור את status ולא לשאול "איך מוסיפים שדה"? כי שאלה מעוגנת בקוד קיים מחזירה תשובה מעוגנת בקוד קיים. זה עיקרון שראינו בפרק 6: הצביעו על דוגמה קיימת.

אימות: ההסבר מזכיר את שלושת מוקדי האמת: ה-Literal במודלים, ה-CHECK בסכמה, והטיפוס ב-Frontend. אם Claude פספס אחד, בקשו ממנו לבדוק שוב; עדיף לגלות עכשיו ולא בשלב 11.

שלב 3: זיהוי קבצים מושפעים

Prompt (Plan Mode)
List every file that must change to add the priority field,
and for each file: what changes and why. Also list files you
considered and decided NOT to change.

תוצאה צפויה: רשימה של שישה קבצים: models.py (שלושה מודלים), database.py (עמודה חדשה + טיפול בבסיסי נתונים קיימים), routers/tasks.py (ה-INSERT והפונקציה _row_to_task), tests/test_tasks.py, types.ts ו-App.tsx. חלק "מה החלטתי לא לשנות" חשוב: בהרצה שלנו Claude ציין שאין צורך לגעת ב-api.ts (כי createTask כבר מעביר Payload שלם) וב-main.py. רשימה כזאת היא חוזה: אם בשלב 8 תראו ב-/diff קובץ שלא הופיע בה, זה דגל אדום.

שלב 4: הכנת Plan

Prompt (Plan Mode)
Create an implementation plan for this feature as a sequence of
small, independently verifiable slices. Each slice: what changes,
what command verifies it. Backend first, then frontend.

מה קורה: Claude מציג Plan מחולק לפרוסות. ה-Plan שאישרנו בהרצה שלנו:

  1. פרוסה 1, מודלים וסכמה: TaskPriority ב-models.py, עמודה + Migration ב-database.py. אימות: הבדיקות הקיימות עדיין עוברות.
  2. פרוסה 2, Router ובדיקות: עדכון ה-INSERT ו-_row_to_task, ארבע בדיקות חדשות. אימות: pytest -q ירוק.
  3. פרוסה 3, Frontend: טיפוסים ותצוגה. אימות: npm run typecheck ירוק ובדיקה ידנית בדפדפן.

ב-Plan Mode אפשר ללחוץ Ctrl+G כדי לפתוח את ה-Plan בעורך הטקסט ולערוך אותו ישירות לפני האישור. אל תאשרו Plan שאתם לא מסכימים איתו; לערוך תוכנית זול פי מאה מלערוך קוד.

שלב 5: Acceptance Criteria

לפני היציאה מ-Plan Mode, מקבעים את הגדרת ה"גמור" כרשימה שאפשר לבדוק מכנית:

Prompt (Plan Mode)
Write the acceptance criteria for this feature as a numbered,
testable checklist. Include validation, defaults, existing data,
and the project's Definition of Done from CLAUDE.md.

תוצאה צפויה: רשימה בסגנון הבא (זו הרשימה שעבדנו מולה בפועל):

  • POST /tasks מקבל priority אופציונלי; בלעדיו הערך medium.
  • ערך עדיפות לא חוקי מוחזר עם 422, ביצירה ובעדכון.
  • PATCH /tasks/{id} מעדכן עדיפות בלי לגעת בשדות אחרים.
  • כל תשובות ה-API כוללות priority, גם עבור משימות שנוצרו לפני השינוי.
  • רשימת המשימות ב-UI מציגה את העדיפות ליד הכותרת.
  • pytest -q ו-npm run typecheck עוברים; התיעוד עודכן (לפי ה-Definition of Done של הפרויקט).

שימו לב שהקריטריונים האלה יהפכו כמעט אחד לאחד לבדיקות בשלב 11 ולתיאור ה-PR בשלב 15. זה לא מקרי: כך נסגר המעגל בין דרישה, קוד והוכחה.

שלב 6: יצירת Branch

צאו מ-Plan Mode (שוב Shift+Tab עד מצב ברירת המחדל) ובקשו:

Prompt
create a git branch for this work: feature/task-priority

מה קורה: Claude מבקש אישור להריץ git checkout -b feature/task-priority (או git switch -c). קראו את הפקודה בחלון האישור ואשרו. ה-Branch מבודד את העבודה: אם הכול משתבש, main נשאר נקי. אימות מהיר, בעצמכם או דרך Claude:

$ git status On branch feature/task-priority nothing to commit, working tree clean

אם השלב נכשל: "working tree not clean" אומר שיש שינויים לא שמורים מעבודה קודמת. אל תמשיכו מעל ערימה קיימת: בקשו מ-Claude לסכם מה השינויים התלויים, והחליטו אם לשמור אותם ב-Commit נפרד או לבטלם. על Git לעומק, כולל Worktrees לעבודה מקבילה, נרחיב בפרק 13.

שלב 7: שינוי קטן ומדורג

עכשיו מבצעים, פרוסה אחת בכל פעם. פרוסה ראשונה:

Prompt
Implement slice 1 of the plan only: add TaskPriority to
models.py (low/medium/high, default medium on create, optional
on update, required on Task), and update database.py so both new
and existing databases get the priority column. Do not touch the
router, tests or frontend yet.

מה קורה: Claude מציע שתי עריכות, ואתם מאשרים כל אחת אחרי קריאת ה-Diff שלה. כך נראה models.py אחרי הפרוסה (החלקים החדשים):

וב-database.py, בנוסף לעמודה בהגדרת הטבלה, Migration קלה לבסיסי נתונים שנוצרו לפני השינוי (כי CREATE TABLE IF NOT EXISTS לא מעדכן טבלה קיימת):

backend/app/database.py (inside init_db)
        conn.execute(
            """
            CREATE TABLE IF NOT EXISTS tasks (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                title TEXT NOT NULL,
                description TEXT NOT NULL DEFAULT '',
                status TEXT NOT NULL DEFAULT 'todo'
                    CHECK (status IN ('todo', 'in_progress', 'done')),
                priority TEXT NOT NULL DEFAULT 'medium'
                    CHECK (priority IN ('low', 'medium', 'high')),
                created_at TEXT NOT NULL DEFAULT (datetime('now'))
            )
            """
        )
        cols = {row["name"] for row in conn.execute("PRAGMA table_info(tasks)")}
        if "priority" not in cols:
            conn.execute(
                "ALTER TABLE tasks ADD COLUMN priority TEXT NOT NULL DEFAULT 'medium'"
            )

פרוסה שנייה, באותה רוח:

Prompt

and _row_to_task returns it, then add tests: create with
priority, default is medium, invalid priority returns 422,

ההנחיה "Do not touch X yet" בפרוסה 1 היא לב השיטה: היא שומרת כל Diff קטן וממוקד, ומשאירה לכם נקודות עצירה טבעיות לאימות.

שלב 8: בדיקת Diff

אחרי כל פרוסה, ולפני כל Commit, בודקים מה השתנה בפועל:

Prompt
/diff

מה קורה: נפתח מציג ה-Diff האינטראקטיבי שהכרנו בפרק 3: חצים למעלה ולמטה עוברים בין קבצים, חצים לצדדים מחליפים בין ה-Git Diff המלא לבין השינויים של כל תור בנפרד, Enter פותח קובץ, Esc חוזר. מה בודקים בפועל? שלושה דברים, לפי הסדר: (א) רשימת הקבצים זהה לרשימה משלב 3, בלי אורחים לא צפויים; (ב) אין שינויים "אגביים" שאינם קשורים ל-Feature (סידור Imports גורף, שינוי פורמט, מחיקת הערות); (ג) הלוגיקה עצמה נכונה. אם מצאתם משהו, זה הרגע לתקן:

Prompt (loop back)
revert the unrelated formatting changes in routers/tasks.py,
keep only the priority changes
אבטחה: הסקירה היא שער החובה

כל מנגנוני האישור של Claude Code שווים בדיוק כמו תשומת הלב שלכם בהם. לסקור Diff לפני אישור זה לא טקס: זו הנקודה שבה תתפסו קוד שמדליף סודות ל-Log, Dependency חדש שלא ביקשתם, או שינוי בקובץ הגדרות רגיש. אם אין לכם זמן לקרוא את ה-Diff, אין לכם זמן לאשר אותו. השלמה טובה היא /security-review, פקודה מובנית שבודקת את ה-Diff הנוכחי לאיתור חולשות אבטחה; נרחיב עליה בפרק 20.

שלב 9: Lint

Linter תופס בעיות סגנון ותקלות שטחיות (משתנים לא בשימוש, Imports מיותרים) לפני שבן אדם מבזבז עליהן זמן סקירה. ל-TaskFlow אין Linter מוגדר ל-Backend, וזו הזדמנות להדגים נקודה חשובה: כשכלי חסר, אפשר לבקש מ-Claude להוסיף אותו כחלק מהעבודה, בנפרד מה-Feature:

Prompt
run a linter on the backend. if none is configured, install ruff
into the virtualenv, run "ruff check backend", and fix only
findings in files we changed. do not add config files yet.

מה קורה: Claude מבקש אישור ל-pip install ruff ואז מריץ ruff check backend. בהרצה נקייה הפלט קצר:

$ ruff check backend All checks passed!

אם השלב נכשל: ממצאי Lint בקבצים שנגעתם בהם, תקנו מיד (זה בדרך כלל תיקון אוטומטי בטוח). ממצאים בקבצים אחרים, אל תתקנו עכשיו: ערבוב ניקיון כללי לתוך Branch של Feature הוא בדיוק ה"שינוי האגבי" שאסרנו בשלב 8. רשמו לעצמכם והקדישו לזה Branch נפרד. הגבלת ההיקף בתוך ה-Prompt ("only findings in files we changed") עושה את זה בשבילכם.

שלב 10: Type Check

ב-Frontend של TaskFlow יש בודק טיפוסים אמיתי מוגדר: tsc במצב strict. אחרי פרוסת ה-Frontend (שלב 7, פרוסה 3) מריצים:

Prompt
Implement slice 3: add TaskPriority to frontend types, include
priority in the Task interface and as optional in TaskCreate,
and show the priority next to each task title in App.tsx.
Then run "npm run typecheck" in frontend/ and fix any errors.

למה זה שלב נפרד מ-Tests: בדיקת טיפוסים תופסת סוג אחר של שגיאות, חוסר עקביות בין חלקי המערכת, בלי להריץ שום קוד. אצלנו היא בדיוק מה שתופס מצב שבו הוספתם priority ל-Interface אבל שכחתם לעדכן קוד שבונה אובייקט Task ידנית. ב-Backend אין בפרויקט בודק טיפוסים סטטי מוגדר (הרמזים נאכפים בזמן ריצה על ידי Pydantic); בפרויקט Python גדול הייתם מוסיפים כאן גם mypy או דומיו. התוצאה הצפויה:

$ npm run typecheck > tsc --noEmit (ללא פלט: הצלחה)

אם השלב נכשל: שגיאת TypeScript מצביעה בדיוק על הקובץ והשורה. הדביקו אותה כמות שהיא ל-Claude (או שהוא כבר רואה אותה, אם הוא הריץ את הפקודה בעצמו) ובקשו תיקון של השורש: אל תרשו as any או @ts-ignore כדרך לעקוף.

שלב 12: Self Review

לפני שמזמינים סוקר אנושי, מריצים סוקר טרי ואוטומטי. ה-Skill המובנה /code-review סוקר את ה-Diff הנוכחי לאיתור באגים של נכונות, בתוך Subagent עם Context נקי, כך שהוא לא "מאוהב" בקוד שזה עתה נכתב:

Prompt
/code-review

אפשר לשלוט בעומק עם רמות מאמץ (low עד max, ו-ultra לסקירת ענן עמוקה), ולבקש החלה אוטומטית של הממצאים עם --fix. בהרצה שלנו הסקירה החזירה ממצא אחד ראוי: הבדיקות לא מכסות עדכון עדיפות עם ערך לא חוקי ב-PATCH (בדקנו רק ב-POST). הוספנו בדיקה. שימו לב לאזהרה מהתיעוד הרשמי: סוקר שמתבקש למצוא פערים כמעט תמיד ימצא משהו; אמצו ממצאים שנוגעים לנכונות ולדרישות, והרשו לעצמכם לדחות הערות סגנון בנימוק קצר. השלימו את הסקירה האוטומטית בשאלה ממוקדת:

Prompt
before we commit: re-read the full diff against the acceptance
criteria from step 5. anything missing, and anything that changed
but is outside the scope we agreed on?

ה-Definition of Done של TaskFlow (בקובץ CLAUDE.md של הפרויקט) קובע במפורש: התיעוד מתעדכן כשההתנהגות משתנה. אצלנו זה אומר שתי שורות:

Prompt
update the project docs for the new field: add the priority

למה זה שלב ולא מטלה נשכחת: קובץ ה-CLAUDE.md של הפרויקט הוא לא רק תיעוד לבני אדם; Claude קורא אותו בתחילת כל Session (פרק 15). שורת "priority values: low, medium, high" שם פירושה שכל Session עתידי יכיר את מרחב הערכים בלי לחקור מחדש. תיעוד שמתעדכן באותו Commit עם הקוד הוא היחיד שנשאר נכון לאורך זמן.

שלב 14: Commit

Prompt
commit the changes with a descriptive message. use two commits:
one for the backend (model, schema, router, tests), one for the
frontend and docs.

מה קורה: Claude מריץ git status ו-git diff כדי לסכם, ואז מבקש אישור לפקודות git add ו-git commit עם הודעות שהוא ניסח. קראו את ההודעות בחלון האישור; הודעה טובה מתארת את ה"למה", לא רק את ה"מה". אימות:

$ git log --oneline -2 3f2c1aa Add priority to frontend task list and update docs 9d84b07 Add priority field to tasks API with validation and migration

אם השלב נכשל: אם ה-Commit הראשון כולל בטעות גם קבצים מהפרוסה השנייה, בקשו "undo the last commit but keep the changes staged, then split it as we agreed". פיצול נכון של Commits הופך גם את הסקירה ב-PR וגם Revert עתידי לנקודתיים.

Prompt

מה קורה: Claude משתמש ב-CLI של GitHub בשם gh (נדרש שיהיה מותקן ומחובר; פרק 13) ומבקש אישור ל-git push ול-gh pr create. התיעוד הרשמי ממליץ לסקור את ה-PR שנוצר לפני שליחה ולבקש מ-Claude להצביע על סיכונים, וזה בדיוק מה ששילבנו בתיאור. תוספת נחמדה מהתיעוד: Session שיצר PR דרך gh pr create מקושר אליו אוטומטית, ואפשר לחזור אליו בעתיד עם claude --from-pr 1234 (עם מספר ה-PR שלכם).

תוצאה צפויה: קישור ל-PR מודפס בשיחה. ה-PR קטן (בהרצה שלנו: 6 קבצים, סדר גודל של 60 שורות), עם תיאור שסוקר אנושי יכול לקרוא בדקה. זה המבחן הסופי של כל התהליך: אם הגעתם לכאן עם Diff שקל לסקור, התהליך עבד.

טעויות נפוצות

  • לדלג על שלבים 1 עד 5 "כי המשימה ברורה": אם היא באמת ברורה במשפט אחד, בסדר. אבל רוב ה"ברור לי" מתגלה כלא ברור בשלב 11, ששם התיקון יקר יותר.
  • לאשר עריכות בלי לקרוא: אחרי עשרה אישורים מתחילים ללחוץ בלי לקרוא. זה בדיוק הרגע לעצור, או לעבור במודע ל-acceptEdits ולהעביר את כל כובד הסקירה ל-/diff לפני ה-Commit. סקירה חייבת לקרות באחת הנקודות; בחרו איפה.
  • פרוסה "קטנה" שהיא בעצם שלוש: אם ה-Prompt שלכם כולל "and" שלוש פעמים, אלו כנראה שלוש פרוסות.
  • לתקן ממצאי Lint בכל ה-Repository: ערבוב ניקיון רוחבי לתוך Branch של Feature מנפח את ה-Diff והופך את הסקירה לחסרת ערך.
  • להסתפק בבדיקות ירוקות: ראינו למעלה: הבדיקות רצות על בסיס נתונים טרי, והבאג האמיתי חיכה בבסיס נתונים ותיק. הריצו גם את המערכת עצמה.
  • Commit אחד ענק בסוף היום: מאבד את כל היתרון של הפרוסות. עשו Commit בכל נקודה ירוקה.

עלות ו-Context

תהליך של 15 שלבים נשמע יקר, אבל בפועל הוא בדרך כלל זול יותר מ-Prompt גדול שנכשל: כישלון של פרוסה עולה סבב תיקון קצר, בעוד כישלון של Big Bang עולה את כל הניסיון מחדש. שלושה הרגלים חוסכים בפועל: ראשית, עשו את שלבי המחקר (2 עד 3) ממוקדים; חקירה פתוחה של כל ה-Repository ממלאת את ה-Context בקבצים שלא תצטרכו, ובפרויקט גדול עדיף להאציל אותה ל-Subagent. שנית, עקבו אחרי ההקשר עם /context, ואם סיימתם נושא, אל תגררו אותו הלאה: Session אחד ל-Feature אחד. שלישית, אל תדביקו פלטים ארוכים (למשל Log שלם של CI) כשמספיקות עשר השורות הרלוונטיות. על מבנה העלויות המלא נרחיב בפרק 30.

Best Practices

  • נסחו "מה מחוץ לתחום" בכל דרישה. זו השורה שהכי מצמצמת הפתעות.
  • חקרו דפוס קיים (אצלנו: status) ובקשו ליישר את החדש אליו.
  • דרשו מ-Claude רשימת קבצים מושפעים מראש, והשוו אליה את ה-/diff בסוף.
  • כל פרוסה מסתיימת בפקודת אימות שרצה בפועל, ובראיות: פלט הבדיקות בשיחה, לא "הכול עובר" סתמי.
  • סקרו את ה-Diff בנקודה מוגדרת אחת לפחות: באישור העריכה או ב-/diff לפני ה-Commit.
  • סיימו כל ישיבת עבודה בנקודה ירוקה עם Commit, כדי שלמחרת תתחילו ממצב נקי.

Anti-patterns

  • ה-Big Bang: "תממש הכול ותגיד לי כשסיימת" במצב שמאשר הכול אוטומטית, ואז לגלות בסוף היום Diff של 900 שורות שאיש לא סקר.
  • הכחשת הלולאה: להתעקש "רק תתקן את הבדיקה" שוב ושוב במקום לחזור שלב אחורה ולתקן את ההבנה או את ה-Plan.
  • ריכוך בדיקות: כשבדיקה נכשלת, "לתקן" אותה כך שתעבור (להחליש Assert, למחוק מקרה קצה) במקום לתקן את הקוד. בקשו במפורש: תקן את הקוד, לא את הבדיקה, אלא אם הבדיקה מוכחת כשגויה.
  • Branch נצחי: Branch שחי שבועיים וסופג עוד ועוד "עוד דבר קטן". התהליך בנוי להגיע ל-PR קטן ולסיים.
  • דילוג על תיעוד "בינתיים": אין בינתיים. תיעוד שלא עודכן באותו Commit לא יעודכן.

תרגיל

תרגיל 9.1: שדה done_at, מקצה לקצה

בצעו את כל 15 השלבים עבור דרישה חדשה ב-TaskFlow: לכל משימה יתווסף שדה done_at, חותמת זמן שמתמלאת אוטומטית כשמשימה עוברת לסטטוס done, ומתאפסת (null) כשהיא עוזבת אותו. השדה אינו מתקבל מהלקוח, רק מוחזר. דרישות: הוא מופיע בכל תשובות ה-API (כ-null כשאין ערך), נשמר לאורך עדכונים אחרים, ומכוסה בבדיקות. מחוץ לתחום: תצוגה ב-UI מעבר להוספת הטיפוס. נסחו בעצמכם את ה-Acceptance Criteria לפני שאתם מבקשים Plan, ושימו לב במיוחד לשאלה: מה קורה כשמעדכנים משימה שכבר done לסטטוס done שוב?

פתרון מוסבר

שלבים 1 עד 5: הנקודה העדינה בדרישה היא סמנטיקת המעברים, וזו בדיוק השאלה ששווה להציף בשלב 1: קבענו ש-done אל done לא מרענן את החותמת (המשימה "הושלמה" פעם אחת). קריטריונים מרכזיים: יצירה מחזירה done_at: null; מעבר ל-done ממלא ערך; מעבר מ-done לסטטוס אחר מאפס; עדכון שלא נוגע בסטטוס לא משנה את הערך; הלקוח לא יכול לקבוע את הערך בעצמו.

קבצים מושפעים: models.py (הוספת done_at: Optional[str] = None למודל Task בלבד; לא ל-TaskCreate ולא ל-TaskUpdate, כי השדה אינו קלט), database.py (עמודה done_at TEXT בהגדרה, ו-ALTER TABLE tasks ADD COLUMN done_at TEXT ב-Migration כשהיא חסרה), routers/tasks.py (הלוגיקה), בדיקות, ו-types.ts (done_at: string | null).

לב המימוש נמצא ב-update_task: לפני בניית ה-UPDATE, אם fields כולל status, משווים לסטטוס הנוכחי בבסיס הנתונים; מעבר אל done מוסיף done_at = datetime('now') לשדות המתעדכנים, מעבר החוצה מ-done מוסיף done_at = NULL, וכל מקרה אחר לא נוגע בעמודה. זה מחייב SELECT של המשימה לפני העדכון, וזה שינוי מבני קטן שראוי שיופיע במפורש ב-Plan. גם _row_to_task מתעדכן להעביר done_at=row["done_at"]; אם תשכחו, תפגשו בדיוק את כשל ה-ValidationError שראינו בשלב 11, והפעם תזהו אותו מיד.

בדיקות מינימליות: ארבע: יצירה מחזירה null; PATCH ל-done ממלא ערך; PATCH חזרה ל-todo מאפס; עדכון כותרת בלבד על משימת done משאיר את הערך במקומו. בדיקת בונוס ששווה נקודות: שליחת done_at ב-Payload של PATCH פשוט מנוטרלת (ברירת המחדל של Pydantic מתעלמת משדות לא מוכרים), כלומר לא משנה את הערך.

סיום: /diff מול רשימת הקבצים, Lint, npm run typecheck, pytest -q, /code-review, עדכון CLAUDE.md (שורת קונבנציה על סמנטיקת done_at), שני Commits, ו-PR עם הקריטריונים כרשימת סימון. אם כל זה לקח לכם פחות משעה, התהליך כבר יושב לכם ביד.
