Team Workflows: עבודת צוות עם Claude Code

עד עכשיו עבדנו בעיקר כמפתח יחיד. בפרק הזה נעבור לרמת הצוות: אילו קבצי הגדרה משתפים דרך Git ואילו נשארים מקומיים, איך מפיצים יכולות לכל הצוות עם Plugins, איך מנהלים מרכזית מדיניות עם Managed Settings בתוכניות Team ו-Enterprise, איך שומרים על סדר עם Writer/Reviewer ו-Branches, איך עוקבים אחרי עלויות ושימוש, ואיך מונעים התנגשויות בין כמה Agents שעובדים במקביל. בסוף נתרגל תכנון תצורה מלאה לצוות של שישה מפתחים על פרויקט TaskFlow.

מהי עבודת צוות עם Claude Code ואיזו בעיה היא פותרת

כשמפתח אחד עובד עם Claude Code, ההגדרות שלו הן עניין אישי: קובץ CLAUDE.md שהוא כתב, הרשאות שאישר, ו-Skills שבנה לעצמו. ברגע שיש צוות, כל אחד מהדברים האלה הופך לשאלה ארגונית: אם כל מפתח מגדיר לבד, מקבלים שישה עותקים שונים של "חוקי הפרויקט", תוצאות לא עקביות ב-Code Review, ופערי אבטחה שאף אחד לא רואה.

החדשות הטובות: Claude Code תוכנן מראש לעבודת צוות. מערכת ה-Scopes של ההגדרות (שהכרנו בפרק 17) מפרידה בין מה ששייך לפרויקט (משותף דרך Git), מה ששייך למשתמש (אישי), ומה שנכפה על ידי הארגון (Managed). הפרק הזה מלמד להשתמש בהפרדה הזאת נכון, ומוסיף את השכבות הארגוניות: הפצה, אכיפה, מדידה וממשל נתונים.

מתי להשקיע בזה, ומתי לא

  • השקיעו כשיש שני מפתחים או יותר על אותו Repository, כשיש דרישות Compliance, או כשהארגון משלם על שימוש ורוצה שליטה בעלויות.
  • השקיעו במיוחד כשחלק מהעבודה רצה אוטומטית (CI, GitHub Actions, Subagents): שם אין אדם שמאשר כל פעולה, והתצורה המשותפת היא קו ההגנה.
  • אל תגזימו בצוות של שניים-שלושה על פרויקט צד: קובץ CLAUDE.md משותף וקובץ .claude/settings.json אחד מספיקים בהתחלה. Managed Settings ולוחות Analytics רלוונטיים בעיקר לתוכניות Team ו-Enterprise.

איך זה עובד מושגית: שלוש שכבות של סמכות

כל מה שנראה בפרק נשען על מודל פשוט אחד. חשבו על שלוש שכבות, מהרכה לקשה: קונבנציה (מה שכתוב ב-CLAUDE.md וב-Skills: מנחה את Claude אבל אינו נאכף טכנית), תצורת פרויקט (מה שב-.claude/settings.json המשותף: חוקים שהלקוח אוכף, אבל מפתח יכול להרחיב מקומית), ומדיניות מנוהלת (מה שהארגון כופה מלמעלה: אף שכבה מתחתיה לא יכולה לבטל אותה). האומנות של תצורת צוות טובה היא לשים כל דבר בשכבה הנמוכה ביותר שמספיקה לו: מה שיכול להישאר קונבנציה נשאר קונבנציה, כי אותה הכי זול לעדכן (עוד PR), ומה שחייב אכיפה מטפס למעלה. כשמשהו יושב בשכבה גבוהה מדי, כל שינוי קטן דורש Owner ארגוני; כשהוא יושב נמוך מדי, אי אפשר לסמוך עליו.

אזהרה: Credentials לעולם לא ב-Commit

קובץ .mcp.json משותף מגדיר אילו שרתים קיימים, אבל מפתחות API וסודות נשארים במשתני סביבה מקומיים או ב-.env שמוחרג מ-Git. מי שמריץ לראשונה פרויקט עם .claude/settings.json רואה בדיוק אילו חוקי הרשאות התיקייה מבקשת, כחלק מחלון ה-Trust (ראו פרק 3): זה מנגנון מכוון, כי תצורה משותפת היא גם משטח תקיפה.

Review לשינויי תצורה

קבצי התצורה האלה הם קוד לכל דבר, ולפעמים מסוכנים יותר מקוד: שינוי ב-.claude/settings.json יכול להוסיף חוק allow רחב, Hook שמריץ פקודת Shell אצל כל חברי הצוות, או שרת MCP חדש. לכן מומלץ לקבוע מדיניות מפורשת:

  • כל שינוי ב-.claude/, ב-CLAUDE.md וב-.mcp.json עובר Pull Request עם Review אנושי, כמו קוד Production.
  • הגדירו ב-GitHub קובץ CODEOWNERS שממפה את הנתיבים האלה ל-Tech Lead או לצוות Platform, כך ש-Review שלהם נדרש אוטומטית.
  • ב-Review של Hook חדש בודקים את הסקריפט עצמו, לא רק את ה-JSON: הוא ירוץ על המכונה של כולם.
  • חוקי deny חדשים בטוחים לאישור מהיר; חוקי allow חדשים מקבלים את הבדיקה הקפדנית ביותר.

Plugins: מנגנון ההפצה של הצוות

שיתוף דרך ה-Repository עובד מצוין לפרויקט אחד. אבל כשיש לצוות עשרה Repositories, לא מעתיקים את אותם Skills ו-Agents לכל אחד מהם. בשביל זה קיימים Plugins, שהכרנו לעומק בפרק 26: חבילה אחת עם Skills, Agents, Hooks, פקודות ושרתי MCP, שמותקנת בפקודה אחת ומתעדכנת מרכזית.

הדפוס הצוותי המקובל: מקימים Marketplace פרטי של הארגון (Repository ייעודי ב-Git, ראו פרק 26, סעיף Marketplace פרטי), מפרסמים בו Plugin ארגוני אחד או יותר, וכל מפתח מתקין משם. עדכון גרסה ב-Marketplace מגיע לכולם, במקום לרדוף אחרי עותקים; ניהול הגרסאות של ה-Plugin עצמו (ראו פרק 26) נותן לצוות גם דרך מסודרת לגלגל שינוי לאחור. בארגונים עם Managed Settings אפשר גם להקשיח: ההגדרה strictKnownMarketplaces מגבילה מאילו מקורות מותר להתקין, וההגדרה strictPluginOnlyCustomization חוסמת Skills, Agents, Hooks ושרתי MCP שלא מגיעים מ-Plugin או מהגדרות מנוהלות, כך שכל היכולות בצוות עוברות דרך צינור הפצה מבוקר אחד.

Best Practice

חלוקת עבודה מומלצת: מה שייחודי ל-Repository אחד (מוסכמות הקוד שלו, פקודות ה-Build שלו) נשאר ב-.claude/ של אותו Repository. מה שמשותף לכל הארגון (Skill של תהליך Release, Agent של Code Review, חיבורי MCP פנימיים) עובר ל-Plugin ארגוני.

Managed Settings: מדיניות מרכזית ב-Team ו-Enterprise

קבצים ב-Repository הם המלצה חזקה, אבל כל מפתח יכול לעקוף אותם בהגדרות המשתמש שלו. כשצריך אכיפה אמיתית, ארגונים בתוכניות Claude for Teams ו-Claude for Enterprise משתמשים בשכבת ההגדרות המנוהלות, שנמצאת בראש היררכיית ה-Precedence: אף שכבה אחרת, כולל דגלים בשורת הפקודה, לא יכולה לדרוס אותה (למעט חריגים בודדים המתועדים בעמוד ה-Settings).

Server-Managed Settings: ניהול מהענן

Server-managed settings מוגדרים בקונסולת הניהול של claude.ai תחת Admin Settings > Claude Code > Managed settings, ורק בעלי תפקיד Owner או Primary Owner יכולים לצפות בהם ולערוך אותם. לקוחות ה-Claude Code של המשתמשים מושכים את ההגדרות אוטומטית בעת התחברות עם חשבון הארגון, ומתעדכנים בפולינג שעתי במהלך Sessions פעילים. זה פתרון שנועד בדיוק לארגונים בלי תשתית ניהול תחנות (MDM): אין שום דבר להתקין על המחשבים.

ההגדרות נכתבות כ-JSON באותו פורמט של settings.json. דוגמה מהתיעוד הרשמי, שאוכפת רשימת חסימות ומונעת עקיפת הרשאות:

Admin Settings > Claude Code > Managed settings
{
  "permissions": {
    "deny": [
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true
}

managed-settings.json: הווריאנט המקומי

ארגונים עם MDM או ניהול תחנות יכולים לפרוס את אותה מדיניות ישירות למכשירים (Endpoint-managed). המיקומים המתועדים של קובץ managed-settings.json:

מערכת הפעלהנתיב
macOS/Library/Application Support/ClaudeCode/managed-settings.json
Linux / WSL/etc/claude-code/managed-settings.json
WindowsC:\Program Files\ClaudeCode\managed-settings.json

בנוסף קיימים ערוצי מדיניות ברמת מערכת ההפעלה: Plist בשם com.anthropic.claudecode ב-macOS ורישום HKLM\SOFTWARE\Policies\ClaudeCode ב-Windows. סדר העדיפויות בתוך השכבה המנוהלת: Server-managed נבדק ראשון, ואם הוא מספק תצורה כלשהי, מקורות ה-Endpoint מתעלמים (המקורות לא מתמזגים, למעט חריגים מתועדים כמו מיזוג פר-משתנה של בלוק env). לפי התיעוד, ל-MDM יש יתרון אבטחתי במכשירים מנוהלים, כי אפשר להגן על הקובץ ברמת מערכת ההפעלה; מנגד, הגדרות Endpoint לא מגיעות ל-Sessions בענן, ולכן ארגונים שמשתמשים ב-Claude Code on the web צריכים להגדיר גם Server-managed.

הגדרות שמריצות קוד אצל המשתמש (Hooks, משתני סביבה רגישים, תוכן claudeMd) מציגות למשתמש דיאלוג אישור אבטחה לפני החלה; דחייה סוגרת את Claude Code. חשוב לזכור את ההסתייגות מהתיעוד: הגדרות מנוהלות הן בקרת Client, לא גבול אבטחה. במכשיר לא מנוהל, משתמש נחוש יכול לעקוף אותן; אכיפה חזקה יותר דורשת MDM או בקרות רשת.

Allowlists מנוהלים ל-MCP

שרתי MCP הם תעלת הנתונים החוצה, ולכן יש להם בקרות ייעודיות. שני דפוסים מתועדים:

  • שליטה מלאה: פריסת קובץ managed-mcp.json עם סט קבוע של שרתים (דרך ערוצי Endpoint בלבד; אי אפשר להפיץ אותו דרך Server-managed settings).
  • סינון במדיניות: allowedMcpServers ו-deniedMcpServers מסננים מה שמשתמשים מגדירים בעצמם, לפי URL, פקודה או שם. הוספת allowManagedMcpServersOnly: true הופכת את ה-Allowlist לסמכותי: מה שלא ברשימה חסום.

אימות

כך מוודאים שהמדיניות באמת הגיעה לתחנה: מריצים /status בתוך Claude Code ובודקים שבשורת Setting sources מופיע Enterprise managed settings עם המקור בסוגריים: (remote), (plist), (HKLM), (HKCU) או (file). את חוקי ההרשאות בפועל בודקים עם /permissions. לאיתור תקלות מריצים claude --debug-file <path> ומחפשים Remote settings ביומן.

סטנדרטים, Review ואסטרטגיית Branches

תצורה משותפת קובעת מה Claude רשאי לעשות; מדיניות עבודה קובעת איך הצוות משתמש בו. שלושה עקרונות מחזיקים את רוב המשקל:

הפרדת Writer ו-Reviewer

אל תתנו לאותו הקשר גם לכתוב וגם לבקר. Session שכתב קוד "מאוהב" בפתרון שלו, בדיוק כמו מפתח. הדפוסים המומלצים:

  • הכותב עובד ב-Session רגיל; ה-Review נעשה ב-Session נקי אחר (או Subagent ייעודי של Review, ראו פרק 25) שמקבל רק את ה-Diff ואת הדרישות.
  • ברמת הצוות, ה-Review האוטומטי ב-Pull Requests רץ דרך Code Review ו-GitHub Actions שהגדרנו בפרק 28, עם אדם שמאשר בסוף.
  • כלל אצבע צוותי: Claude מציע, אדם ממזג. אישור Merge של קוד שנכתב עם Claude נשאר באחריות מפתח בשם, לא באחריות "הכלי".

משמעת Pull Requests

  • PR קטן וממוקד לכל משימה. משימות ענק מפורקות מראש (ב-Plan Mode, פרק 7) לסדרת PRs.
  • כל PR כולל: מה התבקש, מה Claude עשה, אילו בדיקות רצו, ומה נבדק ידנית. תבנית PR ב-Repository עוזרת לאכוף את זה.
  • בדיקות הן חלק מההגדרה של "מוכן": PR בלי בדיקות שרצות הוא טיוטה.

אסטרטגיית Branches: ענף אחד, בעלים אחד

הכלל הצוותי החשוב ביותר לעבודה עם Agents: על כל Branch עובד בכל רגע נתון גורם אחד בלבד, אדם או Agent. שני Agents (או Agent ומפתח) שכותבים לאותו Branch דורסים זה את זה ויוצרים קונפליקטים שקשה לשחזר. עבודה מקבילית נעשית ב-Branches נפרדים, ועדיף ב-Worktrees נפרדים, כפי שנראה מיד.

בעלות ו-Auditability: לדעת מי עשה מה

Attribution בהגדרות

כברירת מחדל Claude Code מוסיף ל-Commits שהוא יוצר Trailer בסגנון Co-Authored-By: Claude ... <noreply@anthropic.com> (עם שם המודל הפעיל), ולתיאורי Pull Requests שורת "Generated with Claude Code". ההתנהגות נשלטת בהגדרת attribution עם המפתחות commit, pr ו-sessionUrl; מחרוזת ריקה מסתירה. ההגדרה הזאת גוברת על ההגדרה הישנה includeCoAuthoredBy Deprecated. המלצתנו לצוותים: השאירו את ה-Attribution דולק וקבעו אותו ב-.claude/settings.json המשותף. שקיפות על מקור הקוד עוזרת ב-Debugging, ב-Review ובמדידה, ואין סיבה טובה להסתיר אותה.

.claude/settings.json
{
  "attribution": {
    "commit": "Co-Authored-By: Claude <noreply@anthropic.com>",
    "pr": "Generated with Claude Code"
  }
}

צורכי Audit

  • שינויי מדיניות: אירועי Audit Log על שינויים ב-Managed Settings זמינים ללקוחות Enterprise דרך Compliance API או ייצוא, בתיאום עם צוות החשבונות של Anthropic. האירועים כוללים את סוג הפעולה, החשבון והמכשיר, והפניות לערך הקודם והחדש.
  • שינויי תצורה בזמן ריצה: Hook מסוג ConfigChange (פרק 22) יכול לרשום או לחסום שינויים לא מורשים לפני שהם נכנסים לתוקף.
  • טלמטריה מפורטת: ייצוא OpenTelemetry שולח לתשתית הניטור שלכם מדדים ואירועים פר משתמש: claude_code.token.usage, claude_code.cost.usage, claude_code.lines_of_code.count, אירועי הרצת כלים ועוד. זו האפשרות היחידה שעובדת בזמן אמת על כל ספקי ה-API.

Cost Governance לצוותים

את הצד הכמותי המלא של עלויות נלמד בפרק 30; כאן עקרונות הממשל ברמת צוות:

  • Seats מול API: בתוכניות Team ו-Enterprise כל חבר צוות צורך מהקצאת ה-Seat שלו (חלון מתגלגל של חמש שעות וחלון שבועי, בגודל שתלוי בסוג ה-Seat: Standard או Premium). בגישת Console (API) החיוב הוא פר Token לארגון. אם הארגון מערבב שיטות התחברות, כל מפתח נמדד לפי השיטה שבה התחבר בפועל.
  • תקרות: ב-Team/Enterprise ההקצאה של ה-Seat היא התקרה כברירת מחדל; מעבר לה מפעילים Usage Credits וקובעים Spend Limits ברמת הארגון, הקבוצה או המשתמש הבודד. ב-Console קובעים Workspace Spend Limits על ה-Workspace הייעודי "Claude Code" שנוצר אוטומטית.
  • ניטור פר משתמש: דוח Spend עם ייצוא CSV (Team/Enterprise), טבלת Team Insights בלוח ה-Console, או OTEL. לפי התיעוד הרשמי (נכון ל-29.07.2026), העלות הממוצעת בפריסות Enterprise בגישת API היא בסביבות 13 דולר למפתח ליום פעיל ו-150 עד 250 דולר למפתח לחודש; המספרים משתנים מאוד לפי מודל, גודל Codebase ודפוסי עבודה, וכפופים לשינוי.

הימנעות מ-Agents מתנגשים

ככל שהצוות מאמץ Subagents, Sessions מקביליים ואוטומציה, גדל הסיכון ששני תהליכים יגעו באותם קבצים. שלושה מנגנונים פותרים את זה:

Worktrees לעבודה מקבילית

Git Worktree הוא תיקיית עבודה נפרדת עם Branch משלה שחולקת את היסטוריית ה-Repository. הפעלת כל Session בעץ עבודה משלו מבטיחה שעריכות ב-Session אחד לעולם לא יגעו בקבצים של אחר:

$ claude --worktree feature-auth # נוצר Worktree תחת ‎.claude/worktrees/feature-auth על Branch בשם worktree-feature-auth

נקודות מתועדות שחשוב להכיר ברמת צוות:

  • Claude Code אוכף את הבידוד: עריכות ופקודות שמנסות להגיע ל-Checkout הראשי נחסמות.
  • Worktree הוא Checkout טרי: קבצים שמוחרגים מ-Git (כמו .env) לא נמצאים בו. קובץ .worktreeinclude בשורש הפרויקט (בתחביר .gitignore) מגדיר אילו קבצים כאלה יועתקו אוטומטית לכל Worktree חדש; שווה לקבוע אותו פעם אחת לכל הצוות ולבצע לו Commit.
  • אפשר לקבוע ל-Subagent קבוע בידוד תמידי עם isolation: worktree ב-Frontmatter שלו.
  • ביציאה מ-Session אינטראקטיבי Claude מציע לנקות; הוסיפו .claude/worktrees/ ל-.gitignore המשותף.

/batch לשינויים רחבים

לשינוי גדול שחוצה את ה-Codebase, הפקודה /batch מפרקת את העבודה ליחידות בלתי תלויות ומריצה כל אחת ב-Worktree משלה. זה הכלי הנכון כשמשימה אחת גדולה הייתה הופכת אחרת לסדרת קונפליקטים.

והכלל הארגוני

הטכנולוגיה עוזרת, אבל הכלל "Branch אחד, בעלים אחד" הוא קונבנציה אנושית: קבעו בצוות שכל Agent ארוך טווח (למשל Session רץ ברקע או Automation ב-CI) עובד רק על Branch שנוצר עבורו, ושאיש לא דוחף ל-Branch של מישהו אחר בלי תיאום.

Data Governance: מדיניות נתונים, Retention ו-ZDR

שאלת "מה קורה לקוד שלנו" היא בדרך כלל הראשונה שארגון שואל. התמונה המתועדת, נכון ל-29.07.2026:

  • אימון מודלים: בתנאים המסחריים (Team, Enterprise, API וספקי צד שלישי) Anthropic לא מאמנת מודלים גנרטיביים על קוד או Prompts שנשלחים ל-Claude Code, אלא אם הארגון הצטרף מפורשות לתוכנית כמו Development Partner Program. בחשבונות צרכניים (Free/Pro/Max) קיימת בחירת משתמש שמשפיעה על אימון ועל Retention.
  • Retention: ללקוחות מסחריים ברירת המחדל היא 30 יום. משוב שנשלח ב-/feedback (וגם /bug ו-/share) נשמר 5 שנים. בנוסף, תמלילי Sessions נשמרים מקומית על מחשב המפתח ב-~/.claude/projects/ כטקסט רגיל למשך 30 יום כברירת מחדל (נשלט בהגדרה cleanupPeriodDays): נקודה שצריך להביא בחשבון על מחשבים ניידים לא מוצפנים.
  • Zero Data Retention (ZDR): זמין לחשבונות מתאימים ב-Claude for Enterprise בלבד, לא כלול בתוכנית הסטנדרטית, ומופעל פר ארגון על ידי צוות החשבונות של Anthropic. עם ZDR, Prompts ותשובות לא נשמרים אחרי החזרת התשובה (למעט חריגי חוק והפרות מדיניות, שבהן ייתכן Retention של עד שנתיים).
מה כבוי תחת ZDR

תכונות שדורשות שמירת שיחות מנוטרלות בצד השרת: Claude Code on the web, Cloud Sessions מאפליקציית Desktop, Artifacts, שליחת משוב (/feedback, /bug, /share) ו-Remote Control. בנוסף, מדדי התרומה בלוח ה-Analytics לא זמינים (נשארים מדדי שימוש בלבד), והמודל Claude Fable 5 אינו זמין לארגוני ZDR כי הוא דורש Retention. שקללו את זה מול הדרישה הרגולטורית לפני שמבקשים ZDR.

עוד נקודה חשובה: ZDR חל על ההסקה (Inference) של Claude Code בארגון ה-ZDR עצמו. הוא לא מכסה שיחות Chat ב-claude.ai, לא Cowork, ולא נתונים שעוברים בכלים חיצוניים ושרתי MCP של צד שלישי; את אלה בודקים בנפרד. כדי לוודא שכל התעבורה באמת מגיעה לארגון ה-ZDR, אוכפים התחברות עם forceLoginMethod ו-forceLoginOrgUUID.

קליטת מפתח חדש ל-Repository עם Claude

כשהתצורה המשותפת קיימת, קליטה טובה נמשכת פחות משעה. רשימת בדיקה מומלצת (הצעדים הטכניים לקוחים מהתיעוד; הסדר הוא המלצת המדריך):

  • ודאו שהוקצה למפתח Seat עם גישת Claude Code בקונסולת הניהול (אם מופיעה הודעת "You haven't been added to your organization yet", ה-Seat לא כולל גישה).
  • התקנה והתחברות: claude ואז /login עם חשבון הארגון; פתרון תקלות נפוץ: /logout ואז /login, או claude update אם אפשרות ההתחברות הארגונית חסרה.
  • שכפול ה-Repository, הרצת claude משורש הפרויקט ואישור חלון ה-Trust אחרי קריאת חוקי ההרשאות שהוא מציג.
  • אימות מדיניות: /status מציג את מקור ההגדרות המנוהלות; /permissions מציג את החוקים בתוקף.
  • היכרות עם הפרויקט: לבקש מ-Claude סיור ב-Codebase (כמו בפרק 6) ולקרוא את CLAUDE.md המשותף.
  • הרצת ה-Skills הצוותיים המרכזיים פעם אחת בליווי (למשל Skill של הרצת בדיקות), כדי לראות את התהליך התקין.
  • קריאת מדיניות הצוות: כללי PR, "Branch אחד בעלים אחד", ומה מותר להריץ בלי אישור.
  • שיתוף חומרי הלימוד הרשמיים: Quickstart, Common Workflows, וקורסי Anthropic Academy (בשמם הרשמי: Claude 101 ו-Claude Code in Action).

מוסכמות Handoff ו-Definition of Done

בעבודת צוות עם Agents, המסירה (Handoff) בין אדם לאדם, בין אדם ל-Agent ובין Session ל-Session היא נקודת האיבוד הקלאסית של הקשר. הכלים המובנים עוזרים: /rename נותן ל-Session שם שאפשר למצוא, /resume חוזר אליו, ו-/export מוציא תמליל. אבל הקונבנציה חשובה מהכלי. הצעה שעובדת בפועל (זו המלצת מתודולוגיה של המדריך, לא פיצ'ר מתועד):

  • Handoff תמיד דרך ה-Repository, לא דרך זיכרון ה-Session: מצב העבודה נמסר כ-Commit + PR Draft + הערת מצב, כך שכל אדם או Agent יכולים להמשיך מנקודה נקייה. Session של מישהו אחר הוא לא ממשק מסירה: אי אפשר לסמוך על כך שההקשר בו שלם, מעודכן או נקי מכיווני חשיבה שננטשו.
  • הערת מצב קבועה בסוף יום עבודה על Branch פתוח: מה הושלם, מה בעבודה, מה הצעד הבא, אילו החלטות התקבלו ולמה. אפשר לבקש מ-Claude לנסח אותה מתוך ה-Session.
  • Definition of Done צוותי לעבודה עם Claude: הקוד עבר בדיקות שרצו בפועל; עבר Review של Session נקי או Reviewer אנושי; ה-PR מתעד מה נעשה אוטומטית; אין TODO או קוד מת שנשארו מהאיטרציות; ו-CLAUDE.md עודכן אם השתנתה קונבנציה. רק אז מותר Merge.

שיקולי Security

תצורה משותפת היא משטח תקיפה

מי שיכול לשנות את .claude/settings.json, Hook או Plugin ארגוני, יכול להריץ קוד על המחשב של כל מפתח בצוות. לכן: Review חובה לכל שינוי תצורה, CODEOWNERS על נתיבי התצורה, הרשאות Marketplace מוגבלות, וב-Enterprise גם allowManagedHooksOnly ו-strictPluginOnlyCustomization היכן שמתאים. זכרו שוב: Managed Settings הן בקרת Client; את הסודות האמיתיים מגינים ברמת הרשת וה-Secrets Management, לא רק בהגדרות.

תרגיל: תצורת צוות ל-TaskFlow

תרגיל 29.1: תכנון תצורה לצוות של שישה

צוות של שישה עובד על TaskFlow: ארבעה מפתחים, Tech Lead אחד ומהנדס DevOps אחד. הארגון בתוכנית Claude for Teams. תכננו על נייר (או בקבצים אמיתיים בעותק שלכם של examples/taskflow):

  1. אילו קבצים יהיו ב-Repository ומה יהיה בכל אחד: CLAUDE.md, .claude/settings.json, .claude/rules/, .mcp.json, .worktreeinclude.
  2. שלושה חוקי deny ושני חוקי allow שתקבעו לכל הצוות, עם נימוק.
  3. מה תגדירו ב-Server-managed settings (ולא ב-Repository), ולמה דווקא שם.
  4. מדיניות Review לשינויי תצורה ומדיניות Branches לעבודה עם Agents.
  5. איך תעקבו אחרי אימוץ ועלות בחודש הראשון.
פתרון מוסבר

1. קבצים ב-Repository. CLAUDE.md קצר (עד 200 שורות): תיאור הארכיטקטורה (FastAPI + SQLite ב-Backend, React + TypeScript ב-Frontend), פקודות הרצה ובדיקות, ומוסכמות שמות. .claude/rules/api-conventions.md עם paths: backend/app/** לכללי ה-API, ו-.claude/rules/testing.md עם paths: "**/*.test.*" לכללי בדיקות: כך הם נטענים רק כשרלוונטי. .mcp.json עם שרת ה-MCP של מערכת ניהול המשימות של הצוות, בלי סודות. .worktreeinclude עם .env כדי ש-Worktrees יקבלו את קובץ הסביבה. .gitignore מקבל את .claude/worktrees/.

2. חוקי הרשאות ב-.claude/settings.json. deny: קריאת .env ו-.env.* (סודות), Bash(git push --force *) (הגנה על היסטוריה משותפת), וכתיבה לתיקיית ה-Migrations בלי אישור. allow: הרצת חבילת הבדיקות (Bash(pytest *), Bash(npm test *)) ופקודות git diff/git log, כי אלה פעולות קריאה בטוחות שהצוות מריץ עשרות פעמים ביום, ואישור ידני שלהן רק מייצר עייפות אישורים.

3. ב-Server-managed settings (בקונסולת claude.ai, על ידי ה-Owner): חסימות שאסור שאף מפתח יעקוף, כמו Read(./secrets/**), disableBypassPermissionsMode: "disable" ו-forceLoginOrgUUID. ההבדל מהסעיף הקודם: מה שב-Repository הוא מוסכמה שקל לעדכן ב-PR; מה שב-Managed הוא מדיניות שמנצחת כל הגדרה מקומית ואי אפשר לעקוף מה-CLI. שינויים שם דורשים Owner, אז שומרים שם רק את מה שבאמת חייב אכיפה.

4. מדיניות. CODEOWNERS ממפה את .claude/**, CLAUDE.md ו-.mcp.json ל-Tech Lead ול-DevOps; כל שינוי שם דורש אישור שלהם. Branches: כל משימה על Branch משלה, Agents רצים ב-Worktrees (claude --worktree), ואיש לא כותב ל-Branch שאינו שלו. Definition of Done כמו בפרק: בדיקות רצו, Review של Session נקי או אדם, PR מתועד.

5. מעקב. שבוע ראשון: ה-Owner מפעיל את לוח ה-Analytics ב-claude.ai/analytics/claude-code ומתקין את אפליקציית ה-GitHub למדדי תרומה. חודש ראשון: מעקב שבועי אחרי משתמשים פעילים ו-Sessions (איתור מי שנתקע), דוח ה-Spend פר משתמש אם הופעלו Usage Credits, ושיחת צוות אחת על ממצאי /insights אישיים. רק אחרי Baseline של חודש קובעים Spend Limits מספריים.

סיכום

  • מה ששייך לפרויקט נכנס ל-Git: CLAUDE.md, .claude/settings.json, rules/, skills/, agents/, .mcp.json. מה שאישי נשאר ב-settings.local.json וב-~/.claude/. שינויי תצורה עוברים Review כמו קוד.
  • Plugins עם Marketplace פרטי הם מנגנון ההפצה הרב-פרויקטי; Managed Settings (מהענן או מקובץ managed-settings.json) הם שכבת האכיפה של Team/Enterprise, כולל Allowlists ל-MCP, והם תמיד בראש ה-Precedence.
  • סדר צוותי: הפרדת Writer/Reviewer, PRs קטנים ומתועדים, ו"Branch אחד, בעלים אחד" עם Worktrees ו-/batch לעבודה מקבילית.
  • שקיפות: Attribution ב-Commits וב-PRs, לוחות Analytics, Analytics API ו-OTEL למדידה, ו-Audit Logs לשינויי מדיניות.
  • ממשל נתונים: אין אימון על נתונים מסחריים, Retention של 30 יום כברירת מחדל, ו-ZDR ל-Enterprise במחיר של ויתור על תכונות ענן מסוימות.

בפרק הבא נצלול למספרים עצמם: איך נבנית עלות של Session, מה עושה ה-Prompt Caching, ואיך מודדים ומקטינים עלויות בלי לפגוע בתפוקה.
