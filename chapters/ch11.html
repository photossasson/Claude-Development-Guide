Testing

בדיקות הן לא רק ביטוח נגד Bugs: בעבודה עם Claude Code הן מנגנון האימות שסוגר את הלולאה האגנטית. בפרק הזה נמפה את סוגי הבדיקות ואת דפוסי ה-Prompt לכל אחד, נעבוד עם Fixtures ו-Mocking, נמדוד Coverage ונסגור פערים באחריות, נטפל בבדיקות Flaky, נלמד את המשמעת של בדיקה נכשלת לפני תיקון, ונתרגל דוגמה מלאה: יצירת חבילת בדיקות ל-Endpoint אמיתי של TaskFlow, כולל סינון הבדיקות שנוצרו.

בדיקות כמנגנון האימות של Claude

התיעוד הרשמי של Claude Code מנסח עיקרון מרכזי: תנו ל-Claude דרך לאמת את העבודה של עצמו. בלי בדיקה שהכלי יכול להריץ, הסימן היחיד לסיום משימה הוא "זה נראה גמור", ואתם הופכים למנגנון הבקרה היחיד: כל טעות מחכה שתשימו לב אליה. כשיש חבילת בדיקות, הלולאה נסגרת מעצמה: Claude כותב קוד, מריץ את הבדיקות, קורא את התוצאה, ומתקן עד שהכול ירוק. זה ההבדל בין Session שאתם צריכים לפקח עליו לבין Session שאפשר לתת לו לרוץ.

מכאן נובעות שתי מסקנות מעשיות לכל הפרק:

  • הבדיקות הן חלק מה-Prompt. משימה שמנוסחת עם קריטריון בדיק ("כתוב את הפונקציה, הרץ את הבדיקות ותקן כשלים") מסתיימת טוב יותר ממשימה בלי קריטריון. את התבנית המלאה למשימת בדיקות ראינו בספריית ה-Prompts של פרק 5.
  • איכות הבדיקות קובעת את איכות האוטונומיה. חבילת בדיקות חלשה נותנת ל-Claude אישור כוזב. לכן חצי מהפרק עוסק לא בכתיבת בדיקות אלא בביקורת עליהן.

מתי להשתמש בעזרת Claude לבדיקות: הרחבת כיסוי לקוד קיים, שחזור Bug כבדיקה, כתיבת מקרי קצה שקל לפספס, ותחזוקת חבילה קיימת. מתי להיזהר: כש-Claude כותב גם את הקוד וגם את הבדיקות באותו Session, בלי ביקורת שלכם, הבדיקות נוטות לשקף את המימוש במקום את הכוונה. נטפל בזה בהמשך הפרק.

דרישות מוקדמות

נדרש פרויקט ה-TaskFlow מפרק 3, עם Python 3.10+ וסביבה שבה pytest מותקן (pip install -r backend/requirements.txt). מומלץ לרענן את פרק 10 (Debugging): שני הפרקים חולקים את אותה לולאת שחזור ואימות.

Unit Tests

בדיקת יחידה בודדת, בלי רשת ובלי Database. ב-TaskFlow המועמדים הטבעיים הם מודלי ה-Pydantic ב-models.py: הם מרכזים את חוקי הולידציה (אורך כותרת 1 עד 200 תווים, סטטוס מתוך שלושה ערכים). דפוס ה-Prompt: ציינו קובץ, התנהגות, והעדפות. התיעוד הרשמי מדגים בדיוק את ההבדל: לא add tests for foo.py אלא ניסוח ממוקד:

Prompt
write unit tests for backend/app/models.py: TaskCreate and TaskUpdate
validation rules only. cover boundary lengths (0, 1, 200, 201 chars)
and every allowed status value. no mocks, no database.

Integration Tests

בדיקת כמה רכיבים יחד. חבילת הבדיקות הקיימת של TaskFlow (backend/tests/test_tasks.py) היא בעצם כזאת: היא מפעילה את ה-API דרך TestClient של FastAPI מול SQLite אמיתי בקובץ זמני. זו נקודה חשובה כשאתם מבקשים בדיקות: Claude בוחן את קובצי הבדיקה הקיימים ומחקה את הסגנון, ה-Frameworks ודפוסי ה-Assertions שכבר בשימוש. אם החבילה הקיימת טובה, הבדיקות החדשות יתחילו טובות.

Prompt
add integration tests for DELETE /tasks/{id} in the style of
backend/tests/test_tasks.py: deleting twice, deleting a task that
appears in the list, and the list state after deletion.

End-to-End Tests

בדיקה שמדמה משתמש אמיתי: ה-Frontend של React מדבר עם ה-Backend, וכלי כמו Playwright מקליק בדפדפן. אלה הבדיקות היקרות והאיטיות ביותר, ולכן שומרים אותן לזרימות קריטיות בלבד: יצירת משימה מהמסך ועד ה-Database, סימון כ-done. כשמבקשים מ-Claude חבילת E2E, הגדירו מראש כמה תרחישים מותר לו לכתוב, אחרת תקבלו עשרות בדיקות איטיות שמכפילות את מה שבדיקות ה-Integration כבר מכסות.

Regression Tests

בדיקה שמנציחה תיקון: היא משחזרת את ה-Bug ונכשלת אם הוא חוזר. זה למעשה התוצר הקבוע של כל תיקון לפי המשמעת שנראה בסעיף הבא: הבדיקה שכתבתם כדי להוכיח את ה-Bug נשארת בחבילה לתמיד. דפוס מומלץ: לתת לבדיקה שם שמצביע על התקלה, למשל test_patch_with_only_null_fields_returns_400, כדי שכישלון עתידי יסביר את עצמו.

Property-based Tests

במקום לבחור דוגמאות ידנית, מגדירים תכונה שחייבת להתקיים לכל קלט, וכלי כמו Hypothesis (ב-Python) מייצר מאות קלטים וגם מכווץ כל כישלון לדוגמה מינימלית. ב-TaskFlow: "כל כותרת מעל 200 תווים נדחית, תמיד":

backend/tests/test_models_properties.py
import pytest
from hypothesis import given, strategies as st
from pydantic import ValidationError

from app.models import TaskCreate


@given(st.text(min_size=201))
def test_long_titles_always_rejected(title):
    with pytest.raises(ValidationError):
        TaskCreate(title=title)

Claude טוב במיוחד בניסוח תכונות: בקשו suggest 3 properties of TaskUpdate that should hold for any input, then implement them with Hypothesis, ובדקו שהתכונות באמת נובעות מהחוזה ולא מהמימוש.

Security Tests

בדיקות שמתעדות שהמערכת עומדת בקלט עוין. ה-Endpoint של עדכון משימה ב-TaskFlow בונה משפט SQL דינמי, ולכן ראוי לבדיקה שמוכיחה שהערכים עוברים כפרמטרים ולא משורשרים:

backend/tests/test_security.py
def test_sql_injection_in_title_is_stored_literally(client):
    payload = {"title": "x'); DROP TABLE tasks; --"}
    res = client.post("/tasks", json=payload)
    assert res.status_code == 201
    assert res.json()["title"] == payload["title"]
    # הטבלה עדיין קיימת: הרשימה נענית ומכילה את המשימה
    assert client.get("/tasks").status_code == 200

שימו לב לבדיקת יושרה נוספת שכדאי לבקש: בדיקה שמתעדת ש-/tasks פתוח ללא אימות. היא לא "מאשרת" את המצב, היא הופכת אותו לגלוי: ביום שיתווסף אימות, הבדיקה תיכשל ותזכיר לעדכן את החוזה.

Performance Tests

מדידת זמנים לפני מסקנות. ברמה הפשוטה: בדיקה שיוצרת אלף משימות ומוודאת ש-GET /tasks חוזר בזמן סביר; ברמה המקצועית: כלים ייעודיים כמו pytest-benchmark או Locust. שני כללים כשעובדים עם Claude: ראשית, בקשו מדידה לפני ואחרי כל שינוי ביצועים, לא הערכה. שנית, אל תכניסו בדיקות זמן רגישות לחבילה הרגילה: הן המקור הקלאסי לבדיקות Flaky, כפי שנראה בהמשך.

נתוני בדיקה, Fixtures ו-Mocking

ה-Fixture האמיתי של TaskFlow

Fixture הוא מנגנון של pytest להכנת סביבה לבדיקה: פונקציה שמכינה משאב, מוסרת אותו לבדיקה, ומנקה אחריה. כך זה נראה היום ב-backend/tests/test_tasks.py, קוד אמיתי מהפרויקט:

backend/tests/test_tasks.py (המצב הקיים)
import os
import tempfile

import pytest
from fastapi.testclient import TestClient

# Point the app at a temporary database BEFORE importing it.
_tmp = tempfile.NamedTemporaryFile(suffix=".db", delete=False)
os.environ["TASKFLOW_DB"] = _tmp.name

from app.database import init_db  # noqa: E402
from app.main import app  # noqa: E402


@pytest.fixture()
def client():
    init_db()
    with TestClient(app) as c:
        yield c

שלוש נקודות ללמידה מהקוד הזה: ראשית, משתנה הסביבה TASKFLOW_DB נקבע לפני ה-import של האפליקציה, כי נתיב ה-Database נקרא בזמן הטעינה. שנית, הבדיקות רצות מול SQLite אמיתי בקובץ זמני, לא מול Mock: זה נותן ודאות גבוהה בעלות אפסית. שלישית, יש כאן חולשה מכוונת שנחשוף בתרגיל: ה-Fixture לא מנקה את הטבלה בין בדיקות.

כשחבילת הבדיקות גדלה לכמה קבצים, הקוד המשותף הזה עובר לקובץ conftest.py: קובץ מיוחד ש-pytest טוען אוטומטית, וכל ה-Fixtures שבו זמינים לכל הבדיקות בתיקייה. בקשו את המעבר מ-Claude יחד עם שדרוג קטן: Fixture נוסף שמספק משימה קיימת:

backend/tests/conftest.py (אחרי ההעברה)
@pytest.fixture()
def client():
    init_db()
    with get_conn() as conn:
        conn.execute("DELETE FROM tasks")   # בידוד בין בדיקות
    with TestClient(app) as c:
        yield c


@pytest.fixture()
def task(client):
    """A task that already exists in the database."""
    return client.post("/tasks", json={"title": "Fixture task"}).json()

נתוני בדיקה

שלושה כללים לנתונים: קטנים ככל האפשר (רק השדות שהבדיקה צריכה), מפורשים (הערך הנבדק מופיע בבדיקה עצמה, לא קבור בקובץ עזר), ומזויפים בבירור (שמות כמו Fixture task, לעולם לא נתונים אמיתיים של משתמשים). כשצריך עשרות רשומות, בקשו מ-Claude פונקציית Factory קטנה במקום קובצי JSON ענקיים: make_task(title="X", status="done") עם ברירות מחדל.

Mocking: מתי כן ומתי לא

Mock הוא תחליף מזויף לרכיב אמיתי: אובייקט שמעמיד פני שירות חיצוני ומתעד איך קראו לו. הכלל: מזייפים את מה שלא בבעלותכם או שאי אפשר להריץ בבדיקה (שירות תשלומים, שליחת מייל, שעון), ולא מזייפים את מה שזול להריץ באמת. TaskFlow הוא דוגמה טובה לצד השני: אין סיבה לזייף את SQLite כשקובץ זמני עושה את העבודה. חשוב לדעת ש-Claude נוטה להציע Mocks בנדיבות; התיעוד הרשמי עצמו מדגים הנחיה שמוסיפה במפורש avoid mocks. אמצו את ההרגל: כתבו בהנחיה מה מותר לזייף, ואם קיבלתם בדיקה שכולה Mocks של קוד פנימי, זה סימן אזהרה שנרחיב עליו בסעיף על בדיקות מראה.

Coverage: מדידה וסגירת פערים באחריות

Coverage מודד אילו שורות והסתעפויות בקוד הורצו במהלך הבדיקות. ב-Python משתמשים ב-pytest-cov (pip install pytest-cov). מריצים מתיקיית backend:

$ pytest --cov=app --cov-report=term-missing -q ........ [100%] Name Stmts Miss Cover Missing ----------------------------------------------------- app/routers/tasks.py 40 3 92% 55-56, 63

פירוש הדגלים: --cov=app מודד את החבילה app; --cov-report=term-missing מוסיף את מספרי השורות שלא כוסו; -q מקצר את הפלט (חשוב גם לחיסכון ב-Context). הפלט אצלכם יהיה שונה במספרים; מה שחשוב הוא העמודה Missing: היא הופכת את השאלה "מה לא בדוק?" לרשימת שורות קונקרטית שאפשר למסור ל-Claude:

Prompt
coverage says lines 55-56 and 63 of app/routers/tasks.py are untested.
read the code, explain what user-visible behavior each gap represents,
and add a test only where the behavior matters. if a line is not worth
testing, say so and explain why.

זו סגירת פערים אחראית: ההנחיה מבקשת התנהגות, לא אחוזים. הצבת יעד כמו "הגע ל-100%" מייצרת את הרע משני העולמות: בדיקות ריקות שקוראות לקוד בלי Assertions משמעותיים, שמעלות את המספר ומורידות את הערך. Coverage גבוה הוא תוצר לוואי של חבילה טובה, לא מטרה. זכרו גם את הגבול המובנה של המדד: הוא מוכיח שהקוד רץ, לא שהוא נבדק. שורה יכולה להיות מכוסה במלואה בלי שאף Assertion בודק את התוצאה שלה.

בדיקות Flaky: איתור, בידוד, תיקון

בדיקה Flaky עוברת לפעמים ונכשלת לפעמים, בלי שהקוד השתנה. היא מסוכנת פעמיים: היא שוחקת את האמון בחבילה ("זה סתם ה-Flaky, תריץ שוב"), והיא מטעה את Claude, שלולאת העבודה שלו מניחה שכישלון פירושו קוד שבור.

איתור: החשוד המיידי הוא כישלון שנעלם בהרצה חוזרת. אפשר לאתר שיטתית בהרצה חוזרת של החבילה כמה פעמים ברצף, ובהרצת בדיקה בודדת מול הרצת הקובץ המלא (כישלון רק באחד מהמצבים מסגיר תלות בסדר). זו משימת האבחון שנוח למסור ל-Claude, כי היא לולאת הרצה-והשוואה:

Prompt
test_list_tasks fails when the whole suite runs but passes alone.
run it both ways to confirm, then find the shared state that causes
the difference. do not change the assertion, fix the isolation.

הגורמים הנפוצים: מצב משותף בין בדיקות (ה-Database הזמני של TaskFlow נשמר בין בדיקות באותה הרצה: דוגמה חיה בתרגיל בסוף הפרק), תלות בזמן ובשעון, תלות ברשת, מקביליות, וסדר איטרציה לא מובטח. בידוד (Quarantine): כשאין זמן לתקן מיד, מסמנים את הבדיקה במפורש, למשל עם @pytest.mark.skip(reason="flaky: TASK-123"), עם הפניה למשימת תיקון. בדיקה מבודדת בלי כרטיס מעקב היא בדיקה שנמחקה בשקט. תיקון: תמיד בשורש: בידוד נתונים, הזרקת שעון, Retry מבוקר סביב תלות חיצונית. הרצה חוזרת אוטומטית של כל החבילה כפתרון קבע רק מסתירה את הבעיה.

המשמעת: בדיקה נכשלת לפני התיקון

זה ההרגל החשוב ביותר בפרק, והוא מופיע כלשונו בתיעוד הרשמי כניסוח מומלץ: write a failing test that reproduces the issue, then fix it. הסדר מחייב:

  1. שחזור: כתבו (או בקשו מ-Claude לכתוב) בדיקה שמבטאת את ההתנהגות הנכונה, זו שה-Bug מפר.
  2. אדום: הריצו וודאו שהיא נכשלת, ומהסיבה הנכונה. בדיקה שנכשלת בגלל ImportError לא הוכיחה כלום.
  3. תיקון: רק עכשיו מתקנים את הקוד.
  4. ירוק: הבדיקה עוברת, וכל שאר החבילה נשארת ירוקה.

למה השלב האדום קריטי דווקא עם Claude? כי בלעדיו אין לכם הוכחה שהבדיקה מסוגלת להיכשל. תרחיש נפוץ: Claude מתקן קוד וכותב בדיקה באותו מהלך, הבדיקה עוברת, וכולם מרוצים. אבל אם הבדיקה הייתה עוברת גם על הקוד השבור, היא לא בדקה את התיקון. לכן כשאתם מוסרים Bug, נסחו את הסדר במפורש:

Prompt
PATCH /tasks/{id} with {"title": null} returns 400, but the frontend
expects null fields to be simply ignored when other fields are present.
first write a failing test that reproduces this with
{"title": null, "status": "done"}. run it, show me the failure output,
and stop. do not fix anything yet.

ה-stop בסוף מכוון: אתם רואים את הכישלון במו עיניכם, מוודאים שהוא מבטא את ה-Bug, ורק אז נותנים אישור להמשיך לתיקון. הבדיקה הזו נשארת בחבילה כבדיקת Regression לתמיד.

הסכנה: בדיקות שמשקפות את המימוש

הכשל העמוק ביותר בבדיקות שנוצרות אוטומטית: בדיקה שנגזרת מהקוד במקום מהכוונה. אם הקוד מכיל באג לוגי, בדיקה שמשקפת את הקוד תקבע את הבאג כ"התנהגות נכונה". ולבדיקה כזאת יש גם עלות תחזוקה: היא נכשלת בכל Refactoring למרות שההתנהגות לא השתנתה. שלוש הגנות:

1. לבקש בדיקות מהחוזה, לא מהקוד

נסחו את ההנחיה סביב ההתנהגות הגלויה למשתמש: קלט, פלט, קודי סטטוס. השוו:

חלש (מראה של המימוש)חזק (חוזה)
write tests for the update_task functionwrite tests for the PATCH /tasks/{id} contract: partial update, unknown id, invalid status, empty payload. test only through the HTTP API

הדרישה "רק דרך ה-API" חוסמת בדיקות שמציצות לתוך המימוש (קריאה ישירה ל-Database, Mock על פונקציה פנימית) וכך שורדות Refactoring. חיזוק נוסף שהתיעוד מציע: הפרדת כותב ומבקר. בקשו מ-Subagent, או מ-Session נפרד עם Context נקי, לבקר את הבדיקות: מבקר שלא ראה את הקוד שופט את הבדיקות לגופן. באותה רוח אפשר גם להפוך את הסדר: Claude אחד כותב בדיקות מהמפרט, ואחר כותב קוד שיעבור אותן.

2. לבקר כל Assertion

עברו על כל בדיקה שנוצרה ושאלו שתי שאלות: "אם הקוד היה שבור, הבדיקה הזאת הייתה נכשלת?" ו"אם המימוש ישתנה בלי שינוי התנהגות, הבדיקה תשרוד?". Assertion שנכשל בשתי השאלות (למשל: בדיקה שמוודאת שמשפט ה-SQL המדויק הורץ) מוחקים או מחליפים.

3. Mutation Testing: לבדוק את הבדיקות

הרעיון: מכניסים בכוונה שינוי קטן ושובר לקוד (Mutation), ומריצים את החבילה. אם שום בדיקה לא נכשלה, ה-Mutation "שרד" והחבילה עיוורת לאזור הזה. יש כלים אוטומטיים לכך (בעולם ה-Python מוכר mutmut), אבל אפשר לקבל את רוב הערך בגרסה ידנית מהירה עם Claude:

Prompt
introduce one deliberate bug into app/routers/tasks.py (for example,
invert the rowcount check in update_task). run the suite. report which
tests failed. then revert the change and confirm the suite is green.
repeat for two more mutations of your choice.

Mutation ששרד הוא מתנה: הוא מצביע בדיוק על הבדיקה שחסרה. שימו לב שהתרגיל דורש הרשאות הרצה ועריכה, והחזרת הקוד לקדמותו בסופו; ודאו שהוא רץ על עותק נקי ב-Git כדי שאפשר יהיה לאמת שהכול חזר למקומו (git diff ריק בסוף).

לתת ל-Claude להריץ בדיקות, או רק לכתוב?

הרצת בדיקות היא פקודת Bash, ולכן במצב ברירת המחדל כל הרצה מבקשת אישור. יש שלוש רמות עבודה:

הרמה האמצעית היא נקודת האיזון לרוב הפרויקטים: הרצת בדיקות היא פעולה בטוחה יחסית (היא לא נוגעת ב-Production), והיא בדיוק מה שמאפשר ל-Claude לסגור את הלולאה לבד. מוסיפים כלל דרך הפקודה /permissions או ישירות בקובץ ההגדרות של הפרויקט:

דוגמה מלאה: חבילת בדיקות ל-PATCH /tasks/{id}

נעבור את התהליך המלא על ה-Endpoint העשיר ביותר של TaskFlow: עדכון חלקי של משימה. הוא מכיל ולידציה, בניית SQL דינמית, טיפול ב-404 וטיפול בגוף ריק: כר מושלם למקרי קצה.

שלב 1: הנחיה ממוקדת חוזה

Prompt
create backend/tests/test_update_task.py covering the PATCH /tasks/{id}
contract. requirements:
- test only through the HTTP API, in the style of test_tasks.py
- cover: partial update preserving other fields, boundary title lengths
  (200 ok, 201 rejected, empty rejected), invalid status, unknown id,
  empty payload, payload with only null fields, unknown extra fields,
  created_at unchanged after update
- one behavior per test, descriptive names, no mocks
run the file and make sure every test passes. do not modify app code.

שימו לב לסוגר: do not modify app code. במשימת כתיבת בדיקות לקוד קיים, כישלון בדיקה צריך לחזור אליכם כשאלה ("זה Bug או התנהגות מכוונת?"), לא להפוך לתיקון שקט של האפליקציה.

שלב 2: התוצר (אחרי הרצה ירוקה)

backend/tests/test_update_task.py
"""Contract tests for PATCH /tasks/{task_id}."""


def test_partial_update_preserves_other_fields(client, task):
    res = client.patch(f"/tasks/{task['id']}", json={"title": "New title"})
    assert res.status_code == 200
    body = res.json()
    assert body["title"] == "New title"
    assert body["description"] == task["description"]
    assert body["status"] == task["status"]


def test_title_boundaries(client, task):
    url = f"/tasks/{task['id']}"
    assert client.patch(url, json={"title": "x" * 200}).status_code == 200
    assert client.patch(url, json={"title": "x" * 201}).status_code == 422
    assert client.patch(url, json={"title": ""}).status_code == 422


def test_invalid_status_rejected(client, task):
    res = client.patch(f"/tasks/{task['id']}", json={"status": "archived"})
    assert res.status_code == 422


def test_unknown_id_returns_404(client):
    assert client.patch("/tasks/999999", json={"title": "x"}).status_code == 404


def test_empty_payload_returns_400(client, task):
    assert client.patch(f"/tasks/{task['id']}", json={}).status_code == 400


def test_only_null_fields_treated_as_empty(client, task):
    res = client.patch(f"/tasks/{task['id']}", json={"title": None})
    assert res.status_code == 400


def test_unknown_fields_ignored(client, task):
    res = client.patch(
        f"/tasks/{task['id']}", json={"title": "ok", "priority": "high"}
    )
    assert res.status_code == 200
    assert "priority" not in res.json()


def test_created_at_unchanged_by_update(client, task):
    res = client.patch(f"/tasks/{task['id']}", json={"title": "later"})
    assert res.json()["created_at"] == task["created_at"]

הבדיקות משתמשות ב-Fixtures client ו-task מ-conftest.py שבנינו קודם. שימו לב לשתי בדיקות שמתעדות התנהגות לא מובנת מאליה: גוף ריק מחזיר 400 (לא 422), ושדה עם null מפורש נחשב כלא נשלח. אלה בדיוק הבדיקות שהופכות התנהגות שקטה לחוזה גלוי.

  • לרדוף אחוזי Coverage. המדד עולה, הערך יורד. בקשו כיסוי התנהגויות, לא שורות.

  • להתעלם מבדיקה Flaky. היא תלמד אתכם, ואת Claude, להתעלם גם מכישלונות אמיתיים.

אבטחה: סודות ונתונים בבדיקות

  • אסור סודות אמיתיים ב-Fixtures. קובצי בדיקה נכנסים ל-Git ונקראים על ידי Claude כהקשר. השתמשו בערכים מזויפים במובהק בסגנון test-api-key-not-real.
  • אל תעתיקו נתוני Production לבדיקות. גם "רק כמה שורות לדוגמה" הן דליפת מידע אישי. בקשו מ-Claude לייצר נתונים סינתטיים באותו מבנה.
  • חסמו קריאת קובצי סודות עם כלל כמו "deny": ["Read(./.env)"], כך שסוד לא יזלוג לבדיקה שנוצרת (ראו פרק ההרשאות).
  • זכרו שבדיקות הן קוד רץ. בהרשאת Bash(pytest *) גורפת, עריכת קובץ בדיקה שקולה להרצת קוד. בפרויקטים שאינם שלכם, השאירו אישור ידני.
  • בדיקות Security הן תיעוד חי. בדיקה שמתעדת "אין אימות על /tasks" שווה יותר מהערה בקוד: היא תיכשל כשהמצב ישתנה.

עלות ו-Context: חבילות גדולות בלולאה

לולאת "הרץ בדיקות ותקן" היא צרכנית ה-Context הגדולה של הפרק: כל הרצה מזרימה פלט לשיחה, וכל כישלון מוסיף Traceback. בחבילה גדולה זה מצטבר מהר. ההמלצות, כולן בהשראת התיעוד הרשמי:

  • הריצו בדיקות בודדות, לא את כל החבילה. זו המלצה מפורשת לתוך CLAUDE.md: העדיפו pytest tests/test_update_task.py או pytest -k update על פני הרצה מלאה בכל איטרציה. את החבילה המלאה מריצים פעם אחת בסוף.
  • קצרו פלט: -q תמיד; -x (עצירה בכישלון הראשון) בלולאת תיקון; --lf (הרצת הנכשלות בלבד מההרצה הקודמת) בין איטרציות.
  • נקו בין משימות: אחרי Session תיקונים ארוך, /clear לפני משימה חדשה. עשרות Tracebacks ישנים ב-Context מבלבלים יותר משהם עוזרים.
  • העבירו חקירות רועשות ל-Subagent: אבחון Flaky שדורש עשר הרצות יכול לרוץ ב-Context נפרד ולהחזיר רק מסקנה.

Best Practices

  • כל משימת קוד מסתיימת ב"הרץ את הבדיקות ותקן כשלים": סגירת הלולאה כברירת מחדל.
  • Bug מתחיל בבדיקה נכשלת; הבדיקה נשארת כ-Regression לתמיד.
  • בקשו בדיקות מהחוזה ("דרך ה-API בלבד"), וגזמו כל Assertion שלא ישרוד Refactoring.
  • הפקודה הקנונית להרצת בדיקות מתועדת ב-CLAUDE.md, והרשאת Bash(pytest *) חוסכת אישורים.
  • Coverage הוא מצפן לפערים, לא יעד. סוגרים פערים לפי ערך ההתנהגות.
  • מדי פעם, הריצו סבב Mutation ידני: ודאו שהחבילה יודעת להיכשל.

תרגיל 11.1

בעותק ה-TaskFlow שלכם (עם ה-Fixture המקורי, לפני התיקון מהפרק): הוסיפו ל-backend/tests/test_tasks.py את הבדיקה הבאה:

בדיקה חדשה
def test_list_contains_exactly_created_tasks(client):
    a = client.post("/tasks", json={"title": "A"}).json()
    b = client.post("/tasks", json={"title": "B"}).json()

הריצו אותה לבד (pytest -k exactly -q), ואז הריצו את הקובץ המלא (pytest -q). הסבירו את ההבדל בתוצאות, ותקנו את הגורם, לא את הבדיקה. מותר ומומלץ להיעזר ב-Claude, אבל נסחו את ההנחיה כך שהוא יאבחן לפני שהוא מתקן.

פתרון מוסבר

מה קורה: לבד הבדיקה עוברת; בהרצה מלאה היא נכשלת (ברוב סדרי ההרצה). הסיבה: קובץ ה-SQLite הזמני נוצר פעם אחת בטעינת המודול, וה-Fixture client קורא ל-init_db() שמריץ CREATE TABLE IF NOT EXISTS: הוא לא מנקה כלום. כל הבדיקות שרצו קודם השאירו משימות בטבלה, ולכן הרשימה מכילה יותר משתי המשימות שהבדיקה יצרה. זו תלות בסדר: הצורה הנפוצה ביותר של Flakiness בחבילות אמיתיות.

הנחיה לאבחון:

Prompt
test_list_contains_exactly_created_tasks passes alone but fails in the
full run. run both to confirm, diagnose the root cause, and propose a
fix in the fixture, not in the test. wait for my approval before editing.

התיקון: בידוד ב-Fixture: ניקוי הטבלה לפני כל בדיקה (DELETE FROM tasks כמו ב-conftest.py שבנינו בפרק), או קובץ Database זמני נפרד לכל בדיקה. שימו לב מה לא עשינו: לא שינינו את ה-Assertion ל"מכיל את A ו-B" כדי שיעבור. הבדיקה צדקה; הסביבה הייתה שבורה. ואחרי התיקון, הריצו את כל החבילה שוב: תיקוני בידוד יכולים לחשוף בדיקות אחרות שנשענו בשקט על נתונים משותפים.

סיכום

  • בדיקות הן מנגנון האימות שהופך את Claude מעוזר מפוקח לסוכן שסוגר לולאה לבד; איכות הבדיקות קובעת כמה אוטונומיה מותר לתת.
  • לכל סוג בדיקה יש דפוס Prompt: ממוקד קובץ והתנהגות ב-Unit, בסגנון החבילה הקיימת ב-Integration, מוגבל תרחישים ב-E2E, תכונות ב-Property-based.
  • Bug מטופל בסדר קבוע: בדיקה נכשלת, צפייה בכישלון, תיקון, ירוק. בלי השלב האדום אין הוכחה.
  • הסכנה המרכזית היא בדיקות מראה: מתגוננים בבקשת חוזה, בביקורת כל Assertion, וב-Mutation Testing.
  • Bash(pytest *) משחרר את הלולאה; CLAUDE.md עם הפקודה הקנונית ובדיקות בודדות במקום חבילה מלאה שומרים על ה-Context.
  • בפרק הבא נשתמש בכל זה כרשת ביטחון למשימה הרגישה ביותר: Refactoring בלי שינוי התנהגות.
