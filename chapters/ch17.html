Settings ו-Configuration

כמעט כל התנהגות של Claude Code ניתנת לכוונון דרך קובצי JSON פשוטים: אילו פקודות מותר להריץ בלי לשאול, אילו קבצים אסור לקרוא לעולם, איזה מודל ורמת Effort יופעלו, אילו Hooks ירוצו ואיך ייראה ה-Status Line. בפרק הזה נבין את היררכיית קובצי ההגדרות ואת סדר העדיפויות המדויק, נסקור את משתני הסביבה החשובים, נצלול לתחביר חוקי ה-Permissions ולהגדרות המודל, ובמרכז הפרק: שני קובצי settings.json שלמים ומוסברים שורה אחר שורה, אחד אישי ואחד צוותי לפרויקט TaskFlow.

מה זה Settings ואיזו בעיה זה פותר

עד עכשיו שלטנו ב-Claude בעיקר דרך שיחה: אישרנו בקשות הרשאה אחת-אחת, החלפנו מודל עם /model, וכתבנו הנחיות ב-CLAUDE.md. זה עובד, אבל לא מדרגי: אתם לא רוצים לאשר את npm run lint בפעם המאה, ולא רוצים שכל מפתח חדש בצוות יגלה לבד שאסור לגעת ב-.env. קובצי ה-Settings הם שכבת התצורה הקבועה: הם נטענים אוטומטית, נאכפים על ידי Claude Code עצמו (בניגוד ל-CLAUDE.md, שהוא הנחיה בלבד, כפי שראינו בפרק 16), וניתנים לשיתוף דרך Git או לפריסה ארגונית כפויה.

מתי להשתמש: לכל כלל שאמור לחול תמיד, בלי תלות בשיחה: הרשאות, מודל ברירת מחדל, משתני סביבה, Hooks. מתי לא: הנחיות התנהגות ותוכן ("כתוב בדיקות בסגנון X") שייכות לשכבות הידע מפרק 16, לא לכאן.

Claude Code קורא הגדרות מכמה מקורות ומכריע ביניהם לפי סדר עדיפויות מתועד, מהגבוה לנמוך:

בנוסף לקובץ, ארגונים יכולים לפרוס מדיניות דרך MDM (רישום מערכת ב-Windows, plist ב-macOS) או דרך Server-Managed Settings: הגדרות שמנהל בתפקיד Owner מגדיר בקונסולת הניהול של claude.ai (Admin Settings > Claude Code), זמין בתוכניות Team ו-Enterprise. ההגדרות נמשכות אוטומטית כשהמשתמש מתחבר עם חשבון הארגון, יושבות באותה מדרגת עדיפות עליונה כמו קובצי Managed Settings, והמקורות לא מתמזגים ביניהם: אם השרת מספק הגדרות כלשהן, קובצי ה-Managed המקומיים מנוטרלים. העמקה בנושא בפרק 29.

איך ערכים מוכרעים בפועל

  • ערכים סקלריים (כמו model או effortLevel): המקור בעדיפות הגבוהה ביותר מנצח ודורס את האחרים.
  • חוקי Permissions מתמזגים מכל הרמות ולא דורסים זה את זה. חוק deny בכל רמה שהיא חוסם, גם אם רמה אחרת מרשה: deny ברמת המשתמש גובר על allow ברמת הפרויקט, ולהפך.
  • Managed תמיד מנצח: אפילו ארגומנט שורת פקודה כמו --allowedTools לא עוקף deny ארגוני.
קובץ נפרד: ~/.claude.json

אל תתבלבלו: הגדרות MCP ברמת המשתמש ומצב פנימי יושבים בקובץ אחר, ~/.claude.json, והגדרות MCP של פרויקט בקובץ .mcp.json. פירוט בפרק 23.

שלוש דרכים לערוך הגדרות

1. ממשק אינטראקטיבי: הפקודה /config (כינוי: /settings) פותחת ממשק הגדרות עם לשוניות: ערכת נושא, מודל, Output Style והעדפות נוספות.

2. עריכה ישירה מהשורה: החל מגרסה 2.1.181 אפשר להעביר ל-/config זוגות key=value בלי לפתוח ממשק, למשל /config theme=dark או /config model=sonnet. הפקודה /config --help מציגה את כל המפתחות הניתנים לקביעה. זה עובד גם במצב לא-אינטראקטיבי (-p).

3. עריכת הקבצים ישירות: פותחים את קובץ ה-JSON בעורך. רוב השינויים נטענים אוטומטית לתוך Session רץ (למשל permissions ו-hooks), אבל model ו-outputStyle דורשים Session חדש או /clear.

לאימות: /status מציג אילו מקורות הגדרות פעילים, ו-/doctor מאתר קובצי הגדרות שלא ניתנים לפענוח וערכים לא תקינים.

משתני סביבה

משתני סביבה שולטים בהתנהגויות שחוצות את גבול קובץ ההגדרות: אימות, רשתות, Timeouts ומתגי תכונות. אפשר לקבוע אותם בשתי דרכים: ייצוא ב-Shell (export VAR=value ב-Bash, $env:VAR = "value" ב-PowerShell), או, נוח יותר, במפתח env בתוך כל קובץ settings.json, ואז הם חלים על כל ה-Sessions ותתי-התהליכים. לפי התיעוד, ערכי env מקובצי הגדרות גוברים על משתני סביבה של ה-Shell, ודגלי CLI ופקודות בתוך ה-Session (כמו /model) גוברים על שניהם.

אזהרה: ANTHROPIC_API_KEY

אם משתנה הסביבה ANTHROPIC_API_KEY מוגדר, הוא נשלח ככותרת X-Api-Key וגובר על חיוב דרך המנוי (Pro/Max/Team). מפתחים רבים גילו חיובי API לא צפויים כי מפתח ישן נשאר מיוצא ב-.zshrc. אם אתם על מנוי, ודאו שהמשתנה לא מוגדר, ולעולם אל תשמרו מפתחות אמיתיים בקובצי הגדרות שנכנסים ל-Git.

הגדרת Permissions: התחביר המלא

מפתח ה-permissions הוא ליבת האבטחה של קובץ ההגדרות. שלושה סוגי חוקים, וסדר הערכה מתועד וקבוע: קודם deny, אחר כך ask, ולבסוף allow. ההתאמה הראשונה בסדר הזה קובעת, וספציפיות לא משנה את הסדר: deny רחב כמו Bash(aws *) חוסם גם קריאה שתואמת allow צר יותר.

  • allow: הכלי רץ בלי בקשת אישור.
  • ask: בקשת אישור בכל שימוש, גם אם חוק allow תואם.
  • deny: חסימה. חוק deny עם שם כלי חשוף (כמו Bash) מסיר את הכלי מה-Context של Claude לגמרי; חוק תחום (כמו Bash(rm *)) משאיר את הכלי וחוסם קריאות תואמות.

תבנית חוק: Tool (כל השימושים בכלי) או Tool(specifier). הצורות החשובות:

תחבירמה הוא תופס
Bash(npm run build)בדיוק הפקודה npm run build
Bash(npm run test *)כל פקודה שמתחילה ב-npm run test; ה-* יכול להופיע בכל מיקום ותופס גם רווחים
Bash(ls *) לעומת Bash(ls*)הרווח לפני ה-* כופה גבול מילה: ls * תופס ls -la אבל לא lsof; בלי רווח, שניהם נתפסים

Edit(/src/**)/ בודד מעגן לשורש מקור ההגדרות (בקובץ פרויקט: שורש הפרויקט); זה לא נתיב מוחלט!

עוד שלוש עובדות מתועדות שחשוב להכיר: (1) חוקי Edit חלים על כל הכלים המובנים שעורכים קבצים, וחוקי Read נאכפים גם על פקודות קבצים מזוהות ב-Bash כמו cat ו-head, אבל לא על סקריפטים שרצים כתת-תהליך ופותחים קבצים בעצמם; לאכיפה ברמת מערכת ההפעלה יש Sandboxing. (2) Claude Code מודע לאופרטורים של ה-Shell: חוק allow חייב להתאים לכל תת-פקודה בנפרד, כך ש-Bash(safe-cmd *) לא מתיר את safe-cmd && other-cmd. (3) קבוצה מובנית של פקודות קריאה בלבד (ls, pwd, grep וכדומה) רצה בלי בקשה בכל מצב, אלא אם הוספתם להן חוק ask או deny.

שני מפתחות נוספים תחת permissions: additionalDirectories (רשימת תיקיות נוספות ש-Claude רשאי לגשת אליהן מעבר לתיקיית העבודה) ו-defaultMode, שקובע את מצב ההרשאות ההתחלתי של ה-Session. הערכים המתועדים של defaultMode: default (בקשת אישור בשימוש ראשון בכל כלי; מוצג בממשק כ-Manual), acceptEdits (אישור אוטומטי לעריכות קבצים), plan (קריאה וחקירה בלבד), auto (אישור אוטומטי עם בדיקות בטיחות ברקע), dontAsk (דחייה אוטומטית של כל מה שלא אושר מראש) ו-bypassPermissions (דילוג על רוב הבקשות; מסוכן). ההגדרה permissions.disableBypassPermissionsMode: "disable" מונעת שימוש במצב העוקף, והיא שימושית במיוחד ב-Managed Settings. פירוט מלא של המצבים והעבודה איתם: פרק 18.

הגדרות מודל

ארבעה מפתחות עיקריים (הרחבה על בחירת מודלים בפרקי העבודה המתקדמים):

  • model: המודל הראשי. מקבל כינוי (sonnet, opus, haiku, fable, best, sonnet[1m], opus[1m], opusplan) או שם מודל מלא כמו claude-sonnet-5 לנעילת גרסה. הכינויים מתעדכנים עם הזמן לגרסה המומלצת. הערך default מנקה את הבחירה וחוזר לברירת המחדל של סוג החשבון. סדר עדיפויות לקביעת מודל: /model בתוך ה-Session, ואז claude --model בהפעלה, ואז משתנה הסביבה ANTHROPIC_MODEL, ולבסוף המפתח model בהגדרות.
  • effortLevel: שמירת רמת ה-Effort בין Sessions. ערכים חוקיים בהגדרות: low, medium, high, xhigh (הרמות max ו-ultracode הן ל-Session בודד ואינן נשמרות כאן). ברירת המחדל היא high ברוב המודלים התומכים.
  • availableModels: רשימת היתר של מודלים שמותר לבחור, מיועד בעיקר ל-Managed Settings ארגוניים. תופס משפחה (sonnet), קידומת גרסה או מזהה מלא. התוספת enforceAvailableModels: true מחילה את הרשימה גם על אפשרות ה-Default בבורר.
  • fallbackModel: מערך של עד שלושה מודלים חלופיים שינוסו לפי הסדר כשהמודל הראשי עמוס או לא זמין; המעבר תקף לתור הנוכחי בלבד. מקבילה לזמן הפעלה: הדגל --fallback-model sonnet,haiku, שגובר על ההגדרה.

Hooks, MCP ו-Plugins: מצביעים קדימה

Hooks (פרק 22): המפתח hooks רושם פקודות Shell שרצות באירועי מחזור חיים קבועים, למשל PostToolUse אחרי כל עריכת קובץ או PreToolUse לפני הרצת כלי, עם matcher שמסנן לאילו כלים להגיב. בניגוד ל-CLAUDE.md, Hook רץ תמיד, בלי תלות בהחלטת המודל, ולכן זה מנגנון האכיפה האמיתי. נראה Stub בסיסי בקובץ הצוותי בהמשך הפרק, והעמקה מלאה בפרק 22.

MCP (פרק 23): שרתי MCP עצמם לא מוגדרים ב-settings.json אלא ב-.mcp.json (פרויקט) וב-~/.claude.json (משתמש). מה שכן יושב ב-settings.json: מפתחות שליטה כמו enabledMcpjsonServers ו-disabledMcpjsonServers (אישור או דחייה של שרתים מ-.mcp.json), enableAllProjectMcpServers (אישור גורף), וחוקי הרשאה בתבנית mcp__server__tool. פרק 23 מכסה הכול.

Plugins (פרק 26): Plugins אורזים Skills, Hooks, Agents ו-MCP לחבילה מותקנת אחת. בקובצי ההגדרות תפגשו מפתחות כמו enabledPlugins, ובצד הארגוני מפתחות ניהול כמו strictKnownMarketplaces ו-blockedMarketplaces. פירוט בפרק 26.

Status Line ו-Output Styles

Status Line: שורת סטטוס מותאמת אישית בתחתית הממשק, שמריצה סקריפט Shell שאתם בוחרים. Claude Code שולח לסקריפט נתוני Session כ-JSON ב-stdin (מודל, תיקייה, אחוז ניצול Context ועוד), ומציג את מה שהסקריפט מדפיס. הדרך הקלה: הפקודה /statusline עם תיאור חופשי, למשל /statusline show model name and context percentage, ש-Claude יכתוב עבורכם את הסקריפט ויעדכן את ההגדרות. הדרך הידנית: מפתח statusLine עם "type": "command" ונתיב הסקריפט ב-command, ואופציונלית padding לריווח. נראה דוגמה בקובץ האישי בהמשך.

Output Styles: תכונה פעילה ועדכנית שמשנה את ה-System Prompt: תפקיד, טון ופורמט תשובה. סגנונות מובנים: Default, Proactive (ביצוע מיידי עם פחות עצירות), Explanatory (תוספות לימודיות) ו-Learning (עבודה משותפת עם משימות TODO(human) עבורכם). בוחרים דרך /config תחת Output style; הבחירה נשמרת ב-.claude/settings.local.json, ואפשר גם לקבוע את המפתח outputStyle ישירות בקובץ הגדרות. שימו לב: הפקודה העצמאית /output-style הוצאה משימוש בגרסה 2.1.73 והוסרה בגרסה 2.1.91. סגנונות מותאמים אישית הם קובצי Markdown ב-~/.claude/output-styles (משתמש) או .claude/output-styles (פרויקט), ושינוי סגנון נכנס לתוקף אחרי /clear או Session חדש.

  },
  "permissions": {
    "deny": [
      "Read(~/.ssh/**)",
      "Read(~/.aws/**)"
    ]
  },
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh",
    "padding": 2
  }
}

שורה אחר שורה:

  • "$schema": מפנה לסכמת ה-JSON הרשמית, כך שעורכים כמו VS Code יציעו השלמות ויסמנו מפתחות שגויים תוך כדי הקלדה. לא חובה, מומלץ מאוד.
  • "model": "sonnet": כינוי משפחה, לא גרסה נעולה. הכינוי יתורגם תמיד לגרסת ה-Sonnet המומלצת אצל הספק שלכם. מי שרוצה לנעול גרסה יכתוב שם מלא כמו claude-sonnet-5.
  • "effortLevel": "high": רמת ה-Effort שתחול בכל Session חדש. ערכים חוקיים כאן: low / medium / high / xhigh.
  • "autoUpdatesChannel": "stable": קבלת עדכוני גרסה מערוץ ה-Stable השמרני במקום latest. בחירה טובה למי שמעדיף יציבות על חידושים.
  • "cleanupPeriodDays": 60: מחיקה אוטומטית של קובצי Sessions ישנים אחרי 60 יום במקום ברירת המחדל של 30. מי שנשען הרבה על /resume היסטורי ירצה ערך גבוה יותר.
  • "includeCoAuthoredBy": true: הוספת שורת Co-Authored-By ל-Commits ש-Claude יוצר, לשקיפות בהיסטוריית ה-Git.
  • "autoMemoryEnabled": true: הצהרה מפורשת על הפעלת Auto Memory (זו גם ברירת המחדל; כתיבה מפורשת מתעדת כוונה). ראו פרק 16.
  • "env": משתני סביבה שיחולו על כל ה-Sessions. כאן: העלאת ה-Timeout של פקודות Bash ל-5 דקות (300000 מילישניות), שימושי לחבילות בדיקות איטיות. שימו לב שהערכים הם תמיד מחרוזות.
  • "permissions.deny": חגורת בטיחות אישית שחלה בכל פרויקט: איסור קריאה של מפתחות SSH ואישורי AWS. שימו לב לתחביר: דווקא בגלל שזה קובץ ברמת המשתמש, חובה לעגן עם ~/ (או //); תבנית עם / בודד הייתה נמדדת יחסית ל-~/.claude/ ולא תופסת את מה שהתכוונתם.
  • "statusLine": הרצת הסקריפט ~/.claude/statusline.sh כשורת סטטוס. "type": "command" פירושו "הרץ פקודת Shell", ו-"padding": 2 מוסיף שני תווי ריווח אופקי.

שימו לב מה אין כאן: חוקי allow ספציפיים לפרויקטים. אלה שייכים לקובצי הפרויקט, כי Bash(npm run test *) ברמת המשתמש היה מתיר את הפקודה בכל תיקייה במחשב.

קובץ מלא 2: settings.json צוותי לפרויקט TaskFlow

הקובץ הזה יושב ב-.claude/settings.json בשורש TaskFlow, נכנס ל-Git, וחל על כל חברי הצוות (אחרי שיאשרו את חלון ה-Trust של התיקייה, שמציג להם בדיוק אילו חוקי allow הקובץ מבקש להעניק):

.claude/settings.json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "sonnet",
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Bash(npm run build)",
      "Bash(pytest *)",
      "WebFetch(domain:fastapi.tiangolo.com)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Read(secrets/**)",
      "Bash(curl *)",
      "Bash(wget *)"
    ]
  },
  "env": {
    "BASH_DEFAULT_TIMEOUT_MS": "300000"
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "./scripts/check-style.sh" }
        ]
      }
    ]
  }
}

שורה אחר שורה:

  • "model": "sonnet": הצוות מיישר קו על מודל אחיד לעבודה היומיומית. זו בחירת פתיחה, לא נעילה: כל מפתח יכול להחליף עם /model, וההגדרה הצוותית תוחזר בהפעלה הבאה. נעילה אמיתית דורשת availableModels ב-Managed Settings.
  • "defaultMode": "default": כל Session בפרויקט נפתח במצב הרגיל שבו Claude מבקש אישור. הצהרה מפורשת שמונעת מצב שבו מפתח מגדיר לעצמו ברירת מחדל מתירנית ושוכח.
  • "allow", חמשת החוקים:
    • Bash(npm run lint) ו-Bash(npm run build): התאמה מדויקת, בלי Wildcard. רק הפקודות האלה בדיוק, בלי ארגומנטים נוספים.
    • Bash(npm run test *): הרווח לפני ה-* קובע גבול מילה, כך שנתפסות npm run test עם כל ארגומנט שאחריה (למשל נתיב קובץ בדיקה), אבל לא סקריפט אחר שבמקרה מתחיל באותן אותיות.
    • Bash(pytest *): הרצת בדיקות ה-Backend עם כל ארגומנט. זכרו: Claude Code בודק כל תת-פקודה בנפרד, אז pytest && rm -rf / לא יעבור בזכות החוק הזה.
    • WebFetch(domain:fastapi.tiangolo.com): היתר לקרוא את התיעוד הרשמי של FastAPI בלי בקשה, ורק אותו.
  • "ask": ["Bash(git push *)"]: דחיפה ל-Remote תמיד תעצור לבקשת אישור, אפילו אם מפתח הוסיף לעצמו allow רחב ל-Git; חוקי ask נבדקים לפני allow.
  • "deny", חמשת החוקים:
    • Read(.env) ו-Read(.env.*): איסור קריאת קובצי סודות. שם קובץ חשוף בתחביר gitignore תופס בכל עומק, כך ש-backend/.env חסום גם הוא. חוק Read נאכף גם על פקודות כמו cat ב-Bash, ומגרסה 2.1.208 חוסם גם עריכת הנתיב ויצירת קובץ חדש בו.
    • Read(secrets/**): כחוק deny, התבנית תופסת תיקיית secrets בכל עומק תחת הפרויקט.
    • Bash(curl *) ו-Bash(wget *): חסימת הורדות שרירותיות מהרשת. גישה מבוקרת לרשת נשארת דרך WebFetch עם חוקי domain:, שקל הרבה יותר לתחום. זו בדיוק ההמלצה המתועדת, כי תבניות Bash שמנסות להגביל URL הן שבירות.
  • "env": הבדיקות של TaskFlow יכולות לרוץ כמה דקות; הצוות מיישר את ה-Timeout ל-5 דקות אצל כולם, כדי שכשלון Timeout לא יופיע רק אצל חלק מהמפתחים.
  • "hooks": שלד (Stub) של Hook אחד: אחרי כל שימוש בכלי עריכה או כתיבה (matcher בתבנית Edit|Write), רץ הסקריפט ./scripts/check-style.sh. בשלב הזה הסקריפט יכול להיות שלוש שורות שמריצות Linter על הקובץ שהשתנה; את הפוטנציאל המלא, כולל חסימת פעולות, נפתח בפרק 22. מכיוון ש-Hooks מריצים פקודות Shell, הם מוצגים לאישור המשתמש דרך מנגנון ה-Trust.

ומה בקובץ המקומי? settings.local.json מינימלי

הקובץ .claude/settings.local.json הוא ההשלמה האישית לקובץ הצוותי: אותו פורמט, אבל לא נכנס ל-Git וגובר על קובץ הפרויקט. גם Claude Code עצמו כותב אליו, למשל כשאתם בוחרים "Yes, don't ask again" על פקודת Bash או בוחרים Output Style. דוגמה מינימלית:

.claude/settings.local.json
{
  "permissions": {
    "allow": [
      "Bash(docker compose up *)"
    ]
  },
  "outputStyle": "Explanatory"
}

ההסבר: המפתח הזה מריץ את סביבת הפיתוח שלו דווקא ב-Docker, העדפה אישית שלא כופים על הצוות, ועובד עם סגנון הפלט הלימודי Explanatory. ודאו ש-.claude/settings.local.json רשום ב-.gitignore של הפרויקט, כדי שהעדפות אישיות (וחוקי allow שנשמרו אוטומטית) לא ידלפו ל-Repository.

אימות שלושת הקבצים: כל דוגמאות ה-JSON בפרק נבדקו עם Parser ותקינות. אצלכם: הריצו /doctor אחרי כל עריכה; הוא מדווח על קובצי הגדרות שלא ניתנים לפענוח ועל מפתחות לא תקינים. בדיקה ידנית מהטרמינל: python3 -m json.tool .claude/settings.json תדפיס את הקובץ אם הוא תקין ותצביע על השורה השבורה אם לא.

Troubleshooting: כשההגדרות לא נתפסות

תקלות הגדרות כמעט תמיד נופלות לאחת מחמש קטגוריות:

  1. שגיאת תחביר JSON. פסיק מיותר אחרי האיבר האחרון, מרכאות חסרות, הערת // (אסורה ב-JSON). סימפטום: הקובץ כולו מנוטרל בשקט. אבחון: /doctor, שמאתר קובצי הגדרות לא ניתנים לפענוח, או python3 -m json.tool על הקובץ.
  2. בלבול עדיפויות: "הגדרתי, אבל קובץ אחר מנצח". זכרו את הסולם: Managed, ואז שורת פקודה, ואז settings.local.json, ואז קובץ הפרויקט, ואז קובץ המשתמש. ערך סקלרי כמו model בקובץ המקומי ידרוס את קובץ הפרויקט; ולגבי הרשאות, deny מכל רמה שהיא גובר, כך שאי אפשר "לפתוח" ברמה נמוכה מה שנחסם ברמה גבוהה (או הפוכה). אבחון: /status מציג את מקורות ההגדרות הפעילים, ו-/permissions מציג ליד כל חוק מאיזה קובץ settings.json הוא הגיע.
  3. חוקי allow של פרויקט לא חלים לפני אישור Trust. חוקי permissions.allow ו-additionalDirectories בקובץ פרויקט נאכפים רק אחרי שאישרתם את חלון ה-Trust של התיקייה (חוקי deny ו-ask חלים תמיד, כי הם רק מגבילים). אם עמית מתלונן שה-Allowlist "לא עובד" אצלו, בדקו אם הוא דחה את החלון.
  4. ההגדרה דורשת Session חדש. רוב ההגדרות נטענות מחדש תוך כדי ריצה, אבל model ו-outputStyle נקראים בתחילת Session; שינוי בקובץ ייתפס רק אחרי /clear או הפעלה מחדש.
  5. משתנה סביבה חיצוני דורס. למשל ANTHROPIC_MODEL ישן שמיוצא ב-.zshrc וגובר על מפתח model בהגדרות. אבחון עומק: claude --debug מדפיס לוג מפורט של תהליך הטעינה, כולל אילו קבצים נקראו ומה נדחה.
Security

קובץ .claude/settings.json שמגיע מ-Repository זר הוא וקטור תקיפה: הוא יכול לבקש חוקי allow מסוכנים ו-Hooks שמריצים קוד. זו בדיוק הסיבה שחלון ה-Trust מציג את חוקי ההרשאות לפני האישור. קראו אותם באמת לפני שאתם מאשרים תיקייה שלא אתם יצרתם, ולעולם אל תשימו סודות (מפתחות API, סיסמאות) בשום קובץ הגדרות שנכנס ל-Git.

Best Practices ו-Anti-patterns

Best Practices
  • התחילו מ-deny ורק אז הוסיפו allow: קל להרחיב הרשאות בהמשך, קשה לאסוף חזרה סודות שנקראו.
  • כתבו חוקי allow צרים ככל האפשר: פקודה מדויקת עדיפה על תבנית, ותבנית עם רווח לפני * עדיפה על תבנית בלי.
  • שמרו על חלוקת תפקידים בין הקבצים: העדפות אישיות בקובץ המשתמש, חוזה הצוות בקובץ הפרויקט, חריגות מקומיות ב-settings.local.json, ואכיפה ארגונית ב-Managed Settings בלבד.
  • העבירו כל שינוי בקובץ הפרויקט דרך Pull Request, בדיוק כמו CLAUDE.md בפרק 16: שינוי הרשאות הוא שינוי התנהגות אצל כל הצוות.
  • הוסיפו את "$schema" לכל קובץ, והריצו /doctor אחרי כל עריכה ידנית.
Anti-patterns
  • חוק allow רחב כמו Bash(git *) "כדי לחסוך אישורים": הוא מתיר גם git push --force וגם git clean -fdx.
  • ניסיון להגביל כתובות רשת דרך תבניות curl ב-Bash: התיעוד מגדיר זאת במפורש כתבנית שבירה; חסמו את curl והשתמשו ב-WebFetch(domain:...).
  • הכנסת .claude/settings.local.json ל-Git: הקובץ צובר חוקים אישיים אוטומטיים ואין לו מקום ב-Repository.
  • שכפול אותם חוקי allow לכל פרויקט ביד במקום לרכז העדפות אמת בקובץ המשתמש.
  • סוד כלשהו, אפילו "זמני", בתוך מפתח env בקובץ שנכנס ל-Git.

תרגיל

תרגיל 17.1: בניית שכבות ההגדרות ובדיקת ההכרעה

על פרויקט TaskFlow (או כל פרויקט תרגול):

  1. צרו .claude/settings.json עם החוקים מהדוגמה הצוותית (אפשר לצמצם), כולל deny על Read(.env).
  2. צרו קובץ .env עם תוכן דמה (API_KEY=dummy123), פתחו Session חדש, אשרו את חלון ה-Trust, ובקשו מ-Claude: read the .env file and tell me what is in it. תעדו מה קורה.
  3. הריצו /permissions ומצאו את חוק ה-deny שלכם ואת הקובץ שממנו הגיע.
  4. נסו "לעקוף": הוסיפו ב-.claude/settings.local.json חוק allow של Read(.env), פתחו Session חדש ובקשו שוב. מה קרה, ולמה?
  5. סיימו עם /doctor: ודאו שאין אזהרות על קובצי ההגדרות, ומחקו את קובץ ה-.env הדמה.
פתרון מוסבר

(2) Claude ינסה לקרוא את הקובץ וייחסם: תראו הודעת דחייה שמפנה לחוק ההרשאות. ייתכן ש-Claude יעיר בעצמו שהקובץ חסום, ואולי אף ינסה דרך cat .env ב-Bash, וגם זה ייחסם, כי חוקי Read נאכפים גם על פקודות קבצים מזוהות ב-Bash. (3) ב-/permissions תראו את החוק לצד מקורו: .claude/settings.json. (4) הקריאה עדיין נחסמת. זה הלקח המרכזי של הפרק: חוקי Permissions מתמזגים בין הרמות ולא דורסים, וסדר ההערכה הוא deny תחילה. deny מקובץ הפרויקט מנצח allow מהקובץ המקומי, למרות שהקובץ המקומי "חזק יותר" עבור ערכים סקלריים כמו model. ההבחנה בין שני סוגי ההכרעה, דריסה לסקלרים מול מיזוג עם קדימות deny להרשאות, היא מה שהתרגיל בא לקבע. (5) אם /doctor מדווח על קובץ לא תקין, כמעט תמיד מדובר בפסיק עודף; תקנו והריצו שוב.

סיכום

למדנו את שכבת התצורה של Claude Code מקצה לקצה: חמש רמות הגדרות עם סדר עדיפויות מוגדר (Managed, שורת פקודה, מקומי, פרויקט, משתמש), כללי ההכרעה (דריסה לסקלרים, מיזוג עם קדימות deny להרשאות), ושלוש דרכי עריכה: /config, /config key=value ועריכת קבצים ישירה. סקרנו את משתני הסביבה החשובים ואת אזהרת ה-ANTHROPIC_API_KEY, פירקנו את תחביר חוקי ה-Permissions על עוגני הנתיבים שלהם, עברנו על הגדרות המודל (model, effortLevel, availableModels, fallbackModel), והצצנו ל-Hooks, MCP, Plugins, Status Line ו-Output Styles שיעמיקו בפרקים הבאים. במרכז: שלושה קובצי הגדרות מלאים ומוסברים שאפשר לאמץ כבסיס אמיתי. בפרק הבא נעמיק במצבי ההרשאות עצמם: Permission Modes.
