כיצד לדבר עם Claude Code

איכות התוצאה של Claude Code נקבעת במידה רבה על ידי איכות ה-Prompt שלכם. בפרק הזה נלמד שיטה מסודרת לניסוח הנחיות: מבנה מומלץ עם Context, Objective, Constraints ו-Acceptance Criteria, השוואה בין Prompt חלש, סביר ומקצועי על פרויקט TaskFlow, וספריית תבניות מוכנות להעתקה לשנים עשר סוגי משימות: מהסבר Codebase ועד Migration ושדרוג Dependencies.

מדוע ניסוח ה-Prompt קובע את איכות התוצאה

ראינו בפרק 1 שכל משימה מתחילה בהנחיה שלכם, וממנה נגזר כל מה שהכלי יעשה: אילו קבצים יקרא, מה יחפש, מה ישנה ואיך יבדוק את עצמו. התיעוד הרשמי מדגיש שתי נקודות שנראות סותרות אך משלימות זו את זו:

  • זו שיחה, לא טופס. אינכם חייבים Prompt מושלם. אפשר להתחיל, לראות מה קורה, ולתקן: "זה לא בדיוק זה, הבעיה בטיפול ב-Session". Claude Code בנוי לאיטרציה, ואפשר לעצור ולכוון אותו בכל רגע.
  • דיוק מראש חוסך תיקונים. ככל שההנחיה הראשונית מדויקת יותר, כך תידרשו לפחות סיבובי תיקון. הנחיה שמפנה לקבצים ספציפיים, מציינת אילוצים ומגדירה מה נחשב הצלחה, מצליחה לעיתים קרובות כבר בניסיון הראשון.

יש גם סיבה כלכלית: כל סיבוב תיקון ממלא את ה-Context Window בניסיונות כושלים, וביצועי המודל יורדים ככל שהחלון מתמלא (פרק 14 עוסק בכך לעומק). ההמלצה הרשמית חד משמעית: אחרי שני תיקונים כושלים באותו נושא, עדיף להריץ /clear ולנסח מחדש הנחיה טובה יותר שמשלבת את מה שלמדתם, מאשר להמשיך לתקן בתוך Session עמוס. במילים אחרות: ההשקעה בניסוח היא הדרך הזולה ביותר לשפר תוצאות.

כדי להבין למה כל רכיב בהנחיה משפיע, כדאי לחזור רגע ל-Agentic Loop מפרק 1 ולראות מה כל חלק של ההנחיה עושה בתוכה:

  • הקשר ומיקום מקצרים את שלב איסוף ה-Context: במקום לסרוק את הפרויקט, הכלי ניגש ישר לקבצים הנכונים. פחות קריאות מיותרות פירושו גם Context Window פנוי יותר לעבודה עצמה.
  • מטרה וגבולות מכווננים את שלב הפעולה: הם קובעים כמה רחב יהיה ה-Diff ומונעים "שיפורים" אגביים שלא ביקשתם, שהם אחת הסיבות הנפוצות ל-Diffs שקשה לאשר.
  • קריטריונים ואימות מפעילים את שלב הבדיקה: הם נותנים ללולאה תנאי עצירה אמיתי במקום "נראה גמור", ומאפשרים לכלי לתקן את עצמו לפני שהוא חוזר אליכם.
  • הגדרת תוצר משפרת את מה שחוזר אליכם בסוף: תשובה בפורמט שביקשתם נסקרת מהר יותר, וזה החלק שחוסך לכם, לא לכלי, את רוב הזמן.

שלוש רמות של Prompt: חלש, סביר, מקצועי

נמחיש את ההבדל על תרחיש מציאותי בפרויקט TaskFlow. נניח שהתקבל דיווח: משתמשים מעדכנים סטטוס של משימה דרך ה-API, מקבלים תשובת הצלחה, אבל הרשימה ממשיכה להציג את הסטטוס הישן. הקוד הרלוונטי נמצא ב-backend/app/routers/tasks.py.

רמה 1: Prompt חלש

Prompt
fix the bug in tasks

מה חסר כאן? הכול. איזה Bug? באיזה קובץ? מה התסמין? מה נחשב "מתוקן"? Claude ייאלץ לנחש: הוא יקרא קבצים רבים בחיפוש אחר משהו חשוד, אולי "יתקן" משהו שאינו קשור, ואתם תגלו זאת רק בסוף. הנחיה כזו אינה אסורה: היא לגיטימית כשאתם עצמכם עוד לא יודעים מה הבעיה ורוצים חקירה פתוחה. אבל אם יש לכם מידע, להסתיר אותו מהכלי זה בזבוז.

רמה 2: Prompt סביר

Prompt
Users report that PATCH /tasks/{id} returns 200 but GET /tasks
still shows the old status afterwards. Find the root cause in
backend/app/routers/tasks.py and fix it.

כבר הרבה יותר טוב: יש תסמין מדויק (Endpoint, קוד תשובה, התנהגות שגויה) ומיקום משוער. Claude יכול לגשת ישר לקוד הרלוונטי. מה עדיין חסר? דרך אימות (איך נדע שהתיקון עובד ולא רק "נראה נכון"), גבולות (מה מותר לשנות), והגדרת תוצר (מה אנחנו רוצים לקבל בסוף).

רמה 3: Prompt מקצועי

Prompt
Context: TaskFlow backend, FastAPI + SQLite. Task routes live in
backend/app/routers/tasks.py, tests in backend/tests/test_tasks.py.

Bug report: PATCH /tasks/{id} with {"status": "done"} returns 200,
but GET /tasks afterwards still shows the old status.

Objective: find and fix the root cause.

Process:
1. Write a failing test in backend/tests/test_tasks.py that
   reproduces the report before touching any code.
2. Investigate and explain the root cause to me before fixing.
3. Fix the root cause. Do not suppress the error or special-case
   the test.

Constraints: no new dependencies, keep the public API unchanged,
follow the existing code style.

Verification: run the full pytest suite and show the output.
Out of scope: the frontend, and any refactoring beyond the fix.

Required output: root cause explanation, the diff, and the final
test results.

ההנחיה הזו ארוכה יותר, אבל כל שורה בה עובדת: היא מבוססת על שני עקרונות רשמיים שנרחיב עליהם בהמשך, "כתוב קודם Test נכשל שמשחזר את הבעיה" ו"תקן את שורש הבעיה, אל תסתיר את השגיאה". נשווה את שלוש הרמות:

היבטחלשסבירמקצועי
זמן חקירה של הכליגבוה: סריקה עיוורת של הפרויקטנמוך: יעד ברורנמוך: יעד ותהליך ברורים
סיכון לתיקון שגויגבוהבינוני: אין אימות מוגדרנמוך: Test משחזר לפני תיקון
צריכת Contextגבוהה: קריאת קבצים מיותריםבינוניתנמוכה יחסית למשימה
יכולת שלכם לבדוק את התוצאהאין: לא הוגדר מה נחשב הצלחהחלקיתמלאה: פלט Tests והסבר שורש הבעיה
מתי מתאיםחקירה פתוחה בלבדמשימות קטנות ומוכרותכל משימה עם השלכות אמיתיות
הערה

לא כל משימה מצדיקה את הרמה השלישית. ההמלצה הרשמית: אם אפשר לתאר את ה-Diff הצפוי במשפט אחד (תיקון שגיאת כתיב, הוספת שורת Log, שינוי שם משתנה), בקשו זאת ישירות בלי טקס. המבנה המלא נועד למשימות שבהן טעות עולה ביוקר.

מבנה Prompt מומלץ: שמונת הרכיבים

למשימות משמעותיות, המדריך ממליץ על מבנה קבוע של שמונה רכיבים. אין חובה למלא את כולם בכל פעם, אבל כדאי לעבור עליהם בראש כרשימת בדיקה: כל רכיב שמושמט הוא החלטה שהעברתם לכלי בלי לשים לב.

רכיבעונה על השאלהדוגמה
Contextמה הכלי צריך לדעת על הסביבהה-Stack, קבצים רלוונטיים, החלטות עבר, דיווח התקלה
Objectiveמה צריך להיות נכון בסוף, במשפט אחד"עדכון סטטוס נשמר ומוחזר ב-GET"
Scopeבאילו קבצים ואזורים מותר לגעת"רק backend/app ו-backend/tests"
Constraintsאילו כללים אסור להפרללא Dependencies חדשים, שמירת תאימות API, סגנון קיים
Acceptance Criteriaאילו טענות ניתנות לבדיקה יגדירו הצלחהרשימת תנאים שכל אחד מהם ניתן לאימות
Verificationאילו פקודות ירוצו ומה פלט תקיןpytest -q עובר; npm run typecheck נקי
Out of Scopeמה לא לעשות, גם אם מתחשק"בלי Refactoring אגבי, בלי לגעת ב-Frontend"
Required Outputמה אתם רוצים לקבל בסוףהסבר, Diff, פלט Tests, שאלות פתוחות

והנה תבנית מלאה להעתקה. שמרו אותה בצד והתאימו לכל משימה:

prompt-template.txt
## Context
[Stack, relevant files and directories, prior decisions,
error reports or logs. Reference files with @path when useful.]

## Objective
[One sentence: what should be true when the task is done.]

## Scope
[Files and areas that may change.]

## Constraints
[Style rules, dependency policy, compatibility requirements,
process rules such as "plan first" or "small steps with diffs".]

## Acceptance Criteria
- [Verifiable statement 1]
- [Verifiable statement 2]

## Verification
[Exact commands to run and what output counts as success.]

## Out of Scope
[What must not change, even if it looks tempting to "improve".]

## Required Output
[What to hand back: explanation, diff, test output, open questions.]
Best Practice

שני הרכיבים שמשפרים תוצאות יותר מכל השאר הם Acceptance Criteria ו-Verification. ההסבר הרשמי: Claude עוצר כשהעבודה "נראית גמורה". כשאתם נותנים לו בדיקה שהוא יכול להריץ בעצמו (חבילת Tests, Build, Linter, השוואת צילום מסך), הלולאה נסגרת לבד: הוא עובד, בודק, קורא את התוצאה ומתקן עד שהבדיקה עוברת. בלי זה, אתם לולאת האימות.

בדיקה עצמית לפני שליחת Prompt משמעותי:

  • האם ציינתי את הקבצים או התיקיות הרלוונטיים, במקום לתת לכלי לנחש?
  • האם המטרה מנוסחת כמצב סופי שניתן לבדוק, ולא כפעולה עמומה ("לשפר", "לסדר")?
  • האם הגדרתי לפחות בדיקה אחת שהכלי יכול להריץ בעצמו, ומה נחשב פלט תקין?
  • האם אמרתי מה אסור לשנות?
  • האם ההנחיה עוסקת במשימה אחת בלבד?

עקרונות מהתיעוד הרשמי

מעבר למבנה, ארבעה עקרונות מה-Best Practices הרשמיים שכדאי להטמיע:

  • ספקו הקשר עשיר בדרכים חכמות. הפניה לקובץ עם @src/utils/auth.js מכניסה את תוכנו לשיחה; אפשר להדביק צילומי מסך ותמונות ישירות; לתת כתובות URL של תיעוד; ולהזרים נתונים עם Pipe, למשל cat error.log | claude.
  • הפרידו מחקר מביצוע. במשימות מורכבות, קודם בקשו קריאה והבנה (או עבדו ב-Plan Mode, פרק 7), סקרו את התוכנית, ורק אז אשרו ביצוע. גישה דו שלבית מניבה תוצאות טובות יותר מקפיצה ישר לקוד.
  • הצביעו על דוגמאות קיימות. "ראה איך ממומש ה-Widget הקיים ולך לפי אותה תבנית" עדיף על תיאור מופשט של התבנית. הקוד שלכם הוא מפרט מצוין.
  • תנו לו לראיין אתכם. ל-Feature גדול, ההמלצה הרשמית היא להתחיל מהנחיה מינימלית ולבקש: Interview me in detail using the AskUserQuestion tool, עד לכתיבת מפרט מלא ל-SPEC.md. ואז מתחילים Session נקי לביצוע המפרט.

ספריית Prompts לפי סוג משימה

לכל אחד משנים עשר סוגי המשימות הנפוצים, הנה תבנית מלאה להעתקה, מותאמת לפרויקט TaskFlow וניתנת להתאמה לכל פרויקט. התבניות מבוססות על הדפוסים שבתיעוד הרשמי (Common Workflows, Best Practices ו-Prompt Library), עם הרחבות של המדריך. הנחיות נכתבות כאן באנגלית, כפי שמקובל בעבודה מול כלי פיתוח; אפשר לכתוב ל-Claude Code גם בעברית, אבל שמות קבצים, פקודות ומונחים טכניים נשארים באנגלית בכל מקרה.

1. הסבר Codebase

Prompt
Give me an overview of this codebase: architecture, key
directories, and how the pieces connect. Then trace one request
end to end: what happens when the frontend creates a new task,
from the React component to the SQLite database. Do not change
any files.

מתחילים רחב ואז מצרים: סקירה כללית, ואז מעקב אחר זרימה אחת קונקרטית. השורה האחרונה קובעת שזו משימת קריאה בלבד. השאלה הפותחת לקוחה כלשונה מספריית ה-Prompts הרשמית. התוצאה הצפויה: תיאור מבנה התיקיות, הרכיבים המרכזיים והקשרים ביניהם, ואחריו מעקב שלב אחר שלב אחרי הבקשה. ההמלצה הרשמית להמשך: לשאול שאלות המשך כמו שהייתם שואלים מהנדס ותיק בצוות, בלי טקסיות: "איך עובד ה-Logging כאן?", "אילו מקרי קצה מטופלים בפונקציה הזו?". פרק 6 מקדיש לטכניקות האלה דיון שלם.

2. מחקר לפני שינוי

Prompt
Research only, do not edit any files.
I plan to add user authentication to TaskFlow. Map everything the
change would touch: routers, models, database schema, frontend
API calls, and tests. List each affected file with one line on
why it matters, then finish with the open questions I should
answer before we plan the implementation.

מחקר ממוקד עם תוצר מוגדר: רשימת קבצים מושפעים ושאלות פתוחות. שימו לב שהשאלה תחומה לשינוי מסוים; "תחקור את המערכת" בלי גבול הוא האנטי דפוס שהתיעוד מכנה חקירה אין סופית. אם המחקר צפוי להיות רחב מאוד, עטפו אותו ב-Subagent ("use a subagent to investigate...") כדי שקריאת עשרות הקבצים לא תמלא את ה-Context הראשי שלכם: ה-Subagent קורא בחלון נפרד ומחזיר סיכום בלבד. זו המלצה רשמית שנרחיב עליה בפרק 25.

3. תכנון Feature

Prompt
I want to add due dates to tasks in TaskFlow.

Context: backend is FastAPI + SQLite (backend/app), frontend is
React + TypeScript (frontend/src). The Task model lives in
backend/app/models.py.

Create an implementation plan: files to change, API changes,
database schema change, frontend changes, and the tests we need.
Include trade-offs for storing the date as TEXT vs INTEGER in
SQLite, and recommend one. Do not write any code yet.

הנחיית תכנון טובה מבקשת גם חלופות ו-Trade-offs, לא רק תוכנית אחת. את ההנחיה הזו טבעי להריץ ב-Plan Mode, שמבטיח ברמת המערכת שקבצי המקור לא ישתנו בשלב התכנון (פרק 7). התוצר הצפוי הוא תוכנית שאתם קוראים, מתקנים ומאשרים לפני שנכתבת שורת קוד אחת: זו הנקודה הזולה ביותר לתקן בה טעות תכנון. הטעות הנפוצה כאן היא לאשר תוכנית בלי לקרוא אותה באמת, ואז לגלות את הבעיות ב-Diff.

4. תיקון Bug

Prompt
Users report that deleting a task twice crashes the client: the
second DELETE /tasks/{id} should return 404 but the client sees a
different error. Reproduce first: write a failing test in
backend/tests/test_tasks.py that captures the report. Then find
the root cause in backend/app/routers/tasks.py, explain it to me,
and fix it. Address the root cause, do not suppress the error.
Run the full test suite and show the output.

שלושת המרכיבים הקריטיים, כולם מההמלצות הרשמיות: תסמין מדויק (עדיף עם הודעת השגיאה המלאה מודבקת), Test נכשל שמשחזר את הבעיה לפני התיקון, ודרישה מפורשת לטפל בשורש ולא בתסמין. טיפים רשמיים נוספים: ציינו את הפקודה שמשחזרת את הבעיה ואת צעדי השחזור, וכתבו אם השגיאה עקבית או מופיעה לסירוגין; ב-Bug לסירוגין הכלי יחפש גורמים אחרים לגמרי (תזמון, מצב משותף) מאשר ב-Bug דטרמיניסטי. פרק 10 מרחיב על Debugging שיטתי.

5. Refactoring

Prompt
Refactor backend/app/routers/tasks.py to move all SQL access into
a separate repository module, without changing behavior.

Constraints: keep the public API and response shapes identical,
keep type hints, no new dependencies.
Acceptance criteria: all existing tests in backend/tests pass
unchanged. Work in small steps and show me the diff after each
step before continuing.

ב-Refactoring, ה-Acceptance Criteria החשוב ביותר הוא "ה-Tests הקיימים עוברים ללא שינוי": שינוי ב-Tests פירושו שינוי התנהגות, וזה כבר לא Refactoring. הדרישה לצעדים קטנים עם Diff ביניהם שומרת עליכם בעמדת בקרה, וההמלצה הרשמית תואמת: לבצע Refactoring במנות קטנות וברות בדיקה. אם האזור שאתם משנים אינו מכוסה ב-Tests כלל, הפכו את זה לצעד הראשון בהנחיה: קודם בדיקות שמקבעות את ההתנהגות הקיימת, רק אחר כך שינוי מבנה. פרק 12 מוקדש לנושא.

6. כתיבת Tests

Prompt
Write tests for backend/app/routers/tasks.py, run them, and fix
any failures. Cover these cases: creating a task with an empty
title returns 422, updating a non-existent task returns 404,
deleting a task twice returns 404 on the second call, and
GET /tasks returns tasks ordered by id. Follow the style of the
existing tests in backend/tests/test_tasks.py and avoid mocks.

הבסיס "write tests for X, run them, and fix any failures" לקוח מספריית ה-Prompts הרשמית; התוספת החשובה היא רשימת מקרים מפורשת. בלי זה תקבלו לרוב בדיקות ל"מסלול המאושר" בלבד. ציון סגנון קיים והעדפה לגבי Mocks חוסך סיבוב תיקונים שלם: לפי התיעוד, Claude בוחן ממילא את קובצי ה-Tests הקיימים כדי להתאים את עצמו למסגרת ולסגנון, אבל העדפות שאינן כתובות בקוד צריכות להיאמר. אפשר גם לבקש ממנו להציע מקרי קצה שפספסתם: תנאי שגיאה, ערכי גבול וקלטים לא צפויים. הסיכון המרכזי בבדיקות שנכתבות אחרי הקוד הוא שהן "מתאימות את עצמן" למימוש הקיים; פרק 11 מציג את הדרכים להתגונן מכך.

7. Code Review

Prompt
Review my uncommitted changes and flag anything that looks risky
before I commit. Focus on correctness, error handling, and
consistency with the existing patterns in backend/app. Report the
findings as a list ordered by severity, with file and line for
each finding. Do not edit any files.

המשפט הפותח הוא תבנית רשמית מספריית ה-Prompts. חשוב להגדיר מוקדי סקירה ותוצר (רשימה לפי חומרה), ולנעול עריכה: סקירה שמתקנת תוך כדי מערבבת שני תפקידים. קיים גם Skill מובנה בשם /code-review שסוקר את ה-Diff הנוכחי ב-Subagent נפרד; ראו פרק 4 להפעלתו. אזהרה מהתיעוד הרשמי שכדאי להפנים: סוקר שמתבקש למצוא בעיות ימצא בעיות כמעט תמיד, גם כשהקוד תקין. הנחו אותו לדווח רק על ממצאים שמשפיעים על נכונות או על הדרישות, והתייחסו לשאר כהצעות אופציונליות, אחרת תמצאו את עצמכם מוסיפים שכבות הגנה מיותרות.

8. Security Review

Prompt
Use a subagent to review backend/app/ for security issues and
report what it finds. Look specifically for: SQL built from user
input, missing input validation, secrets in code, and error
responses that leak internal details. For each finding report
file, line, severity, and a suggested fix. Read-only: do not
change any files.

הפתיחה מבוססת על התבנית הרשמית "use a subagent to review {path} for security issues". ה-Subagent נותן לסקירה הקשר נקי, שאינו "מזוהם" בהנחות מהשיחה הנוכחית: יתרון של ממש כשסוקרים קוד ש-Claude עצמו כתב. רשימת המוקדים מכוונת את הסקירה לסיכונים המרכזיים של ה-Stack שלכם. וחשוב לומר בפירוש: סקירה כזו היא שכבת הגנה מוקדמת וזולה, לא תחליף לתהליכי אבטחה של הארגון, ל-Code Review אנושי או לכלי סריקה ייעודיים. פרק 20 מוקדש לאבטחה, כולל סקירות אבטחה מובנות בתהליך העבודה.

9. ניתוח Performance

Prompt
Optimize GET /tasks to bring its response time with 10,000 tasks
in the database from about 800ms down to under 200ms.

Measure first: write a small script that seeds 10,000 tasks and
times the endpoint, and record the baseline. Then profile,
explain the bottleneck, and propose options with trade-offs
before implementing the one I approve.
Verification: rerun the measurement script and show before/after
numbers.

עבודת ביצועים בלי מדידה היא ניחוש. המבנה הרשמי המומלץ הוא יעד מדיד: "להוריד את {metric} מ-{current} אל מתחת ל-{goal}". שימו לב לסדר המחייב: מדידה, אבחון, חלופות, אישור שלכם, מימוש, ומדידה חוזרת. כך לא תקבלו "אופטימיזציה" שאי אפשר להוכיח. הטעות הנפוצה היא לדלג על שלב המדידה ולבקש ישר "תעשה את זה מהיר יותר": בלי Baseline אין דרך לדעת אם השינוי עזר, הזיק או סתם סיבך את הקוד, וצווארי בקבוק אמיתיים נמצאים לעיתים קרובות במקום אחר לגמרי ממה שנדמה.

10. Documentation

Prompt
Find the public functions in backend/app/ without docstrings and
add them, matching the style already used in the file. Then add a
short API reference section to README.md covering the /tasks
endpoints: method, path, request body, and possible responses.
Do not change any code behavior.

מבוסס על התבנית הרשמית לתיעוד: איתור קוד לא מתועד, הוספה בסגנון הקיים. הגבלת "בלי שינוי התנהגות" חשובה: משימות תיעוד הן הזדמנות מפתה ל"שיפורים" אגביים בקוד, ואתם רוצים Diff שכולו תיעוד, שקל לאשר בביטחון. הטיפים הרשמיים הנוספים: ציינו את סגנון התיעוד המבוקש (JSDoc, Docstrings וכדומה), בקשו דוגמאות שימוש בתוך התיעוד, ואחרי היצירה בקשו בדיקה שהתיעוד עומד בתקן של הפרויקט. תיעוד שנוצר אוטומטית דורש קריאה ביקורתית: הוא משקף את מה שהקוד עושה, כולל באגים, לא בהכרח את מה שהקוד אמור לעשות.

11. Migration

Prompt
Migrate everything from raw sqlite3 access to SQLAlchemy Core:
identify every place that needs to change, then make the changes.

Scope: backend/app/database.py and backend/app/routers/tasks.py.
Constraints: keep the public API identical, keep SQLite as the
engine, one commit per logical step.
Acceptance criteria: all tests in backend/tests pass, and no raw
SQL strings remain outside the new data layer.
Start with a written plan and wait for my approval before editing
any file.

הנוסחה הרשמית ל-Migration היא "identify every place that needs to change, then make the changes": קודם מיפוי מלא, אחר כך ביצוע. התוספות שלנו: Commit לכל צעד לוגי (כדי שאפשר יהיה לחזור אחורה), וקריטריון סיום שניתן לבדיקה מכנית (אין SQL גולמי מחוץ לשכבה). התוצאה הצפויה משלב המיפוי היא רשימה מלאה של נקודות שינוי; אם הרשימה נראית חסרה, עצרו ותקנו אותה לפני הביצוע, כי מיפוי חסר הוא הכשל המרכזי של Migrations. ב-Migrations גדולים באמת, שאינם נכנסים ל-Session אחד, פרק 35 מציג עבודה בשלבים ובמקביל, כולל פיזור העבודה על פני הרצות נפרדות.

12. שדרוג Dependencies

Prompt
Upgrade fastapi and pydantic in backend/requirements.txt to the
latest stable versions.

Before changing anything, list: current versions, target
versions, and any breaking changes between them that affect our
code (check the official changelogs). Then apply the upgrade, fix
any deprecation warnings our code triggers, and run the full test
suite. If a breaking change requires a design decision, stop and
ask me instead of guessing.

שדרוג Dependencies הוא משימה ש-Claude Code מצטיין בה, בתנאי שמחייבים אותו לבדוק את פערי הגרסאות לפני הנגיעה בקוד: הכלי יכול להביא את ה-Changelogs הרשמיים עם WebFetch. השורה האחרונה חשובה במיוחד: היא מגדירה נקודת עצירה במקום ניחוש בהחלטות תכנון. שימו לב שהרצת ההתקנה עצמה (pip install) תבקש את אישורכם, כמו כל פקודת Bash משנה.

מתי Prompt חופשי ומתי Slash Command

בפרק 4 הכרנו את פקודות ה-/: פקודות מובנות (כמו /clear ו-/model) ו-Skills שמופעלים בפקודה (כמו /code-review). מתי בוחרים בפקודה ומתי בהנחיה חופשית?

  • פעולות על הכלי עצמו: תמיד פקודה. ניקוי Context, החלפת מודל, בדיקת הרשאות: אלה פעולות מערכת, לא בקשות מהמודל, ויש להן פקודות ייעודיות (פרק 4).
  • משימה חד פעמית או ייחודית: Prompt חופשי. כל מה שראינו בפרק הזה. הגמישות של שפה חופשית היא בדיוק היתרון.
  • משימה שחוזרת על עצמה: הפכו אותה ל-Skill. הכלל הרשמי: אם אתם מקלידים את אותה הנחיה בפעם השלישית, שמרו אותה כ-Skill שמופעל ב-/name. כך התהליך מקבל שם, גרסה, ושיתוף עם הצוות (פרק 21).
  • כלל שחייב לחול תמיד: לא Prompt בכלל. הנחיה היא בקשה, לא אכיפה. כלל כמו "לעולם אל תערוך את .env" שייך ל-Hook או לכלל Permissions, שפועלים באופן דטרמיניסטי (פרקים 18 ו-22).

שיקולי Context ועלות בניסוח

הנחיה טובה היא גם הנחיה חסכונית. כמה כללי אצבע, כולם נגזרים מהעיקרון הרשמי שה-Context Window הוא המשאב החשוב ביותר לניהול:

  • הנחיה ארוכה זולה מאיטרציה מיותרת. תוספת של עשרים שורות מבנה להנחיה היא זניחה לעומת סיבוב תיקון שלם, שגורר קריאות קבצים, הרצות פקודות ופלטים שכולם נשארים בחלון.
  • הפניית @ טוענת את הקובץ כולו לשיחה. זה מצוין לקובץ שהמשימה באמת עוסקת בו, ובזבוז לקבצים "אולי רלוונטיים". כשאינכם בטוחים, תנו לכלי לאתר לבד עם Grep ו-Glob: הוא יקרא רק את מה שנחוץ.
  • קצצו לוגים לפני הדבקה. במקום להדביק קובץ לוג שלם, הזרימו את הסוף הרלוונטי, למשל tail -200 app.log | claude -p "..." בהרצה לא אינטראקטיבית, או הדביקו רק את קטע השגיאה.
  • מחקר רחב שייך ל-Subagent. כפי שראינו: חקירה שקוראת עשרות קבצים ממלאת את החלון הראשי; Subagent מחזיר סיכום בלבד.
  • שאלת אגב לא חייבת להיכנס להיסטוריה. לשאלה צדדית תוך כדי עבודה קיימת הפקודה /btw: התשובה מוצגת בשכבה נפרדת ואינה נכנסת להיסטוריית השיחה, כך שהיא אינה צורכת Context מהמשימה המרכזית.
  • עקבו אחרי המילוי. הפקודה /context מציגה מה תופס מקום בחלון. אם אתם מתקרבים לקצה באמצע משימה, עדיף לסכם ולפתוח Session נקי מאשר להיאבק בחלון מלא (פרק 14).

תרגיל

תרגיל 5.1: מחלש למקצועי

לפניכם הנחיה שמפתח שלח ל-Claude Code בפרויקט TaskFlow:

make the tasks API faster and also clean up the code

1. זהו לפחות ארבע בעיות בהנחיה הזו, על סמך הפרק.

2. כתבו מחדש את החלק של הביצועים בלבד כ-Prompt מקצועי מלא לפי מבנה שמונת הרכיבים. הניחו שמדדתם: GET /tasks עם 10,000 משימות לוקח כ-900ms, והיעד הוא מתחת ל-250ms.

פתרון מוסבר

חלק 1: הבעיות. (א) שתי משימות לא קשורות בהנחיה אחת: אופטימיזציה ו"ניקוי קוד" הן עבודות שונות עם קריטריונים שונים, וה-Diff המשולב יהיה קשה לסקירה. (ב) "faster" בלי מדד: אין Baseline, אין יעד, ואי אפשר לדעת אם הצלחנו. (ג) "clean up" עמום לחלוטין: לפי איזה קריטריון? (ד) אין Scope: לא ברור באילו קבצים מותר לגעת. (ה) אין Verification: לא הוגדרה שום בדיקה. (ו) אין Out of Scope: הכלי עלול "לשפר" גם את מה שעובד.

חלק 2: ניסוח מקצועי אפשרי.

## Context
TaskFlow backend: FastAPI + SQLite. Routes in
backend/app/routers/tasks.py, DB access in backend/app/database.py.
Measured baseline: GET /tasks with 10,000 tasks takes ~900ms.

## Objective
GET /tasks responds in under 250ms with 10,000 tasks.

## Scope
backend/app only. Tests may be added under backend/tests.

## Constraints
No new dependencies. Keep SQLite. Keep the response shape
identical. Propose options with trade-offs before implementing.

## Acceptance Criteria
- Measurement script shows p95 under 250ms with 10,000 tasks.
- All existing tests in backend/tests still pass.

## Verification
Run the measurement script before and after, run pytest -q,
and show both outputs.

## Out of Scope
Code style cleanups, the frontend, and any API changes.

## Required Output
Bottleneck analysis, chosen option and why, the diff, and the
before/after numbers.

שימו לב ששאלת "ניקוי הקוד" לא נעלמה: היא פשוט תנוסח כמשימת Refactoring נפרדת (סעיף 5 בספריית התבניות), שתרוץ אחרי שמשימת הביצועים הושלמה ואומתה, רצוי אחרי /clear.

סיכום

  • Claude Code בנוי לשיחה איטרטיבית, אבל דיוק מראש חוסך סיבובי תיקון ושומר על Context נקי. אחרי שני תיקונים כושלים: /clear והנחיה טובה יותר.
  • מבנה מומלץ למשימות משמעותיות: Context, Objective, Scope, Constraints, Acceptance Criteria, Verification, Out of Scope, Required Output.
  • הרכיבים החזקים ביותר הם קריטריוני הצלחה ודרך אימות: בדיקה שהכלי יכול להריץ בעצמו סוגרת את הלולאה בלי שתהפכו למנגנון הבקרה היחיד.
  • לכל סוג משימה יש תבנית: מהסבר Codebase ומחקר, דרך Bug, Refactoring ו-Tests, ועד Security, Performance, Migration ושדרוג Dependencies. התאימו את התבניות לפרויקט שלכם.
  • הנחיה חוזרת הופכת ל-Skill; פעולה על הכלי עצמו היא פקודת /; כלל שחייב לחול תמיד שייך ל-Hook או ל-Permissions, לא ל-Prompt.
  • בפרק הבא ניישם את כל זה על משימת הבנה: קריאת Repository שלם ומיפוי הארכיטקטורה שלו.
