Memory ו-Project Knowledge

כל Session של Claude Code מתחיל עם Context Window ריק. מה שגורם ל-Claude "לזכור" את הפרויקט שלכם הוא מערך שלם של שכבות ידע: CLAUDE.md שאתם אוצרים ביד, Auto Memory ש-Claude כותב לעצמו, הקשר זמני של השיחה, Skills, Rules ותיעוד חיצוני. בפרק הזה נמפה את השכבות במדויק, נלמד להחליט איפה כל פיסת ידע צריכה לגור, נטפל בזיכרון מיושן וסותר, ונבצע Knowledge Audit מלא על פרויקט הדוגמה TaskFlow.

איזו בעיה שכבות הידע פותרות

מודל שפה לא זוכר שיחות קודמות. כשאתם סוגרים Session ופותחים חדש, כל מה ש-Claude "למד" על הפרויקט, ההעדפות שלכם, הפקודות שרצות אצלכם, הסיבה שהבדיקה ההיא נופלת, נעלם. בלי מנגנון זיכרון הייתם חוזרים על אותם הסברים בכל בוקר: "אנחנו משתמשים ב-pnpm, לא ב-npm", "הבדיקות דורשות Redis מקומי", "אל תיגע בתיקיית legacy/".

התיעוד הרשמי מגדיר שני מנגנונים שמעבירים ידע בין Sessions: קובצי CLAUDE.md, הוראות שאתם כותבים, ו-Auto Memory, הערות ש-Claude כותב לעצמו על סמך התיקונים וההעדפות שלכם. סביבם קיימות עוד שכבות שמזינות את Claude בידע בזמנים שונים: Rules, Skills, תיעוד בתוך ה-Repository, וההקשר הרגעי של השיחה עצמה. הבעיה המעשית של רוב הצוותים היא לא "אין זיכרון" אלא "הידע נמצא בשכבה הלא נכונה": הוראות קבועות שחיות רק בשיחה ונעלמות, או ערימת פרטים חד-פעמיים שתוקעת את ה-CLAUDE.md ושורפת Context בכל Session.

נקודה קריטית להבנה

גם CLAUDE.md וגם Auto Memory הם הקשר (Context), לא אכיפה. Claude קורא אותם ומשתדל לפעול לפיהם, אבל אין ערובה לציות מוחלט. כדי לחסום פעולה באופן מוחלט, בלי תלות בהחלטה של Claude, משתמשים ב-PreToolUse Hook (פרק 22) או בחוקי Permissions (פרק 17). זו הבחנה מתועדת ומרכזית לכל הפרק הזה.

לפני שנצלול לכל שכבה, הנה המפה המלאה. שימו לב לעמודה "מתי נטען": היא ההבדל המהותי בין השכבות, כי כל מה שנטען בפתיחת ה-Session עולה לכם ב-Tokens בכל שיחה.

CLAUDE.md: הידע שאתם אוצרים

את CLAUDE.md הכרנו לעומק בפרק 15, ולכן כאן רק תזכורת ממוקדת של מה שחשוב להשוואה מול שאר השכבות:

  • אצירה ידנית: אתם כותבים אותו, ואתם אחראים לתוכנו. Claude לא משנה אותו אלא אם ביקשתם במפורש ("add this to CLAUDE.md").
  • נטען במלואו בפתיחה: קובצי CLAUDE.md ו-CLAUDE.local.md בתיקיית העבודה ובתיקיות שמעליה נטענים במלואם בהפעלה, בלי מגבלת אורך, אם כי התיעוד ממליץ להישאר מתחת ל-200 שורות לקובץ כי קבצים ארוכים מקטינים ציות. קבצים בתת-תיקיות נטענים לפי דרישה, כש-Claude קורא קבצים באותן תיקיות.
  • ארבע רמות: מדיניות ארגונית מנוהלת (Managed Policy), משתמש (~/.claude/CLAUDE.md), פרויקט (./CLAUDE.md או ./.claude/CLAUDE.md), ומקומי אישי (./CLAUDE.local.md שמוסיפים ל-.gitignore).
  • מיועד ל: עובדות והוראות ש-Claude צריך להחזיק בכל Session: פקודות Build ובדיקות, קונבנציות, מבנה הפרויקט, כללי "תמיד עשה X".

Auto Memory: הידע ש-Claude כותב לעצמו

Auto Memory הוא המנגנון שבו Claude צובר ידע בין Sessions בלי שתכתבו דבר. תוך כדי עבודה Claude שומר לעצמו הערות: פקודות Build, תובנות Debugging, הערות ארכיטקטורה, העדפות סגנון קוד והרגלי Workflow. התיעוד מדגיש ש-Claude לא שומר משהו בכל Session; הוא מחליט מה שווה לזכור לפי השאלה האם המידע יהיה שימושי בשיחה עתידית. המנגנון פעיל כברירת מחדל.

איפה זה נשמר

לכל פרויקט יש תיקיית זיכרון משלו:

~/.claude/projects/<project>/memory/
~/.claude/projects/<project>/memory/
├── MEMORY.md          # אינדקס תמציתי, נטען לכל Session
├── debugging.md       # קובץ נושא: הערות Debugging מפורטות
├── api-conventions.md # קובץ נושא: החלטות עיצוב API
└── ...                # כל קובץ נושא אחר ש-Claude יוצר

הנתיב <project> נגזר מה-Git Repository: כל ה-Worktrees ותת-התיקיות של אותו Repository חולקים תיקיית זיכרון אחת. מחוץ ל-Repository, שורש הפרויקט משמש במקום. חשוב: Auto Memory הוא מקומי למכונה. הקבצים לא משותפים בין מחשבים או סביבות ענן, ולכן הוא לעולם לא יכול לשמש כמקור ידע צוותי. אפשר לשנות את מיקום האחסון עם ההגדרה autoMemoryDirectory ב-settings.json (הערך חייב להיות נתיב מוחלט או להתחיל ב-~/).

מה נטען ומתי: מגבלות ה-MEMORY.md

המכניקה מדויקת ושווה לדעת אותה בעל פה:

  • בפתיחת כל שיחה נטענות 200 השורות הראשונות של MEMORY.md, או 25KB הראשונים, המוקדם מביניהם. תוכן מעבר לסף לא נטען בפתיחה.
  • קובצי נושא כמו debugging.md לא נטענים בפתיחה. Claude קורא אותם לפי דרישה, עם כלי הקבצים הרגילים שלו, כשהוא צריך את המידע. MEMORY.md מתפקד כאינדקס שמכוון אותו לקובץ הנכון.
  • שמירה על תמציתיות: אחרי ש-Claude כותב ל-MEMORY.md, Claude Code מודד את הקובץ מול המגבלות. אם הוא קרוב לסף, Claude מקבל תזכורת לקצר: שורה אחת לרשומה, פירוט לקובצי נושא, מיזוג ומחיקה של רשומות מיושנות. אם הקובץ עבר את הסף, הכתיבה מצליחה אבל Claude מקבל שגיאה שמורה לו לכתוב את האינדקס מחדש, כי כל מה שמעבר לסף יאבד בטעינה הבאה. YAML Frontmatter והערות HTML לא נספרות במדידה.
  • המגבלה חלה רק על MEMORY.md. קובצי CLAUDE.md נטענים במלואם ללא קשר לאורכם.
  • Subagents: ה-Auto Memory של השיחה הראשית לא נטען ל-Subagents (למעט Fork שיורש את שיחת ההורה). Subagent יכול לנהל Auto Memory נפרד משלו דרך שדה memory בהגדרתו.

מה נכתב לשם ואיך זה נראה

כשאתם רואים בממשק הודעות כמו "Saved 2 memories" או "Recalled 2 memories", Claude מעדכן או קורא קבצים בתיקיית הזיכרון. כשאתם מבקשים מ-Claude לזכור משהו במפורש, למשל remember that the API tests require a local Redis instance, הוא שומר את זה ל-Auto Memory. אם אתם רוצים שההוראה תגיע דווקא ל-CLAUDE.md, בקשו זאת במפורש: add this to CLAUDE.md.

תוספת שימושית לניהול טריות המידע: כש-Claude כותב קובץ זיכרון שמתחיל ב-YAML Frontmatter, Claude Code מתעד את זמן הכתיבה בשדה modified כחותמת זמן בתקן ISO 8601 (דורש גרסה 2.1.214 ומעלה). החותמת מראה, גם לכם וגם ל-Claude, עד כמה העובדה עדכנית. Claude Code לעולם לא מוסיף Frontmatter לקובץ שאין לו.

Best Practice

קובצי ה-Auto Memory הם Markdown רגיל. מותר ואף רצוי לערוך ולמחוק אותם ידנית. אין שם קסם: מה שכתוב בקבצים הוא בדיוק מה ש-Claude יקרא.

Session Context: הידע שנעלם

כל מה שנאמר בשיחה עצמה, הוראות שנתתם, קבצים ש-Claude קרא, פלט של פקודות, הוא הקשר זמני (Ephemeral). הוא קיים רק בתוך ה-Session: אחרי /clear או פתיחת Session חדש הוא איננו (השיחה הישנה נגישה דרך /resume, אבל היא לא מזינה שיחות אחרות). גם Compaction מסנן אותו: אחרי /compact, קובץ ה-CLAUDE.md שבשורש הפרויקט נקרא מחדש מהדיסק ומוזרק חזרה לשיחה, אבל הוראה שניתנה רק בשיחה עלולה ללכת לאיבוד בסיכום. המסקנה המתועדת: אם הוראה חשובה "נעלמה" אחרי Compaction, סימן שהיא חיה בשכבה הלא נכונה. הוסיפו אותה ל-CLAUDE.md כדי שתתמיד.

הכלל המעשי: Session Context הוא המקום הנכון לידע שתקף לשיחה אחת בלבד. "בשיחה הזאת נעבוד רק על ה-Frontend", "תתעלם כרגע מהבדיקות הנופלות של המודול הישן". ברגע שאתם מקלידים את אותה הוראה בפעם השנייה ב-Session אחר, היא כבר לא שייכת לשכבה הזאת.

Skills, Rules ותיעוד חיצוני

Skills: נהלים לפי דרישה

Skill הוא נוהל ארוז: קובץ הוראות למשימה ספציפית שנטען רק כשמפעילים אותו או כש-Claude מזהה שהוא רלוונטי ל-Prompt. התיעוד של Memory מפנה אליהם במפורש: אם רשומה ב-CLAUDE.md היא נוהל רב-שלבי, או רלוונטית רק לחלק מה-Codebase, עדיף להעביר אותה ל-Skill או ל-Rule תחום-נתיב. היתרון: אפס עלות Context בכל שאר ה-Sessions. נוהל שחרור גרסה, תבנית מיגרציה של Database, תהליך יצירת רכיב חדש, כל אלה Skills קלאסיים. פירוט מלא בפרק 21.

Rules: הוראות מודולריות ותחומות-נתיב

תיקיית .claude/rules/ מפצלת את הוראות הפרויקט לקבצים ממוקדי-נושא (testing.md, api-design.md). קובץ Rule בלי שדה paths נטען בפתיחה, באותה עדיפות כמו .claude/CLAUDE.md; קובץ עם Frontmatter של paths נטען רק כש-Claude עובד עם קבצים תואמי-תבנית, מה שחוסך Context ומצמצם רעש. קיימת גם רמת משתמש: ~/.claude/rules/, שנטענת לפני חוקי הפרויקט (כך שלחוקי הפרויקט עדיפות). הרחבה ותחביר מלא בפרק 15.

תיעוד חיצוני: docs/ בתוך ה-Repository

תיעוד מפורט, מסמכי ארכיטקטורה, ADRs (רשומות החלטה ארכיטקטוניות), מדריכי Onboarding, שייך לתיקיית docs/ רגילה ב-Repository, לא לשכבות הזיכרון. Claude יכול לקרוא אותו בכל רגע, בדיוק כמו כל קובץ אחר בפרויקט. שתי דרכים לחבר אותו:

  • הפניה לפי דרישה (המומלץ לרוב): שורה אחת ב-CLAUDE.md בסגנון "לפני שינוי סכמת ה-Database, קרא את docs/adr/". שימו לב לעטוף נתיב כזה ב-Backticks אם אתם לא רוצים ייבוא: כתיבת @docs/file.md מחוץ ל-Backticks בתוך CLAUDE.md מייבאת את הקובץ ומטעינה אותו בכל פתיחה.
  • ייבוא מלא עם @path: מתאים רק לקבצים קצרים שבאמת דרושים בכל Session, כי קבצים מיובאים נטענים בפתיחה ונספרים ב-Context (עומק ייבוא מקסימלי: ארבעה דילוגים).

מתי להפנות את Claude לתיעוד באופן יזום? כשאתם פותחים משימה שנשענת על החלטה מתועדת: read docs/architecture.md before you plan this change. זה זול, מדויק, ולא מלכלך את שכבות הזיכרון הקבועות.

מניעת זיכרון מיושן וסותר

שכבות זיכרון הן נכס שמתכלה. פקודת Build שהשתנתה, קונבנציה שנזנחה, או תובנת Debugging שכבר לא נכונה, כל אלה הופכים מהר מ"ידע" ל"רעש שמטעה את Claude בכל שיחה". התיעוד הרשמי מתייחס לזה ישירות בהקשר של עקביות: אם שני כללים סותרים זה את זה, Claude עלול לבחור אחד מהם באופן שרירותי, וההמלצה היא לסקור תקופתית את קובצי ה-CLAUDE.md, קבצים מקוננים בתת-תיקיות, ואת .claude/rules/ כדי להסיר הוראות מיושנות או סותרות.

סתירות בין CLAUDE.md ל-MEMORY.md: מה מתועד ומה פרקטיקה

נפריד בקפידה בין מה שהתיעוד קובע ובין הנחיות פרקטיות:

מה שמתועד: שתי המערכות נטענות בפתיחת כל שיחה, ושתיהן הקשר ולא תצורה נאכפת. אין בתיעוד הרשמי כלל הכרעה שקובע ש-CLAUDE.md "גובר" על MEMORY.md או להפך. לגבי הוראות סותרות בין קובצי CLAUDE.md עצמם, התיעוד קובע במפורש ש-Claude עלול לבחור אחת מהן באופן שרירותי. סביר להניח שאותה התנהגות חלה גם על סתירה בין CLAUDE.md ל-Auto Memory, אבל זו הסקה שלנו, לא ציטוט.

הנחיה פרקטית (לא כלל מתועד): התייחסו ל-CLAUDE.md כמקור האמת האצור, ול-Auto Memory כטיוטה של Claude. כשמתגלה סתירה, אל תסמכו על "מי ינצח": מחקו או תקנו את הרשומה השגויה בו במקום. אם הכלל הנכון עדיין לא כתוב ב-CLAUDE.md, זה הרגע להוסיף אותו לשם, ואז למחוק את הגרסה הסותרת מהזיכרון האוטומטי.

איך מזהים סתירה בפועל:

  • הסימפטום הקלאסי: Claude מתנהג לא עקבי, פעם לפי הכלל ופעם נגדו, בין Sessions שונים.
  • הריצו /memory, פתחו את תיקיית ה-Auto Memory, וקראו את MEMORY.md ואת קובצי הנושא מול ה-CLAUDE.md. זו קריאה של דקות בודדות.
  • הריצו /context כדי לראות אילו קובצי זיכרון בכלל נטענו ל-Session; אי אפשר לאתר סתירה בקובץ שלא ידעתם שנטען.
  • למתקדמים: ה-Hook מסוג InstructionsLoaded מתעד בדיוק אילו קובצי הוראות נטענו, מתי ולמה (שימושי במיוחד ל-Rules תחומי-נתיב שנטענים באיחור).

שגרת סקירה וגיזום

הנחיה פרקטית שעובדת היטב בצוותים (התיעוד ממליץ על סקירה תקופתית אך לא קובע תדירות):

  • שבועי, 5 דקות, אישי: /memory, מעבר על MEMORY.md. מוחקים רשומות שכבר לא נכונות, ממזגים כפילויות. שדה ה-modified עוזר לזהות רשומות ותיקות שראוי לבדוק.
  • בכל Pull Request שנוגע בתשתית: אם שיניתם פקודת Build, מבנה תיקיות או קונבנציה, עדכנו את CLAUDE.md באותו Commit. כלל "התיעוד זז עם הקוד" חל גם על זיכרון.
  • חודשי, צוותי: קריאת CLAUDE.md ו-.claude/rules/ מלמעלה למטה. כל שורה שאף אחד לא זוכר למה היא שם, נבדקת או נמחקת.
  • עזרה אוטומטית: בדיקת ה-/doctor יודעת להציע קיצוצים ל-CLAUDE.md שנמצא ב-Version Control: היא מציעה לחתוך תוכן ש-Claude יכול לגזור בעצמו מה-Codebase (מבני תיקיות, רשימות תלויות, סקירות ארכיטקטורה) ולשמור דווקא מלכודות, נימוקים וקונבנציות שסוטות מברירות המחדל. היא מדווחת קודם ומבקשת אישור לפני כל שינוי.
אזהרה: זיכרון מזוהם עדיף למחוק, לא "לאזן"

אל תוסיפו ל-CLAUDE.md הוראה חדשה שנועדה "לבטל" רשומת זיכרון ישנה ("ignore what memory says about X"). כך נוצרות שתי הוראות סותרות במקום אפס. מחקו את הרשומה השגויה במקור.

ניהול ידע צוותי מבוקר

ברגע שיותר ממפתח אחד עובד עם Claude Code על אותו Repository, שכבות הידע הופכות לנכס צוותי שדורש ממשל, בדיוק כמו קוד:

  • CLAUDE.md של הפרויקט עובר Code Review. הקובץ יושב ב-Git, ולכן כל שינוי בו צריך לעבור באותו מסלול כמו קוד: Branch, Pull Request, סקירה. שינוי ב-CLAUDE.md משנה את ההתנהגות של Claude אצל כל חברי הצוות, ולכן הוא ראוי לאותה רמת ביקורת. צוותים רבים מגדירים Code Owner לקובץ.
  • גבול אישי / משותף חד וברור. משותף דרך Git: ./CLAUDE.md (או ./.claude/CLAUDE.md) ו-.claude/rules/. אישי בלבד: ~/.claude/CLAUDE.md (כל הפרויקטים שלכם), CLAUDE.local.md (הפרויקט הזה, ב-.gitignore), ו-Auto Memory (תמיד מקומי למכונה). העדפות אישיות שמחלחלות לקובץ הצוותי הן Anti-pattern שמזהים בקלות ב-Review.

  • ב-Monorepo: ההגדרה claudeMdExcludes (רשימת תבניות Glob בכל רמת הגדרות) מאפשרת לדלג על קובצי CLAUDE.md של צוותים אחרים שאינם רלוונטיים לעבודתכם.

Best Practices ו-Anti-patterns

Best Practices
  • כתבו הוראות ספציפיות שאפשר לאמת: "השתמש בהזחה של 2 רווחים" ולא "פרמט את הקוד יפה".
  • שמרו על CLAUDE.md מתחת ל-200 שורות; העבירו פירוט ל-Rules תחומי-נתיב ולקובצי docs/.
  • הוסיפו ל-CLAUDE.md כשאתם מתקנים את Claude על אותו דבר בפעם השנייה. תיקון חוזר הוא האיתות המתועד לכתיבה.
  • קדמו ידע במעלה השרשרת: מ-Session ל-Auto Memory, מ-Auto Memory ל-CLAUDE.md צוותי, דרך Pull Request.
  • השתמשו בהערות HTML (<!-- -->) ב-CLAUDE.md להערות תחזוקה לבני אדם: הן מוסרות לפני ההזרקה ל-Context ולא עולות Tokens.
Anti-patterns
  • שימוש ב-CLAUDE.md כמנגנון אבטחה ("never read secrets"). זו הנחיה, לא אכיפה; לאכיפה יש Permissions ו-Hooks.
  • הדבקת מבנה התיקיות המלא ורשימות תלויות ל-CLAUDE.md. Claude גוזר את אלה מהקוד בעצמו, ו-/doctor אף מציע לחתוך אותם.
  • הוראות "מאזנות" במקום מחיקת הרשומה הסותרת.
  • הסתמכות על Auto Memory כידע צוותי. הוא מקומי למכונה, נקודה.
  • ייבוא @docs/... של מסמכים ארוכים "ליתר ביטחון": קבצים מיובאים נטענים בכל פתיחה ומשלמים Context מלא.

תרגיל

תרגיל 16.1: ביקורת ידע על פרויקט אמיתי

בחרו פרויקט שאתם עובדים עליו עם Claude Code לפחות שבוע, ובצעו:

  1. הריצו /memory, פתחו את תיקיית ה-Auto Memory וקראו את MEMORY.md ואת קובצי הנושא. סמנו: אילו רשומות עדיין נכונות? אילו מיושנות? האם משהו סותר את ה-CLAUDE.md?
  2. מחקו או תקנו לפחות רשומה בעייתית אחת (עריכה ידנית של הקובץ).
  3. מצאו ב-CLAUDE.md פריט אחד שלא שייך לשם לפי טבלת ההחלטה (נוהל רב-שלבי, פירוט תחום-נתיב, או העדפה אישית) והעבירו אותו לשכבה הנכונה.
  4. בקשו מ-Claude בתוך Session: remember that ... עם תובנה אמיתית אחת מהפרויקט, וודאו שהופיעה הודעת Saved memory.
  5. פתחו Session חדש והריצו /context: ודאו שכל קובצי הזיכרון שציפיתם להם אכן נטענו, ושהתובנה מהסעיף הקודם זמינה (שאלו את Claude עליה).
פתרון מוסבר

(1) הממצא הנפוץ ביותר בסקירה ראשונה הוא רשומות Debugging שהיו נכונות לשבוע מסוים ("the build fails because of X") ומזמן נפתרו; אלה מועמדות ראשונות למחיקה, ושדה modified בקובצי הזיכרון עוזר לתארך אותן. (2) עריכה ידנית לגיטימית לחלוטין: אלה קובצי Markdown רגילים. (3) המועמדים הקלאסיים להעברה: נוהל שחרור (ל-Skill), כללי סגנון של תת-מערכת אחת (ל-.claude/rules/ עם paths), והעדפות אישיות (ל-~/.claude/CLAUDE.md או CLAUDE.local.md). (4) הבקשה המפורשת remember מנותבת ל-Auto Memory; אם רציתם שההוראה תגיע ל-CLAUDE.md, הניסוח הוא add this to CLAUDE.md. (5) ב-/context בודקים את הרשימה תחת Memory files; אם קובץ חסר שם, Claude פשוט לא רואה אותו, וזה הכלי הראשון לכל Troubleshooting של זיכרון. שאלה כמו what do you remember about this project's flaky tests? אמורה לגרום ל-Claude לאחזר את הרשומה (לעיתים עם הודעת Recalled memories).

סיכום

מיפינו את שכבות הידע של Claude Code ואת ההבדלים המדויקים ביניהן: CLAUDE.md אצור ידנית ונטען במלואו בכל פתיחה; Auto Memory נכתב על ידי Claude, שמור פר Repository תחת ~/.claude/projects/<project>/memory/, נטען חלקית (200 שורות או 25KB מ-MEMORY.md) עם קובצי נושא לפי דרישה, ונשלט דרך /memory, ההגדרה autoMemoryEnabled או משתנה הסביבה; Session Context זמני ונעלם; Rules ו-Skills טוענים הוראות בצורה ממוקדת וחסכונית; ותיעוד ב-docs/ נקרא לפי דרישה. למדנו להכריע איפה כל פיסת ידע גרה, לתחזק זיכרון נקי מסתירות בעזרת /memory, /context ו-/doctor, ולנהל ידע צוותי דרך Git עם גבול חד בין אישי למשותף. בפרק הבא נעבור לשכבת התצורה הפורמלית: קובצי Settings, Permissions והגדרות מודל.
