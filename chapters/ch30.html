Cost, Tokens ו-Performance

Claude Code הוא כלי שצורך Tokens, וכל Token עולה כסף או שימוש מהמכסה. בפרק הזה נבין איך החיוב באמת עובד: מה ההבדל בין מנוי ל-API, מה בדיוק נספר, איך Session מתמלא, איך Prompt Caching חוסך פי עשרה על ההיסטוריה, למה Session ארוך מתייקר, ואילו כלים מובנים (/usage, /context, /insights) מודדים את זה. נסיים ברשימת בדיקה לאופטימיזציה, בכל מחירי המודלים נכון להיום עם תאריך ומקור, ובחישוב מלא של חודש עבודה בשתי דרכי החיוב.

כל המחירים בפרק: נקודת זמן, לא הבטחה

כל המספרים בפרק נבדקו מול המקורות הרשמיים בתאריך 29.07.2026 ועשויים להשתנות בכל רגע; עמוד התמחור עצמו מציין שהמחירים כפופים לשינוי לפי שיקול דעת Anthropic. שימו לב במיוחד: מחיר ההיכרות של Sonnet 5 (2/10 דולר למיליון Tokens) בתוקף עד 31.08.2026 בלבד, ואחריו המחיר הסטנדרטי 3/15 דולר. בדקו תמיד את עמוד התמחור הרשמי לפני החלטות תקציב.

איך החיוב עובד: מנוי מול API

יש שתי דרכים לשלם על Claude Code, והן מתנהגות שונה לגמרי:

  • מנוי (Pro, Max, Team, Enterprise): מחיר חודשי קבוע, והשימוש נמדד מול מגבלות מכסה: חלון מתגלגל של חמש שעות וחלון שבועי, משותפים לכל המודלים ולשימוש ב-Claude Chat וב-Cowork. אין חיוב פר Token; כשמגיעים לתקרה, מחכים לאיפוס או ממשיכים בתשלום דרך Usage Credits.
  • API (Claude Console, או ספקי ענן): תשלום לפי צריכה בפועל, פר Token, לפי מחירון המודל. אין תקרה מובנית חוץ ממה שתגדירו בעצמכם.

ההשלכה המעשית: במנוי, אופטימיזציה של Tokens קונה לכם יותר עבודה לפני שנתקלים בתקרה; ב-API היא קונה חשבון נמוך יותר. הטכניקות זהות, המוטיבציה שונה. מי בצוות נמדד איך? לפי שיטת ההתחברות בפועל של כל מפתח (ראו פרק 29).

מה קורה בתור אחד

כדי להבין את הטבלה הבאה, צריך לזכור איך Claude Code עובד מאחורי הקלעים (פרק 14): המודל לא זוכר כלום בין בקשות, ולכן כל תור שולח מחדש את כל ההקשר: System Prompt, קובצי CLAUDE.md, כל השיחה עד כה, כל תוצאות הכלים, וההודעה החדשה. יתרה מזאת, תור אחד שלכם הוא בדרך כלל כמה בקשות API: Claude קורא קובץ, מקבל את תוכנו כתוצאת כלי, שולח בקשה נוספת שכוללת גם אותה, מריץ פקודה, וחוזר חלילה עד לתשובה. לכן קריאת קובץ של 2,000 שורות אינה עלות חד-פעמית: היא מצטרפת להקשר ותיסחב בכל בקשה עד סוף ה-Session. זה המפתח להבנת כל השאר בפרק.

אנטומיית ה-Tokens של Session

הפקודה /context (שהכרנו בפרק 14) מציגה בכל רגע פירוט חי של חלון ה-Context לפי קטגוריות, כולל אילו קובצי CLAUDE.md ו-Auto Memory נטענו והצעות אופטימיזציה. מה יש שם עוד לפני שהקלדתם מילה? לפי התיעוד הרשמי של חלון ה-Context, אלה השכבות שנטענות אוטומטית בפתיחת Session:

  • System Prompt: הוראות הליבה והגדרות הכלים המובנים. אתם לא רואים אותו, אבל הוא שם בכל בקשה.
  • Auto Memory: ההערות ש-Claude שמר לעצמו מ-Sessions קודמים (פרק 16).
  • פרטי סביבה: תיקיית עבודה, מערכת הפעלה, מצב Git.
  • שמות כלי MCP: כברירת מחדל נטענים רק השמות (Deferred), וסכימות מלאות נטענות לפי דרישה.
  • תיאורי Skills: שורת תיאור לכל Skill זמין; הגוף המלא נטען רק בהפעלה.
  • CLAUDE.md: הגלובלי (~/.claude/CLAUDE.md) ושל הפרויקט.

מרגע שהעבודה מתחילה, ה-Context מתמלא בעיקר מקריאות קבצים, פלטי פקודות ותשובות. חוקים עם paths: ו-CLAUDE.md מקוננים מצטרפים רק כש-Claude נוגע בקבצים תואמים. המספר שרואים ב-/context הוא בדיוק מה שיישלח שוב בבקשה הבאה, ולכן הוא המדד החשוב ביותר לעלות של "עוד שאלה אחת" ב-Session הזה: לפי התיעוד, גם שאלה של שורה אחת ב-Session שפתוח כל היום גוררת את קריאת ההיסטוריה המלאה, במחיר ה-Cache לפחות.

$ /context # פירוט לפי קטגוריות: System, Tools, MCP, Memory, Skills, Messages + הצעות ייעול

Prompt Caching: החיסכון הגדול

בלי Caching, כל תור היה מעבד מחדש את כל ההיסטוריה במחיר מלא. בפועל, Claude Code מנהל Prompt Caching אוטומטית: ה-API מזהה שתחילת הבקשה (ה-Prefix) זהה לבקשה הקודמת, קורא אותה מה-Cache, ומעבד במלואו רק את מה שהתחדש.

מה זה שווה בכסף

לפי מחירון ה-API הרשמי (נבדק 29.07.2026), פעולות ה-Cache מתומחרות כמכפילים של מחיר ה-Input הבסיסי:

פעולהמכפילמשמעות
כתיבה ל-Cache עם תוקף 5 דקות1.25xמשתלם כבר אחרי קריאה אחת מה-Cache
כתיבה ל-Cache עם תוקף שעה2xמשתלם אחרי שתי קריאות; שורד הפסקות ארוכות
קריאה מה-Cache (Hit)0.1xההיסטוריה כולה נקראת בעשירית ממחיר Input רגיל

תוקף ה-Cache (TTL) מתאפס בכל קריאה, כך שכל עוד עובדים ברצף הוא נשאר חם. מי מקבל איזה TTL? לפי התיעוד: במנוי, Claude Code מבקש אוטומטית TTL של שעה, כך שה-Cache שורד הפסקת קפה ארוכה; ברגע שחורגים מהמכסה ועוברים ל-Usage Credits, הוא יורד אוטומטית לחמש דקות (אפשר להחזיר שעה עם ENABLE_PROMPT_CACHING_1H=1). במפתח API או ספק ענן, ברירת המחדל היא חמש הדקות הזולות, ואפשר להצטרף ל-TTL של שעה עם אותו משתנה. Subagents משתמשים תמיד ב-TTL של חמש דקות.

מה שובר את ה-Cache

ההתאמה היא לפי Prefix מדויק: שינוי בכל מקום בתחילת הבקשה מחשב מחדש את כל מה שאחריו. הפעולות שמתועדות כשוברות Cache, כלומר גוררות תור אחד איטי ויקר של בנייה מחדש:

  • החלפת מודל (/model): לכל מודל Cache משלו. גם opusplan, שמחליף מודל בכניסה וביציאה מ-Plan Mode, נחשב החלפה.
  • שינוי Effort Level (/effort): ה-Cache ממופתח גם לפי Effort; Claude Code מבקש אישור לפני שינוי ששובר Cache.
  • הדלקת Fast Mode באמצע שיחה ארוכה: הבקשה הבאה קוראת את כל ההיסטוריה בלי Cache, ובמחירי Fast Mode.
  • חיבור או ניתוק שרת MCP שכליו טעונים ב-Prefix (עם Tool Search וטעינה נדחית, ברירת המחדל, ה-Cache שורד).
  • חסימת כלי שלם בחוק deny (כמו Bash) באמצע Session: הגדרות הכלים יושבות ב-System Prompt.
  • Compaction: מחליף את ההיסטוריה בסיכום, ולכן בהגדרה בונה Prefix חדש (בהמשך).
  • שדרוג Claude Code: System Prompt חדש, Cache חדש. חידוש Session ישן אחרי שדרוג מעבד מחדש את כל ההיסטוריה.

לעומת זאת, פעולות שנשארות ידידותיות ל-Cache: עריכת קבצים, הפעלת Skills ופקודות, שינוי Permission Mode, /rewind (חוזר ל-Prefix שכבר קיים ב-Cache), ו-Subagents (לא נוגעים ב-Cache של ההורה). לכן ההמלצה המתועדת: קבעו מודל ו-Effort בתחילת ה-Session, ואל תשחקו איתם באמצע משימה.

איך יודעים שה-Caching עובד

עקבו אחרי שני מונים שה-API מחזיר בכל תשובה: cache_read_input_tokens (נקרא מה-Cache, זול) ו-cache_creation_input_tokens (נכתב ל-Cache). יחס קריאה/כתיבה גבוה = Caching בריא. אפשר להציג אותם ב-Statusline, וברמת ארגון דרך OpenTelemetry. אם הכתיבה נשארת גבוהה תור אחרי תור, משהו שובר לכם את ה-Prefix.

הכלכלה של Sessions ארוכים

Session שפתוח כל היום צורך הרבה יותר ממה שהפעילות בו מרמזת, מסיבות מתועדות: כל בקשה נושאת את כל ההיסטוריה (גם אם במחיר Cache, עשירית על מיליון Tokens זה עדיין כסף); ההודעה הראשונה אחרי הפסקה ארוכה מה-TTL מחטיאה את ה-Cache ומעבדת הכול מחדש; ו-Compaction בעצמו קורא את כל מה שהוא מסכם, כך שדחיסת Context ענק היא בקשה גדולה בפני עצמה.

מכאן שני כללים פשוטים:

  • /clear כשעוברים לנושא אחר: לפי התיעוד, כשרוצים התחלה נקייה בלי המשכיות, /clear לא עולה כלום, בעוד /compact הוא בקשה גדולה. Context ישן ולא רלוונטי הוא מס על כל הודעה עתידית.
  • /compact בהפסקות טבעיות, לא באמצע משימה: כשה-Cache חם, העלות סבירה; הכי יקר לדחוס Session ישן שחודש אחרי הפסקה ארוכה. אפשר לכוון מה יישמר: /compact focus on the API changes, ולכוון את סף הדחיסה האוטומטית עם /autocompact.

ההבדל המלא בין השניים, כולל מה שורד דחיסה, נדון בפרק 14. בתוכניות המנוי, המסך של /usage אף מסמן התנהגויות שאחראיות ל-10% או יותר מהשימוש האחרון (כמו Long Context או Cache Misses) עם טיפ לצמצום.

בחירת Model, Effort ו-Fast Mode

בחירת המודל היא ההחלטה הכלכלית הגדולה ביותר (ההיכרות המלאה עם המודלים: פרק 8). ההמלצה המתועדת: Sonnet לרוב משימות הקוד, Opus לארכיטקטורה מורכבת ולחשיבה רב-שלבית, Haiku ל-Subagents פשוטים (model: haiku בהגדרת ה-Subagent).

  • Effort Levels (פרק 8): שליטה בכמה חשיבה המודל משקיע. הרמות הזמינות תלויות במודל (low/medium/high/xhigh/max במודלי 5, ברירת מחדל high). מכיוון ש-Thinking מחויב כ-Output, הורדת Effort במשימות פשוטות היא חיסכון ישיר; זכרו רק ששינוי באמצע Session שובר Cache.
  • Fast Mode Research Preview (/fast): מהירות עד פי 2.5 על Opus 5 ו-Opus 4.8, במחיר פרימיום של 10/50 דולר למיליון Tokens (מקור: עמוד התמחור הרשמי, נבדק 29.07.2026, כפוף לשינוי), לעומת 5/25 במחיר Opus רגיל. במנויים הוא זמין דרך Usage Credits בלבד ואינו נכלל במכסת המנוי. הדליקו אותו בתחילת Session, לא באמצע (שבירת Cache במחירי פרימיום).

מקביליות מכפילה עלות

כל טכניקת מקבול מפרק 25 ומפרק 29 מכפילה גם צריכה: לכל Subagent חלון Context משלו שמתחיל בלי Cache; /batch מריץ כמה יחידות עבודה במקביל; ו-Agent Teams, לפי התיעוד, צורכים בערך פי 7 מ-Session רגיל. ההמלצות המתועדות לריסון: צוותים קטנים, משימות ממוקדות וקצרות לכל חבר צוות, Sonnet ולא Opus לחברי צוות, וסגירת Agents שסיימו. היתרון הכלכלי של Subagent נשמר כשהוא מחליף קריאות ענק ב-Context הראשי: הפלט המפורט נשאר אצלו, ורק סיכום חוזר אליכם.

המספר של /usage אינו החשבון

העלות הדולרית ב-/usage מחושבת מקומית לפי מחירי מחירון מלאים, ולא משקפת הנחות או מחירי מבצע; החיוב הסמכותי הוא בעמוד ה-Usage של ה-Claude Console. למנויים, מספר העלות של ה-Session אינו רלוונטי לחיוב בכלל: מה שחשוב הוא פסי המכסה.

Spend Limits: לעצור לפני החשבון

  • ברמת ארגון API: Workspace Spend Limits ב-Claude Console על ה-Workspace הייעודי "Claude Code" שנוצר אוטומטית, ובנוסף Workspace Rate Limit שמגן על מכסות ה-API של שאר המערכות.
  • ברמת Team/Enterprise: הקצאת ה-Seat היא התקרה המובנית; Usage Credits עם Spend Limits ברמת ארגון, קבוצה או משתמש מאפשרים המשך מבוקר מעבר לה.
  • ברמת ריצה בודדת (Automation): הדגל --max-budget-usd קובע תקרת דולרים לריצת -p (מצב Print בלבד). הוצאות Subagents נספרות בתקרה, וכשמגיעים אליה, ניסיון להפעיל Subagent נוסף נכשל. לדוגמה: claude -p --max-budget-usd 5.00 "query". זה הכלי הנכון לסקריפטים ול-CI, שם אין אדם שרואה את המונה.

Performance: מהירות היא גם עלות

אותם גורמים שמייקרים Session גם מאיטים אותו. גורמי ה-Latency העיקריים, לפי מנגנוני התיעוד שראינו: גודל ה-Context (כל תור מעבד יותר), Cache Misses (התור הראשון אחרי הפסקה או שבירת Cache איטי משמעותית), עומק החשיבה (Effort גבוה חושב יותר), בחירת המודל (Haiku מהיר מ-Sonnet שמהיר מ-Opus; Fast Mode מאיץ את Opus עד פי 2.5 בתשלום), ומספר סבבי הכלים שהמשימה דורשת. דרך פשוטה לקבל תחושה: בלוק ה-Session של /usage מציג גם Total duration (API) לצד זמן הקיר; כשזמן ה-API תופח ביחס לעבודה שנעשתה, ה-Session שלכם סוחב משקל עודף.

המנוף המרכזי הוא היגיינת Context. ומכאן הפרקטיקות, כולן מגובות בעמוד ניהול העלויות הרשמי:

  • Prompts ספציפיים: "add input validation to the login function in auth.ts" במקום "improve this codebase". בקשה מעורפלת מפעילה סריקה רחבה; בקשה ממוקדת קוראת קבצים בודדים.
  • משימות קטנות ותחומות: קובץ אחד, בדיקה, ואז הלאה. Plan Mode לפני משימות גדולות מונע עבודה חוזרת יקרה בכיוון שגוי, ו-Esc מוקדם עוצר סטייה לפני שהיא מצטברת.
  • Skills במקום חקירה חוזרת: Skill שמתאר את הארכיטקטורה או את תהליך העבודה חוסך ל-Claude סבב קריאות שלם בכל פעם; העבירו הוראות ייעודיות מ-CLAUDE.md (שנטען תמיד) ל-Skills (שנטענים לפי דרישה) ושמרו על CLAUDE.md מתחת ל-200 שורות.
  • פלטים מסוכמים: Subagents לפעולות מרובות פלט, ו-Hooks שמסננים פלט לפני שהוא נכנס ל-Context (למשל להחזיר רק שורות שגיאה מקובץ Log של 10,000 שורות).
  • בדיקות ממוקדות: להריץ את קובץ הבדיקה הרלוונטי ולא את כל החבילה; פלט של חבילת בדיקות שלמה הוא אלפי Tokens שרובם "PASS".

ולצד כל אלה, טעות הפוכה ששווה סעיף: אופטימיזציית יתר. אם אתם על מנוי ורחוקים מהתקרות, שעה של כוונון Prompts כדי לחסוך אלפי Tokens שווה פחות מדקת עבודה שלכם. ההשקעה בהיגיינת Context מצדיקה את עצמה כשהיא הרגל זול (Prompt ממוקד, /clear בין משימות) או כשהמספרים מראים בעיה אמיתית (תקרות שנפגעות, חשבון שגדל). קודם מודדים, ורק אז מכווננים.

דוגמה מחושבת: חודש של מפתח יחיד, בשתי הדרכים

נחשב חודש עבודה של מפתחת יחידה על TaskFlow, פעם במסלול API ופעם במנוי. ההנחות שרירותיות ומפורשות בכוונה: הצריכה שלכם כמעט בוודאות שונה, וזו בדיוק הסיבה שמתחילים במדידה ולא בניחוש.

הנחות

  • 21 ימי עבודה בחודש; שלושה Sessions משמעותיים ביום עם היגיינת Context סבירה.
  • מודל: Sonnet 5 בלבד, במחיר ההיכרות (2/10 דולר ל-MTok, בתוקף עד 31.08.2026; מקור: עמוד התמחור, נבדק 29.07.2026).

מסלול B: מנוי

אותו פרופיל שימוש במנוי: Max (החל מ-100 דולר לחודש, מקור: claude.com/pricing, נבדק 29.07.2026) מכסה עבודה יומית רצינית במחיר קבוע, עם מגבלות חלון של חמש שעות ושבועיות במקום מונה דולרים. Pro (17-20 דולר) מתאים לשימוש קל ולא לעבודה יומיומית אינטנסיבית. ההשוואה במקרה שלנו: צריכת ה-API המחושבת (כ-100 דולר בחודש היום, כ-150 אחרי המבצע, ויותר אם הפרופיל כבד מההנחות) נמצאת בדיוק סביב מחיר ה-Max, כך שההכרעה תלויה בשוליים: מי שמריץ גם Subagents כבדים ו-Opus ירוויח מהמנוי הקבוע; מי שעובד במשרה חלקית עם Claude ירוויח מ-API לפי צריכה. Your mileage will vary: מדדו חודש אחד עם /usage ודוחות ה-Console לפני שמתחייבים.

עוד שיקול במעבר בין המסלולים

המסלולים נבדלים גם ב-TTL של ה-Cache (שעה במנוי, חמש דקות ב-API כברירת מחדל) וביכולות סביבן: Usage Credits ו-/usage-credits קיימים רק בהתחברות מנוי. תזכורת מפרק 29: בארגון, ההחלטה הזאת היא גם החלטת ממשל, לא רק מחיר.

שיקולי אבטחה: עלות היא גם משטח תקיפה

עלות לא מבוקרת היא בעיית אבטחה בפני עצמה (Denial of Wallet): הרצה אוטומטית שנתקעת בלולאה, Prompt Injection שגורם לסוכן לקרוא ולעבד קבצים ענקיים, או מפתח API שדלף ומשמש מישהו אחר. ההגנות חופפות לכללי החיסכון: תקרות מפורשות בכל הרצה לא-אינטראקטיבית (--max-turns, --max-budget-usd), Spend Limits ברמת ה-Workspace ב-Console, מפתחות API נפרדים ומצומצמים ל-CI שאפשר לבטל בלי לפגוע במפתחים (פרק 20, פרק 33), ומעקב אחרי /usage ו-Analytics כדי שקפיצה חריגה תתגלה ביום שבו קרתה ולא בחשבון החודשי. אם ראיתם שימוש שלא מוסבר על ידי העבודה שלכם, בטלו את המפתח קודם ותחקרו אחר כך.

תרגיל

תרגיל 30.1: מדידה ואופטימיזציה של Session אמיתי

פתחו את עותק ה-TaskFlow שלכם ובצעו:

  1. פתחו Session חדש, והריצו /context לפני כל פעולה. רשמו: כמה Tokens תופסות הקטגוריות הקבועות (System Prompt, כלים, CLAUDE.md, תיאורי Skills)?
  2. בקשו מ-Claude משימה מעורפלת בכוונה: "improve the backend". אחרי שהוא מסיים לחקור, הריצו /context ו-/usage ורשמו את הצריכה.
  3. הריצו /clear, ובקשו משימה מקבילה אבל ממוקדת: "add input validation for the title field in backend/app/routers/tasks.py, then run backend tests". מדדו שוב.
  4. השוו: כמה Tokens חסך ה-Prompt הממוקד? חשבו את ההפרש בדולרים לפי מחירי Sonnet 5 מהפרק (עם התאריך!).
  5. לסיום, נסחו שלושה שינויים קבועים (ב-CLAUDE.md, ב-Skills או בהרגלים) שהיו מקטינים את הצריכה בפרויקט הזה, והצדיקו כל אחד בנתון שמדדתם.
פתרון מוסבר

שלבים 1-2: ב-Session טרי על TaskFlow תראו בדרך כלל שהבסיס הקבוע (System Prompt, הגדרות כלים, CLAUDE.md, תיאורי Skills) תופס עשרות בודדות של אלפי Tokens עוד לפני שהקלדתם. הבקשה המעורפלת "improve the backend" גוררת סריקה רחבה: Claude קורא את רוב קבצי ה-Backend, ו-/context יראה שקטגוריית ההודעות (Messages) קפצה בעשרות אלפי Tokens. המספרים המדויקים משתנים בין הרצות; מה שחשוב הוא היחס.

שלבים 3-4: הבקשה הממוקדת קוראת בדרך כלל שניים-שלושה קבצים (ה-Router, המודל, קובץ הבדיקות) במקום את כל העץ. הפרש טיפוסי הוא עשרות אלפי Tokens של Input. לדוגמה, אם נחסכו 60K Tokens של קריאות חדשות: במחיר ההיכרות של Sonnet 5 (2 דולר ל-MTok Input, נבדק 29.07.2026) זה 0.12 דולר לפעולה אחת. נשמע זניח? זה בדיוק השיעור: החיסכון האמיתי אינו בפעולה הבודדת אלא בהצטברות. אותם 60K נגררים ב-Cache Reads בכל אחד מעשרות התורים הבאים של ה-Session, ומכפילים את עצמם על פני חודש שלם ועל פני צוות.

שלב 5, שינויים מוצדקים לדוגמה: (1) להוסיף ל-CLAUDE.md מפת "איפה מה נמצא" של שלוש שורות (Routers, Models, Tests), כי מדדתם ש-Claude מבזבז קריאות על ניווט; (2) Skill בשם "run-backend-tests" שמריץ רק את קובץ הבדיקות הרלוונטי עם פלט מקוצר, כי פלט ה-pytest המלא הופיע כצרכן גדול ב-/context; (3) הרגל צוותי של Prompt ממוקד עם נתיב קובץ, מגובה בהפרש שמדדתם בין שלב 2 לשלב 3. כל שינוי כזה נבחן שוב אחרי שבוע עם /usage: אופטימיזציה בלי מדידה חוזרת היא ניחוש.

סיכום

  • מנוי משלם על מכסה (חלונות של חמש שעות ושבועיים), API משלם פר Token; מה שנספר זהה: כל ה-Input כולל תוצאות כלים ו-MCP, כל ה-Output כולל Thinking, וכל Subagent עם ה-Context העצמאי שלו.
  • Prompt Caching הופך את רוב ההיסטוריה לעשירית מחיר: שמרו על ה-Prefix יציב (בלי החלפות מודל, Effort ו-Fast Mode באמצע משימה), והבינו את ה-TTL: שעה במנוי, חמש דקות ב-API וב-Usage Credits.
  • Session ארוך מתייקר מעצם אורכו; /clear חינם בין משימות, /compact ממוקד בהפסקות טבעיות.
