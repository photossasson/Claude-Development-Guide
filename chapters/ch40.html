Prompt Library

ספרייה אצורה של Prompts מוכנים להעתקה, מסודרים לפי שלב בעבודה: Onboarding ל-Repository, תכנון Feature, חקירת Bug, כתיבת בדיקות, Refactoring, סקירות אבטחה, ביצועים, Database, API ו-Frontend, תיעוד, Migration, סקירת Pull Request, ניתוח כשלי CI, Handoff ומוכנות לשחרור. כל Prompt מגיע עם מטרה, מתי להשתמש בו, למה לצפות, טיפ אימות והפניה לפרק המעמיק. כולם בנויים לפי המבנה שלמדנו ב-פרק 5: Context, Objective, Scope, Constraints, Acceptance Criteria, Verification ו-Out of Scope. הדוגמאות בסוגריים מסולסלים מוחלפות בערכים שלכם.

איך להשתמש בספרייה

ה-Prompts כאן הם נקודת פתיחה, לא נוסחה קסומה. הם עובדים כי הם מכניסים ל-Context של Claude את מה שהוא לא יכול לנחש: מה בדיוק צריך להיות נכון בסוף, מה מותר לגעת, מה אסור, ואיך הוא יכול לבדוק את עצמו. התיעוד הרשמי מנסח את זה כך: ככל שההוראה מדויקת יותר, כך פחות תיקונים תצטרכו; ותנו ל-Claude דרך לאמת את עבודתו, כי אחרת אתם לולאת האימות.

כל Prompt באנגלית (Claude מגיב היטב לעברית, אבל מונחי הקוד, שמות הקבצים והפקודות ממילא באנגלית, ואחידות שפה מפחיתה בלבול). ה-Placeholders כתובים כ-{name}. החליפו את כולם לפני שליחה; Placeholder שנשאר גורם ל-Claude לנחש או לשאול.

מרכיב בכל Promptלמה הוא שם
Contextקבצים, Stack, החלטות קודמות, לוגים. הפניה עם @path טוענת את הקובץ בפועל.
Objectiveמשפט אחד: מה צריך להיות נכון בסוף.
Scope / Out of scopeמה מותר ומה אסור לשנות. זה מה שמונע "שיפורים" לא מבוקשים.
Constraintsמדיניות תלויות, סגנון, "plan first", "small steps with diffs".
Acceptance criteriaטענות ניתנות לבדיקה. הרכיב שמשפר תוצאות יותר מכל אחר.
Verificationהפקודות המדויקות ומה נחשב הצלחה. סוגר את הלולאה בלעדיכם.
Required outputמה להחזיר: הסבר, Diff, פלט בדיקות, שאלות פתוחות. דרשו ראיות, לא הצהרות.
Best Practice

ל-Prompts ארוכים, הקלידו \ ואז Enter לשורה חדשה (בכל Terminal), או פתחו עורך חיצוני עם Ctrl+G. אפשר גם לשמור את ה-Prompt בקובץ ולשלוח cat prompt.md | claude להרצה לא-אינטראקטיבית (פרק 33).

להתאים Prompt לפרויקט שלכם

משתנים והקשר

שלוש שאלות לפני כל שליחה: (1) האם כל {placeholder} הוחלף בערך אמיתי? (2) האם הוספתי את הקבצים הרלוונטיים עם @ במקום לתאר אותם במילים? (3) האם קריטריון הקבלה שלי ניתן לבדיקה בפקודה, ולא רק "שיעבוד"? כשה-Prompt מפנה ל"פקודת הבדיקה של הפרויקט", העדיפו לכתוב את הפקודה במפורש (cd backend && pytest -q ב-TaskFlow) גם אם היא כבר ב-CLAUDE.md; כפילות קטנה עדיפה על ניחוש.

מה שייך ל-CLAUDE.md ולא ל-Prompt

אם אתם מוצאים את עצמכם מעתיקים את אותם משפטים לכל Prompt ("no ORM, parameterized SQL only", "TypeScript strict, no any", "tests pass and typecheck passes before done"), הם שייכים ל-CLAUDE.md (פרק 15). ה-Prompt צריך להכיל את מה שייחודי למשימה הזאת. התיעוד הרשמי מזהיר: CLAUDE.md ארוך מדי גורם ל-Claude להתעלם מחצי ממנו, ולכן גם שם, רק מה שמונע טעויות.

מתי Skill במקום Prompt

Prompt חוזר, עם צעדים קבועים, שיותר מאדם אחד בצוות צריך, הוא מועמד להפוך ל-Skill (פרק 21). היתרונות: הוא נטען לפי דרישה בלי לנפח את ה-Context, הוא מנוהל ב-Git, אפשר להעביר לו ארגומנטים ($ARGUMENTS), ואפשר לסמן disable-model-invocation: true לזרימות עם תופעות לוואי. חמישה מה-Prompts בפרק הזה כבר קיימים כ-Skills של המדריך: code-review, bug-investigation, feature-plan, test-generator ו-documentation-update. כלל אצבע: פעם אחת = Prompt; שלוש פעמים = Skill; "חייב לקרות תמיד" = Hook (פרק 22).

Repository onboarding

40.1 מפת Codebase

  • מטרה: תמונה ראשונה של Repository לא מוכר: ארכיטקטורה, תיקיות מפתח, איך החלקים מתחברים.
  • מתי: יום ראשון בפרויקט, או לפני שינוי באזור שלא נגעתם בו. עדיף ב-Plan Mode.
prompt
## Context
I am new to this repository. Stack: {stack}. Entry points I know of: {entry_points}.

## Objective
Give me an overview of this codebase: architecture, key directories, and how the pieces connect.

## Constraints
Read-only. Do not modify files. Prefer reading configuration, entry points and tests over guessing.

## Required output
1. A one-paragraph summary of what the system does.
2. A directory map with one line per top-level directory.
3. The main runtime flow (request in, response out) as numbered steps with file references.
4. Three things that surprised you or look risky.
5. The commands you found for build, test and run.
  • מה לצפות: סיכום מובנה עם הפניות לקבצים אמיתיים; ב-TaskFlow תראו את app/main.py, ה-Router, שכבת ה-SQLite ואת App.tsx.
  • טיפ אימות: בחרו טענה אחת (למשל "הסטטוסים נאכפים ב-CHECK constraint") ופתחו את הקובץ שהוא ציטט.
  • פרק קשור: פרק 6.

40.2 מעקב אחרי זרימה מקצה לקצה

  • מטרה: להבין מה קורה כשמשתמש מבצע פעולה, מה-UI ועד ה-Database.
  • מתי: לפני שינוי בזרימה קיימת או כשמצטרפים כמפתחי Frontend ל-Backend ולהפך.
prompt
I am a {role}. Walk me through what happens when a user {action}, from the UI down to the persisted result.
For each step name the file and function, the data shape passed along, and where validation happens.
End with: where would a bug most likely hide in this flow, and which test currently covers each step.
Read-only, do not change files.
  • מה לצפות: רצף ממוספר: App.tsx ← api.ts ← routers/tasks.py ← database.py, עם ציון בדיקות קיימות.
  • טיפ אימות: בקשו "show me the exact line where {value} is validated" ובדקו שהשורה קיימת.
  • פרק קשור: פרק 6.

40.3 ניתוח השפעה לפני מחיקה או שינוי

  • מטרה: לדעת מה יישבר אם תשנו או תמחקו רכיב.
  • מתי: לפני Refactoring, הסרת קוד מת או שינוי חתימה.
prompt
What would break if I {changed_or_deleted} {target}?
List every caller and every test that references it, grouped by directory.
Classify each as: must change / probably fine / unclear, and say why.
Do not make any changes yet.
  • מה לצפות: רשימת תלויות מסווגת. Claude ישתמש בחיפוש (Grep) ולא בזיכרון.
  • טיפ אימות: הריצו בעצמכם grep -rn "{target}" --include=*.py --include=*.ts . והשוו את המספר.
  • פרק קשור: פרק 6, פרק 12.

Feature planning

40.4 ראיון שמסתיים ב-SPEC.md

  • מטרה: לתת ל-Claude לחלץ מכם את הדרישות, כולל מקרי קצה שלא חשבתם עליהם, ולכתוב מפרט.
  • מתי: Feature גדול, לפני שנוגעים בקוד. אחרי המפרט, פתחו Session חדש ליישום.
prompt
I want to build {brief_description}. Interview me in detail using the AskUserQuestion tool.
Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs.
Don't ask obvious questions, dig into the hard parts I might not have considered.
Keep interviewing until we've covered everything, then write a complete spec to SPEC.md with:
files and interfaces involved, what is out of scope, and an end-to-end verification step.
  • מה לצפות: סבב שאלות (בדרך כלל 5 עד 12), ואז קובץ SPEC.md עם סעיף אימות.
  • טיפ אימות: קראו את סעיף Out of scope; אם הוא ריק, הראיון לא היה מספיק קשה.
  • פרק קשור: פרק 7, פרק 34.

40.5 תוכנית יישום ב-Plan Mode

  • מטרה: תוכנית מפורטת עם קבצים, סדר, סיכונים ובדיקות, לפני שורת קוד אחת.
  • מתי: כל שינוי שנוגע ביותר מקובץ אחד או באזור לא מוכר. הפעילו Shift+Tab עד plan mode, או claude --permission-mode plan.
prompt (plan mode)
## Context
Feature: {feature}. Spec: @SPEC.md. Relevant code: @{dir_or_files}.

## Objective
Produce an implementation plan I can approve before any code changes.

## Required output
1. Files to add or change, one line each, with the reason.
2. Order of work, smallest safe increments first, each ending in a runnable check.
3. Data model or interface changes, with the exact new types or schema.
4. Tests to write, by layer.
5. Risks and open questions. Do not implement.
  • מה לצפות: תוכנית שאפשר לערוך (Ctrl+G) ולאשר. אחרי האישור, יציאה מ-Plan Mode ויישום לפי הסדר.
  • טיפ אימות: ודאו שכל צעד בתוכנית מסתיים בבדיקה שאפשר להריץ; צעד בלי בדיקה הוא צעד שקשה לאשר.
  • פרק קשור: פרק 7.

40.6 פירוק Feature ל-PRs עצמאיים

  • מטרה: לחלק עבודה גדולה ליחידות שאפשר לסקור ולמזג בנפרד, ואם צריך, להקביל.
  • מתי: אחרי התוכנית, לפני שמחליטים על סוכן אחד או כמה.
prompt
Take the plan in @{plan_file} and split it into independent pull requests.
For each PR: title, files it owns, the shared contract it depends on (types, schema, endpoints),
its acceptance criteria, and the exact verification command.
Flag any two PRs that would touch the same file; propose how to remove the overlap.
Recommend a merge order. Do not implement.
  • מה לצפות: רשימת PRs עם מטריצת בעלות. זה הבסיס ל-פרק 38.
  • טיפ אימות: אם שני PRs חולקים קובץ, אל תמשיכו לפני שהחפיפה נפתרה.
  • פרק קשור: פרק 34, פרק 38.

Bug investigation

40.7 חקירת תסמין עד שורש הבעיה

  • מטרה: למצוא ולתקן את הסיבה, לא את התסמין, עם בדיקה שמשחזרת.
  • מתי: דיווח משתמש או תקלה שאתם יכולים לתאר, גם בלי לדעת איפה היא.
prompt
## Context
Users report that {symptom} when {conditions}. Likely area: @{suspect_dir}. Logs or error: {paste}.

## Objective
Find and fix the root cause.

## Constraints
First write a failing test that reproduces the issue, then fix, then run the full suite.
Do not modify existing tests. Do not suppress the error or add a workaround at the call site.
If you find more than one plausible cause, list them with evidence and ask before changing code.

## Verification
{test_command}, all tests pass including the new one.

## Required output
The root cause in two sentences, the diff, and the test output.
  • מה לצפות: בדיקה חדשה שנכשלת, תיקון ממוקד, פלט חבילה ירוק.
  • טיפ אימות: git diff -- {tests_dir} חייב להכיל רק את הבדיקה החדשה.
  • פרק קשור: פרק 10.

40.8 בדיקה נכשלת: תקנו את הקוד, לא את הבדיקה

  • מטרה: טיפול בבדיקה אדומה בלי הפיתוי לרכך Assertion.
  • מתי: אחרי שינוי שלכם או של Claude, או כשה-CI אדום.
prompt
The {test_name} test in @{test_file} is failing. Find out why and fix the root cause in the application code.
Do not modify files under {tests_dir}. If you believe the test itself is wrong, stop and explain why before changing anything.
Run {test_command} and show me the full output, not a summary.
  • מה לצפות: הסבר קצר, תיקון בקוד היעד, פלט מלא.
  • טיפ אימות: אם Claude טוען שהבדיקה שגויה, קראו את נימוקו לפני שאתם מאשרים שינוי בה.
  • פרק קשור: פרק 10, פרק 11.

40.9 Incident: מלוגים לסיבה סבירה

  • מטרה: אבחון מהיר בזמן תקלה בייצור, מבוסס ראיות.
  • מתי: יש לוגים, פריסות אחרונות ושינויי הגדרות; צריך השערה מדורגת.
prompt
{symptom} started at {time}. Here are the logs: @{log_file}. Recent deploys: {deploys}. Config changes: {changes}.
Check the logs, the recent deploys, and the config changes, then tell me the most likely cause,
ranked with the evidence for each. Propose the smallest safe mitigation and the command or change to apply it.
Do not apply anything without my confirmation.
  • מה לצפות: רשימת השערות מדורגת עם ציטוטים מהלוג והצעת Mitigation קטנה.
  • טיפ אימות: דרשו לכל השערה שורת לוג או Commit תומך; השערה בלי ראיה יורדת בדירוג.
  • פרק קשור: פרק 10, פרק 36.

Test creation

40.10 בדיקות למודול קיים

  • מטרה: כיסוי ממוקד למודול, כולל מקרי קצה, בסגנון הקיים.
  • מתי: קוד בלי בדיקות, או לפני Refactoring.
prompt
Write tests for @{path} covering: the happy path, {edge_case_1}, {edge_case_2}, and error handling.
Follow the structure and fixtures already used in @{existing_test_file}. Avoid mocks unless the dependency is external.
Run {test_command}, fix any failures in the tests you wrote (not in the code under test), and show the output.
Do not change files outside {tests_dir}.
  • מה לצפות: קובץ בדיקות חדש או מורחב, שעובר, בסגנון הפרויקט (ב-TaskFlow: fixture ה-client ו-TASKFLOW_DB זמני).
  • טיפ אימות: הכניסו Bug קטן ידנית לקוד היעד ובדקו שבדיקה אחת לפחות נופלת.
  • פרק קשור: פרק 11.

40.11 TDD: בדיקות קודם

  • מטרה: להגדיר התנהגות בבדיקות ורק אז לממש.
  • מתי: Feature עם התנהגות ברורה שאפשר לתאר כ-Test Cases.
prompt
Write tests for {feature} first, based on these cases: {cases}. Run them and confirm they fail for the right reason.
Then implement {feature} in {scope} until they pass, without weakening any test.
Run the full suite with {test_command} at the end and show the output.
  • מה לצפות: שני שלבים מובחנים: אדום, ואז ירוק. Claude יראה שהבדיקות נכשלות לפני היישום.
  • טיפ אימות: ודאו שהכישלון הראשוני הוא מהסיבה הנכונה (פונקציה חסרה), לא משגיאת Import.
  • פרק קשור: פרק 11.

40.12 העלאת כיסוי לפי דוח

  • מטרה: להשקיע בבדיקות איפה שהכי חסר.
  • מתי: יש דוח כיסוי; רוצים להעלות אותו בצורה מסודרת.
prompt
Read the coverage report at @{report} and add tests for the lowest-covered files until each is above {target}%.
Prioritize branches that handle errors and input validation over trivial getters.
Regenerate the report with {coverage_command} after each file and show the before/after numbers.
Stop after {n} files and summarize what remains.
  • מה לצפות: טבלת לפני/אחרי לכל קובץ, ובדיקות שמכוונות לענפי שגיאה.
  • טיפ אימות: הריצו את פקודת הכיסוי בעצמכם והשוו למספרים שדווחו.
  • פרק קשור: פרק 11.

Refactoring

40.13 תוכנית Refactoring בלי לגעת בקוד

  • מטרה: להבין מה ישתנה ובאיזה סדר לפני שמתחילים.
  • מתי: Refactoring שחוצה כמה קבצים.
prompt (plan mode)
Plan how to refactor {target} to {goal}. List the files you would change and what would change in each,
the tests that currently pin the behavior, and any behavior that is not covered by tests today.
Propose the smallest sequence of steps where each step leaves the suite green.
Don't make any changes yet.
  • מה לצפות: תוכנית מדורגת עם זיהוי של פערי כיסוי. אם יש פערים, הצעד הראשון הוא בדיקות מקבעות.
  • טיפ אימות: כל צעד חייב להסתיים ב"suite green"; אם לא, בקשו לפרק אותו.
  • פרק קשור: פרק 12.

40.14 Refactoring בצעדים קטנים עם Diff ביניהם

  • מטרה: שינוי מבנה בלי שינוי התנהגות, תחת בקרה.
  • מתי: אחרי התוכנית מ-40.13.
prompt
Refactor {target} to {goal} following @{plan_file}. Work in small steps: after each step run {test_command},
show me the diff, and wait for my confirmation before the next step.

40.41 זיהוי בדיקות Flaky

תרגיל

תרגיל 40.1: משרשור להתאמה

על TaskFlow: הריצו 40.1 (מפה), ואז 40.5 (תוכנית) ל-Feature "due date למשימה", ואז 40.11 (TDD) ליישום, ואז 40.37 (סקירה לפני Commit). בסוף, הריצו 40.44 ובחרו שורה אחת להוסיף ל-CLAUDE.md. תעדו: אילו Placeholders החלפתם, ואיזה Prompt דרש התאמה נוספת.

פתרון מוסבר

ההתאמה השכיחה ביותר היא ב-40.5: הוספת "the status values are a single source of truth in the CHECK constraint and TaskStatus type" ל-Context, אחרת התוכנית עלולה להציע Enum נפרד. ב-40.11 ה-Placeholder {cases} צריך להיות קונקרטי: "due_date optional ISO date, rejected if in the past on create, returned in GET, filterable by ?due_before=". ההוספה ל-CLAUDE.md תהיה לרוב "Dates are stored as ISO 8601 UTC strings", אם Claude שאל על זה. שימו לב איך כל Prompt מסתיים בבדיקה שהבא בתור יכול להסתמך עליה.

סיכום

ספריית ה-Prompts אינה תחליף לחשיבה, אלא קיצור דרך למבנה שכבר הוכיח את עצמו: הקשר מדויק, מטרה אחת, גבולות ברורים, קריטריונים ניתנים לבדיקה ופקודת אימות. ארבעים ושמונה ה-Prompts כאן מכסים את מחזור החיים המלא, מ-Onboarding ועד שחרור, וכולם מניחים ש-Claude מחזיר ראיות ולא הצהרות. כשה-Prompt חוזר על עצמו, הפכו אותו ל-Skill; כשהוא צריך לקרות תמיד, הפכו אותו ל-Hook; כשהוא נכשל פעמיים, אל תתקנו אותו בפעם השלישית באותו Session. בפרק הבא נרכז את כל הפקודות וההגדרות ל-Cheat Sheet אחד.
