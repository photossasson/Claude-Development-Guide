Migration ו-Large Refactoring

בפרק הקודם בנינו Feature חדש. בפרק הזה משנים דברים שכבר עובדים, וזה מסוכן יותר: שדרוג Dependency לגרסת Major, החלפת שכבת גישה לנתונים ב-Strangler Pattern, שינוי סכמת בסיס נתונים עם תאימות לאחור, הוספת גרסת API חדשה לצד הישנה, ופיצול מודול גדול לשכבות. לכל תרחיש נציג את ה-Prompts המלאים, את נקודות הבקרה ואת האימות. נלמד גם את הכלים של Claude Code לעבודה בקנה מידה גדול: Git Worktrees לענפים מקבילים, ה-Skill המובנה /batch לשינויים מכניים רבי-קבצים, ו-Subagents מבודדים. והכי חשוב: מתי לעצור ולחשוב מחדש.

מה מבדיל Migration גדול משינוי רגיל

Refactoring רגיל (פרק 12) משנה מבנה בלי לשנות התנהגות, בהיקף שאפשר לסקור ב-PR אחד. Migration ו-Large Refactoring חולקים את אותה הבטחה, "ההתנהגות החיצונית נשמרת", אבל שוברים את שני התנאים האחרים: הם לא נכנסים ל-PR אחד, והם חיים לאורך זמן שבו קוד ישן וחדש מתקיימים זה לצד זה. מכאן נובעים ארבעה עקרונות שחוזרים בכל תרחיש בפרק:

  • חוזה תאימות לאחור (Backward Compatibility Contract): הצהרה כתובה, לפני השינוי, על מה שאסור להישבר: תשובות API, סכמת נתונים שלקוחות ישנים קוראים, פורמט קבצים, משתני סביבה. החוזה הופך לבדיקות.
  • כל צעד הפיך: אין שלב שאי אפשר להחזיר תוך דקות. זה קובע את הסדר: מוסיפים לפני שמסירים, כותבים כפול לפני שמפסיקים לכתוב לישן.
  • חבילת רגרסיה לפני הכול: אם אין בדיקות שמתעדות את ההתנהגות הנוכחית, כותבים אותן קודם (Characterization Tests; נרחיב בפרק 36). ההמלצה הרשמית ל-Refactoring היא לעבוד בצעדים קטנים וניתנים לבדיקה, ולבקש במפורש שמירה על תאימות לאחור.
  • נקודות עצירה מוגדרות מראש: מה יגרום לנו לעצור ולהעריך מחדש (בדיקות שנשברות ללא הסבר, היקף שגדל פי שניים, ממצא ארכיטקטוני חדש). מגדירים לפני שמתחילים, כי באמצע הסערה קשה להחליט.

מתי להשתמש בשיטות של הפרק: שינוי שנוגע במעל עשרה קבצים או בחוזה חיצוני, שדורש יותר מיום עבודה, או שקוד ישן וחדש יצטרכו לחיות יחד. מתי לא: שינוי מקומי שאפשר לסיים ולסקור ב-PR אחד; שם התהליך של פרק 9 מספיק. ואל תשכחו את השאלה שקודמת לכל תהליך: האם ה-Migration בכלל נחוץ? "כי הגרסה החדשה יצאה" אינה סיבה; פגיעות אבטחה, סוף תמיכה או יכולת שחסרה בפועל הן סיבות.

תרחיש 1: שדרוג Dependency לגרסת Major

התרחיש (היפותטי, לצורך ההדגמה): ספרייה מרכזית ב-Backend של TaskFlow פרסמה גרסת Major חדשה עם שינויים שוברים, ואנחנו נדרשים לשדרג בגלל סוף תמיכה בגרסה הישנה. הסכנה בשדרוג Major אינה הקומפילציה; היא שינויי התנהגות שקטים שהבדיקות לא מכסות.

צעד 1: קריאת ה-Changelog ומלאי שימושים. ב-Plan Mode, ואחרי שהעתקתם את קטעי ה-Changelog הרלוונטיים לקובץ מקומי (או נתתם URL רשמי; Claude יבקש אישור לגשת אליו):

Prompt (Plan Mode)
We must upgrade <library> from <current major> to <next major>.
Read docs/upgrade-notes.md (the official migration guide I saved).
Then use a subagent to inventory every usage in backend/: for each
breaking change in the guide, list file:line where we rely on the
old behavior, and mark it MECHANICAL (rename/signature) or
SEMANTIC (behavior changed). Also list which of our tests cover
each usage. Do not change anything. Save the inventory to
docs/upgrade-inventory.md.
המחשה: קטע מהמלאי
| Breaking change              | Where                         | Kind      | Covered by |
| default of X changed         | app/models.py:14              | SEMANTIC  | none       |
| helper Y renamed to Z        | app/routers/tasks.py:9,42     | MECHANICAL| test_tasks |
| validation error format      | (all 422 responses)           | SEMANTIC  | 3 tests    |

נקודת בקרה: כל שורה SEMANTIC עם "none" בעמודת הכיסוי היא חור בחבילת הרגרסיה. לפני שדרוג, כותבים לה בדיקת אפיון על הגרסה הישנה. אימות: קראו את המלאי ובדקו שתיים או שלוש שורות בעצמכם עם grep -n. מודל שמייצר טבלה יפה יכול גם לפספס שימוש דינמי.

צעד 2: תוכנית מדורגת ותוכנית Rollback.

תרחיש 2: החלפת שכבת גישה לנתונים ב-Strangler Pattern

TaskFlow משתמש ב-sqlite3 ישירות, בהתאם לקונבנציה "no ORM" ב-CLAUDE.md. נניח שהצוות החליט (החלטה שנרשמת, כולל הסיבה) לעבור ל-SQLAlchemy. הגישה הבטוחה אינה שכתוב אלא Strangler Pattern: יצירת שכבת Repository חדשה, העברת נתיב אחד בכל פעם, והפעלת שתי המימושים זה לצד זה עד שהישן מתרוקן ונמחק.

Prompt 1 (Plan Mode)
We will migrate TaskFlow's data access from raw sqlite3 to
SQLAlchemy Core (not ORM models yet) using a strangler pattern.
Constraints: every endpoint keeps identical responses (status codes,
JSON, ordering, error bodies); the SQLite file format stays
readable by the old code until the migration ends; the CLAUDE.md
"no ORM" rule is updated as an explicit decision, not silently.
Plan: (1) introduce a TaskRepository protocol; (2) implement
SqliteTaskRepository by moving the existing SQL out of the router
with zero behavior change; (3) implement SqlAlchemyTaskRepository;
(4) a contract test module that runs the same test suite against
BOTH implementations; (5) switch endpoints one at a time via a
TASKFLOW_REPO env var; (6) delete the old implementation.
List the files per step and the verification for each. Wait for
approval.

נקודת בקרה ראשונה: ההחלטה עצמה. לפני שנכתבת שורת קוד, ההחלטה לעבור ל-SQLAlchemy נרשמת בקצרה (למה, מה החלופות שנדחו, מה תנאי ההצלחה) ב-docs/decisions/ או ב-SPEC.md, ושורת "no ORM" ב-CLAUDE.md מתעדכנת ל"data access via TaskRepository; sqlite3 implementation is legacy during migration". בלי העדכון הזה, כל Session עתידי יקרא את הכלל הישן ויתנגד לקוד החדש. על Architecture Decision Records נרחיב בפרק 37.

לב השיטה: בדיקות חוזה כפולות. הצעד הרביעי הוא מה שהופך את ה-Migration לבטוח. אותן בדיקות בדיוק רצות פעמיים, פעם על כל מימוש; כל פער בין השניים הוא כשל, גם אם המימוש החדש "צודק יותר":

backend/tests/test_repository_contract.py (המחשה)
import pytest
from app.repositories.sqlite_repo import SqliteTaskRepository
from app.repositories.sqlalchemy_repo import SqlAlchemyTaskRepository


@pytest.fixture(params=[SqliteTaskRepository, SqlAlchemyTaskRepository])
def repo(request, tmp_path):
    return request.param(db_path=str(tmp_path / "t.db"))


def test_create_then_list_preserves_insertion_order(repo):
    a = repo.create(title="a")
    b = repo.create(title="b")
    assert [t.id for t in repo.list()] == [a.id, b.id]


def test_update_unknown_id_returns_none(repo):
    assert repo.update(9999, {"title": "x"}) is None

נקודת בקרה בכל צעד: אחרי צעד 2 (חילוץ ה-SQL הקיים ל-Repository) ה-Diff חייב להיות "העברה בלבד": אותן מחרוזות SQL, אותו סדר, אותם קודי שגיאה. בקשו במפורש: "move, do not improve". שיפורים נרשמים לרשימה ומבוצעים אחרי שהמעבר הסתיים. הפעלת המימוש החדש בפועל נעשית ל-Endpoint אחד, מריצים יום או שניים, ורק אז לבא. ה-Rollback הוא שינוי משתנה סביבה, בלי Deploy.

Prompt (per endpoint switch)
Switch only GET /tasks to use the repository selected by
TASKFLOW_REPO (default "sqlite"). Keep POST/PATCH/DELETE on the
old path. Run the contract tests and the API tests with
TASKFLOW_REPO=sqlite and again with TASKFLOW_REPO=sqlalchemy, and
paste both summary lines. Nothing else changes in this step.

תרחיש 3: שינוי סכמה עם תאימות לאחור (Expand, Migrate, Contract)

הדוגמה: שינוי שם העמודה description ל-notes בטבלת tasks, בזמן שגרסה ישנה של השרת (או של סקריפטים) עדיין קוראת וכותבת description. שינוי שם ישיר שובר את הישן ברגע. הדפוס הבטוח בשלושה שלבים, שכל אחד מהם Deploy נפרד:

  1. Expand: מוסיפים את העמודה החדשה (ALTER TABLE tasks ADD COLUMN notes TEXT), הקוד כותב לשתי העמודות (Dual Write) וקורא מהישנה. סקריפט Backfill מעתיק ערכים קיימים. הישן והחדש עובדים.
  2. Migrate: הקוד עובר לקרוא מהעמודה החדשה, ממשיך לכתוב לשתיים. בדיקת עקביות (SELECT COUNT(*) WHERE notes IS NOT description) חייבת להחזיר אפס.
  3. Contract: מפסיקים לכתוב לישנה, ואחרי תקופת חסד מסירים אותה. ב-SQLite, ALTER TABLE ... DROP COLUMN נתמך בגרסאות מודרניות אך עם מגבלות (למשל עמודה שמשתתפת באינדקס או ב-Constraint); במקרים כאלה נדרש בנייה מחדש של הטבלה לפי הנוהל המתועד של SQLite: יצירת טבלה חדשה, העתקה, מחיקה, שינוי שם, בתוך Transaction. תנו ל-Claude לכתוב את הסקריפט, ובדקו אותו על עותק.
Prompt (Plan Mode)
Plan an expand/migrate/contract migration renaming tasks.description
to tasks.notes with zero downtime for old readers. For SQLite
specifically: which ALTER TABLE operations are supported for this
change, and where a table rebuild is required. Deliver three
separate PR-sized steps, each with: schema change (idempotent, using
PRAGMA table_info checks like init_db already does), code change,
backfill or consistency query, verification command, and rollback.
State explicitly which step is the point of no return.

נקודת הבקרה הקריטית: "נקודת האל-חזור" היא שלב ה-Contract. עד אליו כל צעד הפיך בלי אובדן נתונים; אחריו, החזרה דורשת שחזור מגיבוי. לכן שלב 3 מחכה: שבוע, גרסה, או עד שאין יותר קוראים ישנים, לפי מדידה ולא לפי תחושה. אימות: אחרי כל שלב, sqlite3 taskflow.db ".schema tasks" ושאילתת העקביות; לפני שלב 3, גיבוי מאומת (sqlite3 taskflow.db ".backup pre-contract.db") ובדיקה שהגיבוי נפתח.

כך נראה שלב ה-Expand בקוד, להמחשה. שימו לב שהוא אידמפוטנטי (בטוח להריץ פעמיים) ושה-Backfill נוגע רק בשורות שעדיין לא הועתקו:

backend/app/database.py (expand step, המחשה)
cols = {row["name"] for row in conn.execute("PRAGMA table_info(tasks)")}
if "notes" not in cols:
    conn.execute("ALTER TABLE tasks ADD COLUMN notes TEXT")
# backfill only rows not yet copied; safe to re-run
conn.execute(
    "UPDATE tasks SET notes = description WHERE notes IS NULL"
)

ובשכבת הכתיבה, בזמן ה-Dual Write, כל INSERT ו-UPDATE שנוגעים ב-description כותבים את אותו ערך גם ל-notes. זה בדיוק המקום שבו כדאי לבקש מ-Claude "list every SQL statement that writes description and show me each change", ולהשוות את הרשימה ל-grep -n "description" backend/app. שאילתת העקביות רצה כבדיקה אוטומטית ולא רק ידנית: בדיקה שיוצרת משימה, מעדכנת אותה, וקוראת ישירות מבסיס הנתונים ששתי העמודות שוות.

Migration אינה מריצה מתוך ה-Session על Production

גם כאן חוזר הכלל מפרק 34: המודל כותב סקריפטים אידמפוטנטיים ובדיקות; אדם מריץ אותם על נתונים אמיתיים, אחרי גיבוי, בחלון מתוכנן. הוסיפו חוק Deny ל-Bash(sqlite3 *prod*) וכדומה ב-settings.json אם קובץ ה-Production נגיש מהמכונה (פרק 18).

תרחיש 4: שינוי גרסת API (v1 נשמר, v2 נוסף)

הדרישה: GET /tasks צריך להחזיר מעטפת עם Pagination ({"items": [...], "total": N, "next": ...}) במקום מערך גולמי. לקוחות קיימים (ה-Frontend, סקריפטים) מצפים למערך. הפתרון: /v1/tasks ממשיך להחזיר מערך, /v2/tasks מחזיר מעטפת, ו-/tasks הישן הופך ל-Alias של v1 עם כותרות Deprecation.

Prompt (Plan Mode)
Add API versioning to TaskFlow without breaking existing clients:
mount the current router at /v1 and keep /tasks as an alias of v1
that adds standard deprecation headers (Deprecation, Sunset, and a
Link header to the migration doc). Add /v2/tasks where GET returns
{items,total,next} with limit/offset params (max limit 100); all
other v2 endpoints identical to v1 for now. Share the handlers, do
not copy-paste the router. Tests: v1 responses byte-for-byte
unchanged (snapshot the current JSON of the existing tests first),
alias sends headers, v2 pagination edge cases (offset past end,
limit 0, limit 1000 -> 422). Then update frontend api.ts to v2 in a
separate step. Plan first.

נקודות בקרה: (1) "snapshot the current JSON first" הוא הצעד המגן: בדיקות ה-Snapshot נכתבות על הקוד הישן ולפני כל שינוי; (2) "share the handlers" מונע פיצול שבו תיקון באג יגיע רק לגרסה אחת; (3) מועד ה-Sunset נקבע על ידי אדם, ונרשם גם בתיעוד. אימות:

$ curl -si localhost:8000/tasks | grep -iE "^(Deprecation|Sunset|Link):" Deprecation: true Sunset: Sat, 31 Oct 2026 00:00:00 GMT Link: <https://example.com/docs/api-v2-migration>; rel="deprecation"

הכותרות Deprecation ו-Sunset הן כותרות סטנדרטיות של HTTP (ה-Sunset מוגדר ב-RFC 8594); הפורמט המדויק של ערך ה-Deprecation תלוי בגרסת התקן שאתם מאמצים, ולכן בקשו מ-Claude להצביע על המקור שעליו הוא מסתמך ולא להמציא. הסרת v1 בפועל היא תרחיש 3 בלבוש אחר: Contract אחרי תקופת חסד, עם מדידה של תעבורה ל-v1 לפני ההסרה.

המעבר של ה-Frontend נעשה בצעד נפרד, ורצוי ב-Worktree נפרד כדי לא לערבב שינויי שרת ולקוח ב-PR אחד: claude --worktree frontend-v2, ושם Prompt ממוקד: "switch api.ts to /v2/tasks, adapt listTasks to the {items,total,next} envelope, keep the UI behavior identical, run npm run typecheck". כשה-Frontend ב-Production כבר על v2, המדידה של קריאות ל-/tasks הישן אמורה לרדת; מה שנשאר הם סקריפטים ולקוחות שלא ידעתם עליהם, וזו בדיוק הסיבה שלא מסירים לפי לוח שנה אלא לפי מספרים.

תרחיש 5: פיצול מודול גדול לשכבות Service ו-Repository

routers/tasks.py של TaskFlow קטן, אבל דמיינו אותו אחרי שנתיים: 900 שורות, SQL משולב בלוגיקה עסקית משולבת בטיפול ב-HTTP. הפיצול הרצוי: Router (HTTP בלבד), Service (חוקים עסקיים), Repository (גישה לנתונים). הסיכון: שינוי התנהגות בדרך. ההגנה: בדיקות אפיון קודם.

Prompt 1 (Plan Mode)
Before any refactor of routers/tasks.py: generate characterization
tests that pin its CURRENT behavior, including the odd parts. Use
the API tests as a base and add: exact error bodies for 400/404/422,
behavior of PATCH with an empty body, ordering of list results, and
what happens with title of 200 vs 201 chars. Do not "fix" anything
you find; record surprises in docs/refactor-notes.md as questions
for me. Run the suite; it must be green on the current code.
Prompt 2 (default mode, one move at a time)
Step 1 of the split: create app/services/tasks_service.py and move
ONLY the update_task logic (field filtering, empty-payload rule) out
of the router into TaskService.update(). The router calls the
service; SQL stays where it is for now. Zero behavior change: run
the characterization suite. Show me the diff before committing.

נקודת בקרה: כל תזוזה היא Commit נפרד, וכל Commit ירוק על חבילת האפיון. אם באמצע הפיצול מתגלה באג אמיתי (למשל PATCH ריק שמחזיר 400 במקום 422), הוא נרשם ולא מתוקן: Refactoring ותיקון באגים לא חיים באותו Commit. אחרי סיום הפיצול, פותחים Branch נפרד לתיקונים, ומעדכנים את בדיקות האפיון בכוונה. סיימו ב-/code-review על כל ה-Branch, ואחריו /simplify: לפי התיעוד, זו סקירת ניקיון בלבד שמיישמת פישוטים (כפילויות, קוד מיותר) בלי לצוד באגים, בדיוק מה שנוצר בדרך בפיצול. זכרו ששני הכלים רצים ב-Subagent ברקע, ועריכות שהם מבצעים (למשל עם --fix) אינן נשמרות ב-Checkpoints של ה-Session: /rewind לא יבטל אותן, רק Git.

מבנה הקבצים בסוף הפיצול, להמחשה:

backend/app/ (after the split)
app/
├── main.py
├── database.py
├── models.py
├── routers/
│   └── tasks.py              # HTTP בלבד: פרסור, קודי תשובה, קריאה ל-Service
├── services/
│   └── tasks_service.py      # חוקים עסקיים: מעברי סטטוס, done_at, ולידציה צולבת

שימו לב שהפיצול הזה הוא גם ההכנה הטבעית לתרחיש 2: ברגע שיש Repository עם Protocol, החלפת המימוש מתחת היא צעד קטן. סדר טוב הוא לכן: קודם פיצול (תרחיש 5), אחר כך החלפת טכנולוגיה (תרחיש 2). לנסות את שניהם יחד הוא בדיוק סוג ה"צעד גדול מדי" שתנאי העצירה נועדו לתפוס.

/batch, Worktrees ופריסה מקבילית לשינויים מכניים

חלק מה-Migrations הם מכניים לחלוטין: החלפת שם פונקציה בעשרות קבצים, מעבר מ-API ישן של ספרייה לחדש, הוספת Type Hints. ל-Claude Code יש שלוש דרכים לפרוס עבודה כזאת במקביל:

  • /batch <instruction>: Skill מובנה שחוקר את ה-Codebase, מפרק את העבודה ל-5 עד 30 יחידות בלתי תלויות, מציג תוכנית לאישור, ואז מריץ Subagent ברקע לכל יחידה ב-Git Worktree מבודד; כל Subagent מממש את היחידה שלו, מריץ בדיקות ופותח Pull Request. דורש Repository של Git. הדוגמה מהתיעוד: /batch migrate src/ from Solid to React.
  • Worktrees ידניים: claude --worktree upgrade-a ו-claude --worktree upgrade-b בשני Terminals, למשל כדי לנסות שתי גישות מקבילות ולבחור. Subagent מותאם עם isolation: worktree ב-Frontmatter תמיד רץ ב-Worktree משלו.
  • לולאת claude -p: לפי התיעוד הרשמי, מייצרים רשימת קבצים, ואז for file in $(cat files.txt); do claude -p "Migrate $file ... Return OK or FAIL." --allowedTools "Edit,Bash(git commit *)"; done. מנסים על שניים או שלושה קבצים, מחדדים את ה-Prompt, ורק אז מריצים על הכול.
Prompt: /batch לשינוי מכני
/batch replace every direct call to the deprecated helper
old_helper() in backend/ with new_helper() per
docs/upgrade-notes.md section 3. Each unit must keep pytest green.
Do not touch behavior beyond the rename.
בטיחות בעבודה מקבילית
  • קראו את תוכנית הפירוק לפני האישור: יחידות שאינן באמת בלתי תלויות (שתיים שנוגעות באותו קובץ) ייצרו קונפליקטים ב-Merge.
  • כל PR שנוצר עדיין נסקר על ידי אדם. מקביליות מגדילה תפוקה, לא אמון.
  • סוכני רקע ו-Subagents ב-Worktrees יוצרים ענפים ותיקיות; אחרי הסיום, git worktree list ו-git worktree remove לניקוי (Claude מנקה Worktrees ריקים בעצמו; כאלה עם עבודה נשמרים).
  • אל תריצו /batch על שינוי סמנטי. הוא מצוין ל"החלף X ב-Y", גרוע ל"שנה את מודל ההרשאות".
  • לולאת claude -p רצה ללא השגחה: --allowedTools מצומצם הוא חובה, ו-Sandbox (פרק 20) מומלץ.

איך נראית הרצת /batch בפועל, להמחשה: Claude חוקר את ה-Codebase, מציג רשימה של יחידות (למשל "unit 1: app/routers/tasks.py, unit 2: app/services/, unit 3: scripts/") ומחכה לאישור. אחרי האישור, לכל יחידה נפתח Subagent ברקע ב-Worktree משלו; אתם יכולים להמשיך לעבוד ב-Session הראשי בזמן שהם רצים. כשיחידה מסתיימת, מופיע PR ב-GitHub (דרך gh) עם ההסבר והבדיקות שרצו. הסקירה שלכם היא לכל PR בנפרד, ואם יחידה נכשלה, ה-Worktree שלה נשאר על הדיסק לבדיקה. שני דברים שכדאי לבדוק לפני האישור: שהיחידות באמת לא נוגעות באותם קבצים, ושההוראה כוללת את פקודת הבדיקה שכל יחידה חייבת להעביר.

אסטרטגיית חבילת הרגרסיה

לאורך כל התרחישים, החבילה שמגינה עלינו בנויה משלוש שכבות, וכדאי לבנות אותה בסדר הזה:

  1. בדיקות אפיון (Characterization): מה הקוד עושה היום, כולל המוזרויות. נכתבות לפני השינוי, ירוקות על הקוד הישן.
  2. בדיקות חוזה (Contract): ההבטחות שהצהרנו עליהן בחוזה התאימות: תשובות API, סכמה, פורמטים. רצות על ישן וחדש כאחד (כמו test_repository_contract.py).
  3. בדיקות Smoke ידניות ואוטומטיות: הפעלה אמיתית של המערכת אחרי כל צעד; מה שבדיקות יחידה לא רואות (הגדרות, נתונים ותיקים, לקוחות חיצוניים).

ב-CI (פרק 28) חבילת הרגרסיה רצה על כל PR של ה-Migration, ואפשר להוסיף Hook מסוג Stop (פרק 22) שלא מאפשר לתור להסתיים כשהחבילה אדומה.

מתי לעצור ולהעריך מחדש

הכלל החשוב בפרק: Migration טוב יודע לעצור. הגדירו מראש, ב-SPEC.md, את תנאי העצירה, ובדקו אותם בסוף כל צעד:

  • בדיקות אפיון נשברות ואין הסבר תוך שני סבבי תיקון. עוצרים, /clear, חוקרים בנפרד. לא "מרככים" בדיקה.
  • ההיקף גדל: רשימת הקבצים המושפעים כפולה מהמלאי המקורי. חוזרים ל-Plan Mode ומחלקים מחדש.
  • ממצא ארכיטקטוני חדש (למשל: קוד ישן כותב ישירות לבסיס הנתונים ממקום שלא ידענו עליו). ה-Migration משנה צורה; ה-Spec מתעדכן לפני הקוד.
  • ה-Session חוצה את סף ה-Context שקבעתם (/context). Commit בנקודה ירוקה, Handoff ל-Session חדש (פרק 14).
  • ה-Rollback נהיה לא טריוויאלי (נתונים בפורמט שהישן לא קורא) לפני שהתכוונתם. זו נקודת אל-חזור לא מתוכננת; עוצרים ומחליטים במודע.
  • יותר משני PRs של ה-Migration פתוחים בו זמנית ומחכים לסקירה. מקביליות מעבר ליכולת הסקירה היא חוב, לא תפוקה.

טעויות נפוצות

  • לשדרג ולתקן באותו Commit: אי אפשר לדעת מה נשבר בגלל השדרוג ומה בגלל התיקון.
  • לדלג על מלאי השימושים: "בטח זה רק בשלושה מקומות". בדרך כלל זה בשמונה, ושניים מהם דינמיים.
  • לתת למודל "לשפר תוך כדי": "move, do not improve" הוא המשפט החשוב ביותר בכל Prompt של Refactoring.
  • Contract לפני שהקוראים הישנים נעלמו: מדדו, אל תניחו.
  • לסמוך על /rewind כרשת ביטחון ל-Migration: הוא לא מבטל פקודות Shell ולא שינויים בבסיס הנתונים. Git וגיבויים הם רשת הביטחון (פרק 19).
  • /batch על שינוי סמנטי: 20 PRs שכל אחד פירש את הדרישה קצת אחרת.

Troubleshooting

תסמיןאבחון וטיפול
אחרי הקפצת הגרסה, בדיקות נכשלות בהמוניהן עם אותה שגיאהכמעט תמיד שינוי אחד רוחבי (פורמט שגיאות, ברירת מחדל). אל תתקנו בדיקה-בדיקה; בקשו מ-Claude לקבץ את הכשלים לפי הודעה ולתקן את השורש
בדיקות החוזה עוברות על המימוש הישן ונכשלות על החדש בסדר תוצאותהישן הסתמך על סדר לא מובטח (למשל סדר הכנסה בלי ORDER BY). החליטו: להוסיף ORDER BY מפורש לשני המימושים (ולתעד), או להקל בבדיקה. החלטה של אדם
Failed to resolve base branch "HEAD" ב---worktreeל-Repository אין אף Commit. צרו Commit ראשון
Worktrees ישנים תופסים מקום וענפיםgit worktree list, ואז git worktree remove <path> (עם --force אם יש שינויים לא שמורים). Claude מנקה אוטומטית רק Worktrees ללא עבודה
Claude ב-Worktree מסרב להריץ פקודה "שנוגעת ב-main checkout"זו אכיפת הבידוד: בתוך Worktree נחסמות עריכות ופקודות שפוגעות ב-Checkout הראשי. הריצו את הפקודה מה-Session הראשי, או פצלו לפקודות פשוטות

Security

  • Dependencies: שדרוג הוא הרגע לבדוק את שרשרת האספקה: מקור החבילה, Hash נעול, ומה השתנה ברשימת התלויות העקיפות. אל תתנו למודל להוסיף חבילות "עזר" בדרך.
  • ריצה ללא השגחה: /batch ולולאות claude -p מקבלות הרשאות מינימליות (--allowedTools, חוקי Deny) ורצות ב-Sandbox כשאפשר.
  • נתונים: סקריפטי Migration ו-Backfill נכתבים על ידי המודל, נבדקים על עותק, ומורצים על ידי אדם. גיבוי מאומת לפני כל נקודת אל-חזור.
  • API v1/v2: אותה שכבת הרשאות לשתי הגרסאות; ודאו שהוספת v2 לא פתחה נתיב שעוקף בדיקה קיימת.

עלות ו-Context

Migrations ארוכים הם הצרכן הגדול ביותר של Tokens במדריך, ורוב הבזבוז בא משני מקורות: מלאי שימושים שנעשה ב-Context הראשי (האצילו ל-Subagent), וסבבי תיקון על בדיקות שנשברו בגלל צעד גדול מדי (הקטינו צעדים). /batch ו-Subagents מקבילים מכפילים תפוקה אבל גם צריכה; ב-Session ראשי השאירו את המודל החזק לתכנון ולסקירה, ותנו ליחידות המכניות לרוץ על מודל מהיר יותר. ראו פרק 30.

Best Practices

  • חוזה תאימות כתוב לפני השינוי; הוא הופך לבדיקות חוזה שרצות על ישן וחדש.
  • בדיקות אפיון ירוקות על הקוד הישן לפני התזוזה הראשונה.
  • "move, do not improve"; שיפורים נרשמים ומבוצעים אחרי.
  • הקפצת גרסה, שינוי סכמה ונקודת אל-חזור: כל אחד ב-Commit או PR משלו.
  • תוכנית Rollback כתובה ומנוסה על עותק, לפני ה-Merge.
  • תנאי עצירה מוגדרים מראש ונבדקים בסוף כל צעד.
  • מקביליות (/batch, Worktrees) לשינויים מכניים בלבד, בקצב שהסקירה האנושית עומדת בו.

Anti-patterns

  • ה-Big Bang Rewrite: "תכתוב את שכבת הנתונים מחדש ב-SQLAlchemy" ב-Session אחד ארוך; בסוף אין דרך לדעת מה נשמר ומה השתנה.
  • Migration בלי מדידה: להסיר v1 "כי כבר עברו חודשיים" בלי לדעת אם מישהו עוד קורא לו.
  • ריכוך בדיקות אפיון: כשהחדש מתנהג אחרת, "לעדכן את הבדיקה" במקום להחליט במודע.
  • ה-Session הנצחי: Migration של שבוע ב-Session אחד עם עשרות /compact; ההקשר מתדרדר בדיוק כשהוא הכי נחוץ.
  • מקביליות כתחליף לתכנון: להריץ /batch לפני שיש מלאי, חוזה ובדיקות.

תרגיל

תרגיל 35.1: מזהי משימות מ-INTEGER ל-UUID, בלי להשבית לקוחות

ב-TaskFlow, המזהה id הוא INTEGER AUTOINCREMENT. הדרישה: לעבור למזהה UUID ציבורי (public_id) בכל ה-API, תוך שמירה על תאימות: לקוחות ישנים ממשיכים לעבוד עם המספר לתקופת מעבר, ה-Frontend עובר ל-UUID, וטבלת comments (מפרק 34) ממשיכה להצביע נכון. תכננו וממשו ב-Expand, Migrate, Contract, עם חוזה תאימות, בדיקות אפיון, בדיקות חוזה, תוכנית Rollback מנוסה, ותנאי עצירה. השתמשו ב-Worktree נפרד לצד ה-Frontend.

פתרון מוסבר

חוזה: GET /tasks/{n} עם מספר ממשיך לעבוד עד תאריך Sunset; כל תשובה כוללת גם id וגם public_id בתקופת המעבר; FK של תגובות לא משתנה בשלב ראשון (נשאר על המספר הפנימי, שהוא לעולם לא נחשף אחרי ה-Contract).

Expand: ALTER TABLE tasks ADD COLUMN public_id TEXT (אידמפוטנטי דרך PRAGMA table_info), אינדקס ייחודי, Backfill עם uuid4 לכל שורה קיימת, יצירה חדשה ממלאת אוטומטית. תשובות ה-API מוסיפות public_id. בדיקות אפיון קיימות נשארות ירוקות; בדיקות חדשות: כל שורה מקבלת UUID ייחודי.

Migrate: נתיבים מקבלים גם מספר וגם UUID (זיהוי לפי צורה, עם בדיקות לשני המקרים); ה-Frontend ב-Worktree נפרד עובר ל-public_id; כותרות Deprecation על קריאות עם מספר. מדידה: כמה קריאות עם מספר עדיין מגיעות.

Contract: אחרי שהמדידה יורדת לאפס ותאריך ה-Sunset עבר: הסרת התמיכה במספר בנתיבים, הסרת id מהתשובות. העמודה הפנימית נשארת (PK ו-FK); לא צריך בנייה מחדש של הטבלה, וזה יתרון של החלטת החוזה. Rollback: עד ה-Contract, git revert בלבד; אחריו, שחזור הקוד הישן עדיין עובד כי הנתונים לא נמחקו. תנאי עצירה שכדאי היה לרשום: גילוי לקוח שמפרסר את המזהה כמספר בצד שלו (למשל ממיין לפיו).

סיכום

חמישה תרחישים, מתודולוגיה אחת: חוזה תאימות כתוב, בדיקות אפיון וחוזה לפני השינוי, צעדים קטנים והפיכים שכל אחד Commit ירוק, Expand לפני Contract, תוכנית Rollback מנוסה, ותנאי עצירה מוגדרים מראש. Claude Code מוסיף לזה כלים של קנה מידה: Subagents למלאי, Worktrees לענפים מקבילים, /batch ולולאות claude -p לשינויים מכניים, ו-/code-review לכל פרוסה. מה שהוא לא מוסיף, ולא צריך להוסיף, זה את ההחלטות: מתי נקודת האל-חזור, מתי להסיר את הישן, ומתי לעצור. בפרק הבא ניקח את הכלים האלה למקום הקשה ביותר: קוד Legacy שאיש לא זוכר למה הוא עובד.
