קריאת Repository והבנת Architecture

לפני שנוגעים בשורת קוד אחת, צריך להבין את המערכת. בפרק הזה נלמד להשתמש ב-Claude Code ככלי מחקר טהור: מיפוי מבנה תיקיות ונקודות כניסה, זיהוי שכבות וזרימת נתונים, מעקב אחרי מסלולי קריאה של פונקציות, איתור תלויות, בדיקות, קונפיגורציה וגבולות אבטחה, והפקת תרשימי Architecture ב-Mermaid. נעשה זאת בלי לשנות אף קובץ, על פרויקט הדוגמה TaskFlow, ונסיים בהנחיות לעבודה עם Codebases גדולים.

מהי חקירת Codebase ואיזו בעיה היא פותרת

חקירת Codebase היא שימוש ב-Claude Code כדי להבין פרויקט קיים: מה הוא עושה, איך הוא בנוי, איפה עוברים הנתונים, ומה יישבר אם ניגע במקום הלא נכון. זו אחת המיומנויות עם התשואה הגבוהה ביותר, כי היא פותרת שתי בעיות יקרות:

  • Onboarding איטי. מפתח חדש בפרויקט מבלה ימים או שבועות בקריאת קוד זר. התיעוד הרשמי ממליץ במפורש לשאול את Claude את אותן שאלות שהייתם שואלים מהנדס בכיר: "איך עובד ה-Logging?", "איך מוסיפים Endpoint חדש?". זה מקצר את זמן הכניסה ומוריד עומס מהצוות.
  • שינויים עיוורים. מי שמתקן Bug בלי להבין את זרימת הנתונים מתקן לעיתים קרובות סימפטום ולא סיבה, או שובר משהו במקום אחר. הבנת ה-Architecture קודמת לכל שינוי אחראי, וזה בדיוק הבסיס שעליו נבנה הפרק הבא על Plan Mode.

היתרון של Claude כאן מבני: הוא לא מנחש מתוך זיכרון, אלא קורא את הקבצים בפועל, מריץ חיפושים, עוקב אחרי Imports, ומרכיב תמונה מבוססת ראיות. אתם מקבלים סיור מודרך בקוד שלכם, בקצב שלכם.

מתי להשתמש ומתי לא

מתי כן:

  • הצטרפתם לפרויקט חדש או ירשתם Legacy Code ואתם צריכים מפה מהירה.
  • לפני כל שינוי שנוגע ביותר מקובץ אחד או שניים: קודם מבינים, אחר כך מתכננים, ורק אז מקודדים.
  • לפני Code Review או Design Review של אזור לא מוכר.
  • כשצריך לתעד Architecture קיימת: מסמכים ותרשימים שאיש לא כתב בזמן אמת.

מתי לא:

  • כשאתם כבר מכירים את הקוד והמשימה זעירה וברורה. חקירה מקדימה של פרויקט מוכר לצורך תיקון שורה אחת היא בזבוז Tokens וזמן.
  • כשהשאלה אינה על הקוד אלא על החלטה עסקית או היסטוריה ארגונית שאינה מתועדת ב-Repository. Claude יכול לקרוא רק את מה שקיים בקבצים וב-Git History.
  • כתחליף להרצת המערכת. הבנה סטטית של קוד היא משלימה, לא חלופה, לראיית ההתנהגות בזמן ריצה.

איך זה עובד מושגית: שלב איסוף ההקשר בלולאה

בפרק 3 ראינו שה-Agentic Loop של Claude פועל בשלושה שלבים: איסוף הקשר, ביצוע פעולה ואימות תוצאה. התיעוד הרשמי מציין ששאלה על ה-Codebase עשויה להזדקק לשלב הראשון בלבד. כלומר, חקירה היא לולאה שלמה שמורכבת רק מקריאות: Claude מחליט אילו קבצים לפתוח, קורא, מסיק, מחליט מה לקרוא הבא, וחוזר חלילה עד שיש לו תשובה מבוססת.

חקירה בלי לשנות קוד: שלוש שכבות ביטחון

כשהמטרה היא מחקר בלבד, יש לכם שלוש דרכים להבטיח שלא ישתנה שום קובץ, מהקלה לכבדה:

  1. ניסוח מפורש ב-Prompt. מוסיפים לבקשה משפט כמו this is research only, do not change any code. זו הנחיה למודל, והיא עובדת מצוין ברוב המקרים, אבל היא אינה מנגנון אכיפה.
  2. מצב ברירת המחדל כרשת ביטחון. גם אם Claude ינסה לערוך, במצב ברירת המחדל כל עריכה עוצרת לבקשת אישור. אתם פשוט דוחים. שום דבר לא נכתב לדיסק בלי הסכמתכם.
  3. Plan Mode כאכיפה. לחצו Shift+Tab עד שמופיע החיווי plan mode on בשורת הסטטוס. במצב הזה Claude חוקר ומציע, אך עריכות קוד המקור חסומות עד שתאשרו תוכנית. זו החלופה הקריאה-בלבד המסודרת, ונרחיב עליה מאוד בפרק הבא.

לחקירה של Session שלם, פתחו ישר במצב תכנון: claude --permission-mode plan. כך כל השיחה מוגדרת מראש כמחקר, ואין תלות בזיכרון של אף אחד, לא שלכם ולא של המודל.

דוגמה מציאותית: מיפוי TaskFlow בשישה שלבים

נעבור עכשיו מסלול חקירה שלם ומסודר על TaskFlow. פתחו Session בתיקיית הפרויקט (רצוי במצב plan או פשוט בלי לאשר עריכות). לכל שלב מוצגים ה-Prompt המדויק, מה Claude עושה מאחורי הקלעים, ומה צפוי לחזור. הניסוחים המדויקים של התשובות ישתנו מהרצה להרצה; מה שחשוב הוא סוג המידע שחוזר.

הפקת תרשימי Architecture עם Mermaid

אחרי שהתמונה ברורה, כדאי לקבע אותה בתרשים. Mermaid היא שפת תרשימים טקסטואלית ש-Claude מפיק בקלות כטקסט בתשובה, בלי לגעת באף קובץ. את הקוד שמתקבל מדביקים בכל מקום שמרנדר Mermaid: קובצי Markdown ב-GitHub וב-GitLab, רוב ה-Wikis, או העורך המקוון Mermaid Live Editor.

Prompt

פלט אפשרי (מקוצר) שמתאים למה שמיפינו:

flowchart LR

ולזרימה של פעולה בודדת מבקשים Sequence Diagram:

Prompt
now output a Mermaid sequence diagram of creating a task:
user, App.tsx, api.ts, FastAPI router, Pydantic validation, SQLite
Mermaid: תרשים רצף ליצירת משימה
sequenceDiagram
  participant U as User
  participant A as App.tsx
  participant C as api.ts
  participant R as tasks.py (POST /tasks)
  participant P as Pydantic (TaskCreate)
  participant S as SQLite
  U->>A: submit form
  A->>C: createTask({title})
  C->>R: POST /tasks (JSON)
  R->>P: validate payload
  P-->>R: TaskCreate
  R->>S: INSERT INTO tasks (parameterized)
  S-->>R: new row
  R-->>C: 201 + Task JSON
  C-->>A: Task
  A->>C: listTasks() refresh

בדקו תמיד את התרשים מול מה שלמדתם בשלבים הקודמים: תרשים הוא טענה על המערכת, ו-Claude יכול לטעות בו כמו בכל טענה. אם תרצו לשמור את התוצר כקובץ ARCHITECTURE.md ב-Repository, שימו לב שזו כבר פעולת כתיבה: במצב ברירת המחדל תופיע בקשת אישור, וב-Plan Mode תצטרכו לצאת מהמצב קודם. זה הגבול המדויק שבין מחקר לשינוי.

דוגמה מתקדמת: ארכיאולוגיה של Git ו-Subagents

שתי טכניקות שמרימות את החקירה לרמה הבאה:

1. חקירת היסטוריה. כשקוד נראה מוזר, התשובה נמצאת לפעמים ב-Git History ולא בקוד עצמו. התיעוד הרשמי מדגים בדיוק את זה: במקום לשאול "למה ל-API הזה יש מבנה מוזר?", מכוונים את Claude למקור שיכול לענות:

Prompt
look through the git history of backend/app/models.py and summarize
how the validation rules evolved and why

Claude יריץ פקודות כמו git log ו-git show (פקודות קריאה מ-Git; חלקן בסט הקריאה החופשי וחלקן יבקשו אישור חד פעמי) ויסכם את ההתפתחות. בעותק טרי של TaskFlow יש Commit אחד בלבד, אז את הטכניקה הזאת תפעילו בפרויקטים אמיתיים.

2. חקירה דרך Subagent. חקירה רחבה ממלאת את ה-Context בקריאות קבצים. התיעוד ממליץ להאציל את החקירה כך שרק הממצאים יחזרו לשיחה הראשית:

Prompt
use a subagent to investigate how task status values flow through the
system, and report back only the findings and file references

ה-Subagent קורא את הקבצים ב-Context Window משלו ומחזיר סיכום. בפרויקט בגודל של TaskFlow זה מיותר; ב-Codebase אמיתי זה ההבדל בין שיחה נקייה לשיחה חנוקה. נרחיב על כך בפרק 25 על Subagents.

עבודה עם Codebases גדולים ו-Monorepos

לתיעוד הרשמי יש עמוד ייעודי לנושא (ראו במקורות), והעיקרון המרכזי שלו: ככל שה-Repository גדל, ברירות המחדל שמכוונות לפרויקטים קטנים מתחילות למלא את ה-Context בהוראות ובקריאות שאינן קשורות למשימה. הפתרון הוא למקד את Claude בחלק הרלוונטי:

כלל אצבע לחקירת פרויקט גדול: התחילו ממוקד. במקום "explain this codebase" על Monorepo של מיליוני שורות, שאלו על תת-מערכת אחת, או פתחו את ה-Session מתוך התיקייה שלה. חקירה לא ממוקדת ב-Repository ענק היא ה-Anti-pattern שהתיעוד מכנה "the infinite exploration". את ההגדרות עצמן (settings.json, חוקי הרשאות) נלמד לעומק בפרק 17 ובפרק 18.

אימות: איך יודעים שההבנה נכונה

חקירה מסתיימת רק כשההבנה נבדקה. תשובות של מודל שפה יכולות להיות שוטפות ומשכנעות וגם שגויות, ולכן שלב האימות אינו רשות. שלוש בדיקות מהירות:

  • בדיקת מדגם מול הקוד: בחרו שתיים או שלוש טענות מרכזיות מהסיכום (למשל "כל השאילתות עם פרמטרים") ופתחו בעצמכם את הקובץ הרלוונטי לוודא. אם מדגם קטן נקי, רמת האמון בשאר עולה; אם לא, חוזרים לחקירה.
  • בדיקת ה-Transcript: פתחו Ctrl+O וודאו שהקבצים המרכזיים באמת נקראו. טענה על קובץ שלא נפתח היא ניחוש, גם אם היא נשמעת בטוחה.
  • שאלת ניבוי: שאלו את Claude שאלה שהתשובה עליה נובעת מההבנה אך אינה כתובה במפורש בקוד, למשל: if I add a new status value "blocked", what exactly breaks and where?. תשובה נכונה ל-TaskFlow חייבת למנות את אילוץ ה-CHECK ב-database.py, את TaskStatus ב-models.py, את types.ts ואת מפת NEXT_STATUS ב-App.tsx. תשובה שמפספסת אחד מהארבעה חושפת חור בהבנה, של Claude או שלכם, בדיוק בזמן.

שגיאות נפוצות

  • לשאול הכול בשאלה אחת. "explain everything about this repo" מחזיר סיכום שטחי. עבדו בשלבים כמו במסלול למעלה: סקירה, כניסות, שכבות, זרימה, תלויות, אבטחה.
  • לקבל תשובות בלי לדרוש ראיות. בקשו תמיד שמות קבצים ופונקציות בתשובה (name every function and file on the path). טענה בלי הפניה לקוד היא טענה שלא נבדקה.
  • לדלג על אימות. פתחו את הקבצים המרכזיים שהוזכרו, או לחצו Ctrl+O כדי לראות מה באמת נקרא. אם Claude לא פתח את database.py, הוא מנחש לגבי ה-Schema.
  • לחקור ולשנות באותה נשימה. כשחקירה גולשת לתיקונים "קטנים" תוך כדי, מאבדים גם את ניקיון המחקר וגם את השליטה בשינוי. הפרידו: קודם מחקר, אחר כך תוכנית, ואז ביצוע.
  • לשכוח את ה-Context. אחרי חקירה ארוכה, השיחה מלאה בתוכן קבצים. אל תמשיכו ממנה ישר למשימת פיתוח שאינה קשורה; פתחו דף חדש עם /clear.

Troubleshooting

  • Claude עונה באופן כללי בלי לקרוא קבצים. ודאו שאתם בתיקיית הפרויקט הנכונה (מוצגת מעל שורת הקלט), ונסחו מחדש עם עוגן קונקרטי: @backend/app/main.py או שם פונקציה.
  • התשובה סותרת את הקוד. זה קורה, במיוחד אחרי שיחה ארוכה שבה ה-Context התמלא. בקשו אימות ממוקד: re-read models.py and verify your claim about title validation. אם הסתירות חוזרות, /clear והתחלה נקייה.
  • החקירה איטית או נתקעת על Repository ענק. צמצמו את השדה: הפעילו את ה-Session מתת-תיקייה, הגדירו חוקי deny לקוד מיוצר, או האצילו ל-Subagent. ראו את סעיף ה-Codebases הגדולים למעלה.
  • Claude מבקש אישור להריץ פקודה באמצע מחקר. זה תקין: פקודות שאינן בסט הקריאה המובנה (למשל pip list) דורשות אישור. קראו את הפקודה, ואם היא באמת קריאה בלבד, אשרו. אם אינכם בטוחים, דחו ובקשו מ-Claude להסביר מה הפקודה עושה.
  • בקשתם "רק מחקר" ובכל זאת הוצע Diff. ההנחיה בטקסט אינה אכיפה. דחו את העריכה בבקשת ההרשאה, ועברו ל-Plan Mode עם Shift+Tab להמשך החקירה.

Security: חקירת Repository שאינו מהימן

אזהרה: קוד זר יכול לתקוף את החוקר שלו

חקירה מרגישה בטוחה כי "רק קוראים", אבל Repository שהורדתם מהאינטרנט יכול להכיל טקסט עוין בדיוק במקומות ש-Claude קורא: README.md, CLAUDE.md, הערות בקוד, ואף הגדרות ב-.claude/settings.json. זו מתקפת Prompt Injection: הוראות מוסתרות שמנסות לגרום ל-Claude לבצע פעולות בשמכם. לכן קיים חלון ה-Trust בכניסה הראשונה לתיקייה, ולכן מנגנון ההרשאות מציג לאישור כל פקודה שאינה קריאה. בפרויקט לא מוכר: הישארו במצב ברירת המחדל או ב-Plan Mode, קראו כל בקשת הרשאה בעיון לפני אישור, אל תאשרו פקודות רשת כמו curl שאינכם מבינים, ושקלו להריץ את החקירה בסביבה מבודדת (VM או Dev Container). התיעוד הרשמי ממליץ במפורש שלא להזרים תוכן לא מהימן ישירות ל-Claude ולדווח על התנהגות חשודה עם /feedback. הרחבה מלאה על מודל האיומים וההגנות: פרק 20: Security.

שיקולי Cost ו-Context

חקירה ממלאת את ה-Context

כל קובץ ש-Claude קורא נכנס ל-Context Window ונשאר שם. חקירה יסודית של פרויקט בינוני יכולה לצרוך עשרות אלפי Tokens, והתיעוד מציין שביצועי המודל יורדים ככל שה-Context מתמלא. כלים מעשיים: /context מציג מה תופס מקום; /clear מאפס בין חקירה למשימה הבאה; Subagents מעבירים את עלות הקריאות ל-Context נפרד; ובקשה לסכם ממצאים לקובץ או להודעה אחת מרוכזת שומרת את התובנות גם אם השיחה תקוצץ. ניהול Context מלא: פרק 14.

Best Practices

  • התחילו רחב וצרו הדרגתית: סקירה, ואז צלילה לאזור אחד בכל פעם.
  • פתחו חקירת עומק ב-claude --permission-mode plan או הוסיפו "do not change any code" לכל Prompt מחקרי.
  • דרשו הפניות: שמות קבצים, פונקציות ושורות בכל תשובה.
  • סכמו כל שלב חקירה במשפט או שניים לעצמכם; בסוף בקשו מ-Claude סיכום ממצאים אחד מרוכז.
  • הפיקו תרשים Mermaid אחד לפחות לכל מערכת שאתם לומדים, ובדקו אותו מול הקוד.
  • שאלו גם "מה חסר": בדיקות שאין, Validation שאין, תיעוד שאין. היעדרות היא ממצא ארכיטקטוני.
  • ב-Repository גדול, מקדו את השדה לפני שמתחילים: תת-תיקייה, חוקי deny, או Subagent.

Anti-patterns

  • החקירה האינסופית: "תחקור את המערכת" בלי גבולות. Claude יקרא מאות קבצים וימלא את ה-Context. תמיד תחמו: אזור, שאלה, תוצר מבוקש.
  • מפה בלי טריטוריה: לקבל תיאור Architecture יפה ולא לפתוח אף קובץ לאימות. תשובה שגויה אחת שלא נתפסה מזהמת את כל ההחלטות שאחריה.
  • חקירה כתירוץ לדחיינות: לחקור שבוע פרויקט של אלף שורות. עומק החקירה צריך להיות פרופורציונלי לסיכון של השינוי המתוכנן.
  • הדבקת קבצים ידנית: להעתיק תוכן קבצים לתוך ה-Prompt במקום לתת ל-Claude לקרוא בעצמו או להשתמש ב-@. זה מבזבז Tokens ומאבד את היתרון של חקירה אקטיבית.
  • לחקור עם הרשאות פתוחות: להריץ חקירה של קוד זר במצב שמאשר עריכות או פקודות אוטומטית. חקירה צריכה את המצב השמרני ביותר שנוח לכם לעבוד בו.

תרגיל

תרגיל 6.1: מסמך Architecture מלא ל-TaskFlow

הפעילו Session חדש בעותק ה-TaskFlow שלכם במצב plan (claude --permission-mode plan), ובצעו:

  1. הריצו את ששת שלבי החקירה מהפרק, שלב אחר שלב, וודאו שכל תשובה כוללת הפניות לקבצים.
  2. בקשו מ-Claude לזהות את שלושת הסיכונים הארכיטקטוניים המרכזיים של הפרויקט, מנומקים.
  3. בקשו תרשים Mermaid של הרכיבים ותרשים רצף של מחיקת משימה (DELETE /tasks/{id}).
  4. בקשו סיכום ממצאים אחד בפורמט מסמך: סקירה, שכבות, זרימות, תלויות, פערים.
  5. ודאו בעזרת git status (מחוץ ל-Claude או עם !git status) ששום קובץ לא השתנה.
פתרון מוסבר

(1) המסלול אמור לשחזר את הממצאים מהפרק: שתי נקודות כניסה, שלוש שכבות בכל צד, זרימת CRUD דרך Pydantic ל-SQLite, ושישה מבחני API. (2) שלושה סיכונים סבירים שכדאי לצפות להם: ערכי הסטטוס מוגדרים בשני מקורות אמת שיכולים להתפצל; פער ה-Proxy בין /api בלקוח לבין /tasks בשרת בהיעדר vite.config.ts; והיעדר מוחלט של Authentication ו-CORS. אם Claude הציף סיכונים אחרים מנומקים היטב (למשל שרשור שמות שדות ב-update_task או היעדר בדיקות ל-Frontend), גם זו תוצאה טובה. (3) תרשים הרצף למחיקה צריך להראות deleteTask ב-api.ts, נתיב DELETE שמחזיר 204, וטיפול ב-404 כשהמשימה אינה קיימת. (4) מסמך טוב הוא כזה שמפתח חדש יכול לקרוא בחמש דקות ולהתחיל לעבוד. (5) git status נקי הוא ההוכחה שהחקירה הייתה באמת קריאה בלבד; אם משהו השתנה, בדקו ב-/diff מה ואיך, ושחזרו עם Git.

סיכום

למדתם להפעיל את Claude Code כחוקר: מיפוי שיטתי בשישה שלבים (סקירה, נקודות כניסה, שכבות, זרימת נתונים ומסלולי קריאה, תלויות ובדיקות וקונפיגורציה, גבולות אבטחה), הפקת תרשימי Mermaid מהממצאים, והבחנה חדה בין מחקר לשינוי בעזרת ניסוח מפורש, מצב ברירת המחדל ו-Plan Mode. ראיתם שחקירה אמיתית מציפה ממצאים שלא רואים מבחוץ, כמו פער ה-Proxy של TaskFlow, ולמדתם למקד את החקירה ב-Codebases גדולים ולנהל את מחיר ה-Context שלה. בפרק הבא ניקח את הממצאים האלה צעד קדימה: תכנון שינוי מלא ב-Plan Mode לפני שכותבים שורת קוד.
