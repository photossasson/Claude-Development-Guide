Skills

Skill הוא הדרך המרכזית להרחיב את Claude Code ביכולות משלכם: קובץ SKILL.md עם הוראות, ש-Claude טוען אוטומטית כשהוא רלוונטי או שאתם מפעילים ידנית עם /skill-name. בפרק הזה נבין מה זה Skill ומתי לבחור בו על פני כלים אחרים, נפרק את כל שדות ה-Frontmatter המתועדים, ובעיקר: נבנה חמישה Skills מקצועיים ומלאים שתוכלו להעתיק לכל פרויקט, כולל TaskFlow.

לומדה אינטראקטיבית משלימה

מעדיפים ללמוד בצעדים? בלומדה "בונים Skill ב-Claude" בונים Skill אמיתי (checking-hebrew-style) מהרעיון ועד בדיקה, מתקינים אותו גם באפליקציית Claude וגם ב-Claude Code, ובודקים את ה-Frontmatter במאמת חי. הפרק הזה הוא ההפניה המלאה שמאחוריה.

מה זה Skill

Skill הוא תיקייה עם קובץ SKILL.md בתוכה. הקובץ מכיל שני חלקים: YAML Frontmatter בין סימני --- שמגדיר מטא-נתונים (בעיקר תיאור שעוזר ל-Claude להחליט מתי להשתמש ב-Skill), וגוף Markdown עם ההוראות עצמן. ברגע שהקובץ קיים באחד המיקומים המוכרים, Claude מוסיף אותו לארגז הכלים שלו: הוא יכול לטעון אותו אוטומטית כשהבקשה שלכם מתאימה לתיאור, ואתם יכולים להפעיל אותו ישירות בהקלדת / ושם ה-Skill.

העיקרון החשוב ביותר: תיאורי ה-Skills נטענים תמיד להקשר (כדי ש-Claude ידע מה קיים), אבל גוף ה-Skill נטען רק כשמפעילים אותו. לכן חומר עזר ארוך שיושב ב-Skill כמעט לא עולה Tokens עד לרגע שבו באמת צריך אותו. זה ההבדל המהותי מ-CLAUDE.md, שנטען כולו בכל Session.

Claude Code מיישם את התקן הפתוח Agent Skills (agentskills.io), שעובד גם בכלי AI נוספים, ומרחיב אותו ביכולות ייחודיות: שליטה במי רשאי להפעיל את ה-Skill, הרצה בתוך Subagent, והזרקת הקשר דינמית מפקודות מעטפת. Anthropic מפרסמת גם מאגר Skills רשמי לדוגמה ב-github.com/anthropics/skills, הכולל את מפרט התקן, תבנית ליצירת Skill חדש, ואת ה-Skills שמאחורי יכולות המסמכים של Claude (docx, pdf, pptx, xlsx).

איזו בעיה זה פותר

אם אתם מדביקים שוב ושוב את אותן הוראות לצ'אט, או שסעיף ב-CLAUDE.md שלכם הפך מ"עובדה על הפרויקט" ל"נוהל רב-שלבי", זה בדיוק הרגע ליצור Skill. התיעוד הרשמי מגדיר את שני המצבים האלה כטריגר המרכזי ליצירת Skill.

Cowork ו-Cloud Sessions

Sessions בענן וב-Cowork לא קוראים את ~/.claude/skills/ מהמחשב שלכם; הם טוענים Skills שמופעלים בחשבון claude.ai שלכם, וב-Cloud גם Skills שנמצאים ב-.claude/skills/ בתוך ה-Repository. אם Skill קיים רק במחשב המקומי, משימה מתוזמנת בענן תדווח שהוא לא נמצא.

Skills מסונכרנים מ-claude.ai

מ-v2.1.273, Sessions במסוף שנכנסו עם חשבון claude.ai (דרך /login) טוענים אוטומטית את ה-Skills שהופעלו בחשבון: אלה שיצרתם או הפעלתם, Skills שהארגון מספק, ו-Skills מובנים של Anthropic כמו pdf ו-xlsx. הם יורדים ברקע אל ~/.claude/skills/synced/, ו-Claude Code בודק שינויים בערך כל 10 דקות בזמן עבודה וכל 40 דקות במנוחה. ב-/skills הם מופיעים תחת claude.ai sync.

  • חד-כיווני: Claude Code מוריד ולא מעלה. עריכה של קובץ ב-synced/ לא נשמרת בחשבון, וסנכרון הבא עלול לדרוס אותה. משנים את ה-Skill ב-claude.ai.
  • מתי אין סנכרון: Session שמאומת במפתח API או בטוקן מסביבה, Session על Amazon Bedrock או עם CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, ו-Sessions במצב --bare או --safe-mode.
  • הרצה לא אינטראקטיבית: כדי שהרצת claude -p תוריד את ה-Skills ותמתין לרשימה לפני שהיא עונה, הגדירו CLAUDE_CODE_SYNC_SKILLS=1.
  • כיבוי: "syncClaudeAiSkills": false בהגדרות המשתמש. Skills שכבר סונכרנו עוברים ל-~/.claude/skills/.trash/. ארגון יכול לכבות את הסנכרון לכולם באותו מפתח ב-Managed settings, או לכבות את Skills ב-claude.ai.
  • אבטחה: במחשב המקומי, Claude Code לא מריץ פקודות !`...` מתוך Skill מסונכרן, ומסנן תווים מיוחדים מהתיאור שלו.

# Code review

Review the pending changes in this repository against a base branch and report
findings ordered by severity.

## Determine scope

1. Base branch: the first argument (`$0`) if provided, otherwise `main`.
2. Collect the change set:
   - `git status --short` for the working tree state.
   - `git diff <base>...HEAD` for committed work on this branch.
   - `git diff HEAD` for uncommitted work.
3. If both diffs are empty, report "No changes to review" and stop.

## Review procedure

For every changed file:

1. Read the whole file, not only the hunks, whenever a change touches control
   flow, state, error handling, or a public interface.
2. Check the change against every item in [checklist.md](checklist.md).
3. For each modified function, find at least one caller and confirm the
   contract (arguments, return shape, raised errors) still holds.
4. Note tests: does the diff add or update tests for the behavior it changes?

## Report format

Produce a single report with these sections:

### Summary
Two or three sentences: what the change does and your overall assessment.

### Findings
One entry per finding, ordered Critical, High, Medium, Low:

- **[Severity] file:line. Title.** What is wrong, why it matters, and a
  concrete suggested fix. Quote the relevant line.

Severity definitions:
- **Critical**: data loss, security vulnerability, or guaranteed runtime failure.
- **High**: incorrect behavior on realistic inputs, broken contract, missing
  error handling on a likely path.
- **Medium**: edge-case bug, missing test for changed behavior, misleading code.
- **Low**: naming, duplication, or clarity issue worth fixing while here.

### Verdict
One line: "Ready to merge", "Ready after fixing High findings", or
"Needs rework", with the reason.

## Rules

- Report only issues you can tie to a specific file and line.
- Do not propose stylistic rewrites or formatting-only changes.
- Do not edit any files; this is a read-only review.
- If you are not sure a finding is real, say so explicitly and mark it Low.

# Bug investigation

Diagnose the root cause of a bug before changing any code. Investigation and
fixing are separate steps: this skill produces a diagnosis, not a patch.

Bug to investigate: $ARGUMENTS

If no bug description was provided above, use the problem described in the
conversation. If neither exists, ask for the symptom, the expected behavior,
and how to reproduce it, then stop.

## Procedure

1. **Restate the symptom.** One sentence: what happens, what was expected.
2. **Locate the failure surface.** From the error message, stack trace, or
   feature name, find the entry point with Grep and Glob, then read the
   relevant files end to end.
3. **Trace the data flow.** Follow the failing value or request from input to
   the point of failure. Record each file:line hop.
4. **Form hypotheses.** List every plausible cause you found, most likely first.
5. **Verify against the code.** For each hypothesis, find concrete evidence
   for or against it: the exact line, the exact condition, the exact input
   that triggers it. Reproduce with the project's test runner when a failing
   test is available.
6. **Write the diagnosis** using the structure in
   [diagnosis-template.md](diagnosis-template.md).

## Rules

- Do not edit source files during the investigation.
- Separate confirmed facts (with file:line evidence) from hypotheses, and
  label each finding as one or the other.
- One root cause per report. If you find independent additional bugs, list
  them under "Other issues noticed" without investigating them.
- If you cannot confirm a root cause, say so and report the strongest
  hypothesis, the missing evidence, and the next diagnostic step you would run.
- End the report by proposing the minimal fix and which test would prove it,
  but wait for approval before implementing.

# Feature plan

Plan the implementation of a feature. This is a planning-only skill: read the
codebase, then produce a plan. Do not modify any files.

Feature to plan: $ARGUMENTS

If no feature description was provided, ask for one and stop.

## Procedure

1. **Clarify scope.** Restate the feature in one sentence. If the request is
   ambiguous on a point that changes the design (data model, API shape, user
   flow), ask one round of focused questions before planning.
2. **Survey the codebase.** Find the modules the feature touches: entry points,
   data models, existing similar features to imitate, and the test layout.
   Record concrete file paths.
3. **Design the change.** Prefer the smallest design consistent with existing
   patterns in this repository. Reuse existing conventions for naming, error
   handling, and validation; do not introduce new frameworks or layers unless
   the feature is impossible without them.
4. **Write the plan** using the structure in
   [plan-template.md](plan-template.md). Every step must name the files it
   changes and end with a verifiable checkpoint (a command to run or a
   behavior to observe).

## Rules

- Steps must be small enough that each leaves the project working: build
  passing and tests green after every step.
- Include test work inside the steps, not as a final afterthought step.
- List real risks (migrations, breaking API changes, concurrency, performance)
  with a mitigation for each; write "None identified" only after looking.
- State every assumption you made where the request was underspecified.
- End with: "Approve this plan or request changes before implementation."

# Test generator

Write tests for: $target
Framework: $framework

If `$target` is empty, ask what to test and stop. If `$framework` is empty,
detect the framework from the project (test directories, config files,
dependency manifests) and state which one you detected.

## Procedure

1. **Read the target.** Read the target file completely. Identify every public
   behavior: normal paths, error paths, and boundaries.
2. **Learn the local conventions.** Read one or two existing test files closest
   to the target. Match their style exactly: runner, file naming, directory
   placement, fixture usage, assertion style, import paths.
3. **Plan the cases.** Before writing code, list the test cases as one line
   each: name and the single behavior it verifies. Cover, in priority order:
   - the main success path with realistic data;
   - each documented error or exception path;
   - boundaries: empty, zero, one, maximum, malformed input;
   - any bug fix in recent history of the target (regression tests).
4. **Write the tests** following [conventions.md](conventions.md).
5. **Run the tests** with the project's own test command and iterate until
   they pass. If a test fails because of a real bug in the target, keep the
   failing test, mark it as expected-failure per the framework's mechanism,
   and report the bug; do not change production code.

## Rules

- Test files only: never modify production code.
- One behavior per test; the test name states the behavior.
- Deterministic tests only: no real network, no wall clock, no shared state.
- Do not assert on private internals; assert on observable behavior.
- Report at the end: cases added, cases that found real bugs, coverage gaps
  you saw but did not cover, and why.

# Documentation update

Update the project's documentation to match its code. Ground every edit in the
actual current behavior of the code, never in what the docs used to say.

Requested scope: $ARGUMENTS

## Recent changes (injected at load time)

Uncommitted changes:
!`git diff HEAD --stat`

Last commits:
!`git log --oneline -10`

## Procedure

1. **Map the change set.** From the file list and commits above, read the full
   diffs that touch behavior, APIs, configuration, or setup. Ignore pure
   refactors that change nothing observable.
2. **Find the affected doc surfaces.** For each behavioral change, check every
   surface listed in [doc-map.md](doc-map.md) that could describe it.
3. **Verify before editing.** For each doc statement you are about to change,
   confirm the new truth by reading the code, not by guessing. For documented
   commands, check that the command as written matches the project's actual
   scripts and entry points.
4. **Edit.** Update stale statements, add missing documentation for new
   behavior, and delete documentation for removed behavior. Match the
   surrounding style, language, heading structure, and formatting.
5. **Report.** List each doc file changed with a one-line reason, plus any
   stale documentation you found that is outside the requested scope.

## Rules

- Never document behavior you have not confirmed in the code.
- Never invent features, flags, or options; if the code is ambiguous, say so
  in the report instead of guessing in the docs.
- Keep examples runnable: exact paths, exact commands, working snippets.
- Do not rewrite sections that are still accurate; smallest diff that makes
  the docs true.
- Docstrings follow the file's existing docstring style; do not introduce a
  new style into a file.

  • Skills הם קוד שרץ בהרשאותיכם. allowed-tools של Skill בפרויקט חל גם בתיקייה שלא אישרתם ב-Workspace Trust, אפילו בהרצת -p, ולכן Skill יכול להעניק לעצמו גישת כלים רחבה. סקרו Skills של Repository זר לפני שאתם עובדים בו. ארגונים יכולים להגדיר allowManagedPermissionRulesOnly ב-Managed Settings (מ-v2.1.282), ואז Claude Code מתעלם מ-allowed-tools של Skills אישיים ושל פרויקט; /status מציג על אילו Skills ההתעלמות חלה.
  • הזרקת הקשר מריצה פקודות מעטפת אמיתיות ברגע טעינת ה-Skill, לפני כל שיקול דעת של המודל. בדקו כל !`...` ב-Skill שלא כתבתם. בארגונים: disableSkillShellExecution ב-Managed Settings. ב-Skills שמסונכרנים מ-claude.ai, Claude Code לא מריץ את הפקודות האלה במחשב המקומי בכלל.
  • צמצום הרשאות מדויק: העדיפו כללים צרים (Bash(git diff *)) על פני היתר גורף, ו-disallowed-tools ל-Skills שלא אמורים לגעת בקבצים, כמו feature-plan שבנינו.
  • חסימה מרכזית: Deny על Skill מכבה הפעלת Skills על ידי המודל; Skill(deploy *) חוסם נקודתית.

Cost ו-Context

שלושה מספרים מתועדים שכדאי לזכור: תקציב רשימת התיאורים הוא 1% מחלון ההקשר (ניתן לשינוי); כל רשומה ברשימה נחתכת ב-1,536 תווים; ואחרי Compaction כל Skill שהופעל נשמר עד 5,000 Tokens בתקציב משותף של 25,000. המשמעות המעשית: description תמציתי עם מילות המפתח בהתחלה, גוף קצר ומנוסח כהוראות קבע (כי הוא נשאר בהקשר), וחומר ארוך בקבצים תומכים שנקראים לפי דרישה. Skill יקר במיוחד להרצה, כמו סקירת קוד, עדיף עם disable-model-invocation: true כדי שאתם תשלטו מתי משלמים. כדי למדוד במקום לנחש: /skill-doctor (מ-v2.1.252) מציג כמה כל Skill עולה בהקשר וכמה פעמים הופעל, ומסמן Skills שמעולם לא הופעלו; התחילו לכבות מאלה שעולים הכי הרבה.

Best Practices ו-Anti-patterns

  • description שעונה על שתיים: מה ה-Skill עושה, ומתי להשתמש בו, עם מילים שמשתמשים באמת מקלידים.
  • SKILL.md מתחת ל-500 שורות; חומר עזר בקבצים תומכים עם הפניה מפורשת.
  • כל Skill עושה דבר אחד; שרשור עם Stacking (/write-tests /fix-issue 123) עדיף על Skill ענק.
  • מדידה עם skill-creator לפני ואחרי כל שינוי מהותי.

Anti-patterns: Skill שמשכפל את CLAUDE.md (עלות כפולה, סתירות בהמשך); context: fork על Skill של הנחיות בלי משימה; הסתמכות על Skill לאכיפת חובה (המודל בוחר, Hook לא); description גנרי כמו "helps with code" שגורם להפעלות שגויות; ודריסת שם של Bundled Skill בלי כוונה מפורשת.

תרגיל: Skill משלכם

תרגיל 21.1: commit-message

בנו Skill בשם commit-message ב-.claude/skills/ של TaskFlow שמנסח הודעת Commit לשינויים שנמצאים כבר ב-Staging. דרישות: 1) רק אתם יכולים להפעיל אותו. 2) ה-Diff המדורג מוזרק לתוכן מראש. 3) פורמט קבוע: שורת נושא עד 72 תווים בציווי, שורה ריקה, גוף שמסביר מה ולמה. 4) ארגומנט אופציונלי עם הקשר נוסף, למשל מספר Issue. 5) ה-Skill מנסח בלבד ולא מריץ git commit. בדקו אותו אחרי git add על שינוי אמיתי, כולל מקרה הכשל של Staging ריק.

פתרון מוסבר
.claude/skills/commit-message/SKILL.md
---
name: commit-message
description: Draft a commit message for the currently staged changes, with a 72-character imperative subject line and a body explaining what and why.
argument-hint: "[optional context, e.g. issue number]"
disable-model-invocation: true
---

# Commit message

Draft a commit message for the staged changes below. Do not run `git commit`;
output the message text only.

Extra context from the user: $ARGUMENTS

## Staged changes

!`git diff --staged --stat`

!`git diff --staged`

## Format

1. Subject: imperative mood, at most 72 characters, no trailing period.
2. Blank line.
3. Body: what changed and why, wrapped at 72 characters. Reference the
   issue from the extra context if one was given.

If the staged diff above is empty, reply "Nothing is staged; run git add
first" and stop.

ההסבר: disable-model-invocation: true ממלא את דרישה 1, כמתועד; שתי ההזרקות ממלאות את דרישה 2, כשה---stat נותן תמונה מהירה וה-Diff המלא את הפרטים; הפורמט וההוראה "output the message text only" ממלאים את 3 ו-5; ו-$ARGUMENTS עם argument-hint את 4. מקרה הכשל מטופל בשורה האחרונה: הזרקה על Staging ריק מייצרת פלט ריק (git diff מחזיר קוד 0, ולכן ההפעלה לא מתבטלת), וההוראה אומרת ל-Claude לעצור. שדרוג אפשרי בהשראת code-review: הוספת allowed-tools: Bash(git log *) כדי ש-Claude יוכל ללמוד את סגנון ההודעות ההיסטורי בלי בקשת אישור.

סיכום

Skill הוא תיקייה עם SKILL.md: Frontmatter שקובע מתי ואיך הוא מופעל, וגוף הוראות שנטען רק בשימוש. הוא נטען מכמה מקומות (Enterprise, אישי, פרויקט, מקונן, Plugin וחשבון claude.ai) עם סדר דריסה ברור, מופעל אוטומטית לפי תיאור או ידנית עם /name, ומתחזק בעזרת ארגומנטים, קבצים תומכים, הזרקת הקשר דינמית, והרצה ב-Subagent עם context: fork. בנינו חמישה Skills שמדגימים את כל אלה על TaskFlow, ולמדנו למדוד אותם עם skill-creator ו-/skill-doctor ולאבחן תקלות עם /skills, /context, claude plugin validate ו---debug. מי שרוצה לתרגל את כל המסלול בצעדים, כולל העלאה לאפליקציית Claude, ימצא אותו בלומדה המשלימה. בפרק הבא נעבור לצד הדטרמיניסטי של האוטומציה: Hooks.
