Git ו-Pull Requests

Git הוא רשת הביטחון האמיתית של עבודה עם Agent שכותב קוד. בפרק הזה נלמד איך Claude Code עובד עם Git מאחורי הקלעים, אילו פקודות רצות בלי אישור ואילו דורשות אותו, איך לנהל Branches, Commits ו-Pull Requests בעזרת Claude, איך לפתור Merge Conflicts בצורה בטוחה, מתי להשתמש ב-Rebase וב-Cherry-pick, איך Worktrees מאפשרים כמה Sessions במקביל בלי התנגשויות, ולמה Checkpoints הם לא תחליף ל-Git.

איך Claude Code עובד עם Git

אין ל-Claude Code "מנוע Git" נסתר. כשאתם מבקשים ממנו ליצור Branch או לבצע Commit, הוא מריץ את אותן פקודות git שאתם הייתם מריצים, דרך כלי ה-Bash שלו, בתיקיית העבודה של ה-Session. זה אומר שלושה דברים חשובים: כל מה שאתם יודעים על Git תקף גם כאן; כל מה ש-Claude עושה נרשם בהיסטוריית ה-Git הרגילה וניתן לבדיקה; ומנגנון ההרשאות של Claude Code (שראינו בפעולה כבר בפרק 3) הוא שקובע מה ירוץ מיד ומה יחכה לאישור שלכם.

פקודות קריאה לעומת פקודות שינוי

לפי התיעוד הרשמי של מערכת ההרשאות, Claude Code מזהה קבוצה מובנית של פקודות Bash כפקודות קריאה בלבד ומריץ אותן בלי בקשת אישור, בכל מצב הרשאות. הקבוצה כוללת פקודות כמו ls, cat ו-grep, וגם "צורות לקריאה בלבד של git". בפועל: כש-Claude מריץ git status, git log או git diff, זה קורה בשקט. לעומת זאת, כל פקודת git שמשנה מצב, כמו git add, git commit, git checkout, git merge או git push, מציגה בקשת הרשאה במצב ברירת המחדל.

שני חריגים מתועדים שכדאי להכיר, כי הם מפתיעים בפעם הראשונה:

  • Glob לא מצוטט: פקודת git שמכילה תבנית כמו * לא מצוטטת תבקש אישור גם אם היא נראית "קריאה", כי התבנית עלולה להתרחב לדגל מסוכן.
  • שילוב cd עם git: פקודה משולבת שעוברת לתיקייה אחרת ואז מריצה git תבקש אישור, כי הרצת git בתיקייה חדשה יכולה להפעיל Hooks של אותה תיקייה.

בחלון בקשת ההרשאה של פקודת Bash אפשר ללחוץ Ctrl+E כדי לקבל הסבר של הפקודה: מה היא עושה, למה Claude מריץ אותה, ומה עלול להשתבש, עם תווית סיכון. זה שימושי במיוחד לפקודות git מורכבות שאתם לא בטוחים לגביהן.

חוקי הרשאות לפקודות Git

כשאתם בוחרים "Yes, don't ask again" לפקודת Bash, החוק נשמר לצמיתות בקובץ .claude/settings.local.json בשורש ה-Repository, וחל על כל ה-Sessions העתידיים בו, כולל בתיקיות משנה וב-Worktrees. אפשר גם להגדיר חוקים ידנית. הדוגמה הבאה, המבוססת על התיעוד הרשמי, מאפשרת Commits בלי אישור אבל חוסמת Push לחלוטין:

.claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(git commit *)"
    ],
    "ask": [
      "Bash(git checkout *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

סדר ההערכה מתועד וקבוע: קודם deny, אחר כך ask, ורק בסוף allow. חוק deny רחב כמו Bash(git push *) גובר על כל חוק allow צר יותר, ולכן הוא דרך אמינה למנוע מה-Agent לדחוף קוד בלי מעורבות שלכם. התו * תופס כל רצף תווים כולל רווחים, כך ש-Bash(git commit *) מכסה גם git commit -m "fix" וגם git commit --amend.

לשאול במקום להריץ בעצמכם

מכיוון שפקודות הקריאה של git רצות בלי חיכוך, הדרך הנוחה ביותר להתמצא במצב ה-Repository היא פשוט לשאול:

Prompts
what's the current git status? summarize what changed and what's untracked
summarize the diff since main, grouped by feature
look through the git history of backend/app/models.py and explain how it evolved

היתרון על פני הרצה ידנית: Claude לא רק מדפיס פלט, הוא מפרש אותו. סיכום של Diff גדול לפי נושאים, או הסבר של היסטוריית קובץ, חוסכים לכם קריאה של מאות שורות. התיעוד הרשמי אף ממליץ על תבנית "look through the git history" כדרך לענות על שאלות "למה הקוד הזה נראה ככה".

זרימות עבודה יומיומיות

יצירת Branch ועבודה עליו

התחילו כל משימה ב-Branch ייעודי. אפשר לבקש זאת כחלק מהמשימה עצמה:

Prompt
create a new branch called feature/task-priority off main,
then implement a priority field for tasks (low/medium/high) in the backend models.
Don't commit yet, I want to review first.

Claude יריץ git checkout -b feature/task-priority main (או git switch -c), יבקש אישור כי זו פקודת שינוי, ואז ייגש לקוד. שימו לב לחצי השני של ה-Prompt: אמירה מפורשת "אל תבצע Commit עדיין" שומרת את שלב הסקירה בידיים שלכם. אם יש לכם מוסכמות שמות ל-Branches (למשל feature/, fix/, chore/), כתבו אותן ב-CLAUDE.md; התיעוד הרשמי מציין במפורש "Repository etiquette (branch naming, PR conventions)" כתוכן מומלץ לקובץ הזה.

Staging ו-Commit עם הודעה טובה

אחרי שסקרתם את השינויים, בקשו Commit:

Prompt
stage only the backend changes and commit with a descriptive message
following Conventional Commits. Don't include the frontend files.

Claude יריץ git add על הקבצים הרלוונטיים בלבד, ינסח הודעת Commit על סמך ה-Diff בפועל, ויריץ git commit אחרי אישורכם. הודעות שנוצרות כך טובות בדרך כלל מהממוצע האנושי, כי הן נכתבות מול ה-Diff המלא, אבל חובה לסקור אותן לפני אישור, משתי סיבות: ראשית, Claude מתאר את מה שהקוד עושה, לא בהכרח את הסיבה העסקית שבגללה ביקשתם את השינוי; אם ההקשר חשוב (מספר Issue, החלטת מוצר), הוסיפו אותו. שנית, הודעת ה-Commit היא תיעוד קבוע; טעות בה מביכה יותר מטעות בקוד שאפשר לתקן בשקט.

מוסכמה מקובלת ושווה לאימוץ היא Conventional Commits: קידומת סוג (feat:, fix:, docs:, refactor:), תיאור קצר בזמן הווה, ובמידת הצורך גוף הודעה עם ההקשר. אם תציינו זאת ב-CLAUDE.md פעם אחת, כל ה-Commits בפרויקט יהיו עקביים.

שורת ה-Attribution

כברירת מחדל Claude Code מוסיף שורת ייחוס ל-Commits ול-Pull Requests שהוא יוצר. אפשר להתאים או לרוקן אותה דרך ההגדרה attribution ב-settings.json, למשל {"commit": "", "pr": ""} כדי לבטל. בצוותים רבים דווקא משאירים אותה, כי היא מסמנת בשקיפות אילו שינויים נוצרו בעזרת Agent.

תיקון ה-Commit האחרון

שכחתם קובץ או שההודעה לא מדויקת? בקשו git commit --amend:

Prompt
I forgot to include the test file in the last commit.
Amend the commit to add backend/tests/test_tasks.py, keep the same message.

הסיכון: --amend משכתב את ה-Commit האחרון (מזהה ה-Hash משתנה). זה בטוח לחלוטין כל עוד ה-Commit לא נדחף ל-Remote. אם הוא כבר נדחף, תיקון ידרוש Force Push, וזה תרחיש שנרצה להימנע ממנו (ראו Anti-patterns). כלל אצבע: Amend רק על עבודה מקומית.

צפייה בשינויים: /diff ו-git diff

לפני כל אישור Commit, תסתכלו על השינויים. יש לכם שתי דרכים משלימות:

  • /diff: פותח מציג Diff אינטראקטיבי בתוך ה-Session, שמציג גם את השינויים הלא מקובעים (uncommitted) וגם Diff לכל תור של Claude בנפרד. חצים ימינה ושמאלה מחליפים בין תצוגת ה-git diff הנוכחית לתורות בודדים, חצים למעלה ולמטה עוברים בין קבצים, Enter פותח את ה-Diff של הקובץ הנבחר, ו-Esc חוזר לרשימה. התצוגה מתעדכנת אוטומטית כשמצב ה-Git משתנה מחוץ ל-Session.
  • git diff דרך Claude: בקשו "show me the diff and explain the risky parts" כדי לקבל לא רק את השינויים אלא גם פירוש שלהם. ל-Diff גדול, git diff --stat נותן תמונת מבט מהירה בזול (ראו הערת עלות).

Pull Requests עם Claude

דרישה מוקדמת: gh CLI מחובר

הדרך המתועדת והמומלצת לעבודה מול GitHub היא כלי ה-CLI הרשמי gh. התיעוד של Claude Code קובע במפורש: התקינו את gh ו-Claude ידע להשתמש בו ליצירת Issues, פתיחת Pull Requests וקריאת תגובות. בלעדיו Claude יכול לפנות ל-GitHub API ישירות, אבל בקשות לא מאומתות נתקלות מהר ב-Rate Limits. ההתחברות נעשית פעם אחת, מחוץ ל-Session או בתוכו:

$ gh auth login ? Where do you use GitHub? GitHub.com ? What is your preferred protocol for Git operations? HTTPS ... (זרימת אימות בדפדפן) $ gh auth status github.com: Logged in to github.com account your-username

האימות של gh הוא של המשתמש שלכם ברמת מערכת ההפעלה; Claude פשוט מריץ את הפקודות תחת אותו אימות. לכן ההרשאות שיש לכם ב-GitHub הן בדיוק ההרשאות שיש ל-Agent, וזה עוד טעם לחוקי deny על פעולות מסוכנות.

יצירת PR

לפי התיעוד הרשמי אפשר לבקש ישירות "create a pr for my changes", או להוביל בשלבים:

Prompts (זרימה מהתיעוד הרשמי)
summarize the changes I've made to the authentication module
create a pr
enhance the PR description with more context about the security improvements

מאחורי הקלעים Claude ידחוף את ה-Branch (באישורכם) ויריץ gh pr create עם כותרת ותיאור שהוא מנסח מתוך ה-Commits וה-Diff. תכונה מתועדת ושימושית: כשה-PR נוצר עם gh pr create, ה-Session מקושר אליו אוטומטית. כדי לחזור אליו בעתיד מריצים claude --from-pr 1234 (עם המספר שלכם), שפותח את בוחר ה-Sessions מסונן לאותו PR, או מדביקים את כתובת ה-PR בחיפוש של /resume.

תיאור PR טוב הוא מסמך שיווקי פנימי: הוא צריך לומר מה השתנה, למה, איך בדקתם, ומה הסיכונים. Claude מנסח היטב את "מה", אבל את "למה" רק אתם יודעים. ההמלצה הרשמית: סקרו את ה-PR שנוצר לפני שליחה ובקשו מ-Claude להדגיש סיכונים ושיקולים.

מענה לתגובות סקירה

כשה-PR חוזר עם הערות, אפשר לתת ל-Claude לקרוא אותן ולטפל בהן:

Prompt
read the review comments on PR #42 with gh, address each one,
push the fixes, and draft a short reply for every comment explaining what changed

Claude ישתמש בפקודות כמו gh pr view 42 --comments כדי למשוך את ההערות, יתקן, ויכין תשובות. כלל חשוב: אל תיתנו ל-Agent לפרסם תשובות בשמכם בלי לקרוא אותן. בקשו טיוטות ("draft a reply") ופרסמו בעצמכם, לפחות עד שתבנו ביטחון בזרימה.

סקירה מקומית עם /code-review

לפני שדוחפים, שווה להריץ סקירה עצמית. /code-review הוא Skill מובנה שסוקר את ה-Diff הנוכחי לאיתור באגים של נכונות והזדמנויות ניקוי. התחביר המתועד:

$ /code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [target]

מה חשוב לדעת, לפי התיעוד העדכני:

  • מה נסקר כברירת מחדל: ה-Commits של ה-Branch שלכם שמעבר ל-Upstream, ועוד השינויים הלא מקובעים. אפשר להעביר יעד אחר: נתיב קובץ, מספר PR, שם Branch, או טווח כמו main...my-feature.
  • רמות מאמץ: low ו-medium מדווחות רק על הממצאים בעלי הביטחון הגבוה ביותר (פחות אזעקות שווא); high עד max פורשות רשת רחבה יותר וייתכנו ממצאים פחות ודאיים. בלי ארגומנט, הסקירה משתמשת ברמת המאמץ הנוכחית של ה-Session.
  • דגלים: --fix מיישם את הממצאים על עץ העבודה; --comment מפרסם אותם כתגובות Inline על ה-PR ב-GitHub (דורש gh מחובר).
  • איפה זה רץ: הסקירה רצה כ-Subagent ברקע עם Context Window משלה, והממצאים מגיעים לשיחה בסיומה. חשוב: תיקוני --fix של סקירת רקע מוחלים מחוץ ל-Checkpoints של ה-Session, ולכן /rewind לא מבטל אותם; לביטול משתמשים ב-Git.
  • ultra: מריץ סקירת ענן עמוקה (ultrareview) שמחויבת ב-Usage Credits. דורש חשבון claude.ai ואינו זמין ב-Bedrock, ב-Agent Platform של Google Cloud, ב-Microsoft Foundry או בארגונים עם Zero Data Retention.
Code Review בענן Research Preview

בנפרד מהפקודה המקומית, קיים שירות Code Review מנוהל שסוקר PRs אוטומטית ב-GitHub ומפרסם ממצאים כתגובות Inline, עם רמות חומרה. הוא ב-Research Preview, זמין למינויי Team ו-Enterprise, ומופעל עם @claude review בתגובת PR. הסקירה המקומית עם /code-review זמינה בכל התוכניות.

Merge Conflicts: פתרון בטוח

Merge Conflict נוצר כששני Branches שינו את אותן שורות, ו-Git לא יכול להכריע לבד. זו אחת המשימות שבהן Claude מצטיין, כי פתרון טוב דורש להבין את הכוונה של שני הצדדים, לא רק את הטקסט. האסטרטגיה המומלצת בארבעה שלבים:

  1. תמונת מצב לפני הכול. ודאו שעץ העבודה נקי (git status). אל תתחילו Merge עם שינויים לא מקובעים; אם משהו ישתבש, יהיה קשה להפריד בין השינויים שלכם לשל ה-Merge.
  2. ניתוח שני הצדדים לפני פתרון. אחרי ש-git merge נעצר על Conflict, בקשו ניתוח, לא תיקון:
Prompt
we have merge conflicts. For each conflicted file, explain what our branch
changed, what their branch changed, and what the intent of each side was.
Don't resolve anything yet.
  1. פתרון מונחה כוונה. עכשיו בקשו פתרון עם קריטריון מפורש, למשל: "resolve the conflicts keeping both behaviors: our validation logic and their new status field. Show me each resolution before staging". Claude יערוך את הקבצים, יסיר את סמני ה-Conflict (<<<<<<<, =======, >>>>>>>), ויציג לכם כל החלטה.
  2. אימות אחרי פתרון. פתרון Conflict הוא כתיבת קוד חדש לכל דבר, ולכן חובה לאמת: הריצו את הבדיקות, בקשו git diff מול שני ההורים, וּודאו שאין סמני Conflict שנשכחו (grep -rn "<<<<<<<" . תופס אותם). רק אז אשרו את ה-Commit של ה-Merge.
דלת המילוט

בכל שלב לפני ה-Commit, הפקודה git merge --abort מחזירה את ה-Repository למצב שלפני ה-Merge. אם הפתרון מסתבך, עדיף לבטל, למשוך את Claude לניתוח רגוע, ולנסות שוב, מאשר לתקן פתרון גרוע.

מתי לא לתת ל-Claude להכריע: כשה-Conflict נוגע להחלטה עסקית (איזו התנהגות משתי גרסאות היא הנכונה), ההכרעה שלכם. Claude מנתח מצוין, אבל הוא לא יודע מה סוכם בישיבת המוצר. בקשו ממנו להציג את האפשרויות והשלכותיהן, והחליטו בעצמכם.

Rebase ו-Cherry-pick עם Claude

Rebase: מתי ואיך בבטחה

git rebase "משתיל" מחדש את ה-Commits של ה-Branch שלכם על קצה Branch אחר, ויוצר היסטוריה ליניארית ונקייה. המחיר: הוא משכתב היסטוריה. כל ה-Commits מקבלים מזהים חדשים. מכאן נגזר הכלל החשוב ביותר: לעולם לא עושים Rebase ל-Branch שנדחף ואנשים אחרים עובדים עליו. נוהל בטוח לעבודה עם Claude:

Prompt (נוהל Rebase בטוח)
1. create a backup branch pointing at my current HEAD (backup/pre-rebase)
2. rebase feature/task-priority onto the latest main
3. if there are conflicts, stop and analyze both sides before resolving
4. after the rebase, run the backend tests and show me git log --oneline main..HEAD

ה-Branch הגיבוי בצעד 1 הופך את כל התהליך להפיך: אם משהו נשבר, git reset --hard backup/pre-rebase מחזיר אתכם לנקודת ההתחלה. במהלך ה-Rebase, Conflicts מטופלים כמו בסעיף הקודם, עם הבדל אחד: הם עלולים לחזור Commit אחרי Commit, ודלת המילוט היא git rebase --abort.

הימנעו מ-Rebase אינטראקטיבי בתוך Session

git rebase -i פותח עורך טקסט אינטראקטיבי, וסביבת ההרצה של פקודות ב-Claude Code אינה מיועדת לעורכים אינטראקטיביים. זו הנחיה פרקטית של המדריך (לא מגבלה מתועדת פורמלית): בקשו מ-Claude להשיג את אותה תוצאה בדרכים לא אינטראקטיביות, למשל git rebase רגיל, git commit --amend, או איחוד Commits עם git reset --soft ו-Commit חדש.

Cherry-pick: העברת Commit בודד

git cherry-pick מעתיק Commit ספציפי מ-Branch אחד לאחר. השימוש הקלאסי: תיקון דחוף שנעשה ב-Branch פיתוח וצריך להגיע ל-Branch תחזוקה. עם Claude זה נוח במיוחד, כי הוא מוצא בשבילכם את ה-Commit הנכון:

Prompt
find the commit on feature/task-priority that fixed the title validation
(only that fix, not the feature work), and cherry-pick it onto main.
Show me the commit you picked before applying.

הסיכונים: Cherry-pick יוצר Commit חדש עם תוכן זהה אך מזהה שונה, מה שעלול לגרום ל-Conflicts עתידיים כשה-Branches יתמזגו; ו-Commit שנבחר לא נכון עלול לגרור תלות חסרה (הקוד מסתמך על שינוי מ-Commit קודם שלא הועבר). לכן תמיד בקשו לראות את ה-Commit לפני היישום, והריצו בדיקות אחרי.

Worktrees: עבודה מקבילית אמיתית

מה זה ולמה זה חשוב

Git Worktree הוא תיקיית עבודה נוספת של אותו Repository: קבצים משלה ו-Branch משלה, אבל אותה היסטוריה ואותו Remote. בשביל Claude Code זו התשתית לעבודה מקבילית: שני Sessions שרצים באותה תיקייה דורכים זה לזה על הקבצים; שני Sessions בשני Worktrees מבודדים לחלוטין. אחד בונה פיצ'ר בזמן שהשני מתקן באג, ואף עריכה של האחד לא נוגעת בקבצים של השני.

התמיכה המובנית: הדגל --worktree

לפי תיעוד ה-Worktrees הרשמי, מפעילים Session מבודד עם הדגל --worktree (או -w) ושם:

$ claude --worktree feature-auth

מה קורה, כפי שמתועד:

  • ה-Worktree נוצר כברירת מחדל תחת .claude/worktrees/<name>/ בשורש ה-Repository, על Branch חדש בשם worktree-<name>. בלי שם, Claude מגריל שם כמו bright-running-fox.
  • הרצה של אותה פקודה עם שם אחר בטרמינל שני פותחת Session מקביל ומבודד.
  • ה-Repository חייב לפחות Commit אחד; בלעדיו הפקודה נכשלת עם שגיאת Failed to resolve base branch "HEAD".
  • כברירת מחדל (worktree.baseRef בערך "fresh") ה-Branch החדש נגזר מ-Branch ברירת המחדל של ה-Remote, בדרך כלל main. הערך "head" גוזר מה-HEAD המקומי הנוכחי, כולל Commits שלא נדחפו.
  • אפשר להיכנס ישירות ל-Worktree של PR: claude --worktree "#1234" (במרכאות, כדי שה-Shell לא יפרש את # כהערה).
  • גם באמצע Session אפשר לבקש מ-Claude בשפה חופשית "work in a worktree", והוא ייצור אחד עם הכלי המובנה EnterWorktree.

Worktree הוא Checkout טרי, ולכן קבצים שאינם במעקב Git, כמו .env, לא נמצאים בו. הפתרון המתועד: קובץ .worktreeinclude בשורש הפרויקט, בתחביר .gitignore, שמפרט אילו קבצים מתעלמי-Git יועתקו אוטומטית לכל Worktree חדש:

.worktreeinclude
.env
.env.local

ביציאה מ-Session אינטראקטיבי, Claude בודק אם יש ב-Worktree עבודה שתאבד: אם הוא נקי, Session ללא שם מוסר אוטומטית (כולל ה-Branch); אם יש בו שינויים או Commits חדשים, תישאלו אם לשמור או להסיר. חזרה ל-Session עם /resume או --resume מחזירה אתכם לאותו Worktree. שלושה דברים משותפים לכל ה-Worktrees של אותו Repository: תיקיית ה-.git, תוספי Plugins ברמת הפרויקט, ואישורי הרשאות שמורים.

Best Practice

הוסיפו את .claude/worktrees/ ל-.gitignore, כפי שממליץ התיעוד, כדי שתכני ה-Worktrees לא יופיעו כקבצים לא במעקב ב-Checkout הראשי.

חוקי תיאום: בעלים אחד לכל Branch

הבידוד של Worktrees פותר התנגשויות קבצים, אבל לא התנגשויות כוונה. שלושה חוקים פשוטים סוגרים את הפער:

  • בעלים אחד לכל Branch. Agent אחד (או אדם אחד) עובד על Branch נתון בכל רגע. Git עצמו עוזר לאכוף זאת: הוא מסרב לבצע Checkout של Branch שכבר משוחרר ב-Worktree אחר.
  • חלוקה לפי אזורים. כשמריצים שני Sessions על אותו פרויקט, חלקו משימות שנוגעות בקבצים שונים (אחד ב-Backend, אחד ב-Frontend). אחרת תיפגשו ב-Merge עם Conflicts מיותרים.
  • מיזוג דרך נקודה אחת. כל ה-Branches מתמזגים ל-main דרככם, אחד אחרי השני, עם בדיקות בין לבין. אל תיתנו לשני Agents למזג במקביל.

ל-Subagents יש בידוד מתועד משלהם: הוספת isolation: worktree ל-Frontmatter של Subagent מותאם גורמת לו לרוץ תמיד ב-Worktree זמני משלו. נרחיב על כך בפרק על Subagents.

שחזור: revert, reset, ולמה Checkpoints הם לא Git

git revert לעומת git reset

שתי דרכים לבטל Commit, עם הבדל קריטי:

פקודהמה היא עושהמתי בטוחה
git revert <hash>יוצרת Commit חדש שמבטל את השינוי. ההיסטוריה נשמרתתמיד, כולל על Branches משותפים שנדחפו
git reset --hard <hash>מזיזה את ה-Branch אחורה ומוחקת את השינויים מעץ העבודה. ההיסטוריה משוכתבתרק על עבודה מקומית שלא נדחפה

כלל אצבע לעבודה עם Agent: כשמבקשים מ-Claude לבטל משהו, אמרו לו באיזו שיטה להשתמש. "revert the commit that added the priority field" הוא בטוח; "reset" הוא כלי חד שמוחק עבודה, וטוב שהוא דורש אישור הרשאה. אם אתם לא בטוחים, בקשו: "what's the safest way to undo commit abc123 given that it was already pushed?"

ההבחנה הקריטית: Checkpoints/Rewind לעומת Git

ל-Claude Code יש מנגנון Checkpoints מובנה: לפני כל Prompt נשמר מצב הקבצים, ו-/rewind (או Esc Esc) משחזר קוד, שיחה או שניהם (הכרנו אותו בקצרה בפרק 3, ונעמיק בו בפרק 19). קל להתבלבל ולחשוב שזה "Git קטן". זו טעות מסוכנת. אלה ההבדלים המתועדים:

מאפייןCheckpoints / RewindGit
רמת פעולהברמת ה-Session: "ביטול מקומי" של צעדי השיחההיסטוריה קבועה של הפרויקט, לשיתוף פעולה
מה נעקברק עריכות שנעשו בכלי העריכה של Claudeכל שינוי בקבצים במעקב, מכל מקור
שינויים מפקודות Bash (rm, mv, cp)לא נעקבים. לא ניתנים לשחזור ב-Rewindנעקבים כרגיל
עריכות של Subagents (כולל /code-review --fix ברקע)לא משוחזרות ב-Rewindנעקבות כרגיל
שינויים ידניים שלכם מחוץ ל-Sessionלא נעקבים בדרך כללנעקבים כרגיל
תוקףנשמרים עם השיחה; מנוקים אחרי 30 יום כברירת מחדל (הגדרת cleanupPeriodDays), ותמונות קבצים נשמרות ל-100 ה-Checkpoints האחרונים ב-Sessionלצמיתות
Checkpoints הם לא תחליף ל-Git

התיעוד הרשמי מנסח זאת במפורש: חשבו על Checkpoints כעל "local undo" ועל Git כעל "permanent history". פרויקט שמנוהל רק עם Checkpoints הוא פרויקט בלי גיבוי: מחיקת קובץ ב-rm על ידי ה-Agent לא ניתנת לשחזור ב-Rewind, ואחרי 30 יום גם ה-Checkpoints עצמם נעלמים. תמיד עבדו בתוך Repository עם Commits תכופים.

עבודה מקבילית בטוחה: הכללים

נסכם את משטר העבודה כשכמה Sessions או Agents פועלים על אותו פרויקט:

  • Worktree נפרד לכל Session (claude --worktree), לעולם לא שני Sessions כותבים באותה תיקייה.
  • בעלים אחד לכל Branch: אף פעם לא שני Agents על אותו Branch.
  • Commits קטנים ותכופים: כל יחידת עבודה שעוברת בדיקות מקובעת מיד. Commit קטן קל לסקור, קל לבטל עם revert, וממזער את שטח ה-Conflicts.
  • מיזוג סדרתי דרך אדם: אתם נקודת האינטגרציה, לא ה-Agents.
  • משיכת main עדכני לפני כל משימה חדשה, כדי לצמצם סטייה בין Branches.

תבנית עבודה מתועדת ששווה לאמץ: Writer/Reviewer. Session אחד מממש, ו-Session שני עם הקשר נקי סוקר את התוצאה. התיעוד מציין שהקשר טרי משפר סקירה, כי המודל לא מוטה לטובת קוד שהוא עצמו כתב זה עתה.

שגיאות נפוצות

  • קיבוע Secrets. קובץ .env עם מפתחות אמיתיים שנכנס ל-Commit הוא דליפה לצמיתות: גם אחרי מחיקה הוא נשאר בהיסטוריה. הגנות: .gitignore שכולל את קובצי הסודות, חוק Read(.env) ברשימת ה-deny, ובקשה מ-Claude לסרוק את ה-Diff לפני Commit: "check the staged diff for anything that looks like a secret or API key". הרחבה על ניהול סודות בפרק 20.
  • Commits ענקיים. "תבנה את כל הפיצ'ר ואז תעשה Commit אחד" מייצר Diff של אלפי שורות שאי אפשר לסקור באמת. בקשו מ-Claude לקבע בשלבים לוגיים: מודלים, אחר כך Routes, אחר כך בדיקות.
  • לתת ל-Agent לעשות Force Push. git push --force מוחק היסטוריה משותפת ויכול לדרוס עבודה של אחרים. אל תאשרו אותו כבדרך אגב, ושקלו חוק deny על Bash(git push --force*) או על Bash(git push *) כולו. אם באמת צריך (אחרי Rebase של Branch אישי), העדיפו git push --force-with-lease, שנכשל אם ה-Remote התקדם מאז המשיכה האחרונה, והריצו אותו בעצמכם.
  • קיבוע זבל של סביבת העבודה. תיקיות כמו .claude/worktrees/, __pycache__ או node_modules שמגיעות ל-Commit כי אף אחד לא עדכן .gitignore. בקשו מ-Claude לתחזק את הקובץ כחלק מהקמת פרויקט.
  • אישור אוטומטי של הודעות Commit. ההודעה היא התיעוד הקבוע של ההחלטה. שלוש שניות של קריאה לפני האישור חוסכות ארכיאולוגיה עתידית.

Troubleshooting

  • יצירת PR נכשלת עם שגיאת אימות. תסמין: gh מחזיר שגיאה בסגנון "authentication required" או "HTTP 401/403". בדקו עם gh auth status; אם אין התחברות, הריצו gh auth login והשלימו את זרימת הדפדפן. אם ההתחברות קיימת אבל הפעולה נכשלת, בדקו שיש לכם הרשאת כתיבה ל-Repository (ב-Fork, ה-PR נפתח מה-Fork אל המקור).
  • Detached HEAD. תסמין: git status מציג "HEAD detached at ...". זה קורה אחרי Checkout של Hash ספציפי, וזה מצב מסוכן רק אם יוצרים בו Commits בלי Branch. אם לא שיניתם כלום: git switch main (או ה-Branch הקודם עם git switch -). אם כבר יש Commits שאתם רוצים לשמור: git switch -c rescue-branch ואז מיזוג רגיל. אפשר גם פשוט לתאר את המצב ל-Claude ("git says detached HEAD, I don't know why, help me get back safely without losing work"); זו בדיוק משימת האבחון שהוא טוב בה.
  • לולאת Conflicts ב-Rebase. תסמין: כל Commit ב-Rebase נעצר על אותם Conflicts. סיבה שכיחה: ה-Branch ארוך מדי וסטה רחוק מ-main. פתרונות בסדר עדיפות: git rebase --abort ומעבר ל-Merge רגיל (Conflict אחד גדול במקום רבים קטנים); או איחוד ה-Branch ל-Commit אחד לפני ה-Rebase (git reset --soft על נקודת הפיצול ו-Commit חדש); ולמניעה עתידית, הפעלת git config rerere.enabled true, שמלמד את Git לזכור פתרונות Conflict ולהחיל אותם שוב אוטומטית.
  • claude --worktree נכשל. שגיאת Failed to resolve base branch "HEAD" פירושה Repository בלי אף Commit; צרו Commit ראשון. שגיאה על Trust פירושה שטרם אישרתם את התיקייה: הריצו claude רגיל פעם אחת בתיקייה ואשרו.
  • ה-Push נדחה על ידי השרת. תסמין: "protected branch" או "push declined due to repository rule violations". זו לא תקלה אלא מדיניות: ה-Branch מוגן ודורש PR. הזרימה הנכונה היא Branch נפרד ו-gh pr create.

אבטחה

  • אישורי גישה (Credentials). Claude פועל תחת האימות שלכם: ה-Credential Helper של Git וה-Token של gh. לעולם אל תדביקו Personal Access Token בתוך Prompt ואל תבקשו מ-Claude לכתוב אותו לקובץ; השתמשו ב-gh auth login ובמנהלי סודות ייעודיים. זכרו שכל מה שמודבק ב-Session נשמר בתמלול המקומי שלו.
  • Branches מוגנים. הגדירו Branch Protection ב-GitHub על main: חובת PR, חובת CI ירוק, איסור Force Push. זו שכבת הגנה בצד השרת שלא תלויה בשום הגדרה מקומית של Claude Code, ולכן היא עוצרת גם טעות של Agent וגם טעות שלכם.
  • חוקי deny כקו הגנה שני. Bash(git push *) ב-deny בפרויקטים רגישים, לצד Read(.env) ודומיו. זכרו את המגבלה המתועדת: תבניות שמנסות להגביל ארגומנטים הן שבירות, ולכן חוק רחב וברור עדיף על חוק "חכם" וצר.
  • זהירות עם bypassPermissions. התיעוד מציין שהמצב הזה מדלג על כל בקשות האישור, כולל כתיבות לתיקיות רגישות כמו .git. השתמשו בו רק בסביבות מבודדות (Containers, VMs) שבהן נזק אינו אפשרי.
  • Git Hooks של תיקיות זרות. זו הסיבה שהשילוב cd + git מבקש אישור: הרצת git בתיקייה לא מוכרת יכולה להפעיל Hooks שמישהו אחר כתב. אל תאשרו את השילוב הזה על תיקיות שלא אתם שולטים בהן.

הערת עלות ו-Context

פקודות Git עצמן זולות, אבל הפלט שלהן נכנס ל-Context Window ונשאר שם. Diff של 3,000 שורות ששולף Claude הוא אלפי Tokens שמכבידים על כל המשך ה-Session. הרגלים חוסכים: בקשו git diff --stat או git log --oneline לפני צלילה לקבצים ספציפיים; העדיפו Commits קטנים שמייצרים Diffs קטנים; והשתמשו ב-/code-review, שרץ כ-Subagent ברקע עם הקשר משלו ומחזיר רק ממצאים. לגבי כסף אמיתי: סקירת ultra מחויבת ב-Usage Credits עם חלון אישור, ושירות ה-Code Review הענני לארגונים עולה לפי התיעוד הרשמי 15 עד 25 דולר בממוצע לסקירה, לפי גודל ה-PR ומורכבותו (נכון ל-28.07.2026). עוד על ניהול Context בפרק הבא.

Best Practices

  • עבדו תמיד בתוך Repository עם Commit התחלתי, גם בניסויים. זה תנאי ל-Worktrees ורשת הביטחון היחידה מפני פקודות Bash הרסניות.
  • Branch לכל משימה, Commit לכל יחידת עבודה ירוקה, PR לכל מיזוג ל-main.
  • כתבו את מוסכמות ה-Git של הצוות (שמות Branches, פורמט הודעות, שפת PR) ב-CLAUDE.md פעם אחת, במקום לחזור עליהן בכל Prompt.
  • סקרו כל הודעת Commit וכל תיאור PR שנוצרו עבורכם, והוסיפו את ה"למה" שרק אתם יודעים.
  • הריצו /code-review לפני פתיחת PR; זול יותר לתקן לפני שעיני הצוות רואות.
  • לפני Rebase או פעולה משכתבת היסטוריה: Branch גיבוי. אחרי Merge או פתרון Conflict: בדיקות.
  • נצלו את קישור ה-Session ל-PR: claude --from-pr מחזיר אתכם להקשר המלא של העבודה כשהסקירה חוזרת.

Anti-patterns

  • "YOLO merge": אישור פתרון Conflicts בלי לקרוא אותו ובלי להריץ בדיקות. פתרון Conflict שגוי הוא באג שמוסתר בתוך Commit של Merge, המקום האחרון שבו מחפשים.
  • עבודה שבועית על Branch אחד בלי משיכת main: מתכון ללולאת Conflicts. מזגו או עשו Rebase מ-main בתדירות גבוהה.
  • שני Agents על אותו Branch "כי זה מהיר יותר": זה לא. הם ידרסו זה את זה ואתם תשלמו בזמן איחוי.
  • שימוש ב-git reset --hard כפתרון ברירת מחדל לכל בעיה: הוא מוחק עבודה ללא אפשרות חזרה פשוטה. קודם git status והבנה, ורק אז החלטה מודעת בין revert, reset ו-stash.
  • הסתמכות על Rewind כגיבוי: כפי שראינו, שינויים מפקודות Bash ועריכות של Subagents לא משוחזרים, וההיסטוריה נמחקת אחרי 30 יום.
  • --dangerously-skip-permissions על Repository עם גישת Push לסביבות אמיתיות: ביטול כל הבלמים בדיוק במקום שבו הם הכי נחוצים.

תרגיל

תרגיל 13.1: Branch, שינוי מקביל ופתרון Conflict על TaskFlow

נעבוד על עותק ה-TaskFlow מפרק 3 (ודאו ש-git init ו-Commit התחלתי בוצעו). ניצור בכוונה Conflict ונפתור אותו עם Claude:

  1. פתחו claude בתיקיית הפרויקט ובקשו: "create a branch feature/title-length off main, change the title max_length in backend/app/models.py from 200 to 120, run the backend tests, and commit with a conventional message".
  2. חזרו ל-main (בקשו: "switch back to main") וצרו Branch שני: "create a branch feature/title-trim off main, and in backend/app/models.py change the title field so leading/trailing whitespace is stripped before validation. Run the tests and commit".
  3. עכשיו מזגו: "merge feature/title-length into feature/title-trim". שני ה-Branches נגעו באותה שורת title, אז צפוי Conflict.
  4. בקשו ניתוח לפני פתרון: "explain both sides of the conflict and their intent, don't resolve yet".
  5. בקשו פתרון שמשלב את שתי הכוונות: "resolve keeping both: max_length 120 and the whitespace stripping. Show me the resolution before staging".
  6. אמתו: הריצו את הבדיקות, בדקו ב-/diff שאין סמני Conflict, ואשרו את ה-Commit של ה-Merge.
  7. סיום: בקשו "show me git log --oneline --graph for the last 6 commits" וּודאו שאתם מבינים את הגרף שנוצר.
פתרון מוסבר

שלבים 1 ו-2: כל Branch נגזר מ-main בנפרד, ולכן שניהם מכילים גרסאות שונות של אותה שורה: title: str = Field(min_length=1, max_length=200) הופכת בענף אחד ל-max_length=120 ובשני מקבלת לוגיקת Strip (למשל Validator של Pydantic או str_strip_whitespace). שימו לב שכל פקודת שינוי (checkout, add, commit) ביקשה אישור, בעוד git status ו-git diff רצו בשקט; זה בדיוק ההבדל בין פקודות קריאה לפקודות שינוי מהסעיף הראשון.

שלב 3: ה-Merge נעצר עם הודעת CONFLICT על models.py. זה המצב הרצוי בתרגיל. אם במקרה לא נוצר Conflict (למשל כי Claude מימש את ה-Strip בשורות אחרות לגמרי), אפשר לגרום לו במכוון: בקשו בשני ה-Branches שינוי של אותה שורת Field עצמה.

שלבים 4 ו-5: ההפרדה בין ניתוח לפתרון היא לב התרגיל. בניתוח, Claude צריך לזהות ששני הצדדים אינם סותרים באמת: אחד מקשיח אורך, השני מנקה רווחים, ואפשר לשלב. הפתרון הנכון הוא שדה title עם max_length=120 וגם ניקוי רווחים, בלי שום סמן Conflict בקובץ. אם Claude מציע לבחור צד אחד בלבד, תקנו אותו: הכוונה של שני הצדדים צריכה להישמר, וזו בדיוק ההכרעה שאסור להשאיר ל-Agent בלי קריטריון מפורש.

שלב 6: הבדיקות הן האימות האמיתי: ודאו שבדיקת יצירת משימה עם כותרת ארוכה מ-120 נכשלת כמצופה ושכותרת עם רווחים מנוקה. אם אין בדיקות כאלה, זה הרגע לבקש: "add a test for a 121-character title and a test for a title with surrounding whitespace, then run them". Commit ה-Merge מאושר רק אחרי ירוק מלא.

שלב 7: הגרף אמור להציג את שני הענפים מתפצלים מ-main ומתאחדים ב-Commit ה-Merge. אם אתם רואים קו ישר בלבד, ה-Merge בוצע כ-Fast-forward, כלומר לא באמת היה פיצול; חזרו ובדקו ששני ה-Branches אכן נגזרו מ-main ולא זה מזה.

סיכום

Claude Code עובד עם Git בדיוק כמוכם: אותן פקודות, אותה היסטוריה, עם מנגנון הרשאות שמריץ פקודות קריאה בשקט ועוצר פקודות שינוי לאישור. למדנו לנהל את הזרימה היומית (Branches, הודעות Commit שחובה לסקור, /diff), לפתוח ולנהל Pull Requests עם gh ולסקור אותם מקומית עם /code-review, לפתור Conflicts בשיטת "ניתוח לפני פתרון, אימות אחרי", לבצע Rebase ו-Cherry-pick עם Branch גיבוי, ולהריץ Sessions מקבילים ב-Worktrees עם בעלים אחד לכל Branch. והחשוב מכול: Checkpoints הם כפתור ביטול נוח בתוך ה-Session, אבל רק Git, עם Commits קטנים ותכופים, הוא היסטוריה אמיתית. בפרק הבא נטפל במשאב היקר ביותר של כל Session: ה-Context Window.
