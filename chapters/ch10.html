Debugging

Debugging עם Claude Code הוא לא "תדביק שגיאה, תקבל תיקון". זו שיטה: הזנה נכונה של הודעות שגיאה, Stack Traces ו-Logs, רפרודוקציה מינימלית, עבודה מונחית השערות, ובדיקת רגרסיה שמוכיחה שהבעיה באמת נפתרה ולא הוסתרה. בפרק נעבור על השיטה ואז נפעיל אותה על תרחישים אמיתיים מ-TaskFlow: באג ב-Backend עם Stack Trace, באג State אסינכרוני ב-React, בדיקה הפכפכה (Flaky), כשל ב-CI, ו-Race Conditions.

מה משתנה כשמדבגים עם Agent

היתרון הגדול של Claude Code ב-Debugging הוא שהוא לא רק קורא את השגיאה, הוא יכול לפעול: להריץ את פקודת השחזור, לקרוא את הקוד סביב כל Frame ב-Stack Trace, להוסיף Log זמני, להריץ שוב ולהשוות. הלולאה שראינו לאורך המדריך (פעולה, קריאת פלט, מסקנה) היא בדיוק לולאת Debugging. הסיכון המרכזי הוא אותו סיכון: מודל שרוצה "לסגור את המשימה" עלול להציע תיקון שמעלים את התסמין בלי לגעת בשורש. לכן השיטה בפרק הזה בנויה משלושה עוגנים: ראיות (שגיאה מדויקת ושחזור), השערות מדורגות לפני קוד, ובדיקת רגרסיה כתנאי לסיום.

מתי להשתמש בתהליך המלא: באג שאינכם מבינים תוך דקה, באג שחוזר, וכל דבר הפכפך או תלוי תזמון. מתי לא: שגיאת תחביר או Typo שהקומפיילר כבר הסביר; שם, "fix this" עם השגיאה זה כל מה שצריך.

חומר הגלם: שגיאות, Stack Traces ו-Logs

איכות ה-Debugging נקבעת קודם כול באיכות מה שהזנתם. הכלל: ראיות מדויקות, בכמות מדודה.

  • הדביקו את השגיאה מילה במילה. "אני מקבל שגיאת 500" גרוע פי כמה מ-Traceback מלא. ניסוח חופשי מאבד בדיוק את הפרטים שמכריעים: שם החריגה, הקובץ, השורה, הערך.
  • צרפו את דרך השחזור. ההמלצה הרשמית: לומר ל-Claude באיזו פקודה משחזרים את הבעיה, והאם היא עקבית או הפכפכה. "curl כזה מחזיר 422, קורה בכל פעם" נותן ל-Claude יכולת לאמת את התיקון בעצמו.
  • Logs גדולים לא מדביקים, מסננים. קובץ Log של אלפי שורות ימלא את ה-Context ברעש (ראו סעיף ה-Troubleshooting בהמשך). חתכו עם grep או tail, או תנו ל-Claude לקרוא את הקובץ בעצמו ולחפש בו בכלים שלו, במקום להעמיס הכול לשיחה.
  • צילומי מסך עובדים. שגיאה בדפדפן או ב-DevTools? הדביקו צילום מסך ישירות לשיחה (Ctrl+V, או גרירה לחלון). התיעוד ממליץ על כך במפורש לשגיאות ולמצבי UI.

שתי דרכים מעשיות להזרים חומר גלם ל-Session: מבפנים, הרצה ישירה עם קידומת ! כך שהפלט מצטרף לשיחה (!pytest -q למשל); ומבחוץ, צנרת (Pipe) אל claude, שעובדת כמו כל כלי Unix:

Bash
# סיכום חד-פעמי של Log בלי לפתוח Session אינטראקטיבי
tail -n 200 server.log | claude -p "identify the errors in this log, group them, and rank likely root causes"

# שגיאות בלבד, משני הערוצים, ישירות לניתוח
uvicorn app.main:app 2>&1 | grep -i error | claude -p "what is failing here?"

הצורה claude -p (מצב לא אינטראקטיבי, פרק 33) נוחה במיוחד לניתוחי Log: השאלה נענית פעם אחת, וה-Session האינטראקטיבי שלכם נשאר נקי.

עקרון הרפרודוקציה המינימלית

רפרודוקציה מינימלית היא הדרך הקצרה ביותר לגרום לבאג לקרות: פקודה אחת, קלט אחד, בלי כל מה שלא הכרחי. היא משרתת שלוש מטרות: היא מוכיחה שהבנתם את התנאים (אם אינכם יכולים לשחזר, אתם עדיין מנחשים); היא נותנת ל-Claude לולאת אימות, להריץ לפני ואחרי התיקון; והיא הופכת כמעט מעצמה לבדיקת רגרסיה. כשבאג מגיע כתיאור עמום ("לפעמים הכותרות נעלמות"), העבודה הראשונה היא לצמצם:

Prompt
Users report that task titles sometimes appear empty in the list.
Before proposing any fix: find the shortest reproduction you can,
as a single curl command or a single test, and show me the exact
output proving the bug happens.

שימו לב לסדר הכפוי: קודם הוכחה שהבאג קורה, רק אחר כך דיבור על תיקון. זה מגן עליכם מהמצב הנפוץ שבו "תוקן" משהו שלא היה הבאג.

Debugging מונחה השערות

במקום לתת למודל לצלול לקוד ולנסות דברים, מבקשים ממנו קודם לחשוב כמו חוקר: רשימת השערות מדורגת לפי סבירות, ולכל השערה בדיקה ממוקדת שמאשרת או פוסלת אותה. זו התבנית המרכזית של הפרק:

Prompt (תבנית ההשערות)
Here is the error, and how I trigger it: [error + repro].
Give me the 3 most likely root causes, ranked. For each:
what evidence supports it, and one specific, cheap check
(a command, a log line to read, a file to inspect) that would
confirm or eliminate it. Do not change any code yet.

למה זה עדיף על "תתקן"? כי בדיקות ממוקדות זולות, וכי דירוג מפורש חושף את חשיבת המודל לביקורת שלכם. אם ההשערה המובילה נשמעת לכם לא סבירה על סמך מה שאתם יודעים על המערכת, אמרו זאת עכשיו, לפני שנכתב קוד. אחרי שהשערה אושרה בראיות, ורק אז, עוברים לתיקון.

שורש ולא סימפטום: רגרסיה לפני תיקון

ההנחיה החשובה ביותר בפרק, ישירות מתוך ה-Best Practices הרשמיים: לבקש טיפול בשורש הבעיה, לא השתקת השגיאה. התבנית המומלצת בתיעוד לתיקון באג מתחילה בבדיקה נכשלת:

Prompt
write a failing test that reproduces the issue, then fix the
code until the test passes. address the root cause, don't
suppress the error. show me the test output before and after.

הסדר הזה, רגרסיה קודם, נותן שלוש ערובות: הבדיקה הנכשלת מוכיחה שהבנתם את הבאג; המעבר מאדום לירוק מוכיח שהתיקון עובד; והבדיקה נשארת בקוד ומונעת מהבאג לחזור בשקט. "show me the test output before and after" מבקש ראיות, לא הצהרות; זה הרגל שהתיעוד ממליץ עליו לכל אימות. תיקון שמגיע בלי בדיקה שמוכיחה אותו הוא לא תיקון, הוא ניחוש שהתמזל.

/debug ו-claude doctor: לאבחון של Claude Code עצמו

שני כלים שחשוב להכיר, וחשוב לא פחות להבין מה הם לא: הם מאבחנים את Claude Code עצמו, לא את האפליקציה שלכם.

  • /debug [description] הוא Skill מובנה שמפעיל רישום Debug ל-Session הנוכחי וחוקר תקלות בעזרת קריאת קובץ ה-Debug Log של ה-Session (רישום ה-Debug כבוי כברירת מחדל, אלא אם הפעלתם עם claude --debug). אפשר לצרף תיאור כדי למקד את הניתוח. השתמשו בו כשמשהו ב-Claude Code מתנהג מוזר: כלי שנכשל, Hook שלא רץ, MCP Server שלא נטען.
  • claude doctor, מהטרמינל, מדפיס אבחון לקריאה בלבד של ההתקנה בלי לפתוח Session. בתוך Session, ה-Skill המובנה /doctor מריץ בדיקת תקינות רחבה שגם יכולה לתקן: התקנות כפולות, בעיות PATH, הגדרות לא תקינות, Hooks איטיים ועוד.

כלל אצבע: הקוד שלכם שבור, השתמשו בשיטת הפרק הזה. Claude Code עצמו שבור, התחילו מ-claude doctor ו-/debug, והמשיכו בפרק 39 (מדריך ה-Troubleshooting המרוכז).

תרחיש 1: Backend, באג עם Stack Trace ב-FastAPI

נתרגל על תרחיש שאתם יכולים לשתול בעצמכם ב-TaskFlow. נניח שעמית הוסיף Endpoint סטטיסטיקה בסוף הקובץ backend/app/routers/tasks.py (הוסיפו אותו אצלכם כדי לעקוב):

backend/app/routers/tasks.py (נוסף בסוף הקובץ, לצורך התרחיש)
@router.get("/stats")
def stats() -> dict:
    with get_conn() as conn:
        rows = conn.execute(
            "SELECT status, COUNT(*) AS n FROM tasks GROUP BY status"
        ).fetchall()
    total = sum(r["n"] for r in rows)
    done = next((r["n"] for r in rows if r["status"] == "done"), 0)
    return {"total": total, "done_ratio": done / total}

הוא בדק ידנית עם נתונים, עבד לו, ועשה Commit. אתם מושכים את הקוד, מריצים, ומקבלים:

$ curl -s localhost:8000/tasks/stats {"detail":[{"type":"int_parsing","loc":["path","task_id"], "msg":"Input should be a valid integer, unable to parse string as an integer", "input":"stats"}]}

שגיאה מבלבלת: ביקשנו סטטיסטיקה, וקיבלנו תלונה על task_id לא חוקי. מפעילים את תבנית ההשערות עם הראיות המלאות:

Prompt
GET /tasks/stats returns this 422: [paste the JSON above].
It reproduces every time. The endpoint exists in
@backend/app/routers/tasks.py. Give me ranked root causes with
a check for each. Don't change code yet.

מה קורה: ההשערה המובילה של Claude נכונה ומאלפת: ב-FastAPI נתיבים נבחנים לפי סדר ההגדרה, ו-/tasks/stats נתפס על ידי הנתיב הדינמי /tasks/{task_id} שהוגדר לפניו. המחרוזת "stats" נכשלת בהמרה ל-int, ומכאן ה-422. הבדיקה המאשרת: סדר ההגדרות בקובץ. התיקון: להעביר את /stats מעל /{task_id}. אבל לפני התיקון, רגרסיה:

Prompt
confirmed. first add a failing test: GET /tasks/stats should
return 200. then fix by moving the route, and run the tests.

הבדיקה החדשה נכשלת (422), הנתיב מוזז, ואז... הפתעה. הבדיקה עדיין נכשלת, הפעם אחרת:

$ pytest -q tests/test_tasks.py::test_stats_endpoint FAILED ... ZeroDivisionError: division by zero File "app/routers/tasks.py", line 30, in stats return {"total": total, "done_ratio": done / total}

זה ערכו של Stack Trace אמיתי: השורה האחרונה מצביעה בדיוק על הבעיה השנייה, שהוסתרה מאחורי הראשונה. בבסיס נתונים ריק (כמו זה של הבדיקות!) total הוא אפס. העמית לא פגש את זה כי בדק ידנית עם נתונים. Claude מציע תיקון שורש: להחזיר done_ratio: 0.0 כשאין משימות, ולהוסיף מקרה בדיקה לבסיס ריק. שני באגים, שתי בדיקות רגרסיה, ולולאה אחת שיטתית. שימו לב מה לא עשינו: לא עטפנו ב-try/except שמחזיר משהו גנרי. זו בדיוק "הסתרת הבעיה" שנדבר עליה ב-Anti-patterns.

תרחיש 2: Frontend, באג State אסינכרוני ב-React

הבאג הבא קיים בקוד האמיתי של frontend/src/App.tsx, ותוכלו לשחזר אותו בדפדפן: לחיצה מהירה כפולה על כפתור הסטטוס של משימה מקדמת אותה רק שלב אחד במקום שניים, ולפעמים משאירה את התצוגה לא מסונכרנת. תיאור טוב ל-Claude כולל את התסמין, את התנאי (מהירות), ואת הקובץ:

Prompt
In @frontend/src/App.tsx: clicking a task's status button twice
quickly advances the status only one step instead of two.
Slow clicks work. Explain the race step by step before fixing:
what value does each click read, and when does state update?

מה קורה: Claude מסביר את שרשרת האירועים: הלחיצה קוראת NEXT_STATUS[t.status] מתוך ה-Render הנוכחי. שתי לחיצות מהירות רצות לפני ש-refresh הספיק להביא מצב חדש, ולכן שתיהן קוראות אותו סטטוס ישן ושולחות לשרת את אותו עדכון בדיוק (למשל פעמיים "העבר ל-in_progress"). הבעיה אינה בשרת; היא Stale State קלאסי בצד הלקוח. בונוס שנחשף באותה חקירה: השרשרת updateStatus(...).then(refresh) בלי טיפול בשגיאות, כך שכשל רשת נבלע בשקט ולא מגיע ל-setError.

התיקון שאושר אצלנו צנוע ומקומי: חסימת הכפתור בזמן שעדכון בתעופה (מצב pending לכל משימה), הוספת catch שמנתב ל-setError, ורענון בסיום. ב-Frontend קשה יותר לכתוב רגרסיה בלי תשתית בדיקות UI (אין כזו ב-TaskFlow; ראו פרק 11), ולכן האימות כאן ידני ומפורש: npm run typecheck ירוק, ואז שחזור התרחיש בדפדפן, לחיצה כפולה מהירה, ובדיקה שהמשימה התקדמה בדיוק שלב אחד והכפתור היה חסום בזמן הבקשה.

תרחיש 3: בדיקה נכשלת או Flaky

בדיקה הפכפכה היא בדיקה שעוברת לבד ונכשלת בחבילה, או להפך, או נכשלת אחת לכמה ריצות. הצעד הראשון בטריאז' הוא תמיד לקבוע באיזה משלושת הסוגים מדובר, וזה בדיוק מה שמבקשים:

Prompt (תבנית טריאז')
The test [name] is flaky. Run it three ways and report results:
alone, as part of the full suite, and 10 times in a row alone.
Based on the pattern, tell me whether this smells like shared
state, ordering dependency, or timing, and what to check next.

דוגמה אמיתית מ-TaskFlow: נניח שהוספתם בדיקה שסופרת משימות: יוצרים שתיים ומצפים ש-GET /tasks יחזיר בדיוק שתיים. לבדה היא עוברת; בחבילה המלאה היא נכשלת עם שש. הסיבה נמצאת ב-Fixture האמיתי של backend/tests/test_tasks.py: כל הבדיקות חולקות קובץ בסיס נתונים זמני אחד לריצה, ו-init_db רק יוצר את הטבלה אם אינה קיימת, בלי לנקות נתונים בין בדיקות. משימות שנוצרו בבדיקות קודמות מצטברות, וכל בדיקה שמניחה בסיס ריק תלויה בסדר הריצה. התיקון השורשי הוא בידוד: ניקוי הטבלה ב-Fixture לפני כל בדיקה (DELETE FROM tasks), ולא "תיקון" הבדיקה שתצפה לשש. ההבחנה הזאת היא לב הטריאז': כשבדיקה נכשלת, או שהקוד שבור, או שהבדיקה שבורה, או שהבידוד שבור, ולכל אחד מהשלושה תיקון אחר. אל תיתנו ל-Claude לבחור "לרכך את ה-Assert" בלי הוכחה שהבדיקה היא האשמה.

תרחיש 4: נכשל רק ב-CI

"עובר אצלי, נכשל ב-CI" הוא כמעט תמיד הבדל סביבה: גרסאות, משתני סביבה, מצב התחלתי (בסיס נתונים ריק!), מערכת קבצים, או מקביליות. חומר הגלם כאן הוא ה-Log של ריצת ה-CI, ועם GitHub נוח למשוך רק את החלק הכושל דרך ה-CLI בשם gh:

Bash
gh run view --log-failed | claude -p "why did this CI run fail?
the same tests pass locally. rank likely environment differences
based on the log and our workflow file .github/workflows/ci.yml"

הדגל --log-failed מחזיר את ה-Log של הצעדים הכושלים בלבד, בדיוק הסינון שמונע הצפת Context. ב-TaskFlow, קובץ ה-Workflow מריץ pytest -q על סביבה טרייה לגמרי; בדיקת הספירה מהתרחיש הקודם יכולה לעבור מקומית (בגלל סדר מקרי נוח) וליפול שם. באופן כללי, כששגיאת CI לא משוחזרת מקומית, בקשו מ-Claude להשוות במפורש: "list every difference between my local run and the CI job as defined in the workflow file". על אינטגרציית GitHub Actions המלאה, כולל הרצת Claude בתוך ה-CI עצמו, נרחיב בפרק 28.

תרחיש 5: Race Conditions

Race Condition הוא באג שתלוי בסדר או בתזמון של פעולות מקביליות, ולכן הוא הקשה מכולם: הוא לא משוחזר בכל ריצה, נעלם כשמוסיפים Debugger (כי התזמון משתנה), וקורס דווקא בעומס אמיתי. ראינו כבר אחד אמיתי, הלחיצה הכפולה ב-React; דוגמה קלאסית בצד השרת עם SQLite היא שני תהליכים שכותבים בו זמנית ומקבלים database is locked. כיוון שאי אפשר "פשוט לשחזר", האסטרטגיה שונה משאר הפרק בשני מקומות:

  • אפיון במקום שחזור בודד (Characterization): הופכים באג הסתברותי לניתן למדידה על ידי ריצה בלולאה, ומודדים שכיחות לפני ואחרי התיקון. למשל: for i in $(seq 1 50); do pytest -q -k test_name || echo "FAIL $i"; done. אם נכשל 7 מתוך 50 לפני ו-0 מתוך 50 אחרי, יש לכם ראיה סטטיסטית, לא אנקדוטה.
  • רישום (Logging) כראיה מרכזית: במקום לנחש את שרשרת האירועים, מתעדים אותה. בקשו מ-Claude להוסיף רישום זמני וממוקד עם חותמות זמן ומזהה בקשה סביב האזור החשוד, לשחזר בלולאה, ואז לנתח את ה-Log ולשרטט את סדר האירועים בפועל בריצה כושלת מול ריצה תקינה.
Prompt
I suspect a race in [area]. Plan a characterization first:
1) a loop that measures how often it fails,
2) temporary timestamped logging around the suspected section,
3) run, then reconstruct the exact interleaving from the log.
Only after we see the interleaving, propose a fix. Also plan
how we remove the temporary logging afterwards.

הערת יושרה הנדסית: תיקוני תזמון "קוסמטיים" (להוסיף sleep, לנסות שוב עד שמצליח) משנים את ההסתברות, לא את הסיבה. תיקון אמיתי משנה את מבנה הסנכרון: מנעילה, תור, פעולה אטומית, או ביטול השיתוף. דרשו מ-Claude להצביע על השורה שבה שני מסלולים ניגשים לאותו מצב, לפני שאתם מאשרים כל תיקון.

ספריית Prompts ל-Debugging

Prompts לשימוש חוזר
# טריאז' פתיחה (התבנית המרכזית)
Here is the error and the repro: [...]. Rank the 3 most likely
root causes with one cheap check each. No code changes yet.

# הסבר Stack Trace
Explain this stack trace frame by frame: which frames are our
code vs framework code, and where does the bad value originate?

# רפרודוקציה מינימלית
Reduce this bug to the smallest reproduction: one command or one
test. Show the output proving it fails.

# רגרסיה לפני תיקון (מבוסס על התבנית הרשמית)
Write a failing test that reproduces the issue, then fix it.
Address the root cause, don't suppress the error.

# חקירת שינוי אחרון
This worked before. Use git log and git diff on [area] to find
which recent change could cause this behavior.

# טריאז' Flaky
Run the test alone, in the full suite, and 10 times in a row.
Classify: shared state, ordering, or timing?

# השוואת סביבות (CI)
List every difference between my local run and the CI job as
defined in the workflow file. Which could explain the failure?

# אפיון Race
Measure the failure rate in a loop, add timestamped logging,
reconstruct the interleaving, then propose a structural fix.

טעויות נפוצות

  • לתאר את השגיאה במקום להדביק אותה: פרפרזה מוחקת את הפרטים המזהים. תמיד מילה במילה.
  • להדביק Log של 5,000 שורות: ההפך הסימטרי, וקטלני ל-Context. סננו קודם.
  • לדלג על הרפרודוקציה: אם אין פקודה שמפילה, אין דרך לדעת שהתיקון תיקן.
  • לקבל את התיקון הראשון שמעלים את התסמין: שאלו תמיד "מה היה השורש, ולמה התיקון הזה מטפל בו?". תשובה מגומגמת = חזרו להשערות.
  • לדבג בתוך Session עמוס: חקירה רצינית מתחילה נקייה. /clear ואז הראיות בלבד.
  • לשכוח להסיר את הרישום הזמני: תכננו את ההסרה מראש, בתוך אותו Prompt שמוסיף אותו.

Troubleshooting של Session ה-Debugging עצמו

לפעמים מה שנתקע הוא לא הבאג אלא החקירה. שלושה מצבים וטיפולם:

  • ההקשר זוהם ב-Logs ובניסיונות כושלים: אחרי חקירה ארוכה, המודל מתחיל לערבב גרסאות ישנות של הקוד ותסמינים ממקרים קודמים. ההמלצה הרשמית חדה: אחרי שני תיקונים כושלים על אותה בעיה, /clear ו-Prompt פתיחה חדש שמסכם את מה שנלמד (ההשערות שנפסלו הן מידע יקר!). חלופה עדינה: /rewind עם "Summarize from here" שמכווץ את החלק הרועש. ניהול Context שיטתי, בפרק 14.
  • Claude מסתובב במעגלים בין שתי השערות: עצרו את הלולאה ובקשו טבלה: כל השערה, הראיה בעדה, הראיה נגדה, והבדיקה שתכריע. אם אין בדיקה מכריעה, חסר לכם מידע, וזה הממצא.
  • ניתוח Log כבד נדרש אבל חבל על ה-Context: האצילו ל-Subagent: "use a subagent to analyze server.log and report only the error patterns and their frequency". החקירה רצה ב-Context נפרד וחוזר רק סיכום (פרק 25).

Security

סודות בתוך Logs

Logs אמיתיים מכילים לעיתים קרובות בדיוק את מה שאסור להדביק לשום מקום: כותרות Authorization, Tokens, Cookies, מחרוזות חיבור לבסיסי נתונים ופרטים אישיים של משתמשים. לפני שאתם מדביקים Log לשיחה (או מבקשים מ-Claude לקרוא אותו), נקו: sed 's/Bearer [A-Za-z0-9._-]*/Bearer [REDACTED]/g' server.log היא התחלה טובה ל-Tokens, והרגל טוב הוא לחסום קריאת קבצי סודות כמו .env בחוקי Deny (פרק 18). זכרו שגם תוכן שה-Session קורא בעצמו נשלח לעיבוד המודל, בדיוק כמו טקסט שהדבקתם. ואם סוד אמיתי כבר דלף ל-Log או לשיחה, הבעיה אינה השיחה: החליפו (Rotate) את הסוד.

עלות ו-Context

חקירות Debugging הן מהצרכניות הגדולות של Tokens: הרבה פלטי פקודות, הרבה קריאת קבצים, הרבה סבבים. שלושה חיסכונות שלא פוגעים באיכות: הזינו שגיאות מסוננות ולא Logs שלמים (עשר השורות הרלוונטיות שוות יותר מחמשת אלפים); השתמשו ב-claude -p לשאלות ניתוח חד-פעמיות על Logs במקום לנפח את ה-Session האינטראקטיבי; והאצילו סריקות ארוכות ל-Subagents. עקבו עם /context, ואל תהססו לסכם חלק רועש של החקירה עם /rewind. פירוט מלא על עלויות בפרק 30.

Best Practices

  • שגיאה מילה במילה + פקודת שחזור + עקבי או הפכפך: שלושת אלה בכל Prompt פתיחה.
  • השערות מדורגות עם בדיקה מכריעה לכל אחת, לפני כל שינוי קוד.
  • בדיקת רגרסיה נכשלת לפני התיקון, ירוקה אחריו, ונשארת בקוד.
  • ראיות ולא הצהרות: פלט הבדיקה לפני ואחרי, בתוך השיחה.
  • באג הפכפך? קודם מסווגים (מצב משותף, סדר, תזמון) ורק אז מתקנים.
  • חקירה חדשה מתחילה ב-Context נקי, ומסתיימת בניקוי הרישום הזמני.

Anti-patterns

  • ההשתקה: try/except: pass, הורדת רמת Log, או החזרת ערך ברירת מחדל שרירותי במקום לתקן את מקור הערך השגוי. התסמין נעלם, הבאג נשאר.
  • ה-sleep הקסום: השהיה שרירותית ש"פותרת" Race. משנה הסתברות, לא סיבה, ותתפוצץ בעומס.
  • מחיקת הבדיקה הנכשלת: או ריכוך ה-Assert עד שהיא עוברת. הבדיקה היא העדה; אל תעלימו אותה.
  • שדרוג תלויות עיוור: "אולי גרסה חדשה תפתור", בלי ראיה שהבאג בתלות. מוסיף משתנים במקום לצמצם.
  • ה"תנסה משהו" האינסופי: לתת למודל לשנות קוד שוב ושוב בלי השערות ובלי ראיות, עד שבמקרה עובר. גם אם זה "הצליח", אינכם יודעים מה תוקן, וה-Diff מלא שינויים מיותרים.

רשימת בדיקה: לפני שסוגרים באג

  • יש רפרודוקציה מינימלית שנכשלת לפני התיקון ועוברת אחריו, והיא נשמרה כבדיקת רגרסיה.
  • שורש הבעיה מוסבר במשפט אחד עם הפניה לקובץ ולשורה, לא "שיניתי ועכשיו עובד".
  • החבילה המלאה רצה, לא רק הבדיקה שנגעה בבאג, והפלט המלא נבדק ולא סוכם על ידי Claude.
  • ה-Diff נוגע רק בקוד היעד; קובצי הבדיקות הקיימים לא רוככו ולא נמחקו.
  • אם התיקון שינה התנהגות גלויה למשתמש, התיעוד ו-CHANGELOG עודכנו באותו Commit.
  • אם הבאג חזר על עצמו או נבע ממוסכמה לא כתובה, נוספה שורה ל-CLAUDE.md שתמנע אותו בפעם הבאה.

תרגיל

תרגיל 10.1: הכותרות הנעלמות

באג אמיתי שקיים בקוד המקורי של TaskFlow (אם תיקנתם אותו בעקבות פרק 3, קחו עותק טרי של examples/taskflow כדי לתרגל). דיווח המשתמש: "ערכתי כותרת של משימה, ועכשיו היא מוצגת ריקה ברשימה. יצירת משימה עם כותרת ריקה דווקא נחסמת". מטרתכם, בשיטת הפרק: (1) נסחו לפחות שתי השערות ובדיקה מכריעה לכל אחת; (2) מצאו רפרודוקציה מינימלית כפקודת curl אחת; (3) כתבו בדיקת רגרסיה נכשלת; (4) תקנו את השורש; (5) הוכיחו עם פלט לפני ואחרי. רמז לכיוון: השוו מה עובר ב-POST /tasks מול PATCH /tasks/{id}, ושימו לב איזה סוג "ריק" באמת נחסם.

פתרון מוסבר

השערות סבירות: (א) ה-Frontend מציג לא נכון כותרת תקינה; בדיקה: GET /tasks ישירות ב-curl ולראות מה באמת שמור. (ב) ה-API מקבל בעדכון כותרת "ריקה למראה"; בדיקה: PATCH ידני עם ערכים גבוליים. בדיקת (א) מראה שהערך השמור באמת "ריק", ולכן הבעיה בצד השרת.

רפרודוקציה מינימלית: הכותרת שנחסמת היא "" (מחרוזת ריקה), אבל מחרוזת רווחים עוברת. השדה title ב-TaskUpdate (בקובץ backend/app/models.py) מוגדר עם min_length=1, ורווח נספר כתו לכל דבר:

$ curl -s -X PATCH localhost:8000/tasks/1 -H "Content-Type: application/json" -d '{"title": " "}' {"id":1,"title":" ","description":"","status":"todo",...}

סטטוס 200 וכותרת של שלושה רווחים: הבאג מוכח. (אותו פגם קיים גם ב-TaskCreate, ולכן גם POST עם רווחים עובר; דיווח המשתמש על "יצירה נחסמת" נכון רק לגבי "".)

רגרסיה לפני תיקון:

backend/tests/test_tasks.py (added)
def test_update_rejects_blank_title(client):
    task = client.post("/tasks", json={"title": "Valid"}).json()
    res = client.patch(f"/tasks/{task['id']}", json={"title": "   "})
    assert res.status_code == 422


def test_create_rejects_blank_title(client):
    res = client.post("/tasks", json={"title": "   "})
    assert res.status_code == 422

תיקון השורש: Validator של Pydantic שמנקה רווחים ודוחה תוצאה ריקה, על שני המודלים:

backend/app/models.py (added)
from pydantic import BaseModel, Field, field_validator


class TaskCreate(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    description: str = Field(default="", max_length=2000)

    @field_validator("title")
    @classmethod
    def title_not_blank(cls, value: str) -> str:
        value = value.strip()
        if not value:
            raise ValueError("title must not be blank")
        return value

ב-TaskUpdate אותו Validator, עם עצירה מוקדמת כש-value הוא None (שדה שלא נשלח). שימו לב שהתיקון גם מנרמל: כותרת עם רווחים בקצוות נשמרת נקייה. הוכחה: שתי הבדיקות אדומות לפני, ירוקות אחרי, וכל שאר החבילה ירוקה. ולמה זה שורש ולא סימפטום? כי טיפלנו בהגדרת ה"כותרת חוקית" במקום היחיד שאוכף אותה (שכבת ה-Validation), ולא, למשל, בסינון תצוגה ב-Frontend שהיה משאיר נתונים פגומים בבסיס הנתונים.

סיכום

ראינו ש-Debugging טוב עם Claude Code עומד על ארבע רגליים: חומר גלם מדויק ומסונן (שגיאות מילה במילה, Logs דרך grep ו-claude -p, צילומי מסך), רפרודוקציה מינימלית שהופכת לבדיקת רגרסיה, השערות מדורגות עם בדיקות מכריעות לפני כל שינוי קוד, והתעקשות על שורש הבעיה עם ראיות לפני ואחרי. הפעלנו את השיטה על חמישה סוגי תקלות שונים בתכלית, מ-422 מסתורי ועד Race, וראינו שהשלד זהה ורק כלי האימות מתחלפים. בפרק הבא נעמיק ברגל שהכול נשען עליה: Testing שיטתי עם Claude Code.
