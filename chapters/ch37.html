Architecture ו-Design Review

סקירת Architecture ו-Design היא הרגע שבו שואלים "האם אנחנו בונים את הדבר הנכון, בדרך שתחזיק מעמד?" לפני שכותבים קוד או ממזגים אותו. בפרק הזה נלמד להפעיל את Claude Code כאנליסט קריאה-בלבד: מיפוי רכיבים ותלויות, איתור הפרות שכבות, ניסוח ADR, מידול איומים בסגנון STRIDE, סקירת זרימת נתונים, API, דרישות לא-פונקציונליות ותלויות, ביקורת של תוכנית בנייה לפני יישום, וזיהוי סטייה בין תיעוד לקוד. לאורך כל הפרק חוזר כלל אחד: Claude מספק ניתוח והמלצות; בני אדם מחזיקים בהחלטות ה-Architecture ובאחריות עליהן.

מהי סקירת Architecture ו-Design ואיזו בעיה היא פותרת

סקירת Architecture בוחנת את המבנה של המערכת: אילו רכיבים קיימים, איך הם תלויים זה בזה, איפה עוברים הנתונים ואיפה עוברים גבולות האמון. סקירת Design בוחנת החלטה ספציפית לפני שהיא הופכת לקוד: האם הפתרון המוצע מתאים לבעיה, מה החלופות, ומה המחיר לטווח ארוך. שתיהן שונות מ-Code Review רגיל (פרק 9 ו-פרק 28), שבודק שורות קוד קונקרטיות אחרי שנכתבו.

הבעיה שהסקירה פותרת היא בעיה של עלות: טעות בשורת קוד עולה דקות לתקן; טעות במבנה עולה שבועות, כי היא מתפשטת לכל מה שנבנה מעליה. הקושי המסורתי הוא שסקירה כזו דורשת מישהו שקורא את כל הקוד הרלוונטי, זוכר את התלויות ומצליב אותן מול התיעוד. זו עבודה יקרה ומשעממת, ולכן היא לעיתים קרובות לא נעשית כלל. כאן בדיוק Claude מועיל: הוא קורא הרבה קבצים במהירות, לא מתעייף מהצלבות, ומחזיר תמונה מבוססת ראיות שאתם יכולים לאשר, לתקן או לדחות.

הכלל המרכזי: Claude מנתח, בני אדם מחליטים

לפני שנצלול לטכניקות, חשוב לקבע את חלוקת התפקידים. בכל מה שקשור ל-Architecture, Claude הוא יועץ, לא בעל ההחלטה. שלוש סיבות מהותיות:

  1. אחריות (Accountability). כשמערכת נופלת בייצור, מישהו צריך להסביר למה נבחר מבנה מסוים. "המודל המליץ" אינה תשובה מקצועית. החלטת Architecture היא התחייבות של הצוות, ומי שחותם עליה צריך להבין ולעמוד מאחוריה.
  2. הקשר שמחוץ ל-Repository. Claude רואה את מה שקיים בקבצים וב-Git History. הוא לא רואה את התקציב, את החוזה עם הלקוח, את הכישורים של הצוות, את מפת הדרכים לשנה הבאה, או את הסיבה הפוליטית שבגללה מערכת ישנה עדיין חיה. חלק גדול מהחלטות ה-Architecture נקבע דווקא על ידי הגורמים האלה.
  3. תמריצים. מודל שמתבקש "למצוא בעיות" ימצא בעיות; מודל שמתבקש "להמליץ" ימליץ בביטחון. התיעוד הרשמי מציין במפורש שסוקר שהתבקש למצוא פערים ידווח בדרך כלל על כמה גם כשהעבודה תקינה. הביקורת של Claude אינה מכוילת לפי מה שחשוב לעסק שלכם, אלא לפי מה שביקשתם. אתם הפילטר.
Best Practice

נסחו כל בקשת סקירה עם שלושה חלקים: היקף (מה בודקים), קריטריונים (מה נחשב ממצא) ופורמט פלט (טבלה, רשימה מדורגת, מסמך). ואז התייחסו לתוצאה כאל טיוטה של יועץ חיצוני: קראו, אמתו מול הקוד, החליטו.

מתי להשתמש ומתי לא

מתי כן:

  • לפני התחלת Feature שנוגע ביותר ממודול אחד, כדי לאשר תוכנית לפני שנכתב קוד (בהמשך ל-פרק 7).
  • לפני Merge של שינוי מבני: הוספת שכבה, החלפת ספרייה מרכזית, שינוי חוזה API.
  • בכניסה לפרויקט קיים (פרק 6) או Legacy (פרק 36), כשאין תיעוד עדכני.
  • לפני ביקורת אבטחה או תאימות, כאשר צריך מיפוי איומים וסיווג נתונים.
  • באופן מחזורי, למשל אחת לרבעון, כדי לגלות סחף בין התיעוד לבין המציאות.

מתי לא:

  • לשינויים זעירים ומקומיים. סקירת מבנה לתיקון שגיאת כתיב היא בזבוז Tokens וזמן.
  • כתחליף לדיון צוותי. Claude מכין חומר לדיון; הוא לא מחליף את הדיון.
  • כשההחלטה תלויה בעיקר בגורמים שאינם בקוד (עלות רישוי, כישורי צוות, לוחות זמנים). אפשר לבקש מ-Claude לרשום את השיקולים, אבל השקילה היא שלכם.
דרישות מוקדמות

הפרק מניח שאתם יודעים לחקור Repository במצב קריאה-בלבד (פרק 6), לעבוד ב-Plan Mode (פרק 7) ולהגדיר Subagents (פרק 25). הדוגמאות רצות על TaskFlow מהתיקייה examples/taskflow.

איך זה עובד מושגית: סוקר קריאה-בלבד

סקירת Architecture היא לולאת Agentic שמורכבת כמעט רק מקריאות: Read, Grep, Glob, ולעיתים Bash לפקודות כמו git log. שום דבר לא צריך להשתנות. לכן שלוש דרכי ההגנה מפרק 6 תקפות גם כאן: ניסוח מפורש ("research only"), מצב ברירת המחדל שעוצר כל עריכה, ו-Plan Mode כאכיפה. הדרך הנקייה ביותר לסקירה שלמה היא לפתוח את ה-Session כך:

$ cd examples/taskflow $ claude --permission-mode plan

יש שתי דרכים לארגן את הסקירה, ושתיהן לגיטימיות:

  • בשיחה הראשית. מתאים לסקירה קצרה, כשאתם רוצים לשאול שאלות המשך ולנווט בעצמכם.
  • ב-Subagent ייעודי. מתאים לסקירה רחבה. ה-Subagent קורא עשרות קבצים ב-Context Window נפרד ומחזיר רק סיכום, כך שהשיחה הראשית נשארת נקייה. במדריך הזה מוגדרים כבר שני סוקרים בתיקייה subagents/: architecture-reviewer (כלים: Read, Grep, Glob בלבד, זיכרון פרויקט) ו-security-reviewer (כולל Bash ל-git diff, קריאה-בלבד). העתיקו אותם ל-.claude/agents/ של הפרויקט כפי שהוסבר ב-פרק 25.

עיקרון נוסף מהתיעוד הרשמי: Context טרי משפר סקירה, כי הסוקר לא מוטה כלפי קוד או תוכנית שהוא עצמו ייצר. לכן דפוס "הסוקר השני" (Adversarial Reviewer) חוזר לאורך הפרק: אחרי שהשיחה הראשית ניסחה ניתוח, מבקשים מ-Subagent טרי לנסות להפריך אותו.

מיפוי Architecture: ארבעה Prompts

הצעד הראשון בכל סקירה הוא מפה. ארבעה Prompts מכסים את רוב הצרכים. הריצו אותם בזה אחר זה באותו Session, כדי שכל תשובה תבנה על קודמתה.

1. מפת רכיבים

prompt (plan mode)
Research only, do not modify files.
Produce a component map of this repository: for each top-level component
(backend app, routers, storage layer, models, frontend app, API client, CI),
give: responsibility (one sentence), entry file(s), what it depends on,
what depends on it. Output as a table, then a short list of anything
that does not fit the layering described in CLAUDE.md.

2. גרף תלויות

prompt (plan mode)
Build a dependency graph of the backend package: list every import
between modules under backend/app/ (module A -> module B). Then render it
as a Mermaid graph LR diagram. Flag any cycle and any import that goes
from a lower layer (database) to a higher layer (routers).

3. הפרות שכבות

prompt (plan mode)
Assume the intended layering is: routers -> models/services -> database.
Search for layer violations: SQL strings outside database.py, HTTP
concerns (status codes, request objects) inside the storage layer,
frontend code that hardcodes backend URLs instead of using api.ts.
For each finding give file:line, why it is a violation, and the cheapest fix.
If you find none, say so explicitly.

4. זיהוי גבולות

prompt (plan mode)
Identify the boundaries of this system: process boundaries (browser,
API server, database file), trust boundaries (where untrusted input enters),
and ownership boundaries (which directory a hypothetical frontend team vs
backend team would own). For each boundary, name the file(s) that implement
the crossing (e.g. CORS setup, fetch calls, sqlite3.connect).

תוצאה צפויה (המחשה) לשאלת הפרות השכבות ב-TaskFlow:

המחשה: פלט מקוצר Layer violations found: 1 1. backend/app/routers/tasks.py:10 _row_to_task() maps a raw sqlite3.Row into a Task model inside the router. This couples the HTTP layer to the column order of the tasks table. Cheapest fix: move the mapper into database.py (or a new repository module) and return Task objects. No SQL strings found outside database.py. Frontend uses api.ts consistently.

שימו לב למבנה התשובה: מיקום מדויק, סיבה, תיקון זול. אם התשובה שאתם מקבלים אינה במבנה הזה, בקשו אותו במפורש. וכמו תמיד, לפני שאתם מסמנים ממצא כאמיתי, פתחו את הקובץ ובדקו.

אימות המיפוי: לפני שממשיכים, בדקו שלושה דברים: (1) כל רכיב בטבלה מצביע על קובץ שקיים בפועל (הריצו ls על הנתיבים); (2) גרף התלויות תואם ל-import אמיתי לפחות בשני מודולים שבחרתם אקראית; (3) כל "הפרת שכבות" נפתחה בעורך ואושרה או נדחתה על ידיכם. רק ממצאים שעברו את הבדיקה נכנסים למסמכי ה-docs/.

ADR: תיעוד החלטות Architecture

ADR (Architecture Decision Record) הוא מסמך קצר, קובץ אחד להחלטה אחת, שמתעד הקשר, החלטה, חלופות והשלכות. הערך שלו מתגלה אחרי חצי שנה, כשמישהו שואל "למה בחרנו ככה?". Claude מצטיין בניסוח הטיוטה, כי הוא רואה את הקוד ואת ההיסטוריה; אתם מצטיינים בהוספת ההקשר העסקי ובחתימה.

תבנית

docs/adr/0000-template.md
# ADR-NNNN: <short decision title>

- Status: Proposed | Accepted | Superseded by ADR-XXXX
- Date: YYYY-MM-DD
- Deciders: <names, humans only>
- Drafted with: Claude Code (analysis); decision owned by deciders

## Context
What forces are at play: technical, business, team, timeline.

## Decision
The decision, stated in one or two sentences, in the active voice.

## Alternatives considered
For each: what it is, why it was not chosen.

## Consequences
Positive, negative, and neutral. What becomes easier, what becomes harder.

## Follow-ups
Concrete tasks, owners, revisit date.

Prompt לטיוטה

prompt (plan mode)
Draft an ADR using docs/adr/0000-template.md for the decision:
"Keep raw sqlite3 in TaskFlow vs adopt SQLAlchemy".
Base the Context section on what you can verify in the code (database.py,
routers/tasks.py, tests, CLAUDE.md conventions). List at least three
alternatives. Mark every statement you cannot verify from the repository
with [ASSUMPTION]. Set Status to Proposed. Do not decide; present the
tradeoffs and leave the Decision section as two options for the deciders.

טיוטה שחוזרת (המחשה, מקוצרת):

docs/adr/0003-sqlite3-vs-sqlalchemy.md (draft, המחשה)
# ADR-0003: Keep raw sqlite3 vs adopt SQLAlchemy

- Status: Proposed
- Date: 2026-07-29
- Deciders: [ASSUMPTION] backend lead
- Drafted with: Claude Code (analysis); decision owned by deciders

## Context
TaskFlow's storage layer is a single module (backend/app/database.py) using
the standard-library sqlite3 with parameterized SQL and a context-managed
connection. CLAUDE.md states "no ORM; parameterized SQL only". There is one
table (tasks) with a CHECK constraint that is the source of truth for
status values. Tests point TASKFLOW_DB at a temp file.
[ASSUMPTION] The team expects to add comments and users within two releases.

## Decision
Option A: keep sqlite3, add a small repository module for row mapping.
Option B: adopt SQLAlchemy Core (not ORM) with Alembic migrations.

## Alternatives considered
1. SQLAlchemy ORM: most features, largest conceptual jump, conflicts with
   the "no ORM" convention; would require rewriting the CHECK-based enum.
2. SQLAlchemy Core: typed query building and migrations without ORM
   sessions; moderate cost.
3. Keep sqlite3 and hand-written migrations: zero new dependencies; cost
   grows with each new table.

## Consequences
A: no dependency change, fastest now, manual migrations later.
B: one new dependency, migration tooling, learning curve, easier growth.

## Follow-ups
- Decide by: [ASSUMPTION] next planning meeting
- If B: spike Alembic on a branch, measure test runtime

עכשיו החלק שלכם: מוחקים או מאשרים כל [ASSUMPTION], בוחרים אופציה, מוסיפים שיקולים שאינם בקוד (למשל: "אין לנו ניסיון עם Alembic ואנחנו לפני שחרור"), משנים ל-Accepted וחותמים בשם. הקובץ נכנס ל-Commit יחד עם השינוי שמיישם אותו. אל תתנו ל-Claude לשנות סטטוס ל-Accepted; זה הרגע שבו האחריות עוברת אליכם, וזה צריך להיות מעשה מכוון.

מידול איומים בסגנון STRIDE

מידול איומים שואל "מה יכול להשתבש, איפה, ומה נעשה בעניין". STRIDE הוא ראשי תיבות של שש קטגוריות איום: Spoofing (התחזות), Tampering (שיבוש נתונים), Repudiation (הכחשת פעולה), Information Disclosure (חשיפת מידע), Denial of Service (מניעת שירות) ו-Elevation of Privilege (הסלמת הרשאות). התהליך המומלץ: Claude מציע, אתם מאמתים ומדרגים.

שלב א: גבולות אמון וסיווג נתונים

אזהרה

מידול איומים אינו בדיקת חדירה. Claude מזהה דפוסים בקוד; הוא לא מוכיח שאיום ניתן לניצול ולא מוכיח שאיום אינו קיים. אל תציגו טבלת STRIDE שנוצרה על ידי מודל כאישור אבטחה.

סקירת זרימת נתונים

תרשים זרימת נתונים (DFD) מראה מאיפה נתון נכנס, דרך אילו תהליכים הוא עובר, איפה הוא נשמר ולאן הוא יוצא. זה הכלי הטוב ביותר למצוא מסלולים שבהם מידע רגיש דולף ללוגים, לתשובות שגיאה או ל-Frontend.

prompt (plan mode)
Draw a level-1 data flow diagram of TaskFlow as a Mermaid flowchart:
external entities (browser user), processes (Vite dev server / proxy,
FastAPI app, routers, storage layer), data stores (taskflow.db),
and data flows with the payload named on each edge.
Then trace the path of the TASKFLOW_DB environment variable and of any
error message from the database up to the HTTP response, and tell me
whether internal details (paths, SQL, stack traces) can reach the client.

הנקודה שלרוב עולה בסקירה כזו: מסלולי שגיאה. חריגה מ-sqlite3 שלא נתפסת עלולה להפוך לתשובת 500 עם פרטים פנימיים, בהתאם להגדרות ה-Debug של השרת. הבקשה "tell me whether internal details can reach the client" מכריחה את Claude להסתכל על מסלול השגיאה ולא רק על המסלול השמח. את התרשים שחוזר שומרים ב-docs/architecture/dfd.md, ובודקים אחת לכמה זמן שהוא עדיין נכון (ראו סעיף הסחף בהמשך).

סקירת API

סקירת API בודקת את החוזה בין צרכן לספק, לא את המימוש. ארבעה צירים:

  • חוזים (Contracts). האם הסכמה של הבקשה והתשובה מוגדרת במקום אחד? ב-TaskFlow: מודלי Pydantic ב-Backend ו-types.ts ב-Frontend. האם הם מסונכרנים?
  • גרסאות (Versioning). מה יקרה כשנשנה שדה? האם יש נתיב /v1/, כותרת גרסה, או לפחות מדיניות?
  • סמנטיקת שגיאות. האם קודי הסטטוס עקביים (404 לחסר, 422 לקלט לא תקין, 409 להתנגשות)? האם גוף השגיאה במבנה אחיד?
  • אידמפוטנטיות (Idempotency). האם קריאה חוזרת של PATCH או DELETE נותנת אותה תוצאה? האם POST חוזר יוצר כפילויות, ואם כן, האם צריך Idempotency Key?
prompt (plan mode)
Review the TaskFlow HTTP API as a contract. For each endpoint list:
method, path, request schema, response schema, status codes actually
returned (read the code, do not guess), and whether it is idempotent.
Then compare backend models.py against frontend src/types.ts and report
any field or enum mismatch. Finally, propose a versioning policy in three
sentences and list the breaking changes that would trigger it.

תוצאה צפויה (המחשה): טבלה של שישה Endpoints (חמישה של משימות ועוד /health), שבה POST /tasks מסומן כלא אידמפוטנטי, PATCH ו-DELETE מסומנים כאידמפוטנטיים, וכל קודי הסטטוס נלקחו מהקוד עצמו (201, 204, 404, ו-422 שמגיע מ-FastAPI על קלט לא תקין). בהשוואת הטיפוסים צפוי דיווח שערכי הסטטוס תואמים בין ה-CHECK ב-Database לבין TaskStatus ב-types.ts, בהתאם לקונבנציה ב-CLAUDE.md. אם Claude מדווח על אי-התאמה, זו הזדמנות טובה לבדוק מי צודק: הקוד, התיעוד או המודל.

הביטוי "read the code, do not guess" חשוב: בלי הנחיה כזו, מודל עלול להשלים מהזיכרון קודי סטטוס "סבירים" שאינם קיימים בקוד. סקירת API טובה היא סקירה של מה שיש, לא של מה שאמור להיות.

דוגמה מתקדמת: דוח סטייה אוטומטי ב-CI

ברגע שיש לכם Prompt סטייה שעובד, אפשר להריץ אותו באופן לא-אינטראקטיבי בכל Pull Request. שמרו את ה-Prompt בקובץ prompts/drift.md והריצו:

$ claude -p "$(cat prompts/drift.md)" --permission-mode plan --output-format json --max-turns 40 --max-budget-usd 2 | jq -r '.result' > drift-report.md

הסבר הדגלים: -p מריץ ללא ממשק אינטראקטיבי; --permission-mode plan מבטיח קריאה-בלבד גם אם ה-Prompt ינוסח לא טוב; --output-format json מחזיר אובייקט עם השדה result ועם total_cost_usd; --max-turns ו---max-budget-usd (שניהם זמינים רק עם -p) מגבילים את מספר הסבבים ואת ההוצאה. את הדוח אפשר לפרסם כהערה על ה-PR באמצעות gh pr comment. הרחבה על הרצה ב-CI, כולל --bare וניהול הרשאות, ב-פרק 33. סיכון לניהול: הדוח נוצר בלי אדם בלולאה, ולכן הוא מוגש כהערה בלבד ולעולם לא כ-Commit אוטומטי לתיעוד.

Subagents ייעודיים ודפוס הסוקר השני

שני הסוקרים המוגדרים במדריך מתאימים בדיוק לפרק הזה. architecture-reviewer בודק מבנה, שכבות ותלויות ומדווח לפי השפעה (Blocking / Should fix / Consider); security-reviewer עוקב אחרי קלט חיצוני עד לנקודת הפענוח, האחסון או ההרצה. שניהם קריאה-בלבד ברמת הכלים, כך שגם אם ה-Prompt ינוסח לא טוב, הם לא יערכו קבצים.

דפוס הסוקר השני משלב אותם: אחרי שהשיחה הראשית (או סוקר ראשון) ניסחה מסקנה, מפעילים סוקר טרי עם משימה הפוכה:

prompt
Use the security-reviewer subagent as a second, adversarial reviewer.
Here is the threat model produced earlier: @docs/threat-model.md.
Do not repeat it. Try to refute it: find threats it missed, mitigations
it overstates, and severity ratings you disagree with, with evidence
from the code. If you agree with an item, say nothing about it.

למה זה עובד: הסוקר השני לא רואה את שרשרת ההנמקה שהובילה למסקנה, רק את התוצר ואת הקוד. התיעוד הרשמי מתאר בדיוק את הדפוס הזה תחת "Add an adversarial review step". וזכרו את האזהרה שמופיעה שם: סוקר שהתבקש למצוא פערים ימצא פערים; בקשו ממנו לסמן רק מה שמשפיע על נכונות או על הדרישות, והתייחסו לשאר כאופציונלי.

שגיאות נפוצות

  • קבלת ממצאים בלי לפתוח את הקובץ. כל ממצא צריך file:line, ואתם צריכים להסתכל שם.
  • לתת ל-Claude "להחליט". "מה עדיף, A או B?" בלי הקשר יחזיר תשובה בטוחה בעצמה ולא בהכרח נכונה לכם. בקשו טבלת שיקולים, החליטו בעצמכם.
  • סקירה במצב עריכה. אם ה-Session אינו ב-Plan Mode ואינו מוגבל לכלי קריאה, סקירה עלולה להפוך ל"תיקון קטן" לא מבוקש. פתחו ב---permission-mode plan.
  • Prompt בלי קריטריון. "review the architecture" יחזיר חיבור כללי. ציינו מה נחשב ממצא.
  • הסתמכות על זיכרון המודל לרישיונות וגרסאות. דרשו "verify" או הרצה של כלי אמיתי.
  • ADR שנכתב אחרי המעשה כדי להצדיק. ADR נכתב כשההחלטה מתקבלת, כולל החלופות שנדחו.

Security

  • סקירת Architecture היא קריאה-בלבד. הגבילו כלים ברמת ה-Subagent, לא רק ב-Prompt.
  • מסמכי מידול איומים הם עצמם מידע רגיש: הם מפרטים איפה המערכת חלשה. שמרו אותם ב-Repository פרטי או במערכת ניהול מסמכים עם הרשאות, לא ב-Issue ציבורי.
  • בסקירת זרימת נתונים, ודאו שהפלט של Claude עצמו אינו מכיל סודות שנקראו מקבצי סביבה. אם יש קבצי .env בפרויקט, הוסיפו Read(.env) לרשימת ה-deny (פרק 18).
  • אל תציגו תוצרים שנוצרו על ידי מודל כאישור עמידה בתקן. הם קלט לתהליך אנושי.

Cost ו-Context

סקירה מלאה של פרויקט קטן כמו TaskFlow צורכת עשרות אלפי Tokens של קריאה; בפרויקט גדול, מאות אלפים. שלוש דרכים לשלוט בעלות: לפצל לתחומים ולהאציל ל-Subagents שמחזירים סיכום בלבד; לשמור תוצרי ביניים לקבצים ולהתחיל Session חדש לכל שלב (מיפוי, איומים, API) במקום שיחה אחת ארוכה; ולהשתמש בקבצי docs/ שנוצרו בסקירה הקודמת כנקודת פתיחה במקום למפות מאפס. השתמשו ב-/cost כדי לראות את הצריכה של ה-Session הנוכחי.

Best Practices

  • פתחו סקירות ב-claude --permission-mode plan.
  • דרשו file:line לכל ממצא, ובדקו לפחות מדגם.
  • הגדירו במפורש היקף, קריטריונים ופורמט פלט.
  • שמרו כל תוצר סקירה כקובץ ב-docs/ תחת בקרת גרסאות.
  • סמנו הנחות ב-[ASSUMPTION] וסגרו אותן לפני קבלת החלטה.
  • הריצו סוקר שני ב-Context טרי לפני מסקנות מהותיות.
  • ADR נחתם על ידי בני אדם, וסטטוס Accepted נקבע ידנית.
  • חזרו על בדיקת הסחף אחרי כל שינוי מבני משמעותי.

Anti-patterns

  • "Claude אמר". שימוש בפלט המודל כסמכות בדיון צוותי במקום כקלט לדיון.
  • סקירה חד-פעמית. מיפוי שנעשה פעם אחת ולא מתעדכן הופך בעצמו לתיעוד סוטה.
  • הצפת ממצאים. דוח של שישים פריטים ללא דירוג לא יטופל. דרשו דירוג לפי השפעה ומגבלה על מספר הפריטים.
  • ADR שנכתב על ידי מודל ונחתם על ידי אף אחד.
  • ערבוב סקירה ותיקון באותו Session. קודם סקירה במצב קריאה, החלטה, ואז Session נפרד ליישום.

תרגיל

תרגיל 37.1: ADR ומודל איומים להוספת Auth ל-TaskFlow

ההנהלה החליטה ש-TaskFlow יוצא מ-localhost ויוגש לצוות של עשרים משתמשים. הכינו את שני המסמכים הבאים, בעזרת Claude כאנליסט ובלי לשנות קוד:

  1. docs/adr/0004-authentication.md: ADR על מנגנון האימות (לפחות שלוש חלופות: Session cookie, JWT, הזדהות דרך ספק חיצוני כמו OAuth), עם סטטוס Proposed, כל הנחה מסומנת, ושתי אופציות בסעיף ההחלטה.

לאחר מכן הריצו את security-reviewer כסוקר שני על מודל האיומים, קלטו לפחות ממצא אחד שלו, וקבלו החלטה אנושית: אילו שתי הגנות נכנסות ל-Sprint הראשון ולמה. תעדו את ההחלטה ב-ADR ושנו את הסטטוס בעצמכם.

פתרון מוסבר

שלב 1: הקשר. פתחו claude --permission-mode plan ב-examples/taskflow. הריצו את ה-Prompt של זיהוי הגבולות מהסעיף "מיפוי Architecture" כדי שהשיחה תכיר את המערכת.

שלב 2: ADR. השתמשו ב-Prompt של הטיוטה עם ההחלטה "How should TaskFlow authenticate users when served to a 20-person team". דרשו שהחלופות יכללו: (א) Session cookie עם טבלת משתמשים ב-SQLite; (ב) JWT חתום, ללא מצב בשרת; (ג) OAuth מול ספק זהות ארגוני. Claude צפוי לציין שהאפשרות (א) הכי קרובה לקונבנציות הקיימות (אין תלויות חדשות כבדות, SQL פרמטרי), ש-(ב) דורש ניהול סודות ורענון, ו-(ג) מעביר את ניהול הסיסמאות החוצה אך תלוי בתשתית ארגונית. כל הנחה על "יש לארגון ספק זהות" תסומן [ASSUMPTION]. אתם סוגרים אותה: אם יש ספק זהות ארגוני, (ג) לרוב עדיפה; אם אין, (א) היא הצעד הראשון הסביר.

שלב 3: מודל איומים. הריצו את ה-Prompt של STRIDE עם התוספת "assume the chosen ADR option is implemented". הטבלה צריכה לכלול כעת שורות חדשות: Spoofing על POST /login (Brute force, צורך ב-Rate limiting), Information Disclosure של סיסמאות בלוגים, Elevation of Privilege אם משתמש יכול לגשת למשימה של אחר (בדיקת בעלות בכל Endpoint), Tampering ב-Cookie ללא HttpOnly/Secure. סיווג הנתונים: סיסמה מוצפנת (Hash) = Secret; אימייל = Confidential; משימות = Internal.

שלב 4: סוקר שני. הפעילו את security-reviewer עם ה-Prompt ההפוך מהסעיף "דפוס הסוקר השני". ממצא אופייני שהוא יוסיף: אין CSRF בטבלה, למרות שאימות מבוסס Cookie חשוף אליו; או שדירוג ה-DoS על GET /tasks צריך לעלות כי כעת המערכת חשופה לרשת.

שלב 5: החלטה אנושית. בחירה סבירה ל-Sprint ראשון: (1) בדיקת בעלות בכל Endpoint של משימות, כי היא סוגרת את איום ההסלמה שהוא הכי חמור והכי זול; (2) הגנות Cookie ו-CSRF, כי הן קלות ליישום עם המסגרת הקיימת. Rate limiting ו-Audit log נדחים ל-Sprint הבא ומתועדים ב-Follow-ups. אתם משנים את הסטטוס ל-Accepted, מוסיפים את שמכם ל-Deciders, ומבצעים Commit לשני הקבצים.

הנקודה החינוכית: כל התוכן נכתב על ידי Claude; כל ההחלטות והחתימות הן שלכם.

סיכום

סקירת Architecture ו-Design עם Claude Code היא שימוש שיטתי במודל כאנליסט קריאה-בלבד: מיפוי רכיבים, תלויות, שכבות וגבולות; טיוטות ADR עם הנחות מסומנות; מידול איומים בסגנון STRIDE עם גבולות אמון וסיווג נתונים; סקירת זרימת נתונים, API, דרישות לא-פונקציונליות ותלויות; ביקורת תוכנית לפני יישום; וזיהוי סחף בין תיעוד לקוד. ה-Subagents architecture-reviewer ו-security-reviewer ודפוס הסוקר השני מספקים הפרדה ו-Context טרי. ומעל הכול: Claude מנתח וממליץ, בני אדם מחליטים וחותמים. בפרק הבא נעבור מסקירה לביצוע מקבילי: איך מפצלים עבודה בין כמה סוכנים בלי שיתנגשו.
