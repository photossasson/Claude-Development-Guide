GitHub Actions ו-Code Review

בפרק הזה Claude Code עוזב את המחשב שלכם ועובר לעבוד ב-CI: עונה לאזכורי @claude ב-Issues וב-Pull Requests, הופך Issues ל-PRs, מריץ משימות תחזוקה מתוזמנות, וסוקר כל PR אוטומטית. נקים את האינטגרציה בשני מסלולים, נפרק ארבע דוגמאות Workflow מלאות שורה אחרי שורה, נכיר את שירות ה-Code Review המנוהל ואת /code-review המקומי, ונסגור עם אבטחה, עלויות, GitHub Enterprise Server ו-GitLab CI/CD.

מה האינטגרציה עושה, ומה היא לא

Claude Code GitHub Actions היא GitHub Action רשמית (anthropics/claude-code-action) שמריצה את Claude Code בתוך ה-Workflows של ה-Repository, על ה-Runners שלכם. שני מצבי עבודה: מזכירים @claude בתגובה ל-Issue או PR ו-Claude מנתח, מיישם ודוחף Commits; או נותנים לו Prompt קבוע שרץ אוטומטית על כל אירוע GitHub, מפתיחת Issue ועד לוח זמנים של Cron.

כמה מוצרים חולקים את השם, וחשוב להפריד:

דרישות מוקדמות

Repository ב-GitHub עם הרשאות Admin, מפתח API מ-Claude Console או מנוי Claude בתשלום, והיכרות בסיסית עם GitHub Actions (קובצי YAML ב-.github/workflows/). למסלול המהיר נדרש גם GitHub CLI (gh) מחובר.

התקנה מהירה: /install-github-app

המסלול המהיר עושה הכול מתוך Claude Code. התקינו את GitHub CLI והתחברו עם gh auth login, פתחו claude בתיקיית ה-Repository, והריצו:

$ claude > /install-github-app

מה קורה מאחורי הקלעים, לפי הסדר:

  1. התקנת ה-GitHub App: Claude Code מתקין את Claude GitHub App על ה-Repository (פירוט ההרשאות בהמשך).
  2. יצירת Secret לאימות: אם ל-Claude Code כבר יש מפתח API, הוא מציע להשתמש בו; אחרת בוחרים בין יצירת Token ארוך-טווח מהמנוי (נשמר בשם CLAUDE_CODE_OAUTH_TOKEN) לבין הדבקת מפתח API (נשמר בשם ANTHROPIC_API_KEY).
  3. יצירת ה-Workflows: Claude Code דוחף Branch עם קובצי ה-Workflow שבחרתם, כבר מכוונים ל-Secret הנכון, ופותח את הדפדפן עם PR מוכן ליצירה. ממזגים את ה-PR, ו-@claude עובד.

המסלול המהיר עובד עם ה-API הישיר ועם מנויי Claude בלבד; ל-Bedrock, Agent Platform או Foundry יש מדריך ספקי ענן נפרד. ב-GitHub Enterprise Server הפקודה לא זמינה (ראו סעיף בהמשך).

התקנה ידנית

שלושה צעדים, שימושיים כשלא מריצים Claude Code מקומית או כשרוצים שליטה מלאה:

  1. התקינו את Claude GitHub App על ה-Repository. ה-Action נשען על שלוש הרשאות: Contents (קריאה וכתיבה, שינוי קבצים), Issues (קריאה וכתיבה, מענה ל-Issues) ו-Pull requests (קריאה וכתיבה, יצירת PRs ודחיפת שינויים).
  2. הוסיפו Secret לאימות ב-Settings ואז Secrets and variables ואז Actions: או ANTHROPIC_API_KEY (מפתח מ-Claude Console), או CLAUDE_CODE_OAUTH_TOKEN (נוצר מקומית עם claude setup-token, זמין במנויי Pro, Max, Team ו-Enterprise).
  3. העתיקו את קובץ ה-Workflow examples/claude.yml מה-Repository של ה-Action אל .github/workflows/ אצלכם. הקובץ הוא Workflow עובד, לא רק דוגמה. אם בחרתם ב-Token של מנוי, החליפו את שורת anthropic_api_key ב-claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}.

הרשאות ה-GitHub App: מה מאשרים בפועל

ה-App המשותף משרת את כל האינטגרציות של Claude עם GitHub (Actions, Code Review, Auto-fix של Web), ולכן סט ההרשאות המלא רחב מהנדרש ל-Action לבדו: Actions, Checks, Contents, Discussions, Issues, Repository hooks ו-Workflows בקריאה וכתיבה; Members, Metadata ו-Statuses בקריאה. GitHub לא מאפשר לאשר תת-קבוצה. ארגון שדורש צמצום מוחלט יכול ליצור GitHub App מותאם עם Contents, Issues ו-Pull requests בלבד ולהעביר אותו דרך הקלט github_token; אבל App מותאם מכסה רק את ה-Action, ו-Code Review ו-Auto-fix עדיין דורשים את ה-App הרשמי.

פריסה ארגונית: מתקינים את ה-App פעם אחת ברמת הארגון, שומרים את ה-Secret כ-Organization Secret (עדיף מפתח API ולא OAuth Token, שקשור למנוי של אדם אחד), ומוסיפים את ה-Workflow לכל Repository או מגדירים Reusable Workflow אחד. כדי לוותר על Secret ארוך-טווח לגמרי, ה-Action תומך ב-Workload Identity Federation: החלפת ה-Token של GitHub OIDC בגישת API דרך Service Account ב-Console (קלטים: anthropic_federation_rule_id, anthropic_organization_id ועוד), עם הרשאת id-token: write ב-Workflow.

הגרסה הנוכחית והקלטים של ה-Action

הגרסה הראשית הנוכחית היא anthropics/claude-code-action@v1. אם ירשתם Workflows עם @beta, עדכנו: החליפו ל-@v1, הסירו את הקלט mode (המצב מזוהה אוטומטית), החליפו direct_prompt ב-prompt, והעבירו קלטים כמו max_turns ו-model אל תוך claude_args. הקלטים המרכזיים, מאומתים מול התיעוד הרשמי:

קלטמה הוא עושהברירת מחדל

מצב אינטראקטיבי מול אוטומציה

ה-Action מזהה את המצב לבד מהתצורה, בלי קלט mode:

  • מצב אינטראקטיבי (אין prompt): Claude ממתין לביטוי ההפעלה (@claude כברירת מחדל) בתגובת Issue או PR, בסקירת PR, או בגוף ובכותרת של Issue חדש, ואז מגיב. ההתקדמות והתוצאות מופיעות כתגובה על ה-Issue או ה-PR.
  • מצב אוטומציה (יש prompt): Claude רץ מיד על כל אירוע שה-Workflow מאזין לו, בלי להמתין לאזכור. התוצאות מופיעות בלוג של ריצת ה-Workflow, לא כתגובה (אלא אם ה-Prompt מנחה לפרסם תגובות עם כלים מורשים).

מי יכול להפעיל, ומניעת לולאות: לפני שה-Action מריץ את Claude הוא בודק שניים, ונכשל אם אחד נדחה:

  • הרשאת כתיבה: באירועי Issue ו-PR, המשתמש המפעיל חייב הרשאת Write ל-Repository. חריגים דורשים allowed_non_write_users יחד עם github_token משלכם (מסוכן; ראו אבטחה). אירועים בלי מחבר אנושי, כמו schedule, מדלגים על הבדיקה.
  • שחקן אנושי: ה-Action דוחה Bots אלא אם נרשמו ב-allowed_bots. זה מנגנון מניעת הלולאות: בלעדיו, Bot אחד שמגיב ל-Bot אחר יכול להפעיל את Claude שוב ושוב. שימו לב שגם ריצות מתוזמנות מיוחסות למשתמש (בדרך כלל מי ששינה אחרון את ה-Cron); אם זה Bot, הוסיפו אותו לרשימה.

דוגמה 1: עונה ל-@claude

ה-Workflow הקנוני, מבוסס על הדוגמה הרשמית, במצב אינטראקטיבי מלא:

.github/workflows/claude.yml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened]
  pull_request_review:
    types: [submitted]
jobs:
  claude:
    if: |
      contains(github.event.comment.body, '@claude') ||
      contains(github.event.issue.body, '@claude') ||
      contains(github.event.review.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

שורה אחרי שורה:

  • on: ארבעת סוגי האירועים שבהם אזכור יכול להופיע: תגובת Issue, תגובת סקירה על שורת קוד, Issue חדש (גוף וכותרת), וסקירת PR.
  • if: מסנן ברמת ה-Job: לא מרימים Runner (ולא משלמים על דקות Actions) עבור תגובות בלי @claude. ה-Action בודק את ביטוי ההפעלה גם בעצמו, אז הסינון הזה הוא חיסכון, לא אבטחה.
  • permissions: ההרשאות שה-Job מקבל: contents: write לדחיפת Commits, pull-requests ו-issues: write לתגובות, id-token: write נדרש לאימות ברירת המחדל של ה-Action מול ה-GitHub App, ו-actions: read מאפשר ל-Claude לקרוא תוצאות CI על PRs.
  • actions/checkout@v6 נותן ל-Claude עותק מקומי של ה-Repository; fetch-depth: 1 משכפל רק את ה-Commit האחרון, מהר יותר.
  • הצעד של ה-Action: במצב אינטראקטיבי מספיק ה-Secret. אין github_token: ה-Action מאומת כ-Claude GitHub App, מה שגם מאפשר ל-CI לרוץ על ה-Commits של Claude (Commits עם GITHUB_TOKEN רגיל לא מפעילים Workflows).

אחרי המיזוג, מזכירים בכל תגובה: @claude fix the TypeError in the user dashboard component, ו-Claude עונה בתגובה על אותו Issue או PR ומעדכן אותה תוך כדי עבודה.

דוגמה 2: סקירת PR אוטומטית

מצב אוטומציה: prompt קבוע שרץ על כל PR חדש או מעודכן, מבוסס על הדוגמה הרשמית במדריך הפתרונות של ה-Action:

.github/workflows/claude-review.yml
name: Claude PR Review
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          use_sticky_comment: true
          prompt: |
            REPO: ${{ github.repository }}
            PR NUMBER: ${{ github.event.pull_request.number }}

            Review this pull request. Focus on:
            - Logic errors and edge cases
            - Security issues (injection, secrets, authorization)
            - Violations of the guidelines in CLAUDE.md

            Use `gh pr comment` for a summary comment.
            Use `mcp__github_inline_comment__create_inline_comment`
            (with `confirmed: true`) for line-specific issues.
            Do not approve or request changes.
          claude_args: |
            --max-turns 15
            --allowedTools "mcp__github_inline_comment__create_inline_comment,Bash(gh pr comment:*),Bash(gh pr diff:*),Bash(gh pr view:*)"

מה חדש כאן לעומת דוגמה 1:

  • types: [opened, synchronize]: ריצה בפתיחת PR ובכל דחיפת Commits אליו. אין צורך ב-if: יש prompt, אז כל אירוע מפעיל ריצה.
  • contents: read בלבד: סוקר לא צריך לכתוב קבצים. עיקרון ההרשאה המינימלית בפעולה.
  • use_sticky_comment: true: תגובה אחת שמתעדכנת בכל ריצה במקום תגובה חדשה על כל Push.
  • ה-Prompt כולל את פרטי ההקשר: התבנית הרשמית ממליצה לכלול תמיד REPO ו-PR NUMBER במצב אוטומציה. Claude מקבל את ה-Branch כבר משוכפל בתיקיית העבודה.
  • --allowedTools: במצב אוטומציה עם Prompt טקסטואלי, ל-Claude אין גישה ל-Shell או ל-API של GitHub עד שמעניקים אותה מפורשות. כאן מותרים בדיוק ארבעה כלים: כלי התגובה על שורות (שרת MCP מובנה של ה-Action) ושלוש פקודות gh ספציפיות. שום Edit, שום Write: הסוקר פיזית לא יכול לשנות קוד.
  • --max-turns 15: תקרת סבבים שמונעת ריצות אינסופיות ומגבילה עלות.
חלופה מתועדת: Plugin של code-review

התיעוד הרשמי מציג גם גרסה שמריצה את אותו Plugin שמאחורי סקירת ה-Workflows של ההתקנה המהירה: קלטי plugin_marketplaces ו-plugins עם prompt: "/code-review:code-review ...". ולמי שלא רוצה לתחזק Workflow בכלל, שירות ה-Code Review המנוהל בהמשך הפרק עושה זאת בלי YAML.

דוגמה 3: מ-Issue ל-PR עם Guardrails

הדוגמה השלישית משתמשת בקלט המתועד label_trigger: הדבקת Label בשם claude-implement על Issue שולחת את Claude ליישם אותו. זה מצב אינטראקטיבי (אין prompt), כך שכל ההקשר של ה-Issue נטען אוטומטית:

.github/workflows/claude-implement.yml
name: Issue to PR
on:
  issues:
    types: [labeled]
jobs:
  implement:
    if: github.event.label.name == 'claude-implement'
    runs-on: ubuntu-latest
    timeout-minutes: 30
    concurrency:
      group: claude-issue-${{ github.event.issue.number }}
      cancel-in-progress: false
    permissions:
      contents: write
      issues: write
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          label_trigger: "claude-implement"
          branch_prefix: "claude/"
          claude_args: |
            --max-turns 20
            --model claude-sonnet-5

שלושת ה-Guardrails בדוגמה:

  • timeout-minutes: 30: מנגנון סטנדרטי של GitHub Actions שהורג את ה-Job אחרי חצי שעה, גם אם Claude נתקע. תקרת עלות קשיחה על דקות Actions.
  • concurrency: קבוצת מקביליות פר Issue: אם מישהו מדביק ומסיר את ה-Label שוב ושוב, ריצות לא יצטברו במקביל על אותו Issue.
  • --max-turns 20: תקרת סבבי שיחה על צריכת ה-Tokens. יישום Feature דורש יותר סבבים מסקירה, לכן 20 ולא 15. (עצה מעשית: התחילו נמוך והעלו אם ריצות לגיטימיות נעצרות באמצע.)

ומה עם ה-PR עצמו? נקודה חשובה שמתועדת במסמכי האבטחה של ה-Action: בתצורת ברירת המחדל Claude לא יוצר Pull Requests בעצמו. הוא דוחף את השינויים ל-Branch חדש (עם הקידומת claude/ שקבענו) ומצרף לתגובתו קישור לעמוד יצירת ה-PR. אתם לוחצים, סוקרים ויוצרים. פיקוח אנושי מובנה בתהליך, לא תוספת.

דוגמה 4: תחזוקה מתוזמנת

מצב אוטומציה על לוח זמנים: דוח תחזוקה שבועי המבוסס על הדוגמה הרשמית, מותאם לפרויקט TaskFlow:

.github/workflows/claude-maintenance.yml
name: Weekly Maintenance
on:
  schedule:
    - cron: "0 6 * * 1"
  workflow_dispatch:
jobs:
  maintenance:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: read
      issues: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            REPO: ${{ github.repository }}

            Perform weekly repository maintenance:
            1. Check for outdated dependencies in requirements.txt
               and frontend/package.json
            2. Review open issues older than 90 days
            3. Look for TODO comments added in the last week

            Create a single GitHub issue that summarizes the findings.
          claude_args: |
            --max-turns 15
            --allowedTools "Read,Grep,Glob,Bash(gh issue list:*),Bash(gh issue create:*),Bash(git log:*)"
  • cron: "0 6 * * 1": כל יום שני ב-06:00 UTC. שתי מגבלות מתועדות של GitHub: Workflows מתוזמנים רצים רק מה-Branch הראשי, וב-Repositories ציבוריים התזמון מושבת אחרי 60 יום ללא פעילות.
  • workflow_dispatch: מוסיף כפתור הרצה ידנית בלשונית Actions, שימושי לבדיקת ה-Workflow בלי לחכות ליום שני.
  • fetch-depth: 0: היסטוריית Git מלאה, כי המשימה כוללת ניתוח git log.
  • הכלים המורשים הם בדיוק מה שהמשימה צריכה: קריאת קבצים וחיפוש (Read, Grep, Glob), רשימת Issues ויצירת Issue, ולוג של Git. אין הרשאת עריכה, אין gh pr.
  • בדיקת השחקן: ריצת schedule מיוחסת למשתמש שעדכן אחרון את התזמון. אם זה חשבון אנושי, אין בעיה; אם Bot ארגוני, הוסיפו אותו ל-allowed_bots.

Code Review: השירות המנוהל

Code Review Research Preview הוא שירות סקירה מנוהל שרץ על תשתית Anthropic, זמין למנויי Team ו-Enterprise (לא לארגונים עם Zero Data Retention). בניגוד ל-Workflow מדוגמה 2, כאן אין YAML בכלל: Owner מפעיל פעם אחת ב-admin-settings, מתקין את ה-GitHub App, בוחר Repositories, וזהו.

איך זה עובד: צי של Agents מתמחים מנתח את ה-Diff בהקשר של כל ה-Codebase במקביל, כל אחד מחפש סוג בעיה אחר (שגיאות לוגיקה, פרצות אבטחה, מקרי קצה שבורים, רגרסיות עדינות). שלב אימות בודק מועמדים מול התנהגות הקוד בפועל כדי לסנן התרעות שווא, והממצאים מדורגים ומפורסמים כתגובות Inline על השורות הרלוונטיות. סקירה אורכת כ-20 דקות בממוצע. כל ממצא מתויג ברמת חומרה:

סימוןחומרהמשמעות
אדוםImportantBug שראוי לתקן לפני מיזוג
צהובNitבעיה מינורית, כדאי אך לא חוסם
סגולPre-existingBug שקיים ב-Codebase אך לא נוצר ב-PR הזה

מתי סקירה רצה: לכל Repository בוחרים התנהגות: Once after PR creation (פעם אחת בפתיחה), After every push (בכל דחיפה, הכי יקר), או Manual. בנוסף, פקודות תגובה עובדות בכל מצב: @claude review מריץ סקירה בודדת, @claude review always מריץ ומנוי את ה-PR לסקירות בכל Push, ו-@claude review once זהה לפקודה הבסיסית. הפקודה חייבת להיות תגובה ראשית (לא Inline), בתחילת התגובה, ממשתמש עם גישת Owner, Member או Collaborator, על PR פתוח.

התאמה אישית: שני קבצים מנחים את הסקירה. CLAUDE.md נקרא כהקשר פרויקט, והפרות חדשות שלו מדווחות כ-Nits. REVIEW.md בשורש ה-Repository הוא הוראות ייעודיות לסקירה, מוזרקות לכל Agent בעדיפות הגבוהה ביותר: הגדרה מחדש של Important עבור ה-Repo שלכם, תקרת Nits לסקירה, רשימות דילוג (קוד מיוצר, Lockfiles), בדיקות חובה ("לכל Route חדש חייב Integration Test") ורף ראיות לממצאים.

ה-Check Run לא חוסם: הסקירה מפרסמת Check Run בשם Claude Code Review שמסתיים תמיד במסקנה ניטרלית, כך שהוא לא חוסם מיזוג דרך Branch Protection. מי שרוצה לשער (Gate) מיזוגים על ממצאים קורא את השורה האחרונה של ה-Details, שהיא הערה קריאת-מכונה עם ספירת ממצאים לפי חומרה, ומעבד אותה ב-CI משלו עם gh ו-jq.

תמחור: לפי התיעוד הרשמי (נבדק 29.07.2026), Code Review מחויב לפי שימוש ב-Tokens, בעלות ממוצעת של 15 עד 25 דולר לסקירה, תלוי בגודל ה-PR ובמורכבות. החיוב נפרד, דרך Usage Credits, ולא נספר במכסת המנוי. Owner יכול לקבוע תקרת הוצאה חודשית ב-admin-settings/usage; כשהתקרה נחצית, סקירות מדלגות עם תגובה מסבירה וחוזרות בתחילת תקופת החיוב הבאה. מעקב בלוח ה-Analytics ב-claude.ai/analytics/code-review.

/code-review מקומי, ורמת ultra בענן

בלי GitHub App ובלי מנוי Team אפשר לסקור Diff מקומית: הפקודה /code-review (עם הכינוי /review) רצה בכל Session של Claude Code כ-Subagent ברקע עם חלון הקשר משלה, וסוקרת את ה-Commits של ה-Branch שלכם מעל ה-Upstream בתוספת שינויים לא שמורים. אפשר להעביר יעד (נתיב, מספר PR, שם Branch או טווח כמו main...my-feature) ודגלים: --fix מחיל את התיקונים על עץ העבודה, --comment מפרסם ממצאים כתגובות Inline על ה-PR.

מעבירים גם רמת מאמץ, מ-low עד max: רמות נמוכות מדווחות רק ממצאים בביטחון גבוה (פחות התרעות שווא), רמות גבוהות מרחיבות כיסוי. הרמה המיוחדת ultra מסלימה ל-Ultrareview: סקירה עמוקה שרצה בענן ומחזירה ממצאים ל-Session (/code-review ultra --fix גם מחיל אותם). דרישות ultra המתועדות: אימות עם חשבון claude.ai; לא זמין דרך Bedrock, Agent Platform או Foundry, ולא לארגונים עם Zero Data Retention. כשהסקירה תחייב Usage Credits, Claude Code עוצר לאישור חיוב אינטראקטיבי (בסקריפטים משתמשים ב-claude ultrareview, שהרצתו היא הסכמה לחיוב). כש-ultra אינו זמין, הפקודה מריצה סקירה מקומית במקום.

מהכשל ב-CI חזרה לטרמינל

ה-CI נכשל על PR שיצרתם עם Claude? שתי דרכים מתועדות לחזור להקשר במהירות:

  • claude --from-pr 123: פותח את בוחר ה-Sessions מסונן ל-Sessions המקושרים ל-PR (הקישור נוצר אוטומטית כש-Claude יצר את ה-PR). מקבל מספר PR או URL של GitHub, GitHub Enterprise, GitLab ו-Bitbucket. ממשיכים בדיוק את השיחה שבנתה את הקוד, עם כל ההקשר.
  • /autofix-pr: מפעיל Session של Claude Code on the web שצופה ב-PR של ה-Branch הנוכחי ודוחף תיקונים כשה-CI נכשל או כשסוקרים משאירים הערות. מזהה את ה-PR עם gh pr view; אפשר לצמצם את המנדט, למשל /autofix-pr only fix lint and type errors. דורש gh וגישה ל-Claude Code on the web.

GitHub Enterprise Server ו-GitLab CI/CD

GitHub Enterprise Server (GHES): נתמך במנויי Team ו-Enterprise. Owner מחבר את מופע ה-GHES פעם אחת דרך admin-settings (יצירת GitHub App במופע שלכם, מונחית או ידנית), ואז Code Review, Sessions בענן ו-Teleport עובדים כמו ב-github.com. שני הבדלים חשובים ל-Actions: /install-github-app עובד רק מול github.com, כך שב-GHES מתאימים את examples/claude.yml ידנית; ושרת ה-MCP של GitHub לא עובד מול GHES, ולכן העצה הרשמית היא gh מחובר למופע שלכם (gh auth login --hostname github.example.com). דרישת רשת: המופע חייב להיות נגיש מתשתית Anthropic עבור Sessions מנוהלים וסקירות (Allowlist לכתובות ה-API של Anthropic), אלא אם רצים בסביבה בניהול עצמי.

GitLab CI/CD Beta: אינטגרציה מקבילה שמתוחזקת על ידי GitLab, בנויה על ה-CLI וה-Agent SDK. ההקמה: משתנה CI/CD ממוסך (Masked) בשם ANTHROPIC_API_KEY ב-Settings ואז CI/CD ואז Variables, ו-Job ב-.gitlab-ci.yml שמתקין את ה-CLI ומריץ claude -p עם הרשאות וכלים מוגדרים. הדוגמה הרשמית מריצה על אירועי Merge Request והפעלות Web, ותומכת גם ב-Bedrock ו-Agent Platform דרך OIDC בלי מפתחות סטטיים. כל שינוי עובר דרך MR, כך שסקירות ואישורים ארגוניים נשמרים. לתמיכה: ה-Issue הרשמי של GitLab.

אבטחה

Prompt Injection דרך תוכן של זרים

כל טקסט ב-Issue, בתגובה או ב-PR הוא קלט למודל. תורם חיצוני יכול להטמין הוראות נסתרות בהערות HTML, בתווים בלתי נראים, ב-Alt Text של תמונות או במאפיינים חבויים. ה-Action מסנן את הטכניקות האלה (Stripping של הערות HTML, תווים נסתרים, Alt Text ועוד), אבל טכניקות עקיפה חדשות צצות. ההמלצות הרשמיות: סקרו את התוכן הגולמי של קלט מתורמים חיצוניים לפני ש-Claude מעבד אותו; ב-Repos ציבוריים השתמשו ב-include_comments_by_actor כדי להעביר ל-Claude רק תגובות ממשתמשים ברשימה, וב-exclude_comments_by_actor לסינון רעשי Bots; והגבילו את הכלים המורשים למינימום, כך שגם הזרקה מוצלחת לא יכולה לעשות הרבה.

  • Secrets תמיד ב-GitHub Secrets. לעולם לא מפתח API בתוך קובץ Workflow. ה-Token שה-App מקבל הוא קצר-חיים ותחום ל-Repository שבו הריצה; אין גישה בין Repositories.
  • PRs מ-Forks: ב-Repositories ציבוריים, GitHub מונע Secrets מריצות שהופעלו על ידי PR מ-Fork, ולכן Workflow הסקירה מדוגמה 2 רץ רק על PRs מ-Branches באותו Repository. אל תעקפו זאת עם pull_request_target בקלות דעת: אירוע כזה רץ עם ה-Secrets של ה-Repository הבסיסי, והכלל הקריטי המתועד הוא לא לבצע Checkout של Ref לא מהימן לשורש סביבת העבודה לפני ה-Action. אם חייבים את קובצי ה-PR, משכפלים אותם לתת-תיקייה ומעבירים עם --add-dir.
  • תצורת Claude מה-Branch הבסיסי: בריצה על PR, ה-Action משחזר רשימה קבועה של נתיבי תצורה (.claude/, CLAUDE.md, .mcp.json ועוד) מ-Branch הבסיס, כך ש-PR זדוני לא יכול לשתול Hooks או הרשאות משלו. גרסאות ה-PR נשמרות ב-.claude-pr/ לעיון בלבד.
  • allowed_bots בזהירות: Bots שברשימה לא נבדקים להרשאות כתיבה. ב-Repo ציבורי עם '*', כל GitHub App חיצוני שפותח Issue או תגובה יכול להפעיל את ה-Action עם Prompt בשליטתו. העדיפו רשימה מפורשת.
  • allowed_non_write_users מסומן רשמית כמסוכן: עוקף את מנגנון האבטחה המרכזי. אם בכל זאת, רק עם github_token: ${{ secrets.GITHUB_TOKEN }} (לא PAT סטטי) ועם הרשאות Workflow מינימליות.

עלות ובקרתה

כל ריצה צורכת שני משאבים: דקות GitHub Actions (ה-Runner) ו-Tokens (מפתח API לפי תמחור API, או המנוי אם אימתתם עם OAuth Token). אמצעי הבקרה המתועדים, מהזול ליקר:

  • בקשות @claude ספציפיות: פחות סבבים עד לסיום. תבניות Issue שמספקות הקשר מראש עוזרות.
  • CLAUDE.md תמציתי: הוא נקרא בכל ריצה.
  • --max-turns ב-claude_args: תקרת סבבים.
  • --model: בחרו מודל זול יותר למשימות פשוטות כמו תיוג Issues.
  • timeout-minutes ברמת ה-Job: תקרת זמן קשיחה.
  • concurrency: מניעת ריצות מקבילות מיותרות.
  • סינון if ברמת ה-Job: לא מרימים Runner בכלל על אירועים לא רלוונטיים.

עלות Code Review המנוהל נפרדת (Usage Credits) ונשלטת דרך בחירת ה-Trigger (סקירה בכל Push היא הכפלה במספר ה-Pushes) ותקרת הוצאה חודשית ב-admin-settings.

Branch Protection וביקורת אנושית

שום דבר בפרק הזה לא נועד להחליף סוקר אנושי, והמערכת בנויה כך בכוונה: Claude לא יוצר PR בעצמו בתצורת ברירת המחדל אלא רק Branch וקישור; ממצאי Code Review לא מאשרים ולא חוסמים PR, וה-Check Run תמיד ניטרלי. את שכבת האכיפה בונים בצד שלכם עם GitHub: חוקי Branch Protection (או Rulesets) שדורשים לפחות סוקר אנושי אחד ובדיקות CI ירוקות לפני מיזוג. כך גם אם ה-Automation השתבש, שום קוד לא נכנס ל-main בלי עיניים אנושיות. סקרו את ה-Commits של Claude כפי שהייתם סוקרים תורם חדש: בדיקות עוברות אינן תחליף לקריאת ה-Diff.

שגיאות נפוצות

  • להעביר github_token: ${{ secrets.GITHUB_TOKEN }} בלי סיבה. זה מבטל את אימות ה-GitHub App, וה-CI מפסיק לרוץ על ה-Commits של Claude (GitHub לא מפעיל Workflows על Commits של ה-Token המובנה). משמיטים, אלא אם יש App מותאם.
  • לצפות שסקירת האוטומציה תגיב על ה-PR בלי כלים. במצב אוטומציה עם Prompt טקסטואלי אין גישת Shell או GitHub API כברירת מחדל; בלי --allowedTools הממצאים נשארים בלוג הריצה.
  • לכתוב /claude או @claude-bot. ביטוי ההפעלה הוא @claude כמילה שלמה (אלא אם שיניתם עם trigger_phrase).
  • לשכוח את id-token: write. ההרשאה נדרשת לאימות ברירת המחדל של ה-Action, וגם ל-Workload Identity Federation.
  • OAuth Token כ-Secret ארגוני. ה-Token קשור למנוי של מי שהריץ claude setup-token; כשהוא עוזב, הכול נשבר. לארגון: מפתח API או Federation.
  • לנסות להריץ מחדש סקירת Code Review כושלת מכפתור Re-run. הכפתור בלשונית Checks לא מפעיל סקירה מחדש; מגיבים @claude review או דוחפים Commit.

Troubleshooting

Claude לא מגיב ל-@claude: ודאו שה-GitHub App מותקן על ה-Repository, ש-Workflows מופעלים, שה-Secret קיים בשם הנכון, שהתגובה מכילה @claude כמילה שלמה, ושלמגיב יש הרשאת Write. בדקו את לשונית Actions: אם ה-Workflow בכלל לא רץ, הבעיה ב-Trigger או ב-if; אם רץ ונכשל, פתחו את הלוג.

שגיאות אימות: בדקו את המפתח או ה-Token מקומית עם claude לפני שחופרים ב-Workflow. מפתח שנמחק מה-Console או Token שפג נכשלים באותה צורה.

CI לא רץ על Commits של Claude: כמעט תמיד github_token מיותר ב-with:. הסירו אותו. בנוסף ודאו שה-Triggers של ה-CI כוללים את האירועים שהדחיפות של Claude מייצרות (push, pull_request).

סקירת Code Review נכשלה או פגה: Check Run עם כותרת Code review encountered an error או timed out אינו חוסם, אך גם לא מנסה שוב לבד. הגיבו @claude review לסקירה טרייה.

הסקירה דילגה עם הודעת תקרת הוצאה: תקרת ה-Spend החודשית נחצתה. Owner מעלה אותה ב-admin-settings/usage או ממתינים לתקופת החיוב הבאה.

Best Practices

  • התחילו מהמסלול המהיר (/install-github-app) וערכו את ה-Workflows שנוצרו, במקום לכתוב מאפס.
  • הגדירו סטנדרטים ב-CLAUDE.md וכללי סקירה ב-REVIEW.md; שני הקבצים משרתים גם את ה-Action וגם את Code Review.
  • הרשאות Workflow לפי הצורך בפועל: לסוקר contents: read, למיישם contents: write. אף פעם לא יותר.
  • תמיד --max-turns ו-timeout-minutes על Workflows של אוטומציה. תקרה שלא הגדרתם היא חשבון שלא תכננתם.
  • צרו Label ייעודי (כמו claude-implement) במקום להפעיל אוטומציה על כל Issue חדש; שליטה אנושית על מה נכנס לתור.
  • שלבו את השכבות לפי תקציב: /code-review מקומי לפני Push (חינם במסגרת המנוי), Workflow אוטומציה זול על כל PR, ו-Code Review מנוהל על Repos קריטיים.
  • אכפו Branch Protection עם דרישת סוקר אנושי על main לפני שמפעילים כל אוטומציה כותבת.

Anti-patterns

  • allowed_bots: '*' ב-Repository ציבורי. הזמנה פתוחה לכל App חיצוני להריץ את Claude עם Prompt זר.
  • Checkout של Ref מ-Fork לשורש ה-Workspace תחת pull_request_target. הקוד הלא מהימן פוגש את ה-Secrets שלכם. השתמשו בתבנית --add-dir המתועדת.
  • --allowedTools רחב מהצורך במצב אוטומציה, למשל Bash לא מסויג לסוקר. תנו בדיוק את הפקודות הדרושות בתחביר Bash(gh pr comment:*).
  • Code Review במצב After every push על Repository עמוס בלי תקרת הוצאה. העלות מוכפלת במספר ה-Pushes; קבעו Spend Cap קודם.
  • מיזוג אוטומטי של PRs שנוצרו מהאוטומציה בלי סוקר. ביטול הפיקוח האנושי מבטל את מודל האבטחה של כל השרשרת.
  • הפעלת show_full_output (או Debug Mode של Actions) ב-Repo ציבורי. הלוגים ציבוריים ועלולים לחשוף תוכן קבצים ופלטי פקודות רגישים.

תרגיל

תרגיל 28.1: סקירה אוטומטית ל-TaskFlow

העלו את פרויקט TaskFlow ל-Repository פרטי חדש ב-GitHub והוסיפו לו סקירת PR אוטומטית:

  1. הקימו את האינטגרציה במסלול המהיר או הידני, עם Secret בשם ANTHROPIC_API_KEY.
  2. כתבו Workflow בשם claude-review.yml שרץ על opened ו-synchronize, עם הרשאות מינימליות, תגובה אחת מתעדכנת, --max-turns 10, וכלים מורשים לתגובות בלבד.
  3. הוסיפו לשורש ה-Repository קובץ REVIEW.md קצר: הגדירו ש-Important הוא רק שגיאת לוגיקה, פרצת אבטחה או קריסה; הגבילו ל-3 Nits לכל סקירה; והוסיפו בדיקת חובה אחת: "כל Endpoint חדש ב-backend חייב בדיקה ב-tests".
  4. פתחו PR שמוסיף ל-backend/app/routers/tasks.py ‏Endpoint חדש בכוונה בלי בדיקה, וצפו בסקירה.
  5. שאלת בונוס: למה ה-Workflow לא ירוץ על PR שיגיע מ-Fork של ה-Repository אם תהפכו אותו לציבורי?
פתרון מוסבר

שלבים 1 עד 2: ה-Workflow זהה במבנהו לדוגמה 2 של הפרק, עם --max-turns 10 ורשימת הכלים mcp__github_inline_comment__create_inline_comment ופקודות gh pr לקריאה ולתגובה. ההרשאות: contents: read, pull-requests: write, id-token: write. שימו לב ש-REVIEW.md אינו נטען אוטומטית על ידי ה-Action כמו ב-Code Review המנוהל; כדי שהסוקר שלכם יכבד אותו, הוסיפו ל-Prompt שורה כמו Follow the review rules in REVIEW.md והוסיפו Read לכלים המורשים.

שלב 4: תוצאה צפויה: תגובת סיכום אחת על ה-PR (בזכות use_sticky_comment) והערת Inline על ה-Endpoint החדש שמציינת את היעדר הבדיקה, בהתאם לכלל שהגדרתם. אם הוספתם גם Bug מכוון, הוא אמור להיתפס כ-Important.

שלב 5 (בונוס): ב-Repositories ציבוריים GitHub מונע Secrets מריצות שהופעלו על ידי PR מ-Fork, ולכן ANTHROPIC_API_KEY לא יהיה זמין וה-Action לא יוכל לאמת. זו התנהגות רצויה: אל תעקפו אותה עם pull_request_target בלי להבין את סיכוני ה-Checkout שתוארו בסעיף האבטחה.

סיכום

  • anthropics/claude-code-action@v1 מריץ את Claude Code ב-Workflows שלכם: מצב אינטראקטיבי עם @claude (בלי prompt) ומצב אוטומציה (עם prompt), בזיהוי אוטומטי.
  • ההקמה: /install-github-app או ידנית (App, ‏Secret, קובץ Workflow). התצורה זורמת דרך prompt, claude_args ו-settings; הקלטים הישנים הוצאו משימוש.
  • Guardrails חובה: --max-turns, ‏timeout-minutes, ‏concurrency, הרשאות מינימליות ו---allowedTools מדויק.
  • Code Review המנוהל (Research Preview, ‏Team ו-Enterprise) סוקר PRs על תשתית Anthropic ב-15 עד 25 דולר לסקירה בממוצע דרך Usage Credits; /code-review המקומי חינמי במסגרת המנוי, ו-ultra מסלים לסקירת ענן עמוקה.

  • GHES נתמך (הקמה ידנית ל-Actions); GitLab CI/CD זמין ב-Beta בתחזוקת GitLab.
