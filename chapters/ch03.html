ה-Session הראשון

בפרק הזה נעבור יחד, צעד אחר צעד, את ה-Session הראשון שלכם ב-Claude Code: מפתיחת הטרמינל ועד יציאה וחזרה לשיחה. נעבוד על פרויקט הדוגמה TaskFlow, נשאל שאלות על הקוד, נאתר Bug אמיתי, נבצע תיקון מבוקר, נריץ בדיקות, ונלמד לאשר, לדחות ולבטל שינויים בביטחון.

מה זה Session ומה נעשה בפרק

Session הוא שיחה אחת רציפה עם Claude Code בתוך תיקיית פרויקט: כל מה שאתם כותבים, כל מה ש-Claude קורא ומשנה, וכל פלט של פקודות, נשמרים כהקשר אחד. הפרק בנוי כתרגול מודרך של אחד עשר שלבים. בכל שלב תראו את הפקודה או ה-Prompt המדויקים, מה קורה מאחורי הקלעים, מה צפוי להופיע על המסך, ומה יכול להשתבש.

איך זה עובד מושגית

כדי שהשלבים הבאים יהיו מובנים ולא ירגישו כמו קסם, הנה המנגנון בקצרה. כשאתם שולחים Prompt, Claude לא רק "עונה": הוא פועל בלולאה. הוא מחליט אילו כלים להפעיל (קריאת קובץ, חיפוש בקוד, הרצת פקודה, עריכה), מפעיל אותם, קורא את התוצאות, ומחליט על הצעד הבא, עד שהמשימה הושלמה. שלושה עקרונות נובעים מזה:

  • אתם לא צריכים להדביק קוד. Claude קורא את הקבצים בעצמו, לפי הצורך, מתוך תיקיית העבודה.
  • פעולות קריאה שקטות, פעולות כתיבה מבוקרות. קריאת קבצים לא דורשת אישור; עריכת קבצים והרצת פקודות דורשות, במצב ברירת המחדל.
  • הכול שקוף. כל צעד בלולאה מוצג על המסך בזמן אמת, ומציג ה-Transcript (Ctrl+O) חושף את הפירוט המלא.
דרישות מוקדמות

נדרשת התקנה עובדת ומחוברת של Claude Code. אם עוד לא התקנתם והתחברתם, חזרו לפרק 2: הכנת סביבת העבודה. כדאי גם Python 3.10+ ו-Node.js מותקנים כדי להריץ את הבדיקות של פרויקט הדוגמה, אבל אפשר להשלים את רוב הפרק גם בלעדיהם.

הכנת פרויקט התרגול: TaskFlow

TaskFlow הוא פרויקט הדוגמה הקבוע של המדריך: אפליקציית ניהול משימות קטנה עם Backend ב-Python ו-FastAPI (עם SQLite), ו-Frontend ב-React עם TypeScript. הוא נמצא בחבילת המדריך בתיקייה examples/taskflow. העתיקו אותו לתיקיית עבודה משלכם, כדי שתוכלו לשנות בו דברים בחופשיות:

Bash (macOS / Linux / WSL)
cp -r /path/to/guide/examples/taskflow ~/projects/taskflow
cd ~/projects/taskflow
git init && git add -A && git commit -m "TaskFlow baseline"
PowerShell (Windows)
Copy-Item -Recurse C:\path\to\guide\examples\taskflow $env:USERPROFILE\projects\taskflow
cd $env:USERPROFILE\projects\taskflow
git init; git add -A; git commit -m "TaskFlow baseline"

יצירת ה-Commit הראשוני אינה חובה, אבל מומלצת: כך תמיד תוכלו להשוות למצב ההתחלה. אין לכם את חבילת המדריך ביד? אפשר לבצע את כל הפרק על כל פרויקט קטן שאתם מכירים; פשוט התאימו את שמות הקבצים ב-Prompts.

ערכת הישרדות: שישה קיצורים שחייבים להכיר

לפני שמתחילים, שננו את הטבלה הקצרה הזאת. אלה הקיצורים שיחלצו אתכם מכל מצב ב-Session הראשון (הרשימה המלאה בפרק על מצב אינטראקטיבי):

קיצור / פקודהמה הוא עושה
Shift+Tabמחליף בין מצבי הרשאות (Permission Modes): מצב ברירת המחדל שבו Claude מבקש אישור, מצב acceptEdits שמאשר עריכות קבצים אוטומטית, ומצב plan שבו Claude רק מתכנן בלי לגעת בקבצים
Escעוצר את Claude באמצע פעולה. העבודה שכבר נעשתה נשמרת ואפשר לכוון מחדש. כשחלון דו-שיח פתוח (למשל בקשת הרשאה), Esc סוגר את החלון
Esc Escכששורת הקלט ריקה: פותח את תפריט ה-Rewind לשחזור מצב קודם. כשיש טקסט בשורת הקלט: מנקה אותו (הטיוטה נשמרת בהיסטוריה)
/helpמציג את הפקודות הזמינות
/clearפותח שיחה חדשה עם הקשר ריק (השיחה הקודמת נגישה דרך /resume)
Ctrl+Oפותח וסוגר את מציג ה-Transcript: תצוגה מפורטת של כל קריאות הכלים והפעולות שמאחורי כל תשובה

למה דווקא השישה האלה? כי הם מכסים את שלושת הצרכים הדחופים של מתחיל: שליטה במה ש-Claude מורשה לעשות (Shift+Tab), עצירה וביטול כשמשהו לא מסתדר (Esc ו-Esc Esc), והתמצאות כשלא ברור מה קורה (/help, Ctrl+O) או כשההקשר התלכלך (/clear). כל השאר יכול לחכות לפרקים הבאים.

Best Practice

יציאה: /exit, או Ctrl+D פעמיים. גם Ctrl+C פעמיים על שורת קלט ריקה יוצא. הקלדת ? על שורת קלט ריקה פותחת פאנל עזרה לקיצורים, בלי לשלוח שום דבר למודל.

שלב 1: פתיחת הטרמינל

ב-macOS פתחו את Terminal (או iTerm2) דרך Spotlight. ב-Windows פתחו Windows Terminal או PowerShell, ואם התקנתם בתוך WSL2 פתחו את טרמינל ההפצה (למשל Ubuntu). ב-Linux כל אמולטור טרמינל יעבוד. אפשר גם להשתמש בטרמינל המשולב של VS Code או JetBrains; היתרון שם הוא שתצוגות ה-Diff ייפתחו בתוך ה-IDE.

מה יכול להשתבש: אם claude --version לא עובד בטרמינל שפתחתם, חזרו לסעיף ה-Troubleshooting של פרק 2 (כמעט תמיד זו בעיית PATH או טרמינל שלא נפתח מחדש אחרי ההתקנה).

שלב 2: מעבר לתיקיית הפרויקט

נווטו לתיקיית ה-TaskFlow שהעתקתם:

$ cd ~/projects/taskflow $ ls CLAUDE.md README.md backend frontend

ב-PowerShell הפקודה זהה בשם אך הנתיב שונה: cd $env:USERPROFILE\projects\taskflow. חשוב להפעיל את Claude Code משורש הפרויקט: תיקיית העבודה קובעת אילו קבצים Claude רואה כברירת מחדל, ואיפה הוא יחפש את קובץ ה-CLAUDE.md עם הוראות הפרויקט.

מה יכול להשתבש: הפעלה מתיקיית הבית (~) במקום מתיקיית הפרויקט תגרום ל-Claude לראות את כל הקבצים האישיים שלכם, ואישור ה-Trust שם נשמר לאותו Session בלבד. תמיד עדיף להפעיל מתיקיית פרויקט ספציפית.

שלב 3: הפעלת claude ואישור ה-Trust

$ claude

מה קורה: נפתח ממשק אינטראקטיבי בתוך הטרמינל. מעל שורת הקלט מוצגים הגרסה, המודל הנוכחי ותיקיית העבודה, ובשורת הקלט מחכה סמן. משם והלאה הכול שיחה: מקלידים טקסט חופשי ולוחצים Enter, או מקלידים / כדי לפתוח את תפריט הפקודות. אם זו ההרצה הראשונה אי פעם, תתבקשו קודם להתחבר לחשבון ולעבור תהליך הגדרה ראשוני קצר (כפי שראינו בפרק 2; ערכת הצבעים ניתנת לשינוי בכל שלב עם /theme). הערה כנה: פרטי המסך המדויקים משתנים מגרסה לגרסה, ולכן אנחנו מתארים כאן את ההתנהגות המתועדת ולא צילום מסך מילולי; אל תיבהלו אם אצלכם הניסוח מעט שונה.

אישור ה-Trust: בהרצה הראשונה בתיקיית קוד חדשה, Claude Code מבקש אימות אמון (Trust Verification) לפני שהוא מתחיל לעבוד עם הקבצים. זהו מנגנון אבטחה מתועד: תיקייה זרה עלולה להכיל הגדרות והרשאות שמישהו אחר כתב, ולכן החלון מציג לאישורכם גם את חוקי ההרשאות שהתיקייה מבקשת להעניק (אם קיים בה קובץ .claude/settings.json). בחרו באפשרות שמאשרת את האמון בתיקייה (בנוסח "Yes, I trust this folder") רק אם אתם יודעים מה מקור הקוד. האישור נשמר פר תיקייה, כך שהוא לא יופיע שוב בהרצות הבאות באותו פרויקט.

מה יכול להשתבש: אם החלון חוזר בכל הפעלה, בדקו אם אתם מפעילים את claude ישירות בתיקיית הבית: שם האישור נשמר ל-Session הנוכחי בלבד ואינו נכתב לדיסק, בכוונה. פתרון: עברו לתיקיית פרויקט.

שלב 4: שאלה ראשונה על ה-Repository

הקלידו את ה-Prompt הראשון ולחצו Enter:

Prompt
what does this project do? give me a short overview of the structure

מה קורה: Claude קורא בעצמו את הקבצים הדרושים: בדרך כלל יתחיל מ-README.md ו-CLAUDE.md, יציץ ב-backend/app/main.py וב-package.json, ויחזיר סיכום. אין צורך "להאכיל" אותו בקבצים; הוא קורא לפי הצורך. תראו על המסך את שורות הפעולה (אילו קבצים נקראו) ואז תשובה מסכמת: אפליקציית ניהול משימות עם API ב-FastAPI ו-Frontend ב-React.

תוצאה צפויה: הניסוח המדויק של התשובה משתנה מהרצה להרצה; זה טבעו של מודל שפה. מה שחשוב הוא שהתשובה תזהה נכון את הרכיבים: Backend, Frontend, SQLite, ומבנה התיקיות. קריאת קבצים היא פעולת קריאה בלבד ולכן אינה דורשת אישור.

המשיכו לתרגל עם עוד כמה שאלות חקירה מהסוג שהתיעוד הרשמי ממליץ עליו למתחילים. כל אחת מהן מלמדת אתכם משהו על הפרויקט ומדגימה סגנון Prompt שימושי:

Prompts לתרגול
what technologies does this project use?
where is the main entry point?
explain the folder structure
how do the frontend and backend talk to each other?

מה יכול להשתבש: אם Claude עונה באופן כללי מדי בלי לקרוא קבצים, ודאו שהפעלתם אותו בתיקייה הנכונה (השורה מעל שורת הקלט מציגה את תיקיית העבודה). ואם תרצו לראות בדיוק אילו קבצים נקראו ובאיזה סדר, לחצו Ctrl+O לפתיחת מציג ה-Transcript ושוב Ctrl+O לסגירתו.

שלב 5: בקשת הסבר על קובץ מסוים

עכשיו נצלול לקובץ אחד. הקלידו @ כדי לקבל השלמה אוטומטית של נתיבי קבצים, ובחרו את קובץ ה-Router:

Prompt
explain @backend/app/routers/tasks.py: what does each endpoint do, and how does it talk to the database?

מה קורה: האזכור עם @ מצרף את הקובץ להקשר באופן מפורש. Claude יסביר שהקובץ מגדיר חמישה Endpoints של CRUD (רשימה, יצירה, שליפה, עדכון ומחיקה של משימות), שכולם עובדים מול SQLite בשאילתות עם פרמטרים דרך הפונקציה get_conn. ייתכן שיעיר גם על פרטים כמו קוד הסטטוס 201 ביצירה ו-404 כשמשימה לא נמצאת.

תוצאה צפויה: הסבר קריא, פסקה או שתיים לכל Endpoint. זו דרך מצוינת ללמוד Codebase חדש: במקום לקרוא קוד זר לבד, מבקשים סיור מודרך.

שלב 6: איתור Bug

בואו נבקש מ-Claude לחפש בעיה אמיתית שקיימת בקוד:

Prompt
I think the API accepts tasks with a whitespace-only title like "   ".
Look at the validation in the backend, tell me if that's true and where the bug is.
Don't change any code yet.

מה קורה: Claude יקרא את backend/app/models.py ויאשר את האבחנה: המודל TaskCreate דורש min_length=1 לשדה title, אבל מחרוזת של רווחים בלבד עוברת את הבדיקה הזאת, כך שאפשר ליצור משימה עם כותרת "ריקה" למראה. שימו לב לניסוח ה-Prompt: ביקשנו במפורש לא לשנות קוד עדיין. הרגל טוב: קודם מבינים, אחר כך משנים.

מה יכול להשתבש: אם Claude מציע מיד תיקון מלא, זה בסדר; פשוט אל תאשרו עריכות בשלב הזה. אתם תמיד שולטים במה שנכתב לדיסק. חלופה מסודרת: לחצו Shift+Tab עד מצב plan, שבו Claude חוקר ומתכנן בלי לערוך כלל.

שלב 7: ביצוע שינוי קטן

עכשיו נבקש את התיקון עצמו:

Prompt
fix it: reject titles that are empty after trimming whitespace,
in both TaskCreate and TaskUpdate. keep the change minimal.

מה קורה: Claude יציע עריכה של backend/app/models.py, למשל הוספת Validator של Pydantic שמסיר רווחים ודוחה כותרת ריקה. במצב ברירת המחדל, לפני כתיבת השינוי לדיסק תופיע בקשת הרשאה: תצוגת השינוי המוצע ולצדה אפשרויות לאשר, לדחות, או להנחות את Claude לעשות משהו אחר. עברו בין האפשרויות עם מקשי החצים.

תוצאה צפויה: אחרי האישור, הקובץ נערך והשינוי מדווח בשיחה. אם תאשרו עם האפשרות שמאשרת גם עריכות עתידיות (או תעברו למצב acceptEdits עם Shift+Tab), עריכות הקבצים הבאות באותו Session לא יבקשו אישור מחדש.

מה יכול להשתבש: אם ה-Diff המוצע גדול או נוגע בקבצים שלא ציפיתם להם, אל תאשרו. דחו, וכתבו הנחיה מדויקת יותר, למשל "only touch models.py, do not modify the routers". דחייה היא חלק רגיל מהעבודה, לא כישלון: אתם עורכים ראשיים, ו-Claude הוא המבצע.

שיקול עלות והקשר

כל פעולה ב-Session צורכת Tokens מתוך מכסת השימוש של התוכנית שלכם (או מהקרדיטים, בחיוב API). שיחה ממוקדת בנושא אחד היא גם זולה יותר וגם מדויקת יותר, כי ההקשר נשאר רלוונטי. הפקודה /usage מציגה את מצב המכסה בתוכניות המנוי, ועל ניהול הקשר מתקדם נדבר בפרקים הבאים.

אזהרה

אל תעברו למצבים אוטומטיים מתוך הרגל ביום הראשון. מצב ברירת המחדל, שבו רואים כל שינוי לפני שהוא נכתב, הוא כלי הלמידה הטוב ביותר שיש למתחילים. על מצבי הרשאות מתקדמים נרחיב בפרק על מערכת ההרשאות.

שלב 8: צפייה ב-Diff

כדי לראות את כל מה שהשתנה עד עכשיו, הריצו:

Prompt
/diff

מה קורה: נפתח מציג Diff אינטראקטיבי בתוך הטרמינל, שמציג את השינויים הלא מקומטים (Uncommitted) בגרסת Git, וגם Diff לכל תור של Claude בנפרד. הניווט: חצים ימינה ושמאלה מחליפים בין תצוגת ה-Git Diff הנוכחי לבין תורות בודדים, חצים למעלה ולמטה עוברים בין קבצים, Enter פותח את ה-Diff של הקובץ שנבחר, ו-Esc חוזר לרשימה.

אם אתם עובדים בתוך VS Code עם התוסף, השינויים מוצגים ממילא בתצוגת השוואה זו לצד זו בתוך העורך. ב-JetBrains, כשהתוסף מחובר, אפשר להגדיר ב-/config את Diff tool ל-auto כדי שה-Diffs ייפתחו במציג של ה-IDE.

מה יכול להשתבש: אם לא יצרתם Repository של Git בשלב ההכנה, חלק מתצוגת ה-Diff שמבוססת על Git לא יהיה זמין. זו סיבה טובה נוספת להתחיל כל פרויקט עם git init.

שלב 9: הרצת הבדיקות

תיקון בלי בדיקה אינו תיקון. בקשו מ-Claude להריץ את חבילת הבדיקות של ה-Backend ולהוסיף בדיקה לתרחיש שתיקנו:

Prompt
run the backend tests. then add a test that POST /tasks with a whitespace-only title returns 422, and run the tests again.

מה קורה: הרצת פקודת Shell כמו pytest -q היא פעולה שמשנה את המערכת, ולכן במצב ברירת המחדל תופיע בקשת הרשאה שמציגה את הפקודה המדויקת לפני הרצתה, עם אפשרות לאשר פעם אחת או לאשר גם להבא. אחרי האישור, Claude מריץ את הבדיקות, קורא את הפלט בעצמו, מוסיף בדיקה חדשה ל-backend/tests/test_tasks.py (עריכה שתדרוש אישור משלה), ומריץ שוב. אם תרצו להריץ פקודה בעצמכם בלי לצאת מה-Session, הקלידו ! בתחילת השורה ואז את הפקודה: היא תרוץ ישירות והפלט שלה יצטרף לשיחה, כך ש-Claude יוכל להתייחס אליו.

תוצאה צפויה: בסוף התהליך כל הבדיקות עוברות, כולל החדשה. אם בדיקה נכשלת, Claude רואה את השגיאה ומציע תיקון; זה בדיוק מחזור העבודה הטבעי שלו: שינוי, הרצה, קריאת פלט, תיקון.

מה יכול להשתבש: אם pytest אינו מותקן, ההרצה תיכשל עם שגיאה ברורה. בקשו מ-Claude להתקין את התלויות (pip install -r requirements.txt, רצוי בתוך Virtual Environment), או עשו זאת בעצמכם בטרמינל אחר.

שלב 10: אישור, דחייה וחרטה

נעצור לרגע ונסכם את כלי השליטה שראינו, ועוד אחד חשוב:

  • בקשות הרשאה: כל עריכת קובץ ורוב פקודות ה-Shell דורשות אישור במצב ברירת המחדל. דחייה אינה מפילה את השיחה; Claude ישאל איך תרצו להמשיך אחרת.
  • עצירה באמצע: Esc קוטע את Claude מיד, תוך שמירת מה שכבר נעשה. שימושי כשאתם רואים שהוא הולך לכיוון לא נכון.
  • Rewind (ביטול): לחצו Esc פעמיים על שורת קלט ריקה, או הריצו /rewind. ייפתח תפריט שמציג את כל ה-Prompts ששלחתם ב-Session; לפני כל Prompt נשמר Checkpoint אוטומטי של הקבצים. בחרו נקודה, ואז בחרו אם לשחזר גם קוד וגם שיחה, רק שיחה, או רק קוד.

תפריט ה-Rewind מציע, לפי התיעוד, את הפעולות הבאות על הנקודה שבחרתם: "Restore code and conversation" משחזר גם את הקבצים וגם את השיחה לאותה נקודה; "Restore conversation" מחזיר את השיחה אחורה אבל משאיר את הקוד הנוכחי; "Restore code" משחזר רק את הקבצים ומשאיר את השיחה; שתי אפשרויות "Summarize" מכווצות חלק מהשיחה לסיכום כדי לפנות מקום בהקשר (נרחיב עליהן בפרק על ניהול Context); ו-"Never mind" יוצא בלי לשנות דבר. שימו לב שאפשרויות שחזור הקוד מופיעות רק כשיש לנקודה שינויי קבצים מתועדים לשחזור.

נסו את זה עכשיו באופן בטוח: הריצו /rewind, הסתכלו על רשימת הנקודות, וצאו עם "Never mind" בלי לשחזר כלום. עצם הידיעה שהתפריט קיים משנה את אופי העבודה: אפשר לתת ל-Claude לנסות מהלך גדול, ולדעת שהדרך חזרה קצרה.

אזהרה: מה Rewind לא מבטל

ה-Checkpoints עוקבים רק אחרי עריכות שנעשו בכלי העריכה של Claude. קבצים ששונו על ידי פקודות Shell (למשל rm או mv), עריכות ידניות שלכם, ועריכות של Subagents, אינם משוחזרים דרך Rewind. לכן Checkpoints הם "ביטול מקומי" נוח, ו-Git נשאר ההיסטוריה האמיתית. אל תוותרו על Commits.

שלב 11: יציאה וחזרה ל-Session

סיימנו את סבב העבודה הראשון. צאו מה-Session:

Prompt
/exit

חלופה: Ctrl+D (הלחיצה הראשונה מציגה רמז אישור, ולחיצה שנייה מיד אחריה יוצאת). היציאה אינה מוחקת דבר: השיחה נשמרת מקומית. עכשיו נחזור אליה. מהטרמינל, באותה תיקייה:

$ claude -c (נטענת השיחה האחרונה בתיקייה הנוכחית, עם כל ההקשר)

הדגל -c (או --continue) ממשיך את השיחה האחרונה בתיקייה הנוכחית. כדי לבחור מתוך כל השיחות הקודמות השתמשו ב--r (או --resume), שפותח בורר אינטראקטיבי, או מקבל מזהה או שם של Session ישירות:

$ claude -r (נפתחת רשימת Sessions לבחירה: תאריך, תקציר ותיקייה לכל שיחה)

אותה יכולת קיימת גם מבפנים: בתוך Session פעיל, הפקודה /resume מציגה את אותו בורר ומאפשרת לקפוץ לשיחה קודמת בלי לצאת. בדקו שההמשכיות אמיתית: אחרי claude -c, שאלו what did we change in the last session? וקבלו סיכום נכון של תיקון ה-Validation.

שלוש הבחנות שיעשו לכם סדר בין הפקודות הדומות:

  • claude -c ממשיך את השיחה האחרונה בתיקייה הנוכחית, בלי שאלות. מהיר ומתאים ל"איפה הייתי הבוקר".
  • claude -r נותן בחירה מכל השיחות של הפרויקט, כולל לפי שם אם נתתם שם ל-Session (עם הדגל -n או הפקודה /rename).
  • /clear הוא ההפך: פתיחת דף חדש ונקי בלי לצאת מהתוכנית, כשהשיחה הקודמת נשארת זמינה דרך /resume.

ההיסטוריה נשמרת מקומית על המחשב שלכם, וכברירת מחדל Sessions ישנים מנוקים אחרי 30 יום (אפשר לשנות זאת בהגדרה cleanupPeriodDays). גם ה-Checkpoints של Rewind נשמרים יחד עם השיחה, כך ששיחה שחזרתם אליה עם claude -c עדיין יכולה להריץ /rewind לנקודות מהסבב הקודם.

טעויות נפוצות של מתחילים

  • הפעלה מהתיקייה הלא נכונה: claude בתיקיית הבית או בתיקיית האב רואה יותר מדי או לא רואה את הפרויקט. תמיד cd לשורש הפרויקט קודם.
  • Prompts כלליים מדי: "fix the bug" עובד פחות טוב מתיאור ממוקד עם שם קובץ, תסמין והתנהגות רצויה, כמו שעשינו בשלב 6.
  • אישור אוטומטי של כל דבר: לחיצת אישור בלי לקרוא את ה-Diff מוותרת בדיוק על שכבת הבקרה שהמצב הזה נותן. קראו לפני שאתם מאשרים.
  • לתת ל-Session להתנפח: כשעוברים למשימה חדשה שאינה קשורה, פתחו דף חדש עם /clear. הקשר ארוך ולא רלוונטי פוגע באיכות ועולה ב-Tokens.
  • להסתמך על Rewind במקום על Git: ראינו למעלה מה הוא לא מכסה. עשו Commit אחרי כל שלב עבודה שהושלם.
  • לחכות בסבלנות כש-Claude טועה כיוון: אין צורך לחכות שיסיים. Esc, הנחיה מתקנת קצרה, והמשך.
  • לשכוח שהשיחה נשמרת: מתחילים רבים סוגרים את הטרמינל באמצע עבודה ומתחילים מחדש מאפס, ומאבדים הקשר יקר. זכרו: claude -c מחזיר אתכם בדיוק לאותה נקודה, כולל ה-Checkpoints.

רשימת אימות: מה אתם אמורים לדעת עכשיו

  • פתחתם Session בתיקיית פרויקט ואישרתם את חלון ה-Trust ביודעין.
  • שאלתם שאלה על ה-Repository וקיבלתם סקירה נכונה בלי לצרף קבצים ידנית.
  • השתמשתם ב-@ לאזכור קובץ ספציפי.
  • איתרתם Bug, אישרתם תיקון דרך בקשת הרשאה, וראיתם אותו ב-/diff.
  • הרצתם בדיקות דרך Claude וראיתם אותו מגיב לפלט שלהן.
  • פתחתם את תפריט ה-Rewind ואתם יודעים מה הוא משחזר ומה לא.
  • יצאתם וחזרתם לאותה שיחה עם claude -c, ואתם מכירים גם את claude -r ו-/resume.
  • אתם זוכרים את ערכת ההישרדות: Shift+Tab, Esc, Esc Esc, /help, /clear, Ctrl+O.

תרגיל

תרגיל 3.1: אותו מסלול, על פרויקט שלכם

בחרו פרויקט אמיתי קטן שלכם (או כל Repository ציבורי קטן שתשכפלו), ובצעו עליו את המסלול המלא:

  1. היכנסו לתיקייה, הפעילו claude, ואשרו את ה-Trust.
  2. בקשו סקירה של הפרויקט, ואז הסבר מעמיק על הקובץ המרכזי ביותר בעזרת @.
  3. בקשו מ-Claude להצביע על בעיה אחת פוטנציאלית (באגים, Validation חסר, קוד כפול), בלי לשנות קוד.
  4. בחרו את הממצא הכי קטן ובטוח, ובקשו תיקון מינימלי. קראו את ה-Diff לפני האישור.
  5. הריצו את הבדיקות אם קיימות (או בקשו בדיקה חדשה קטנה), צפו ב-/diff, וצאו.
  6. חזרו עם claude -c ובקשו סיכום של מה שנעשה.
פתרון מוסבר

אין כאן פלט אחד "נכון", אבל יש מבנה נכון: (1) ה-Trust מופיע רק בפעם הראשונה בתיקייה. (2) סקירה טובה מזהה את מטרת הפרויקט, הטכנולוגיות ונקודת הכניסה; אם היא שטחית, שאלו שאלות המשך ממוקדות. (3) הגבלת הבקשה ל"בלי לשנות קוד" (או מצב plan דרך Shift+Tab) שומרת את שלב האבחון נקי. (4) תיקון מינימלי טוב נוגע בקובץ אחד או שניים; אם ה-Diff גדול מהצפוי, דחו את השינוי ובקשו צמצום, זו פעולה לגיטימית ושכיחה. (5) אם אין בדיקות, בקשה כמו "add one small test for the function you changed and run it" נותנת רשת ביטחון מיידית. (6) אחרי claude -c, שאלה כמו "summarize what we changed and why" צריכה להחזיר תיאור מדויק של סבב העבודה; זו ההוכחה שההקשר באמת נשמר בין הפעלות.

סיכום

עברתם Session ראשון שלם ומציאותי: הפעלה נכונה מתוך תיקיית הפרויקט, אישור Trust מודע, חקירת Codebase בשאלות חופשיות וב-@, איתור Bug אמיתי ותיקונו דרך מנגנון ההרשאות, צפייה בשינויים ב-/diff, הרצת בדיקות כחלק מהמחזור, שליטה עם Esc ו-Rewind, ויציאה וחזרה עם claude -c ו-claude -r. אלו אבני היסוד של כל עבודה ב-Claude Code. בפרק הבא נעשה סדר שיטתי בארגז הכלים: הפקודות הבסיסיות ו-Slash Commands.
