Hooks

Hooks הם הדרך להפוך "בדרך כלל Claude עושה את זה" ל"זה קורה תמיד, בלי יוצא מן הכלל": פקודות שאתם מגדירים, ו-Claude Code מריץ אוטומטית בנקודות מוגדרות במחזור החיים של ה-Session. בפרק הזה נבין את המנגנון לעומק: כל אירועי ה-Lifecycle, תחביר ההגדרה וה-Matchers, סכמת הקלט והפלט, סמנטיקת קודי היציאה, ואבטחה. לאורך הדרך נבנה ונבחן שבעה Hooks מוכנים לעבודה, הכלולים בחבילת המדריך בתיקייה hooks/.

לומדה אינטראקטיבית

לפרק יש לומדה משלימה: Hooks ב-Claude Code, עם שני Hooks שנבדקו בפועל ב-Claude Code 2.1.300, בודק Matchers, סימולטור קודי יציאה וכל 33 האירועים (עודכנה 15.10.2026).

מה זה Hook ואיזו בעיה הוא פותר

Hook הוא מטפל (Handler) שאתם רושמים על אירוע במחזור החיים של Claude Code: לפני הפעלת כלי, אחרי עריכת קובץ, בפתיחת Session, כשהמודל מסיים תור, ועוד. ברוב המקרים המטפל הוא פקודת Shell או סקריפט, שמקבל את פרטי האירוע כ-JSON על stdin ומחזיר החלטה דרך קוד היציאה או דרך JSON על stdout.

הבעיה שהמנגנון פותר היא פער היסודי בין הנחיה לאכיפה. הוראה ב-CLAUDE.md כמו "הרץ Formatter אחרי כל עריכה" היא בקשה מהמודל: לרוב הוא יציית, לפעמים ישכח, ובשיחה ארוכה עם Context עמוס הסיכוי לשכחה עולה. Hook, לעומת זאת, הוא קוד שרץ מחוץ למודל: הוא לא תלוי בשיקול הדעת של Claude, לא נשחק עם ה-Context, ולא ניתן לשכנוע. התיעוד הרשמי מנסח זאת כך: Hooks מספקים שליטה דטרמיניסטית בהתנהגות, ומבטיחים שפעולות מסוימות תמיד יקרו, במקום לסמוך על המודל שיבחר להריץ אותן.

שלושת המנגנונים משלימים זה את זה: חוק Deny ב-Permissions יודע לחסום את הכלי Edit על .env, אבל רק Hook יודע לחסום כתיבה לפי מה שיש בתוכן (למשל מפתח API), כי הוא קוד שרץ ובודק את הקלט בפועל.

מתי להשתמש ומתי לא

השתמשו ב-Hooks כאשר: הכלל חייב לקרות תמיד (פירמוט, Lint, רישום ל-Audit Log); ההחלטה תלויה בתוכן הפעולה (סריקת סודות, זיהוי פקודות מסוכנות); אתם רוצים להזרים הקשר עדכני בתחילת Session; או שאתם מחברים את Claude Code למערכת חיצונית (התראות, שירות רישום ארגוני).

אל תשתמשו ב-Hooks כאשר: מספיקה הוראה רכה (העדפת סגנון: CLAUDE.md); מדובר בחסימה גורפת של כלי או נתיב שחוקי Permissions מכסים; ההחלטה דורשת שיקול דעת אנושי (השאירו את דיאלוג האישור); או שהסקריפט איטי ורץ על כל פעולה, כי אז כל תור ייתקע עליו. שימו לב גם שהתיעוד ממליץ: כשההחלטה דורשת שיפוט ולא כלל דטרמיניסטי, אפשר להשתמש ב-Prompt Hooks או Agent Hooks (בהמשך הפרק) במקום סקריפט.

איך זה עובד מושגית ודרישות מוקדמות

שווה לעצור רגע על מחזור החיים המלא של הפעלת Hook, כי הוא מסביר את כל מה שנראה בהמשך. (1) קורה אירוע: Claude עומד להפעיל כלי, סיים תור, נפתח Session. (2) Claude Code עובר על כל קבוצות ה-Hooks הרשומות לאירוע הזה, מכל מקורות ההגדרה יחד, ובודק לכל קבוצה את ה-Matcher. (3) כל המטפלים התואמים מופעלים במקביל: כל אחד מקבל את נתוני האירוע כ-JSON על stdin. (4) כל מטפל מסיים עם קוד יציאה ואולי פלט. (5) Claude Code ממזג את התוצאות לפי כללי ההכרעה של האירוע ומחיל את האפקט: חסימה, הזרקת הקשר, שכתוב קלט, או כלום. הסקריפט שלכם הוא תהליך רגיל במערכת ההפעלה: הוא רץ עם המשתמש שלכם, יורש את משתני הסביבה (בתוספת CLAUDE_PROJECT_DIR ודומיו), ואין לו שום גישה מיוחדת ל-Claude מעבר לחוזה ה-stdin/stdout/exit-code.

דרישות מוקדמות לפרק: היכרות עם קובצי ההגדרות והיררכיית ה-Scopes מ-פרק 6, ועם מערכת ה-Permissions מ-פרק 7. בצד הכלים: jq מותקן (לסקריפטי Shell שמנתחים JSON) או Python 3, והרשאות הרצה לסקריפטים (chmod +x). את הדוגמאות נריץ על פרויקט TaskFlow מ-פרק 3, אבל הן עובדות בכל פרויקט.

הערה

רשימת האירועים מתרחבת עם הזמן (אירועים כמו TeammateIdle ו-WorktreeCreate נוספו בגרסאות 2.1.x). לפני שאתם מסתמכים על אירוע, אמתו מול ה-Hooks Reference העדכני.

המבנה: אובייקט hooks, בתוכו מפתח לכל שם אירוע, ולכל אירוע מערך של קבוצות. כל קבוצה מכילה matcher (מסנן) ומערך hooks של מטפלים:

{

    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/my-check.sh",
            "timeout": 30
          }
        ]
      }
    ]
  }
}

הסבר כל שדה: matcher קובע מתי הקבוצה נורית (בהמשך); type הוא סוג המטפל; command היא הפקודה שתרוץ (השתמשו ב-$CLAUDE_PROJECT_DIR לנתיב יציב לשורש הפרויקט); timeout בשניות דורס את ברירת המחדל. שדות אופציונליים נוספים: args (מעבר ל-Exec Form שמריץ את הסקריפט ישירות בלי Shell, מומלץ כשיש בעיות Quoting), async ו-asyncRewake (ריצה ברקע), statusMessage (הודעת Spinner מותאמת), ו-if (סינון בתחביר חוקי Permissions, למשל "Bash(git *)", שרלוונטי רק לאירועי כלים).

תחביר Matchers

כללי הפירוש של שדה ה-matcher, כפי שמתועדים:

  • "*", מחרוזת ריקה, או השמטה: התאמה לכל המופעים של האירוע.
  • מחרוזת עם אותיות, ספרות, _, -, פסיק, רווח או | בלבד: התאמה מדויקת. "Edit|Write" תופס את שני הכלים; מגרסה 2.1.191 גם "Edit, Write" שקול.
  • כל תו אחר הופך את הביטוי ל-Regex של JavaScript, לא מעוגן: "mcp__.*__write.*".

על מה ה-Matcher פועל תלוי באירוע: באירועי כלים (PreToolUse, PostToolUse וכדומה) הוא מסנן לפי שם הכלי; ב-SessionStart לפי אופן הפתיחה (startup, resume, clear, compact, fork); ב-Notification לפי סוג ההתראה (permission_prompt, idle_prompt ועוד); ב-SessionEnd לפי סיבת הסיום; ב-PreCompact/PostCompact לפי manual או auto; ב-SubagentStart/SubagentStop לפי סוג ה-Agent; ב-FileChanged זו רשימת שמות קבצים מילולית מופרדת ב-|. חלק מהאירועים, בהם UserPromptSubmit, Stop ו-PostToolBatch, לא תומכים ב-Matcher ותמיד נורים. כלי MCP ממוענים בתבנית mcp__<server>__<tool>, למשל mcp__github__.*.

אזהרה

ה-Matchers רגישים לאותיות גדולות/קטנות: bash לא יתפוס את הכלי Bash. ושדה if על פקודות Bash הוא Best-Effort בלבד (נכשל לכיוון הרצה כשהפקודה לא ניתנת לניתוח); לאכיפה קשיחה השתמשו במערכת ה-Permissions או בבדיקה בתוך הסקריפט עצמו.

סכמת הקלט: מה הסקריפט מקבל ב-stdin

בכל הפעלה, Claude Code כותב ל-stdin של המטפל אובייקט JSON. שדות משותפים לכל האירועים: session_id, prompt_id, transcript_path (נתיב קובץ התמליל), cwd, permission_mode ו-hook_event_name. כל אירוע מוסיף שדות משלו. כך נראה קלט טיפוסי של PreToolUse על הכלי Bash:

stdin (PreToolUse)
{
  "session_id": "abc123",
  "cwd": "/home/dev/taskflow",
  "hook_event_name": "PreToolUse",
  "permission_mode": "default",
  "tool_name": "Bash",
  "tool_use_id": "toolu_01ABC...",
  "tool_input": {
    "command": "pytest -q",
    "description": "Run test suite"
  }
}

באירועי עריכה, tool_input מכיל file_path ואת התוכן (content ב-Write, old_string/new_string ב-Edit). ב-PostToolUse מתווסף tool_response. ב-UserPromptSubmit יש את טקסט ה-Prompt, ב-SessionStart את source ו-model, וב-Stop את stop_hook_active (חשוב למניעת לולאות, ראו בהמשך). לחילוץ שדות בסקריפט Shell נהוג להשתמש ב-jq; ב-Python פשוט json.load(sys.stdin).

שליטה בפלט: קודי יציאה ו-JSON

לסקריפט יש שתי דרכים לדבר חזרה עם Claude Code, ואסור לערבב ביניהן:

  • קוד יציאה 0: אין התנגדות. ה-stdout מנותח כ-JSON מובנה אם הוא כזה. חשוב: ב-PreToolUse, יציאה 0 בלי JSON לא מאשרת את הפעולה, אלא רק לא מתנגדת; זרימת ההרשאות הרגילה ממשיכה. באירועים UserPromptSubmit, UserPromptExpansion ו-SessionStart, כל מה שנכתב ל-stdout מוזרק ל-Context של Claude.
  • קוד יציאה 2: חסימה. ה-stdout מתעלם, וה-stderr מוזן ל-Claude כהסבר. המשמעות תלויה באירוע: ב-PreToolUse הכלי נחסם; ב-UserPromptSubmit ה-Prompt נמחק; ב-Stop החסימה מונעת מ-Claude לעצור והוא ממשיך לעבוד; ב-PostToolUse אי אפשר לבטל (הכלי כבר רץ) אבל ה-stderr מוצג ל-Claude כמשוב.
  • כל קוד אחר: שגיאה לא חוסמת. הפעולה ממשיכה, ובתמליל מופיעה הודעת hook error עם השורה הראשונה של ה-stderr.

לשליטה עדינה יותר, צאו עם קוד 0 והדפיסו JSON ל-stdout. שדות אוניברסליים: continue (כ-false עוצר את העיבוד כולו, עם stopReason), suppressOutput, systemMessage (אזהרה שמוצגת למשתמש). שדות החלטה תלויי אירוע:

אירועמבנה ההחלטה ב-JSONאפשרויות

אל תערבבו: או קוד יציאה 2 עם נימוק ב-stderr, או קוד 0 עם JSON מובנה. כשיוצאים עם קוד 2, Claude Code מתעלם מכל JSON שהודפס.

ריצה מקבילית, Async ו-Timeouts

כשאירוע נורה, כל המטפלים התואמים רצים במקביל, ומטפלים זהים עוברים דה-דופליקציה אוטומטית. אחרי שכולם מסיימים, התוצאות ממוזגות: בהחלטות הרשאה של PreToolUse גוברת התשובה המחמירה ביותר, בסדר deny, defer, ask, allow; טקסט additionalContext נשמר מכל המטפלים. חשוב: deny של מטפל אחד לא מונע ממטפל אחר לרוץ ולבצע תופעות לוואי. עוד מלכודת מתועדת: כשכמה מטפלי PreToolUse מחזירים updatedInput על אותו כלי, האחרון שמסיים מנצח, והסדר לא דטרמיניסטי; הימנעו מזה.

ברירות מחדל של Timeout: 600 שניות ל-command/http/mcp_tool (באירוע UserPromptSubmit יורד ל-30 שניות וב-MessageDisplay ל-10), 30 שניות ל-prompt, 60 ל-agent. מטפל command יכול לרוץ ברקע עם "async": true, ועם "asyncRewake": true הוא גם מעיר את Claude כשהוא מסיים עם קוד 2 (ה-stderr מוצג כתזכורת מערכת). זה שימושי ל-Builds ארוכים שלא רוצים לחסום עליהם את התור.

Hooks במצב לא אינטראקטיבי וב-CI

שלוש עובדות מתועדות שחשוב להכיר כשמריצים את Claude Code במצב Headless (-p, ראו פרק 17): Hooks מסוג PermissionRequest רצים גם שם, חוץ ממצב dontAsk, וקריאה שאף Hook לא החליט עליה ושאין מי שיענה עליה נדחית (עדכון 15.10.2026; במחקר המקורי התיעוד תיאר שהאירוע לא נורה במצב הזה); הדגל --include-hook-events (יחד עם --output-format stream-json) מזרים את אירועי ה-Hooks לפלט, שימושי לניטור; והאירוע Setup עם הדגלים --init-only, --init ו---maintenance נועד בדיוק להכנות חד-פעמיות של סביבת CI: התקנת תלויות, חימום Cache, בדיקות תקינות. בנוסף, ערך ה-permissionDecision הרביעי, defer, קיים רק במצב הזה ומיועד לעטיפות Agent SDK שאוספות קלט וממשיכות.

hooks/format-on-edit/format-on-edit.sh
#!/usr/bin/env bash
set -u

INPUT=$(cat)
FILE_PATH=$(printf '%s' "$INPUT" | jq -r '.tool_input.file_path // empty' 2>/dev/null)

[ -z "$FILE_PATH" ] && exit 0
[ -f "$FILE_PATH" ] || exit 0

case "$FILE_PATH" in
  *.py)
    if command -v black >/dev/null 2>&1; then
      black --quiet "$FILE_PATH" 2>/dev/null || true
    fi
    ;;
  *.js|*.jsx|*.ts|*.tsx|*.json|*.css|*.scss|*.md|*.html|*.yaml|*.yml)
    if command -v npx >/dev/null 2>&1; then
      npx --no-install prettier --write "$FILE_PATH" >/dev/null 2>&1 || true
    fi
    ;;
esac

exit 0

הסבר: הסקריפט שולף את tool_input.file_path ובוחר Formatter לפי סיומת. הוא תמיד יוצא עם 0: כשל פירמוט לא צריך להפריע ל-Session. בדיקה: בקשו מ-Claude לערוך קובץ Python עם רווחים לא עקביים וצפו ב-Diff מתיישר. ידנית: echo '{"tool_input":{"file_path":"app.py"}}' | .claude/hooks/format-on-edit.sh. סיכונים: הסקריפט משנה קבצים; ודאו שתצורת ה-Formatter תואמת לצוות. עריכות דרך Bash לא נתפסות.

2. lint-gate: משוב Lint מיידי

PostToolUse על Edit|Write: מריץ ruff על Python ו-eslint על JS/TS. כשיש ממצאים, יוצא עם קוד 2 וכותב אותם ל-stderr. ב-PostToolUse זה לא מבטל דבר (הכלי כבר רץ), אבל הממצאים מוזנים ל-Claude, שמתקן אותם באותו תור. זה יישום מדויק של סמנטיקת "משוב בלבד" של האירוע.

hooks/lint-gate/lint-gate.sh (הליבה)
report_and_block() {
  {
    echo "lint-gate: $1 reported issues in $FILE_PATH:"
    echo "$2" | head -40
    echo "Fix these lint issues before continuing."
  } >&2
  exit 2
}

case "$FILE_PATH" in
  *.py)
    command -v ruff >/dev/null 2>&1 || exit 0
    OUTPUT=$(ruff check --output-format=concise "$FILE_PATH" 2>&1) \
      || report_and_block "ruff" "$OUTPUT"
    ;;
  *.js|*.jsx|*.ts|*.tsx)
    command -v npx >/dev/null 2>&1 || exit 0
    npx --no-install eslint --version >/dev/null 2>&1 || exit 0
    OUTPUT=$(npx --no-install eslint --no-color "$FILE_PATH" 2>&1) \
      || report_and_block "eslint" "$OUTPUT"
    ;;
esac

בדיקה: בקשו מ-Claude להוסיף לקובץ Python משתנה שלא בשימוש; ב-Transcript (Ctrl+O) תראו את ממצא ה-ruff מוזן חזרה, ו-Claude מתקן. סיכונים: חוקי Lint נוקשים מדי עלולים ליצור לולאת תיקונים; הפלט נחתך ל-40 שורות לחיסכון ב-Context.

3. protect-sensitive-files: חסימת קבצים רגישים

PreToolUse על Edit|Write|NotebookEdit: חוסם עריכת .env וכל .env.*, כל דבר תחת secrets/, וקבצים תחת migrations/ (מיגרציות הן Append-Only). זו הדגמה של דפוס החסימה הפשוט: קוד יציאה 2 עם נימוק ב-stderr.

hooks/protect-sensitive-files/protect-sensitive-files.sh
#!/usr/bin/env bash
set -u

INPUT=$(cat)
FILE_PATH=$(printf '%s' "$INPUT" \
  | jq -r '.tool_input.file_path // .tool_input.notebook_path // empty' 2>/dev/null)

[ -z "$FILE_PATH" ] && exit 0

deny() {
  echo "protect-sensitive-files: editing '$FILE_PATH' is blocked ($1). Ask the user to change this file manually." >&2
  exit 2
}

BASENAME=$(basename "$FILE_PATH")

case "$BASENAME" in
  .env|.env.*) deny "environment file with credentials" ;;
esac

case "$FILE_PATH" in
  secrets/*|*/secrets/*) deny "secrets directory" ;;
esac

case "$FILE_PATH" in
  migrations/*|*/migrations/*) deny "database migrations are append-only; create a new migration instead" ;;
esac

exit 0

אימות שבוצע (28.07.2026): קלט עם file_path: "/x/proj/.env" החזיר קוד 2 עם הנימוק ב-stderr; קלט עם backend/migrations/0002_add.py נחסם; קלט עם backend/app/main.py עבר עם קוד 0 ובלי פלט.

סיכונים: ההגנה מכסה רק את כלי העריכה. Claude יכול לכתוב ל-.env גם דרך Bash (echo ... > .env); לכן שלבו אותה עם חוקי Deny ב-Permissions (פרק 7) להגנה בשכבות.

4. block-dangerous-commands: בולם הפקודות המסוכנות

PreToolUse על Bash, בסקריפט Python: חוסם שלושה דפוסים הרסניים לפני שהם רצים: מחיקה רקורסיבית כפויה של השורש או תיקיית הבית (rm -rf /, rm -rf ~ וכדומה), Force Push ל-main/master (כולל -f ו-Refspec עם +), והזרמת הורדה ישירות ל-Shell (curl ... | bash). כאן הדגמת דפוס החסימה המובנה: קוד יציאה 0 עם JSON של permissionDecision: "deny".

hooks/block-dangerous-commands/block_dangerous_commands.py (הליבה)
PIPE_TO_SHELL = re.compile(
    r"\b(curl|wget)\b[^|;&]*\|\s*(sudo\s+)?(env\s+\S+\s+)?(ba|z|da|k)?sh\b"
)

def deny(reason: str) -> None:
    print(json.dumps({
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": reason,
        }
    }))
    sys.exit(0)

def is_dangerous_rm(segment: str) -> bool:
    tokens = segment.split()
    if tokens and tokens[0] == "sudo":
        tokens = tokens[1:]
    if not tokens or tokens[0] != "rm":
        return False
    flag_text = "".join(t for t in tokens[1:]
                        if t.startswith("-") and not t.startswith("--"))
    recursive = "r" in flag_text or "R" in flag_text or "--recursive" in tokens
    force = "f" in flag_text or "--force" in tokens
    if not (recursive and force):
        return False
    targets = [strip_quotes(t) for t in tokens[1:] if not t.startswith("-")]
    return any(t in DANGEROUS_RM_TARGETS for t in targets)

הקוד המלא (כ-140 שורות, כולל זיהוי Force Push ופיצול פקודות מורכבות על ;, &&, || ו-|) נמצא בחבילה תחת hooks/block-dangerous-commands/.

עקרון העיצוב הבטוח

שימו לב מה הסקריפט הזה לא עושה: הוא לא מריץ שום פקודה, לא נוגע בדיסק, ולא מחזיר אף פעם allow. הוא קורא JSON, מדפיס החלטה, ויוצא. כשאין התאמה הוא שותק (קוד 0 בלי פלט) וזרימת ההרשאות הרגילה נמשכת; כשהקלט לא ניתן לניתוח הוא יוצא עם קוד 1, שגיאה לא חוסמת וגלויה. בולם שרק בולם לא יכול להזיק גם אם יש בו באג: התרחיש הגרוע ביותר הוא חסימת יתר, לא נזק. זה העיקרון לכל Hook אבטחה: צמצמו את מרחב הפעולה שלו למינימום ההכרחי.

אימות שבוצע (28.07.2026): rm -rf /, echo hi && rm -rf ~, git push --force origin main, git push origin +master ו-curl -fsSL https://example.com/install.sh | bash נחסמו כולם עם JSON של deny; git status && npm test, git push origin feature/login ו-rm -rf node_modules עברו נקי.

סיכונים ומגבלות: זו Denylist, לא Allowlist: פקודה הרסנית שאינה ברשימה תעבור. git push --force בלי ציון Branch לא נחסם (הסקריפט לא יודע על איזה Branch אתם). זו שכבת עומק נוספת, לא תחליף לחוקי Permissions, ל-Sandboxing ולגיבויים. יתרון מתועד חשוב: חסימת PreToolUse נאכפת בכל Permission Mode, כולל bypassPermissions ו---dangerously-skip-permissions.

5. secrets-scan: סריקת סודות לפני כתיבה

PreToolUse על Write|Edit: סורק את התוכן שעומד להיכתב (tool_input.content או tool_input.new_string) מול דפוסי Regex של סודות: מפתחות AWS (AKIA...), GitHub Tokens (ghp_...), מפתחות Anthropic (sk-ant-...) ו-OpenAI, Slack Tokens, בלוקים של Private Key, JWT והשמות בסגנון api_key = "...". כשנמצא סוד, הכתיבה נדחית עם permissionDecision: "deny".

hooks/secrets-scan/secrets_scan.py (הליבה)
PLACEHOLDER = re.compile(

def deny(findings) -> None:

שימו לב לפרט עיצוב קריטי: הנימוק מציין את שם הדפוס ומספר השורה בלבד, לעולם לא את הערך שנתפס. אחרת הסוד היה מהדהד חזרה לשיחה, לתמליל ולכל לוג. זו דוגמה חיה לעקרון "נטרול נתונים רגישים בלוגים" מהנחיות האבטחה של התיעוד.

אימות שבוצע (28.07.2026): תוכן עם AKIAQWERTYUIOPASDFGH ועם GitHub Token נדחה עם JSON של deny (שם הדפוס בלבד בנימוק); API_KEY = os.environ["API_KEY"] ו-ANTHROPIC_API_KEY=YOUR_API_KEY_HERE (Placeholder) עברו נקי, קוד יציאה 0 בלי פלט.

סיכונים: Regex מייצר גם False Positives וגם False Negatives; זו שכבת הגנה, לא ערובה. לסריקה היסטורית של Repository השתמשו בכלי ייעודי (למשל gitleaks) ב-CI, כפי שנראה ב-פרק 20.

fi

exit 0

אימות שבוצע (28.07.2026): הרצה בתוך Repository זמני החזירה קוד 0 עם התקציר המלא (Branch, קבצים ב-Staging, הודעת "no commits yet"); הרצה מחוץ ל-Repository החזירה קוד 0 בלי פלט.

בדיקה בתוך Claude Code: פתחו Session חדש ושאלו "על איזה Branch אנחנו ומה השתנה?"; Claude אמור לענות בלי להריץ אף פקודה. סיכונים ועלות: ההזרקה עולה Tokens בכל Session, ולכן הפלט קצוץ; כותרות PR עלולות להכיל מידע רגיש. להזרקה גם אחרי דחיסת Context, הוסיפו קבוצה עם Matcher בערך compact.

דיבוג Hooks

ארבעה כלים עומדים לרשותכם:

  1. /hooks: תפריט לקריאה בלבד שמציג את כל ה-Hooks המוגדרים לפי אירוע, כולל ה-Matcher, הסוג, הפקודה והמקור (User / Project / Local / Plugin / Session / Built-in). עריכה נעשית רק בקובצי ההגדרות; מחיקה מקובץ ההגדרות נקלטת אוטומטית דרך ה-File Watcher.
  2. Transcript (Ctrl+O): שורת סיכום לכל Hook שנורה: הצלחה שקטה, חסימה עם ה-stderr, או הודעת hook error לשגיאה לא חוסמת.
  3. לוג דיבוג: claude --debug או, נוח יותר, claude --debug-file /tmp/claude.log ואז tail -f /tmp/claude.log בטרמינל שני. הלוג מכיל אילו Hooks תאמו, קודי יציאה, stdout ו-stderr מלאים. באמצע Session אפשר להפעיל עם /debug.
  4. בדיקה ידנית: הריצו את הסקריפט ישירות עם קלט מדומה, בדיוק כפי שעשינו באימותים לעיל:
    $ echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | .claude/hooks/block_dangerous_commands.py {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", ...}} $ echo $? 0

טיפול בכשלים ושגיאות נפוצות

  • ה-Hook לא נורה: בדקו ב-/hooks שהוא רשום תחת האירוע הנכון; ה-Matcher רגיש לרישיות; ודאו שאתם על האירוע הנכון (Pre לעומת Post). במצב לא אינטראקטיבי (-p), PermissionRequest רץ חוץ ממצב dontAsk, וקוד יציאה 2 לא נחשב באירוע הזה: דוחים דרך decision ב-JSON. להחלטה לפני כל כלי, PreToolUse אמין יותר.
  • "command not found" או שקט מוחלט: השתמשו בנתיבים מוחלטים או ב-$CLAUDE_PROJECT_DIR, ודאו chmod +x, ובדקו שהשורה הראשונה היא Shebang תקין (#!/usr/bin/env bash או python3).
  • "jq: command not found": התקינו jq (brew install jq / apt-get install jq) או כתבו את המטפל ב-Python.
  • JSON validation failed: אם פרופיל ה-Shell שלכם מדפיס טקסט (למשל echo ב-.bashrc), הוא מזהם את ה-stdout של המטפל. עטפו הדפסות בפרופיל בתנאי אינטראקטיביות ([[ $- == *i* ]]), או עברו ל-Exec Form עם "args": [].
  • Stop Hook שלא מרפה: Claude Code עוקף Stop Hook שחסם שמונה פעמים רצופות בלי התקדמות. סקריפט Stop חייב לבדוק את השדה stop_hook_active בקלט ולצאת 0 אם הוא true, אחרת תיווצר לולאה עד המכסה.
  • Timeout: מטפל איטי נקטע בברירת המחדל של סוגו; העלו timeout נקודתית או העבירו עבודה כבדה ל-async.
  • כיבוי זמני: "disableAllHooks": true בקובץ ההגדרות מכבה את כל ה-Hooks שלכם (אך לא Hooks מ-Managed Settings ארגוניים).

אבטחה

סכנה: Hooks מריצים קוד שרירותי

Hook רץ עם ההרשאות המלאות של המשתמש שלכם, בלי Sandbox, אוטומטית, שוב ושוב. Hook זדוני או רשלני יכול למחוק קבצים, לגנוב סודות או לשתול קוד. לעולם אל תתקינו Hooks ממקור שאינכם בוטחים בו, כולל Hooks שמגיעים בתוך Plugins ו-Hooks שנמצאים ב-.claude/settings.json של Repository שזה עתה שכפלתם. קראו את הסקריפט לפני שהוא רץ. התיעוד הרשמי מדגיש: אתם האחראים הבלעדיים לפקודות שאתם מגדירים.

  • ולידציה של קלט: אל תניחו שהקלט תקין; בדקו קיום שדות והתגוננו מנתיבים עם .. (Path Traversal).
  • ציטוט משתנים: תמיד "$VAR" ולא $VAR בסקריפטי Shell, ונתיבים מוחלטים דרך "$CLAUDE_PROJECT_DIR".
  • נטרול נתונים בלוגים: אל תרשמו תוכן קבצים או תגובות כלים; ראו את העיצוב של audit-log ו-secrets-scan לעיל.
  • דילוג על קבצים רגישים: סקריפטים שנוגעים בקבצים צריכים להחריג .env, מפתחות ו-.git/.
  • Hooks מחמירים אבל לא מקלים: deny של Hook נאכף גם ב-bypassPermissions, אבל allow של Hook לא עוקף חוקי Deny מ-Settings, כולל Managed Settings. הכיוון תמיד לכיוון ההחמרה.
  • בקרה ארגונית: Admin יכול לקבוע allowManagedHooksOnly ב-Managed Settings, שחוסם Hooks של משתמש, פרויקט ו-Plugins. ל-HTTP Hooks יש Allowlist של כתובות (allowedHttpHookUrls) ושל משתני סביבה בכותרות.
  • אמון Workspace: Hooks ב-Frontmatter של Subagents בפרויקט רצים רק אחרי אישור דיאלוג ה-Trust (מגרסה 2.1.218). לעומת זאת, Hooks בקובצי ההגדרות של הפרויקט רצים גם ב-claude -p בתיקייה שמעולם לא אושרה; לפני הרצה כזו ב-Repository לא מוכר, השתמשו ב---setting-sources user, ב---bare או ב---settings '{"disableAllHooks": true}' (עדכון 15.10.2026).

עלות ו-Context

Hooks עצמם רצים מחוץ למודל ולא עולים Tokens, אבל כל טקסט שהם מזריקים כן: additionalContext, נימוקי חסימה, ופלטי stdout ב-SessionStart נכנסים ל-Context ומתומחרים ככל קלט אחר. לכן קצצו פלטים (כמו ה-head -30 ב-session-context וה-head -40 ב-lint-gate). Hooks סינכרוניים גם מוסיפים זמן המתנה לכל תור; העבירו עבודה איטית ל-async, וזכרו שב-UserPromptSubmit ה-Timeout מקוצר ל-30 שניות בדיוק כדי שלא תאטו כל הודעה.

Best Practices ו-Anti-Patterns

  • סקריפט לכל Hook בקובץ נפרד תחת .claude/hooks/, לא פקודות ארוכות בתוך ה-JSON.
  • Fail-Safe מתוכנן: החליטו במודע מה קורה כשהסקריפט נכשל (בולם אבטחה שנכשל צריך להישאר שקט או גלוי? תעדו את הבחירה).
  • בדקו כל Hook ידנית עם קלט מדומה לפני הרישום, ושמרו את פקודות הבדיקה ב-README שלו.
  • Matcher צר ככל האפשר: Edit|Write ולא *, אלא כשבאמת צריך הכול (כמו audit-log).
  • החזיקו Hooks של צוות ב-.claude/settings.json בתוך ה-Repository, עם Code Review על כל שינוי.

Anti-Patterns: Hook שמריץ את כל חבילת הבדיקות אחרי כל עריכה (איטי; העדיפו Stop או async); PermissionRequest עם Matcher ריק שמאשר הכול אוטומטית (ביטול בפועל של מערכת ההרשאות); שני Hooks שמחזירים updatedInput על אותו כלי (סדר לא דטרמיניסטי); Hook שמדפיס סודות בנימוקי חסימה; ושימוש ב-Hook כתחליף יחיד לגיבויים ול-Permissions.

תרגיל

תרגיל 22.1: חסימת Commits שמכילים console.log

כתבו Hook מסוג PreToolUse על Bash שמזהה פקודות git commit, בודק את ה-Diff שנמצא ב-Staging, וחוסם את ה-Commit אם נוספו בו שורות עם console.log. דרישות: (1) הפקודה נבדקת רק אם היא באמת git commit; (2) נבדקות רק שורות שנוספו (מתחילות ב-+), לא שורות הקשר; (3) הנימוק שמוזן ל-Claude כולל את שמות הקבצים הבעייתיים; (4) כשל בסקריפט לא חוסם עבודה תקינה. בדקו ידנית עם קלט מדומה לפני הרישום.

פתרון מוסבר
.claude/hooks/block-console-log-commits.sh
#!/usr/bin/env bash
# PreToolUse hook (matcher: Bash): blocks git commit when the staged
# diff adds console.log lines.
set -u

INPUT=$(cat)
COMMAND=$(printf '%s' "$INPUT" | jq -r '.tool_input.command // empty' 2>/dev/null)

# Only act on real git commit commands.
case "$COMMAND" in
  *"git commit"*) ;;
  *) exit 0 ;;
esac

# Added lines only: start with '+' but not the '+++' file header.
OFFENDERS=$(git diff --cached --unified=0 2>/dev/null \
  | awk '/^\+\+\+ b\// { file=substr($0,7) }
         /^\+/ && !/^\+\+\+/ && /console\.log/ { print file }' \
  | sort -u)

if [ -n "$OFFENDERS" ]; then
  {
    echo "Commit blocked: staged changes add console.log in:"
    echo "$OFFENDERS"
    echo "Remove the console.log lines (or use a proper logger), restage, and commit again."
  } >&2
  exit 2
fi

exit 0
.claude/settings.json (קטע)
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-console-log-commits.sh",
            "timeout": 20
          }
        ]
      }
    ]
  }
}

נקודות המפתח: (1) הסינון על git commit נעשה בתוך הסקריפט; אפשר לחדד עם "if": "Bash(git commit *)" על המטפל, אך זכרו שהשדה הוא Best-Effort. (2) git diff --cached --unified=0 מציג רק שורות שהשתנו ב-Staging, וה-awk עוקב אחרי כותרות +++ b/ כדי לשייך כל שורה שנוספה לקובץ שלה, תוך דילוג על כותרות הקובץ עצמן. (3) קוד יציאה 2 עם הרשימה ב-stderr נותן ל-Claude נימוק קונקרטי, והוא בדרך כלל יסיר את השורות ויבצע Commit מחדש לבד. (4) כל כשל אחר (למשל מחוץ ל-Repository) מסתיים ב-exit 0 דרך ה-2>/dev/null וברירות המחדל, כך שעבודה תקינה לא נחסמת. בדיקה ידנית: העבירו ל-stdin קלט {"tool_input":{"command":"git commit -m test"}} בתיקייה עם console.log ב-Staging וודאו קוד יציאה 2; עם Staging נקי ודאו קוד 0. שדרוג אפשרי: להוסיף גם debugger ו-print( לרשימה, כפי שעושה ה-Skill pr-ready שנארוז ב-פרק 26.

סיכום

Hooks הם שכבת הדטרמיניזם של Claude Code: קוד שלכם, שרץ בנקודות מוגדרות, בלי תלות בשיקול הדעת של המודל. למדנו את שלושים אירועי ה-Lifecycle וחמשת סוגי המטפלים; את מבנה ההגדרה ב-settings.json ותחביר ה-Matchers; את סכמת הקלט ב-stdin ואת שפת הפלט: קוד יציאה 2 עם stderr לחסימה פשוטה, או JSON מובנה עם permissionDecision, decision, updatedInput ו-additionalContext לשליטה עדינה. בנינו ואימתנו שבעה Hooks מעשיים, מהפירמוט האוטומטי ועד בולם הפקודות המסוכנות עם עקרון העיצוב הבטוח שלו. וקבענו את כלל האבטחה: Hook רץ עם ההרשאות שלכם, לכן מתקינים רק ממקור אמין וקוראים כל שורה. בפרק הבא נצא מגבולות המכונה המקומית אל MCP בעבודה מעשית מקצה לקצה, ובפרק 26 נראה איך Hooks נארזים ומופצים לצוות שלם בתוך Plugin.
