בניית Agent מותאם

בפרק הזה בונים סוכן שלם מההתחלה ועד הסוף: סוכן משימות פיתוח שמקבל משימה, חוקר את ה-Repository בקריאה בלבד, מגיש תוכנית מובנית, עוצר לאישור אנושי, מבצע את השינוי, מריץ בדיקות עם לולאת תיקונים מוגבלת, סוקר את ה-Diff ומפיק דוח סיום עם נתוני עלות. נעבור על הקוד האמיתי, קובץ agent-sdk/python/02_code_reviewer.py מחבילת המדריך, סעיף אחרי סעיף, ונסביר כל אפשרות, כל מעקה בטיחות וכל החלטת תכנון.

מה בונים ולמה ככה

סוכן "עשה הכול בפעם אחת" הוא מתכון לצרות: אין נקודת עצירה לביקורת, אין הפרדה בין שלב שקורא לשלב שכותב, וכשמשהו נכשל קשה לדעת איפה. לכן הסוכן שלנו בנוי כשמונה שלבים מוגדרים, שכל אחד מהם ניתן לבדיקה בנפרד:

  1. קבלת משימה מהמפעיל (Command Line).
  2. מחקר ה-Repository בקריאה בלבד: Read, Glob, Grep ולא שום דבר אחר.
  3. הכנת תוכנית כפלט מובנה שאומת מול JSON Schema: קבצים לשינוי, צעדים, סיכונים ופקודת בדיקה.
  4. אישור אנושי: הסקריפט מדפיס את התוכנית ועוצר על input(). בלי "כן" מפורש, שום קובץ לא משתנה.
  5. ביצוע השינוי בעריכות קבצים בלבד; כלי ה-Bash מוסר מה-Context לגמרי בשלב הזה.
  6. הרצת בדיקות: רק פקודות pytest מאושרות מראש.
  7. סקירה: אם הבדיקות נכשלו, לולאת תיקונים עם תקרה קשיחה; ואז סקירת git diff עצמית.
  8. דוח סיום מובנה, בתוספת חשבונאות עלות וטרנים מכל שלב.

העיקרון המארגן הוא הרשאה מינימלית לכל שלב (Least Privilege): כל שלב הוא קריאת query() נפרדת עם סט אפשרויות משלה, וכולן חולקות את אותו Session דרך resume, כך שההקשר (מה שהסוכן כבר למד על הקוד) נשמר בין השלבים בלי לוותר על הבידול בהרשאות. שימו לב שזה עיצוב שונה מ-Subagents (פרק 31): שם סוכן ראשי מאציל לסוכני משנה מקביליים; כאן יש סוכן אחד שעובר בין "מצבי עבודה" טוריים, כי השלבים תלויים זה בזה ואסור שירוצו במקביל. שני הדפוסים משלימים, ואפשר לשלב ביניהם (למשל: שלב המחקר יכול להאציל ל-Subagents).

דרישות מוקדמות

פרק 31 (מושגי ה-SDK), התקנת claude-agent-sdk בגרסה 0.2.139 ומעלה, Python 3.10+, משתנה סביבה ANTHROPIC_API_KEY, ועותק של פרויקט TaskFlow עם Git מאותחל (פרק 3). ה-Repository צריך pytest זמין: pip install -r backend/requirements.txt.

למה Python ולא TypeScript לדוגמה הזאת? שיקול פרקטי בלבד: שער האישור מבוסס input() פשוט במיוחד ב-Python, ופרויקט הדוגמה TaskFlow הוא ממילא Backend של Python, כך שסביבת בדיקות אחת משרתת גם את הסוכן וגם את הקוד הנבדק. כל מה שנבנה כאן ניתן לתרגום ישיר ל-TypeScript עם השמות המקבילים מפרק 31 (canUseTool, maxTurns, outputFormat וכן הלאה), ואת המקבילה ההפוכה, סוכן אצווה ב-TypeScript, תמצאו בקובץ 02-automation.ts שנפגוש בפרק 33.

חלק 1: קונפיגורציה ומעקות בטיחות

בראש הקובץ מרוכזים כל הגבולות במקום אחד, כדי שסקירת אבטחה של הסוכן תתחיל ותיגמר במסך אחד:

agent-sdk/python/02_code_reviewer.py (קטע: קונפיגורציה)
TOTAL_BUDGET_USD = 3.00      # תקרה קשיחה לכל הריצה (אומדן צד-לקוח)
PHASE_BUDGET_USD = 1.00      # תקרה לכל קריאת query() בודדת
MAX_FIX_ATTEMPTS = 2         # לולאת תיקונים חסומה כשבדיקות נכשלות
TRANSIENT_RETRIES = 2        # ניסיונות חוזרים לכשלי תקשורת/תהליך

GLOBAL_DENY_RULES = [
    "Bash(git push *)",       # סוכן אוטומטי לא דוחף ל-Remote, נקודה
    "Bash(rm -rf *)",         # בלי מחיקות רקורסיביות
    "Bash(sudo *)",           # בלי הסלמת הרשאות
    "Read(.env)",             # סודות לא נכנסים ל-Context
    "Edit(.env)",
    "WebFetch",               # שם מלא: הסרת כלי הרשת לגמרי
    "WebSearch",
]

DANGEROUS_COMMAND_MARKERS = [
    "git push", "rm -rf", "sudo", "curl", "wget", "pip install",
    "npm install", "chmod 777", "> /dev/", "mkfs", "shutdown",
]

הסבר כל שדה:

  • TOTAL_BUDGET_USD ו-PHASE_BUDGET_USD: הגנה כפולה. התקרה לשלב מועברת כ-max_budget_usd ל-SDK, שעוצר את השאילתה בעצמו; התקרה הכוללת נבדקת בקוד שלנו אחרי כל שלב, כי כפי שלמדנו בפרק 31, כל query() מדווח רק על עצמו.
  • GLOBAL_DENY_RULES מצורפים ל-disallowed_tools בכל שלב. כלל עם תבנית כמו Bash(git push *) דוחה קריאות תואמות בכל מצב הרשאות, כולל bypassPermissions; שם מלא כמו WebFetch מסיר את הכלי מה-Context כך שהמודל כלל לא רואה אותו. הסוכן הזה עובד רק על קבצים מקומיים, אז אין לו שום סיבה לגשת לרשת.
  • DANGEROUS_COMMAND_MARKERS: שכבת הגנה שנייה (Defense in Depth) בתוך ה-Permission Callback, למקרה שפקודה מסוכנת מגיעה בניסוח שכללי התבנית לא תפסו.

חלק 2: שלוש סכמות פלט

לתוכנית, לתוצאת הבדיקות ולדוח הסיום מוגדרות סכמות JSON Schema (draft-07). זה מה שהופך את הסוכן לרכיב תוכנה אמין: הקוד שלנו ניגש ל-plan["files_to_change"] בביטחון, בלי לנתח טקסט חופשי. כך נראית סכמת התוכנית:

02_code_reviewer.py (קטע: PLAN_SCHEMA)
PLAN_SCHEMA = {
    "type": "object",
    "properties": {
        "task_summary": {"type": "string"},
        "files_to_change": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "path": {"type": "string"},
                    "reason": {"type": "string"},
                },
                "required": ["path", "reason"],
            },
        },
        "steps": {"type": "array", "items": {"type": "string"}},
        "risks": {"type": "array", "items": {"type": "string"}},
        "test_command": {"type": "string"},

שימו לב ש-risks אינו שדה חובה: לפי ההמלצה הרשמית, שדות שאולי אין להם תוכן משאירים אופציונליים, אחרת המודל עלול להמציא תוכן רק כדי לספק את הסכמה. TEST_RESULT_SCHEMA (עם passed, summary ו-failing_tests) ו-REPORT_SCHEMA (קבצים ששונו, תיאור, סטטוס בדיקות והמלצות המשך) בנויות באותו עיקרון.

חלק 3: ה-Permission Callback

02_code_reviewer.py (קטע: guard_tool)
async def guard_tool(tool_name: str, input_data: dict[str, Any], context: Any):
    if tool_name == "Bash":
        command = str(input_data.get("command", ""))
        for marker in DANGEROUS_COMMAND_MARKERS:
            if marker in command:
                log.warning("DENIED dangerous command: %s", command)
                return PermissionResultDeny(
                    message=f"Command contains forbidden pattern '{marker}'. "
                    "This agent may only run the approved test commands.",
                    interrupt=True,  # עצירת התור הנוכחי כולו
                )
        log.info("DENIED unapproved command: %s", command)
        return PermissionResultDeny(
            message="Only the pre-approved pytest commands are allowed in this phase."
        )
    log.info("DENIED unapproved tool: %s", tool_name)
    return PermissionResultDeny(
        message=f"Tool {tool_name} is not part of this phase's allowed set."
    )

נקודות מהותיות, כולן מהתיעוד הרשמי של מערכת ההרשאות:

  • ה-Callback מוזמן רק כשבקשת הכלי "נופלת" עד סוף שרשרת ההרשאות: מה שכבר אושר על ידי allowed_tools או על ידי מצב ההרשאות לא מגיע אליו בכלל. לכן העיצוב כאן הוא "ברירת מחדל: דחייה". כל מה שהסוכן באמת צריך מאושר מראש ברשימות ה-allowed_tools של השלב, ומה שמגיע ל-Callback הוא בהגדרה חריג.
  • PermissionResultDeny עם message מחזיר למודל הסבר, כך שהוא יכול להמשיך בדרך אחרת במקום להיתקע. עם interrupt=True (במקרה של דפוס מסוכן) התור נקטע מיד.
  • כל דחייה נרשמת ל-Log. בסוכן אוטומטי, ה-Log של הדחיות הוא חומר החקירה הראשון כשמשהו מתנהג מוזר.

חלק 4: מריץ השלבים, Logging, עלות ו-Retry

לפני המריץ עצמו, מחלקת עזר קטנה מרכזת את מצב הריצה: מזהה ה-Session המשותף, העלות המצטברת, סך ה-Turns ושורות החשבונאות לדוח:

02_code_reviewer.py (קטע: RunState)
@dataclass
class RunState:
    session_id: str | None = None
    total_cost_usd: float = 0.0
    turns: int = 0
    log_lines: list[str] = field(default_factory=list)

ה-Logging מוגדר בראש הקובץ עם מודול logging הסטנדרטי, לערוץ stderr: כך הפלט "האנושי" (התוכנית, הדוח) נשאר נקי ב-stdout ואפשר להפנות את הלוג לקובץ בנפרד (2>agent.log). מה נרשם? שלושה סוגי אירועים, לפי סדר חשיבות תחקירית: כל דחיית הרשאה (מי ניסה מה ולמה נדחה), כל קריאת כלי (רמת INFO, השלד של "מה הסוכן עשה"), וכל סיכום שלב עם עלות. כשסוכן מתנהג לא צפוי, שלושת אלה עונים על תשעים אחוז מהשאלות.

הפונקציה run_phase() היא הלב התפעולי: היא מריצה קריאת query() אחת, מזרימה התקדמות ל-Log, אוספת את ה-ResultMessage, צוברת עלות, ומיישמת מדיניות Retry זהירה:

02_code_reviewer.py (קטע: run_phase, מקוצר להסבר)
for attempt in range(1, TRANSIENT_RETRIES + 2):
    result: ResultMessage | None = None
    try:
        async for message in query(prompt=prompt, options=options):
            if isinstance(message, AssistantMessage):
                for block in message.content:
                    if isinstance(block, ToolUseBlock):
                        log.info("[%s] tool: %s", phase, block.name)
            elif isinstance(message, ResultMessage):
                result = message
    except (CLIConnectionError, ProcessError, CLIJSONDecodeError) as exc:
        # כשל תעבורה: שווה ניסיון חוזר עם השהיה
        log.warning("[%s] transient failure (attempt %d): %s", phase, attempt, exc)
        if attempt <= TRANSIENT_RETRIES:
            await asyncio.sleep(2**attempt)
            continue
        raise
    except Exception as exc:
        # query() חד-פעמי זורק חריגה רגילה אחרי ResultMessage מסוג שגיאה.
        # אם כבר קיבלנו את התוצאה, זו תוצאת שלב, לא קריסה.
        if result is None:
            raise
        log.warning("[%s] query ended with an error result: %s", phase, exc)
חשוב: Prompt כזרם כשיש Callback

ב-Python SDK, האפשרות can_use_tool עובדת רק כשה-Prompt נשלח כזרם (AsyncIterable) ולא כמחרוזת. עם מחרוזת, query() נכשל מיד בשגיאה can_use_tool callback requires streaming mode. לכן בקובץ המלא run_phase() לא מעביר את הטקסט ישירות, אלא עוטף אותו בפונקציית עזר קטנה, _as_stream(), שמחזירה הודעת משתמש אחת בפורמט {"type": "user", "message": {"role": "user", "content": ...}}. כך כל השלבים, עם Callback ובלעדיו, נשלחים באותה צורה. נבדק מול claude-agent-sdk 0.2.139 ב-18.10.2026.

מדיניות ה-Retry מבחינה בין שני סוגי כשל, וההבחנה הזאת חשובה:

  • כשלים חולפים (Transient): CLIConnectionError, ProcessError ו-CLIJSONDecodeError הם כשלי תקשורת עם תהליך המשנה של Claude Code. אותם מנסים שוב, עד TRANSIENT_RETRIES פעמים, עם Exponential Backoff (2**attempt שניות). חשוב לציין שה-SDK עצמו כבר מבצע Retry לשגיאות API (ברירת מחדל מתועדת: עד 10 ניסיונות, נשלט דרך CLAUDE_CODE_MAX_RETRIES), אז השכבה שלנו מטפלת רק במה שנשאר.
  • כשלים לוגיים: חריגה שמגיעה אחרי שכבר התקבל ResultMessage היא ההתנהגות המתועדת של query() חד-פעמי שנגמר בתוצאת שגיאה (כמו error_max_turns). את זה לא מנסים שוב בעיוורון; מחזירים את התוצאה ונותנים ללוגיקת השלבים להחליט.

אחרי כל שלב מתבצעת החשבונאות: session_id נשמר להמשך, total_cost_usd מצטבר לסכום הכולל, ואם הסכום חצה את TOTAL_BUDGET_USD הריצה כולה נעצרת עם חריגה. זה ההבדל בין "תקציב לשלב" שה-SDK אוכף לבין "תקציב לריצה" שאנחנו אוכפים.

חלק 5: שלב המחקר והתוכנית (שלבים 1 עד 3)

02_code_reviewer.py (קטע: אפשרויות שלב המחקר)
research_options = ClaudeAgentOptions(
    cwd=args.repo,
    system_prompt=(
        "You are a careful senior engineer. Research the repository and plan "
        "the requested change. You are in a READ-ONLY phase: do not modify "
        "anything. The test command in your plan must be runnable from the "
        "repository root and must start with 'python -m pytest'."
    ),
    allowed_tools=["Read", "Glob", "Grep"],
    disallowed_tools=GLOBAL_DENY_RULES,
    permission_mode="dontAsk",  # כל מה שלא אושר מראש נדחה
    max_turns=25,
    max_budget_usd=PHASE_BUDGET_USD,
    output_format={"type": "json_schema", "schema": PLAN_SCHEMA},
)

כל אפשרות והסיבה שלה:

  • cwd: תיקיית העבודה של הסוכן היא ה-Repository שהמפעיל נתן, לא התיקייה שממנה הופעל הסקריפט. בלי זה הסוכן יחקור את התיקייה הלא נכונה.
  • system_prompt כמחרוזת: אנחנו לא צריכים את מלוא ה-Prompt של Claude Code כאן, רק פרסונה ממוקדת. שימו לב לתחבולה המעשית בסופו: אנחנו מכתיבים שפקודת הבדיקה בתוכנית תתחיל ב-python -m pytest, כי בשלב הבדיקות בדיוק הקידומת הזאת תאושר אוטומטית. הסוכן מתכנן את מה שההרשאות שלו יאפשרו לבצע.
  • permission_mode="dontAsk": בשלב קריאה בלבד אין שום סיבה שבקשה כלשהי תגיע ל-Callback. מה שלא אושר, נדחה. שקט, צפוי, בטוח.
  • max_turns=25: מחקר של Repository בינוני דורש עשרות קריאות קבצים; 25 סבבים מספיקים ל-TaskFlow בלי לאפשר שוטטות אינסופית.
  • output_format עם PLAN_SCHEMA: בסוף השלב, result.structured_output מכיל את התוכנית כאובייקט מאומת.

הקוד שקורא לשלב בודק את שני התנאים המתועדים: subtype == "success" וגם קיום structured_output. תוצאה בלי אחד מהם נחשבת כישלון והריצה נעצרת לפני שנגעה בקובץ כלשהו.

מה רואים ב-Log בזמן השלב הזה? רצף אופייני על TaskFlow: קריאת Glob אחת או שתיים למיפוי המבנה, Read על CLAUDE.md ו-README.md, סדרת Grep לאיתור המקומות הרלוונטיים למשימה (למשל חיפוש status ו-completed), ואז Read ממוקדים על models.py, routers/tasks.py וקובצי הבדיקות. אם אתם רואים במקום זה עשרות קריאות Read גורפות על כל הקבצים, המשימה מנוסחת עמום מדי והסוכן "קורא הכול ליתר ביטחון": חדדו את הניסוח, כמו שלמדנו בפרק על כתיבת Prompts.

# ... הדפסת הצעדים, הסיכונים ופקודת הבדיקה ...
answer = input("\nApprove this plan and apply the change? [y/N]: ").strip().lower()
if answer not in ("y", "yes"):
    print("Plan rejected by operator. No changes were made.")
    return 0

זה השלב הפשוט ביותר בקוד והחשוב ביותר בתפעול. שלושה עקרונות עיצוב: ברירת המחדל היא סירוב ([y/N] עם N גדולה: Enter ריק דוחה); הסירוב הוא יציאה נקייה עם קוד 0, כי "המפעיל בחר לא" איננו שגיאה; והתוכנית מודפסת במלואה, כולל הסיכונים, כי אישור על סמך כותרת בלבד אינו אישור. בגרסת ה-CLI של אותו רעיון, זה המקביל ל-Plan Mode עם אישור ידני (פרק 6).

שווה לשים לב מה השער הזה לא עושה: הוא לא מריץ את הסוכן ברקע בזמן ההמתנה, והוא לא פג אחרי Timeout. input() חוסם עד שאדם עונה, וזו בדיוק הכוונה. בסביבה שבה אין טרמינל (למשל שרת), מחליפים את המימוש של השער באותו רעיון בלבוש אחר: שליחת התוכנית לערוץ צוות ועצירה עד לקבלת אישור, או, פשוט יותר, פיצול הסקריפט לשניים: plan שמדפיס תוכנית ושומר את מזהה ה-Session לקובץ, ו-apply שמופעל ידנית אחרי הקריאה, עם resume מאותו קובץ. הארכיטקטורה שבנינו תומכת בזה בלי שינוי, כי ממילא כל שלב הוא קריאה נפרדת שמחוברת ב-resume. חשוב רק לזכור את המגבלה מפרק 31: קובצי Session הם מקומיים למכונה, אז שני החצאים חייבים לרוץ על אותה מכונה, או לחלוק SessionStore.

  • permission_mode="acceptEdits" יחד עם can_use_tool=guard_tool: עריכות בתוך תיקיית העבודה מאושרות אוטומטית (לשם כך קיבלנו אישור אנושי לתוכנית), וכל בקשה אחרת שמגיעה בכל זאת לשרשרת נופלת ל-Callback שלנו, שדוחה כברירת מחדל.

הכלל Bash(python -m pytest *) משתמש בתחביר כללי ההרשאות שהכרנו: הרווח לפני הכוכבית חשוב, כי הוא מפעיל התאמת קידומת מדויקת (python -m pytest backend/tests -q יאושר; python -m pytestX לא). כל פקודת Shell אחרת נדחית על ידי dontAsk.

מה קורה כשהבדיקות נכשלות? זה התרחיש שמפריד סוכן צעצוע מסוכן אמיתי. העיצוב כאן:

  • הלולאה רצה לכל היותר MAX_FIX_ATTEMPTS + 1 פעמים (בדיקה ראשונה ועוד שני סבבי תיקון). בלי תקרה, סוכן יכול "לרדוף אחרי הזנב" של בדיקה שבירה עד שהתקציב נגמר.
  • שלב התיקון מקבל את שמות הבדיקות שנכשלו (מתוך הפלט המובנה של שלב הבדיקה) והנחיה מפורשת: לתקן רק מה שנדרש, בלי לשנות את כוונת התוכנית המאושרת. חשוב: הרשאות שלב התיקון כוללות עריכה וגם pytest, כדי שהסוכן יוכל לאמת את התיקון בעצמו לפני שהוא מחזיר שליטה.
  • אם אחרי כל הניסיונות הבדיקות עדיין אדומות, הסוכן לא מסתיר את זה: הדוח הסופי מסומן tests_passed: false וקוד היציאה של הסקריפט הוא 1, כך שגם בן אדם וגם מערכת CI רואים כישלון.

חלק 9: סקירה ודוח (שלב 8)

השלב האחרון חוזר להרשאות צרות: קריאה, Bash(git diff *) ו-Bash(git status *) בלבד. הסוכן מתבקש לסקור את השינוי של עצמו ולהפיק את הדוח הסופי לפי REPORT_SCHEMA. למה שלב סקירה נפרד ולא לסמוך על שלב הביצוע שידווח? משתי סיבות: ראשית, git diff מראה את מה שקרה בפועל על הדיסק, כולל שינויים משלבי התיקון, ולא את מה שהסוכן זוכר שהתכוון לעשות; שנית, ניסיון מעשי מראה שבקשת ביקורת עצמית מפורשת ("סקור את השינוי שלך") מעלה בעיות שהסוכן לא היה מציין מיוזמתו, כמו Edge Case שלא כוסה בבדיקה. שדה follow_ups בסכמה נותן לזה בית מסודר בדוח. הסקריפט מדפיס את הדוח ואחריו את שורת החשבונאות של כל שלב, מתוך הנתונים שנצברו מכל ResultMessage:

הפלט למעלה הוא המחשה של מבנה הפלט הצפוי, לא תמליל של הרצה אמיתית: המספרים והניסוחים ישתנו מריצה לריצה (ראו סעיף האימות בהמשך).

אימות אחרי ריצה

אל תסמכו על הדוח של הסוכן; אמתו בעצמכם. רשימת בדיקה אחרי כל ריצה:

  • git status ו-git diff: האם שונו בדיוק הקבצים שהתוכנית הבטיחה? קובץ לא צפוי ברשימה הוא דגל אדום.
  • הרצת הבדיקות בעצמכם: python -m pytest backend/tests -q. התוצאה צריכה להתאים ל-tests_passed שבדוח.
  • קריאת ה-Diff בעיניים: האם השינוי מינימלי וממוקד, או שהסוכן "שיפץ" דברים שלא התבקשו?
  • בדיקת הלוג לדחיות הרשאה: דחיות רבות מעידות שהסוכן ניסה שוב ושוב לחרוג מהמגבלות, וכדאי להבין למה.
  • העלות הכוללת מול הצפי: ריצה על TaskFlow שעולה פי כמה מהרגיל מעידה על שוטטות או לולאת תיקונים שהתארכה.

שיקולי Cost ו-Context

  • ה-Resume חוסך כסף פעמיים: גם כי הסוכן לא קורא קבצים מחדש בכל שלב, וגם כי ה-Prompt Caching האוטומטי של ה-SDK מנצל את ההיסטוריה המשותפת. שרשרת שלבים על Session אחד זולה משמעותית מחמישה Sessions נפרדים על אותו קוד.
  • אבל Session מתארך צובר Context: אחרי הרבה שלבים, ההיסטוריה גדלה והעלות לכל תור עולה (פרק 30). לסוכן עם עשרות שלבים שקלו לפצל: להעביר לשלב הבא רק את הסיכום המובנה של השלב הקודם ב-Prompt, במקום resume, בדיוק כפי שהתיעוד מציע לסביבות ארעיות.
  • מודלים לפי שלב: האפשרות model נקבעת לכל query() בנפרד. שלב בדיקות פשוט יכול לרוץ על מודל קטן ומהיר, ואת המודל החזק לשמור למחקר ולביצוע.
  • כוונון התקרות הוא איטרטיבי: התחילו מהערכים שבקובץ, הריצו על משימות אמיתיות, וקראו את שורות החשבונאות. אחרי חמש עד עשר ריצות תדעו מה נורמלי לפרויקט שלכם, ותוכלו להדק את התקציב סביבו.

Security: סיכום המעקות

  • ארבעה סטים של הרשאות, אחד לכל סוג שלב; אף שלב לא מקבל יותר ממה שהוא צריך.
  • כללי Deny גלובליים שחלים בכל מצב הרשאות, כולל על git push, מחיקות רקורסיביות וקבצי סודות.
  • כלי הרשת הוסרו לגמרי: הסוכן לא יכול להדליף קוד החוצה וגם לא למשוך הוראות זדוניות מהאינטרנט.
  • שער אישור אנושי לפני כל כתיבה; ברירת המחדל היא דחייה.
  • Callback שדוחה כברירת מחדל כל מה שלא אושר מראש, עם Log מלא של הדחיות.
  • תקציב כפול (שלב וריצה) ותקרות Turns בכל שלב.
סכנה

אל תריצו את הסוכן עם permission_mode="bypassPermissions" "כדי שיהיה מהיר". במצב הזה allowed_tools לא מגביל דבר וכל כלי מאושר. אם אתם חייבים אוטונומיה מלאה, עשו זאת רק בתוך קונטיינר מבודד בלי אישורי רשת ובלי גישה ל-Repositories אמיתיים, כמתואר בתיעוד ה-Hosting וה-Secure Deployment.

Best Practices ו-Anti-patterns

  • עשו: שלבים נפרדים עם resume משותף; פלט מובנה בין שלבים; תקרות בכל שלב; Log לכל דחיית הרשאה; קוד יציאה שמשקף את האמת.
  • אל: שלב אחד ענק שעושה הכול (Anti-pattern); Retry אוטומטי על כשל לוגי של המודל (זה רק שורף תקציב); הסתרת כישלון בדיקות בדוח; הרחבת allowed_tools "ליתר ביטחון".
  • עשו: הריצו קודם על Repository משוכפל או על Branch נפרד. הסוכן עורך קבצים אמיתיים; Git הוא רשת הביטחון שלכם.

תרגיל

תרגיל 32.1: הוספת שלב Lint לסוכן

הרחיבו את 02_code_reviewer.py בשלב Lint שרץ אחרי שהבדיקות עוברות ולפני שלב הסקירה: הסוכן מריץ ruff check . על ה-Repository, ואם יש ממצאים בקבצים שהשתנו, מתקן אותם (עד שני ניסיונות) ומריץ שוב גם את ה-Lint וגם את הבדיקות. דרישות: (1) סט הרשאות ייעודי לשלב, שמאשר רק את פקודות ה-ruff ואת pytest; (2) פלט מובנה עם clean (בוליאני) ו-issues (רשימה); (3) הממצאים שלא תוקנו מופיעים בדוח הסופי. רמז: תבנית הכלל היא "Bash(ruff check *)", ותצטרכו גם "Bash(ruff format *)" אם תרצו תיקון פורמט אוטומטי.

ולבסוף, בשלב הדוח, מזינים את הממצאים שנשארו ל-Prompt הסקירה (למשל: "Unresolved lint issues: ...") כדי שייכנסו ל-review_notes. שימו לב לשלושה עקרונות שחוזרים מהפרק: שלב הבדיקה של ה-Lint הוא קריאה בלבד עם dontAsk; שלב התיקון מקבל גם pytest כדי לוודא שתיקון סגנון לא שבר לוגיקה; והלולאה חסומה בתקרה. הפתרון עבר את אותו אימות כמו שאר הקוד בפרק: קומפילציה ובדיקת שמות API, ללא הרצה מול ה-API.

סיכום

  • סוכן אמין בנוי משלבים מוגדרים, כל אחד עם קריאת query() נפרדת והרשאות מינימליות משלו, מחוברים ב-resume לאותו Session.
  • פלט מובנה בין השלבים (output_format) הופך את הסוכן לרכיב תוכנה שאפשר לבנות עליו לוגיקה.
  • שער אישור אנושי לפני כתיבה הוא שורת קוד אחת שמונעת את רוב האסונות; ברירת המחדל תמיד דוחה.
  • מדיניות Retry מבחינה בין כשל תעבורה (מנסים שוב) לכשל לוגי (מטפלים, לא חוזרים בעיוורון), ולולאת תיקוני הבדיקות חסומה בתקרה.
  • עלות נצברת מכל ResultMessage ונאכפת בשתי רמות: תקציב לשלב (SDK) ותקציב לריצה (הקוד שלכם).
  • הדוח הסופי אומר את האמת, כולל בדיקות שנכשלו, וקוד היציאה משקף אותה.

בפרק הבא נעבור מהסוכן הבודד לאוטומציה בקנה מידה: מצב לא אינטראקטיבי של Claude Code, אינטגרציה עם CI, משימות מתוזמנות וגבולות הבטיחות של הרצה ללא השגחה.
