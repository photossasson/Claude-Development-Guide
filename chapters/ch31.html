מבוא ל-Claude Agent SDK

עד עכשיו עבדנו עם Claude Code כמוצר: טרמינל אינטראקטיבי שמדברים איתו. בפרק הזה נכיר את ה-Claude Agent SDK: אותו מנוע בדיוק, אותם Tools, אותה לולאה אג'נטית ואותו ניהול Context, אבל כספרייה שמתכנתים ב-Python או ב-TypeScript. נבין מתי לבחור בו לעומת ה-CLI, ה-API הישיר ו-Managed Agents, נתקין אותו, נריץ שאילתה ראשונה בשתי השפות, ונעבור על כל אבני הבניין: הרשאות, Hooks, Subagents, Sessions, פלט מובנה ומעקב עלויות. כל שם ופרמטר בפרק אומתו מול התיעוד הרשמי בתאריך המחקר.

מה זה Agent SDK: ה-Harness כספרייה

בפרק 1 ראינו שמה שהופך מודל שפה לסוכן קוד מעשי הוא ה-Agentic Harness: המעטפת שנותנת למודל כלים (קריאת קבצים, הרצת פקודות, עריכה), מריצה את הלולאה של תכנון, פעולה ובחינת תוצאה, ומנהלת את ה-Context וההרשאות. ב-Claude Code המעטפת הזאת ארוזה בתוך ממשק טרמינל. ה-Claude Agent SDK חושף את אותה מעטפת בדיוק כספרייה: אתם קוראים לפונקציה query() עם Prompt ואובייקט אפשרויות, וה-SDK מריץ עבורכם את כל הלולאה, כולל הפעלת ה-Tools בפועל, ומזרים אליכם הודעות עד לתוצאה הסופית.

טכנית, ה-SDK מפעיל תהליך משנה (Subprocess) של Claude Code ומתקשר איתו דרך stdio. שתי החבילות הרשמיות מגיעות עם קובץ הרצה מובנה של Claude Code, כך שברוב המקרים אין צורך בהתקנה נפרדת של ה-CLI. המשמעות המעשית: כל מה שלמדתם בפרקים הקודמים על Permissions, CLAUDE.md, MCP, Skills ו-Hooks תקף גם כאן, רק שהפעם אתם שולטים בהכול מקוד.

מה ה-SDK עושה בשבילכם, לפי התיעוד: התיאום של הלולאה, ההרצה בפועל של הכלים, ניהול ה-Context (כולל Compaction ו-Prompt Caching אוטומטי), וניסיונות חוזרים מול ה-API. מה שנשאר לכם: לנסח את המשימה, להגדיר גבולות, ולצרוך את זרם ההודעות. זה ההבדל המהותי מול עבודה ישירה עם ה-Messages API, שבה כל קריאת כלי חוזרת אליכם ואתם אחראים להריץ אותה ולהחזיר תוצאה.

הערת שם

בעבר החבילות נקראו Claude Code SDK. השם הנוכחי הוא Claude Agent SDK, והחבילות הן claude-agent-sdk (Python) ו-@anthropic-ai/claude-agent-sdk (TypeScript). אם אתם רואים בקוד ישן @anthropic-ai/claude-code כחבילת SDK, זה השם הישן.

איזו בעיה זה פותר, ומתי להשתמש

ה-CLI מצוין לעבודה אינטראקטיבית, אבל יש משימות שבהן אתם רוצים סוכן שרץ בתוך אפליקציה: Bot שמטפל בפניות, שירות שמנתח Pull Requests, מערכת פנימית שמתקנת באגים לפי כרטיסי Issue, או צינור עיבוד שרץ על עשרות Repositories. בכל המקרים האלה אתם צריכים: שליטה תוכניתית בהרשאות (כולל Callback שמחליט בזמן ריצה), פלט מובנה שאפשר להזין לקוד, ניהול Sessions מרובים, וטיפול בשגיאות ובעלויות. זה בדיוק מה שה-SDK נותן.

מתי לא להשתמש ב-Agent SDK: אם אתם רק רוצים לשוחח עם המודל בלי כלים ובלי לולאה אג'נטית, ה-Client SDK של ה-API הישיר פשוט וזול יותר. אם אתם צריכים סקריפט חד-פעמי, לרוב מספיק claude -p (פרק 33). ואם אתם לא רוצים לתחזק תשתית בכלל, בדקו את Managed Agents.

query() ראשון בשתי השפות

הפונקציה query() היא נקודת הכניסה המרכזית. היא פותחת Session חדש, מריצה את הלולאה האג'נטית, ומחזירה Async Iterator שמזרים הודעות תוך כדי עבודה. מבנה פרויקט מינימלי לניסוי נראה כך:

מבנה תיקיית ניסוי
my-agent/
├── .venv/  או  node_modules/     # תלות ההתקנה
├── agent.py  או  agent.ts        # הסוכן עצמו
└── utils.py                      # קובץ עם באגים מכוונים לתרגול

שתי הדוגמאות הבאות זהות לדוגמת ה-Quickstart הרשמית והן הבסיס לקבצים agent-sdk/python/01_quickstart.py ו-agent-sdk/typescript/01-quickstart.ts שבחבילת המדריך. הן מבקשות מהסוכן לסקור קובץ utils.py (צרו אותו עם שתי פונקציות שקורסות על קלט ריק או None, כמו בתיעוד) ולתקן את מה שהוא מוצא:

agent.py (Python)
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AssistantMessage, ResultMessage


async def main():
    async for message in query(
        prompt="Review utils.py for bugs that would cause crashes. Fix any issues you find.",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Edit", "Glob"],   # אישור אוטומטי לכלים האלה
            permission_mode="acceptEdits",            # אישור אוטומטי לעריכות קבצים
        ),
    ):
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if hasattr(block, "text"):
                    print(block.text)                 # הטקסט של Claude
                elif hasattr(block, "name"):
                    print(f"Tool: {block.name}")      # קריאה לכלי
        elif isinstance(message, ResultMessage):
            print(f"Done: {message.subtype}")         # התוצאה הסופית


asyncio.run(main())
agent.ts (TypeScript)
import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const message of query({
  prompt: "Review utils.py for bugs that would cause crashes. Fix any issues you find.",
  options: {
    allowedTools: ["Read", "Edit", "Glob"],  // אישור אוטומטי לכלים האלה
    permissionMode: "acceptEdits"            // אישור אוטומטי לעריכות קבצים
  }
})) {
  if (message.type === "assistant" && message.message?.content) {
    for (const block of message.message.content) {
      if ("text" in block) console.log(block.text);
      else if ("name" in block) console.log(`Tool: ${block.name}`);
    }
  } else if (message.type === "result") {
    console.log(`Done: ${message.subtype}`);
  }
}

שימו לב להבדל הסגנוני העקבי: ב-Python שמות האפשרויות ב-snake_case (allowed_tools, permission_mode) וההודעות הן מחלקות dataclass שבודקים עם isinstance; ב-TypeScript השמות ב-camelCase (allowedTools, permissionMode) וההודעות הן Union Types שממיינים לפי השדה type. תוצאה צפויה בהרצה (עם מפתח API תקף): שורות טקסט של הסבר, שורות Tool: Read ו-Tool: Edit, ולבסוף Done: success.

התבנית השנייה: שיחה מתמשכת

כל קריאה ל-query() פותחת Session חדש. לשיחות מרובות תורות באותו הקשר יש לכל שפה תבנית מתועדת משלה:

  • Python: המחלקה ClaudeSDKClient מחזיקה Session פתוח. משתמשים בה כ-Async Context Manager: async with ClaudeSDKClient(options=...) as client, ואז await client.query("...") ו-client.receive_response() לכל תור. היא היחידה שתומכת גם ב-Interrupts (עצירה יזומה באמצע).
  • TypeScript: אין מחלקת Client; במקום זה מעבירים continue: true בקריאת query() הבאה, וה-SDK ממשיך את ה-Session האחרון בתיקייה.

כך נראית שיחה דו-שלבית ב-Python, על פי הדוגמה הרשמית בתיעוד ה-Sessions: השאילתה השנייה מקבלת אוטומטית את כל ההקשר של הראשונה, בלי לנהל מזהי Session ידנית:

client_example.py (קטע)
async with ClaudeSDKClient(options=options) as client:
    # שאילתה ראשונה: ה-Client שומר את מזהה ה-Session אצלו
    await client.query("Analyze the auth module")
    async for message in client.receive_response():
        print_response(message)

    # שאילתה שנייה: ממשיכה את אותו Session אוטומטית
    await client.query("Now refactor it to use JWT")
    async for message in client.receive_response():
        print_response(message)

כלל אצבע לבחירה: משימה חד-פעמית עם תוצאה אחת, query(); אפליקציה שמנהלת דו-שיח (צ'אט, עוזר אינטראקטיבי) או צריכה לעצור את הסוכן באמצע, ClaudeSDKClient. בפרק 32 נשתמש דווקא ב-query() עם resume מפורש, כי שם אנחנו רוצים להחליף את סט ההרשאות בין שלב לשלב, וזה בדיוק המקרה שבו שליטה ידנית במזהה עדיפה על ניהול אוטומטי.

הלולאה האג'נטית במונחי SDK

הלולאה שהכרנו בפרק 1 מקבלת כאן צורה של זרם הודעות. לפי תיעוד Agent Loop הרשמי, כל Session עובר את המחזור הבא:

  1. קבלת ה-Prompt. ה-SDK מזרים SystemMessage מסוג init עם מטא-נתונים של ה-Session (מודל, כלים, מזהה Session).
  2. הערכה ותגובה. Claude מחזיר טקסט, בקשות לקריאת כלים, או שניהם: AssistantMessage עם בלוקים של TextBlock ו-ToolUseBlock.
  3. הרצת כלים. ה-SDK מריץ את הכלים בעצמו ומזין את התוצאות חזרה (UserMessage עם תוצאות הכלי). כאן נכנסים Hooks ובדיקות ההרשאות.
  4. חזרה על המחזור. כל סבב כזה הוא Turn אחד. הלולאה נמשכת עד שמתקבלת תשובה בלי קריאות כלים.
  5. תוצאה. ה-SDK מזרים ResultMessage אחרון עם הטקסט הסופי, מספר ה-Turns, נתוני השימוש והעלות המשוערת.

שני בלמים מתועדים כדאי להכיר כבר עכשיו: max_turns / maxTurns מגביל את מספר סבבי הכלים, ו-max_budget_usd / maxBudgetUsd עוצר את השאילתה כשהאומדן הכספי מגיע לתקרה. כשמגבלה נחצית, ה-ResultMessage מגיע עם subtype של error_max_turns או error_max_budget_usd, ובקריאת query() חד-פעמית ה-SDK גם זורק חריגה אחרי ההודעה. התיעוד ממליץ במפורש להגדיר תקציב כברירת מחדל לסוכני Production.

אילו Tools מובנים זמינים

כברירת מחדל הסוכן מקבל את אותם כלים מובנים שהכרתם ב-CLI, ובהם: Read, Write, Edit, Bash, Glob, Grep, WebSearch, WebFetch, NotebookEdit, TodoWrite, Agent (הפעלת Subagents), Skill ו-AskUserQuestion. הרשימה המלאה, כולל אילו כלים דורשים אישור, נמצאת ב-Tools reference הרשמי. שתי דרכים לשלוט ברשימה עצמה:

  • tools: רשימת הכלים שקיימים בכלל עבור המודל, או ה-Preset {"type": "preset", "preset": "claude_code"} לקבלת ערכת ברירת המחדל של Claude Code.
  • disallowed_tools / disallowedTools: שם כלי מלא (כמו "Bash") מסיר את הכלי מה-Context לגמרי; כלל עם תבנית (כמו "Bash(rm *)") משאיר את הכלי אבל דוחה קריאות תואמות בכל מצב הרשאות, כולל bypassPermissions.

בנוסף אפשר להוסיף כלים משלכם דרך MCP: הפונקציות tool() ו-create_sdk_mcp_server() (בשתי השפות, בסגנון המתאים לכל שפה) יוצרות שרת MCP שרץ בתוך התהליך שלכם, בלי תהליך חיצוני ובלי תקורת תקשורת. כך זה נראה ב-Python, על פי הדוגמה הרשמית:

custom_tool.py (קטע, על פי תיעוד Custom tools)
from claude_agent_sdk import tool, create_sdk_mcp_server, ClaudeAgentOptions

@tool("greet", "Greet a user", {"name": str})
async def greet(args):
    return {"content": [{"type": "text", "text": f"Hello, {args['name']}!"}]}

server = create_sdk_mcp_server(name="my-tools", version="1.0.0", tools=[greet])
options = ClaudeAgentOptions(
    mcp_servers={"my-tools": server},
    allowed_tools=["mcp__my-tools__greet"],   # שם מלא: mcp__<server>__<tool>
)

שימו לב למוסכמת השמות: כלי MCP מקבל את השם mcp__<שם-השרת>__<שם-הכלי>, וזה השם שמופיע בכללי ההרשאות. הדקורטור @tool מקבל שם, תיאור וסכמת קלט (מיפוי טיפוסים פשוט או JSON Schema מלא). זה הנושא של תיעוד Custom tools; נעמיק בו כשנצטרך כלי כזה בפועל.

האפשרויות המרכזיות של ClaudeAgentOptions / Options

אובייקט האפשרויות הוא לוח הבקרה של הסוכן. אלה השדות שתשתמשו בהם בפועל, כפי שהם מתועדים היום (Python בסוגריים כשהשם שונה):

אפשרותמה היא עושה

הרשאות: המצבים וה-Callback

כשסוכן רץ בלי אדם מול המסך, אין חלון "Allow?". במקום זה, לפי תיעוד ה-Permissions של ה-SDK, כל בקשת כלי עוברת שרשרת קבועה של שישה שלבים: Hooks, כללי Deny, כללי Ask, מצב ההרשאות, כללי Allow, ולבסוף ה-Callback canUseTool. שתי מסקנות מעשיות מהסדר הזה:

  • כלי שאושר בשלב מוקדם (למשל דרך allowed_tools או acceptEdits) לעולם לא מגיע ל-Callback שלכם. בדיקות שחייבות לרוץ על כל קריאה שמים ב-Hook מסוג PreToolUse, שרץ תמיד ראשון.
  • כללי Deny עם תבנית גוברים על הכול, כולל bypassPermissions.

מצבי ההרשאות המתועדים: default (כל מה שלא אושר נופל ל-Callback), acceptEdits (עריכות קבצים ופקודות מערכת קבצים בסיסיות מאושרות אוטומטית בתוך תיקיית העבודה), plan (חקירה ותכנון בלי לגעת בקבצים), dontAsk (כל מה שלא אושר מראש נדחה בלי לשאול; הבסיס המומלץ לסוכן Headless עם משטח כלים קבוע), bypassPermissions (אישור כמעט גורף; מסוכן, רק בסביבה מבודדת) ו-auto (מסווג מבוסס מודל מחליט במקום חלונות אישור). דוגמה מתועדת ל-Callback ב-Python:

permission_callback.py (קטע)
from claude_agent_sdk import PermissionResultAllow, PermissionResultDeny

async def can_use_tool(tool_name, input_data, context):
    if tool_name == "Bash" and "rm -rf" in input_data.get("command", ""):
        return PermissionResultDeny(message="Destructive command blocked", interrupt=True)
    return PermissionResultAllow()

options = ClaudeAgentOptions(can_use_tool=can_use_tool)

Hooks בתוך ה-SDK

את מנגנון ה-Hooks הכרנו בפרק ייעודי כסקריפטים חיצוניים. ב-SDK הם הופכים לפונקציות רגילות בקוד שלכם, שנרשמות דרך האפשרות hooks לפי אירוע (PreToolUse, PostToolUse, SessionStart ועוד) עם HookMatcher שמסנן לפי שם כלי. הדוגמה הרשמית המקוצרת, Hook שחוסם פקודת Shell מסוכנת:

hook_example.py (קטע, על פי הדוגמה הרשמית)
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher, HookContext
from typing import Any

async def validate_bash_command(
    input_data: dict[str, Any], tool_use_id: str | None, context: HookContext
) -> dict[str, Any]:
    if input_data["tool_name"] == "Bash":
        command = input_data["tool_input"].get("command", "")
        if "rm -rf /" in command:
            return {
                "hookSpecificOutput": {
                    "hookEventName": "PreToolUse",
                    "permissionDecision": "deny",
                    "permissionDecisionReason": "Dangerous command blocked",
                }
            }
    return {}

options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[validate_bash_command])]}
)

ההבדל המכריע בין Hook לבין can_use_tool: ה-Hook רץ ראשון בשרשרת, על כל קריאה, בכל מצב הרשאות, כולל bypassPermissions; ה-Callback רץ רק כשהבקשה נופלת עד סוף השרשרת. לכן חסימות אבטחה קשיחות שייכות ל-Hooks, והחלטות "לאשר או לא" אינטראקטיביות שייכות ל-Callback.

Subagents: הקבלה ובידוד Context

הפרמטר agents מאפשר להגדיר Subagents ישירות בקוד, בלי קובצי Markdown בתיקיית .claude/agents/ (שתי הדרכים נתמכות; ההגדרה התוכניתית גוברת בשמות זהים). כל Subagent מקבל description (מתי להשתמש בו), prompt (ה-System Prompt שלו), ואופציונלית tools מצומצמים, model שונה, maxTurns ועוד. הסוכן הראשי מפעיל אותם דרך הכלי Agent, ולכן כדאי לכלול "Agent" ב-allowed_tools. שלושת היתרונות המתועדים: בידוד Context (רק ההודעה הסופית של ה-Subagent חוזרת לשיחה הראשית), מקבול (כמה Subagents רצים בו-זמנית), והתמחות (לכל אחד Prompt וכלים משלו).

subagents_example.py (קטע, על פי הדוגמה הרשמית)
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Agent"],
    agents={
        "code-reviewer": AgentDefinition(
            description="Expert code review specialist.",
            prompt="You are a code review specialist...",
            tools=["Read", "Grep", "Glob"],   # קריאה בלבד
            model="sonnet",
        ),
    },
)
שימו לב לאותיות

ב-Python, שדות AgentDefinition נשארים ב-camelCase (disallowedTools, maxTurns, permissionMode) כי הם ממופים ישירות לפורמט המשותף עם TypeScript. זה שונה מ-ClaudeAgentOptions שהוא snake_case. העברת שם ב-snake_case ל-AgentDefinition זורקת TypeError.

פלט מובנה (Structured Output)

כשסוכן הוא חלק ממערכת, טקסט חופשי הוא בעיה: צריך לנתח אותו. האפשרות output_format / outputFormat עם {"type": "json_schema", "schema": {...}} מבטיחה שבסוף הריצה תקבלו ב-ResultMessage.structured_output אובייקט JSON שאומת מול הסכמה שהגדרתם (ה-SDK תומך ב-JSON Schema draft-07; מסכמת Zod ממירים עם target: "draft-7", ומ-Pydantic עם model_json_schema()). אם המודל לא מצליח לייצר פלט תקין אחרי מספר ניסיונות, מתקבל subtype של error_max_structured_output_retries. גם תוצאה עם subtype: "success" יכולה להגיע בלי structured_output, ולכן הקוד צריך לבדוק את שניהם. דוגמה מלאה בפרק 33.

Streaming

ברירת המחדל כבר "מזרימה" ברמת הודעות: אתם מקבלים כל AssistantMessage ותוצאת כלי ברגע שהם קורים. מי שצריך רזולוציה של Tokens בודדים (למשל להדפסה חיה ב-UI) מדליק include_partial_messages=True ומקבל בנוסף אירועי StreamEvent גולמיים של ה-API. לרוב משימות האוטומציה אין בזה צורך: Job ברקע או ב-CI פשוט צורך את ההודעות המלאות, וזה גם מה שהתיעוד ממליץ. כיוון הזרימה השני קיים גם הוא: הפרמטר prompt מקבל לא רק מחרוזת אלא גם Async Iterable של הודעות, מה שמאפשר להזין קלט בהדרגה תוך כדי ריצה (Streaming Input) בלי לפתוח Session חדש לכל הודעה.

Sessions והתמדה

כמו ב-CLI, כל ריצה נשמרת כ-Session בדיסק (קובצי JSONL תחת ~/.claude/projects/). שלוש פעולות מתועדות:

  • Continue: continue_conversation=True (או continue: true) ממשיך את ה-Session האחרון בתיקייה, בלי לנהל מזהים.
  • Resume: שומרים את session_id מתוך ה-ResultMessage ומעבירים אותו כ-resume בקריאה הבאה; הסוכן חוזר עם כל ההקשר הקודם. זו התבנית שנשתמש בה בפרק 32 כדי לחבר בין שלב המחקר לשלב הביצוע.
  • Fork: resume יחד עם fork_session=True יוצר Session חדש שמתחיל מעותק של ההיסטוריה, בלי לגעת במקור. שימושי לבחינת שתי גישות במקביל.

חשוב להבין: Session שומר את השיחה, לא את מערכת הקבצים. שחזור קבצים הוא תפקיד ה-File Checkpointing (אפשרות enable_file_checkpointing). להרצה בסביבות ארעיות (CI, קונטיינרים) שבהן הדיסק לא שורד, התיעוד מציע שתיים: העברת קובץ ה-Session בעצמכם, או מתאם SessionStore שמשקף את התמלילים לאחסון חיצוני משותף. ב-TypeScript יש גם persistSession: false לריצות חד-פעמיות שלא צריכות להישמר כלל.

מעקב עלויות

כל ResultMessage מסכם את הריצה: total_cost_usd (אומדן מצטבר), usage (Tokens של הלולאה הראשית, כולל cache_read_input_tokens ו-cache_creation_input_tokens), ו-model_usage / modelUsage (פירוט לפי מודל, כולל פעילות Subagents). שלוש נקודות מתועדות שחוסכות הפתעות:

  • המספרים הם אומדן צד-לקוח מטבלת מחירים שנארזה בזמן ה-Build, לא נתוני חיוב מחייבים. לחיוב אמיתי משתמשים ב-Usage and Cost API או ב-Console. אל תחייבו לקוחות לפי השדות האלה.
  • שדה ה-usage סופר רק את הלולאה הראשית; Tokens של Subagents נכללים ב-total_cost_usd וב-model_usage אבל לא ב-usage.
  • כל קריאת query() מדווחת רק על עצמה. סכום כולל על פני כמה קריאות (או כמה משתמשים) צוברים בעצמכם, כמו שעושה הסוכן בפרק 32.
  • גם תוצאה שנגמרת בשגיאה נושאת נתוני עלות: הTokens שנצרכו עד הכשל עדיין נספרים, אז קראו את הנתונים מכל ResultMessage, בלי תלות ב-subtype.

ה-SDK מפעיל Prompt Caching אוטומטית. לעומסי עבודה עם הפסקות ארוכות בין ריצות אפשר להאריך את חיי ה-Cache לשעה עם משתנה הסביבה ENABLE_PROMPT_CACHING_1H (כתיבת Cache כזו יקרה יותר; ראו פרק 30 על עקרונות עלות).

בסיס ל-Hosting

כשמעבירים סוכן ל-Production, המודל המנטלי החשוב הוא: Session אחד = תהליך claude אחד, עם Shell, תיקיית עבודה וקובצי Session בדיסק המקומי. N ריצות מקבילות הן N תהליכי משנה. מזה נגזרות שלוש תבניות הפריסה שבתיעוד ה-Hosting:

  • Ephemeral: קונטיינר לכל משימה, שנהרס בסיומה. מתאים למשימות חד-פעמיות (תיקון Bug, עיבוד מסמך).
  • Long-running: קונטיינרים קבועים שמחזיקים Sessions פתוחים (Bot תמידי, שירות צ'אט). ב-Python מחזיקים ClaudeSDKClient; ב-TypeScript משתמשים ב-streamInput() וב-startup() לחימום מוקדם.
  • Hybrid: קונטיינרים ארעיים שנטענים מ-SessionStore חיצוני בעלייה ושומרים אליו בירידה. חובה SessionStore, אחרת התמליל אובד.

לכל ריצה מבודדת מעבירים cwd נפרד, ובסביבות רגישות מוסיפים Sandboxing ברמת הקונטיינר. שלוש נקודות תפעוליות נוספות מהתיעוד: מדיניות ה-Retry המובנית של ה-CLI נשלטת דרך משתני סביבה כמו API_TIMEOUT_MS ו-CLAUDE_CODE_MAX_RETRIES שמועברים באפשרות env; ל-Observability משתמשים ב-Callback של stderr וברישום ה-ResultMessage של כל ריצה; ולסביבות מרובות דיירים (Multi-Tenant) התיעוד מדגיש בידוד ברמת קונטיינר לכל דייר, לא רק ברמת תיקייה. מי שלא רוצה לנהל את כל זה, זו בדיוק הנישה של Managed Agents (Beta). פירוט אבטחתי מלא יש בתיעוד Secure Deployment הרשמי.

Best Practices ו-Anti-patterns

  • עשו: תקציב ותקרת Turns לכל שאילתה; cwd מפורש; פלט מובנה כשמערכת אחרת צורכת את התוצאה; רישום session_id ועלות מכל ריצה.
  • עשו: התחילו מ-System Prompt מותאם וקצר. ה-Preset של Claude Code ({type:"preset", preset:"claude_code"}) שימושי כשרוצים את מלוא ההתנהגות של המוצר, אבל לרוב הסוכנים הממוקדים הוא עודף.
  • אל: bypassPermissions כפתרון עצלות לבעיות הרשאה (Anti-pattern); לולאת שאילתות בלי צבירת עלות; ניתוח הטקסט של result ב-Regex במקום להשתמש ב-output_format; הנחה שהסוכן "יזכור" בין קריאות query() בלי resume או continue.
  • אל: לחייב לקוחות או לקבל החלטות פיננסיות לפי total_cost_usd; זה אומדן פיתוח, והתיעוד מזהיר על כך במפורש.

שיקולי Security

  • סוכן SDK הוא קוד שרץ עם ההרשאות של התהליך שלכם. הריצו אותו בתיקיית עבודה ייעודית, לא בשורש הבית.
  • התחילו כל סוכן חדש מ-permission_mode="default" או "dontAsk" עם allowed_tools מינימלי, והרחיבו רק לפי צורך מוכח.
  • זכרו ש-allowed_tools אינו מגביל את bypassPermissions: במצב הזה כל כלי מאושר. חסימה אמיתית עושים עם disallowed_tools או Hooks.
  • שקלו setting_sources=[] בסביבות Production, כדי שהסוכן לא יושפע מהגדרות וקבצים מקומיים שמישהו אחר שתל במכונה.
  • מפתחות API רק ממשתני סביבה או מנהל סודות; לעולם לא בקוד.

        async for message in query(
            prompt="Summarize the backend API endpoints and note any missing input validation",
            options=ClaudeAgentOptions(
                cwd="~/projects/taskflow",
                allowed_tools=["Read", "Glob", "Grep"],
                permission_mode="dontAsk",     # דרישה 2: דחייה במקום שאלה
                max_turns=10,                  # דרישה 3
                max_budget_usd=0.25,           # דרישה 3
            ),
        ):
            if isinstance(message, ResultMessage):
                if message.subtype == "success":
                    print(message.result)
                cost = message.total_cost_usd or 0
                print(f"turns={message.num_turns} cost=${cost:.4f}")
    except Exception as error:
        # query() חד-פעמי זורק חריגה אחרי הודעת תוצאה מסוג שגיאה
        print(f"ended with an error: {error}")


asyncio.run(main())

הנקודות המהותיות: permission_mode="dontAsk" הופך כל בקשה לא מאושרת לדחייה שקטה במקום להיתקע על Prompt שאין מי שיענה עליו, וזו התשובה גם לשאלת הבונוס: קריאת Bash לא נמצאת ב-allowed_tools, ולכן היא תידחה, Claude יקבל את הודעת הדחייה וימשיך בלעדיה. אם הריצה חורגת מהתקציב או מהמגבלה, מתקבל ResultMessage עם subtype של error_max_budget_usd או error_max_turns, ואחריו ה-SDK זורק חריגה שנתפסת ב-except.

סיכום

  • ה-Agent SDK הוא ה-Harness של Claude Code כספרייה ל-Python ול-TypeScript: אותם Tools, אותה לולאה, שליטה מקוד.
  • גבולות המוצרים: CLI לעבודה אינטראקטיבית, Agent SDK לסוכנים בתוך אפליקציות, Client SDK למי שבונה לולאה בעצמו, ו-Managed Agents (Beta) למי שלא רוצה תשתית.
  • הגרסאות בתאריך המחקר: claude-agent-sdk 0.2.139 ו-@anthropic-ai/claude-agent-sdk 0.3.233.
  • query() מזרים הודעות: SystemMessage, AssistantMessage, תוצאות כלים, ולבסוף ResultMessage עם עלות, שימוש ו-session_id.
  • שליטה בסוכן: allowed_tools ו-disallowed_tools, מצבי הרשאות, can_use_tool, Hooks, Subagents דרך agents, פלט מובנה דרך output_format.
  • בלמים לכל סוכן רציני: max_turns, max_budget_usd, ומעקב עלויות מתוך ה-ResultMessage (אומדן, לא חיוב).
  • Sessions נשמרים בדיסק וניתנים ל-Continue, Resume ו-Fork; ל-Production יש SessionStore ושלוש תבניות Hosting.

בפרק הבא ניקח את כל אבני הבניין האלה ונבנה מהן סוכן אמיתי ושלם: סוכן משימות פיתוח עם שלבי מחקר, תכנון, אישור אנושי, ביצוע ובדיקות.
