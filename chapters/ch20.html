Security

זהו פרק עמוד השדרה של המדריך בנושא אבטחה. כשנותנים לסוכן להריץ פקודות, לקרוא קבצים ולגשת לרשת, מודל האיום משתנה מקצה לקצה. כאן נבנה שכבה אחר שכבה: מודל האיום, הגנה מפני Prompt Injection, ניהול סודות, פעולות מסוכנות, גבולות האמון של הרחבות, שרשרת אספקה, פרטיות, רשימת בדיקה מלאה לפני אישור שינוי, ותרחיש תקיפה אמיתי מנותח. המטרה: לעבוד עם Claude Code במהירות, בלי להפוך את המהירות לפרצה.

מודל האיום: מה משתנה כשלסוכן יש ידיים

עורך קוד רגיל הוא כלי פסיבי: הוא מציג לכם טקסט ומחכה שתקלידו. Claude Code הוא סוכן פעיל. הוא פועל בלולאה שבה הוא מחליט בעצמו אילו כלים להפעיל, קורא את התוצאות, ומחליט על הצעד הבא. שלוש היכולות שהופכות אותו לשימושי הן בדיוק אלה שמרחיבות את משטח התקיפה:

  • קריאת קבצים. Claude קורא בעצמו קבצים מתיקיית העבודה. משמעות הדבר שכל טקסט בתיקייה, כולל קבצים שלא כתבתם אתם, יכול להיכנס להקשר של המודל.
  • הרצת פקודות. Claude מריץ פקודות Shell אמיתיות במחשב שלכם, עם ההרשאות שלכם. פקודה שמתחזה לתמימה יכולה למחוק קבצים, לשלוח נתונים החוצה, או להתקין תלות זדונית.
  • גישה לרשת. Claude יכול לשלוף תוכן מהאינטרנט (WebFetch), ופקודות שהוא מריץ יכולות לפתוח חיבורי רשת. זה הופך גם ערוץ קלט חדש (תוכן חיצוני זר) וגם ערוץ פלט אפשרי לזליגת מידע.

העיקרון המרכזי שמאחד את שלוש היכולות נקרא "קלט חיצוני לא מהימן" (External Untrusted Input): כל טקסט שנכנס להקשר של המודל וממקור שאינכם שולטים בו, קובץ README ב-Repository ששכפלתם, תגובה ב-Issue, דף אינטרנט, או פלט של שרת MCP צד שלישי, הוא נתון פוטנציאלית עוין. המודל אינו מבחין באופן מובנה בין "הוראה שאתם נתתם" לבין "הוראה שמישהו שתל בקובץ". מכאן נובעת כל שאר האבטחה.

הגישה של Claude Code לבעיה הזאת בנויה על שלושה עמודים מתועדים: ארכיטקטורה מבוססת הרשאות (ברירת מחדל של קריאה בלבד, אישור מפורש לכל פעולה שמשנה את המערכת), הגנות מובנות (Sandbox, גבול תיקיית עבודה, זיהוי הזרקות), ואחריות המשתמש. התיעוד הרשמי מנסח את העמוד השלישי בצורה חד משמעית: "ל-Claude Code יש רק את ההרשאות שאתם מעניקים לו. אתם אחראים לבחון את הקוד והפקודות המוצעים לבטיחות לפני אישור." אף הגנה טכנית אינה מחליפה את הבחינה הזאת.

שכבות משלימות, לא חלופיות

לאורך הפרק נחזור לשלוש שכבות שעובדות יחד: Permissions (מה Claude מנסה לעשות ומה מותר לו), Sandbox (מה פקודת Bash יכולה לגעת בו ברמת מערכת ההפעלה, גם אם הזרקה עקפה את שיקול הדעת של המודל), ובקרת אנוש (אתם, קוראים את ה-Diff לפני אישור). אף שכבה לבדה אינה מספיקה. יחד הן "הגנה לעומק" (Defense in Depth).

Prompt Injection: הזרקת הוראות דרך תוכן

Prompt Injection היא טכניקה שבה תוקף מכניס טקסט זדוני לתוך תוכן שהמודל קורא, במטרה לעקוף או לשנות את ההוראות שלו. במקום לתקוף אתכם ישירות, התוקף מסתמך על כך ש-Claude יקרא את הטקסט וינהג לפיו. זהו האיום המספר אחד בעבודה עם סוכני קוד, כי הוא מנצל את היכולת הבסיסית ביותר של הסוכן: לקרוא ולהבין טקסט.

מאיפה מגיעה ההזרקה

  • בתוך ה-Repository: קובץ README זדוני, הערות בקוד, טקסט של Issue או Pull Request, הודעות Commit. כל אלה נקראים לרוב כשמבקשים מ-Claude "תסקור את הפרויקט" או "תסכם את ה-Issues הפתוחים".
  • קבצים לא מהימנים: קבצי נתונים, לוגים, פלטים שנוצרו על ידי צד שלישי, קוד שהורדתם ולא סקרתם.
  • תוכן אינטרנט: כל דף ש-Claude שולף עם WebFetch או שפקודה מורידה עם curl.
  • נתונים ממקור MCP או Connector: פלט של שרת צד שלישי, למשל תוצאת חיפוש, תוכן טיקט, שורה ממסד נתונים. זהו וקטור מסוכן במיוחד כי הוא נראה "רשמי" ומגיע דרך כלי מהימן לכאורה.

ההגנות המובנות של Claude Code

התיעוד הרשמי מפרט מספר מנגנוני הגנה מובנים מפני הזרקות. חשוב להבין מה כל אחד עושה ומה מגבלותיו:

מנגנוןמה הוא עושה
Permission systemפעולות רגישות דורשות אישור מפורש. גם אם הזרקה שכנעה את Claude לנסות פעולה מסוכנת, בקשת ההרשאה עוצרת אותה לפני הביצוע.
Context-aware analysisניתוח הבקשה המלאה כדי לזהות הוראות שעלולות להזיק, במקום להסתכל על מחרוזת מבודדת.
Input sanitizationעיבוד קלט המשתמש כדי למנוע Command Injection.
Network command approvalפקודות שמושכות תוכן מהרשת כמו curl ו-wget אינן מאושרות אוטומטית כברירת מחדל. הן מבקשות אישור כמו כל פקודת Bash שאינה קריאה בלבד.
Isolated context windowsשליפת תוכן מהרשת (WebFetch) משתמשת בחלון הקשר נפרד, כדי להימנע מהזרקת Prompts זדוניים ישירות להקשר הראשי.

אזהרה: אף מערכת אינה חסינה לחלוטין

התיעוד הרשמי מנסח זאת מפורשות: "בעוד ההגנות הללו מפחיתות סיכון משמעותית, אף מערכת אינה חסינה לחלוטין מכל התקפה." ההגנות המובנות הן קו התחלה, לא קו סיום. ההגנה החשובה ביותר נשארת אצלכם.

ההגנות שבידיים שלכם

ההמלצות הרשמיות לעבודה עם תוכן לא מהימן ברורות ומעשיות:

  • בחנו כל פקודה מוצעת לפני אישור. קראו את הפקודה, לא רק את הכותרת. במסך בקשת ההרשאה ל-Bash אפשר ללחוץ Ctrl+E כדי לקבל הסבר של Claude על מה הפקודה עושה, למה היא רצה, ומה עלול להשתבש, מסומן Low risk, Med risk או High risk.
  • חקירה של קוד לא מוכר במצב קריאה בלבד. כששכפלתם Repository זר, התחילו במצב plan (Shift+Tab), שבו Claude חוקר ומתכנן בלי לערוך קבצים. כך התוכן הזר לא יכול לגרום לפעולת כתיבה.
  • אל תזרימו תוכן לא מהימן ישירות ל-Claude. הימנעו מ-cat untrusted.txt | claude וכדומה.
  • אמתו שינויים בקבצים קריטיים. קבצי הגדרה, קבצי CI/CD, סקריפטים של בנייה.
  • הפעילו את חלון ה-Trust ביודעין. אשרו "Yes, I trust this folder" רק אם אתם יודעים מהו מקור הקוד. חלון האמון גם מציג את חוקי ההרשאות שהתיקייה מבקשת להעניק, כפי שראינו בפרק 3.
  • השתמשו במכונות וירטואליות (VMs) להרצת סקריפטים וקריאות כלים, במיוחד באינטראקציה עם שירותי רשת חיצוניים.
  • דווחו על התנהגות חשודה עם /feedback.

סודות: מפתחות, אישורים ו-.env

סודות הם המטרה הכי שווה עבור תוקף: מפתח API אחד יכול לפתוח חשבון ענן שלם. שלושה עקרונות עומדים בבסיס ניהול סודות נכון מול Claude Code: לחסום קריאה, לא להקליד סודות ב-Prompt, ולנקות אחרי דליפה.

חסימת קריאה עם Deny Rules

הדרך הישירה לוודא ש-Claude לא יקרא קבצי סוד היא חוק deny בקובץ ההגדרות. חוקי Read ו-Edit משתמשים בתחביר תבניות של gitignore. הנה בסיס טוב:

.claude/settings.json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Read(**/*.pem)",
      "Read(**/*.key)",
      "Read(~/.ssh/**)",
      "Read(~/.aws/**)",
      "Read(**/secrets/**)",
      "Read(**/credentials*)"
    ]
  }
}

נקודות דיוק חשובות מהתיעוד:

  • Read(.env) שקול ל-Read(**/.env): הוא חוסם כל קובץ .env בתיקייה הנוכחית ומתחתיה, בכל עומק. שמות קבצים בודדים עוקבים אחר סמנטיקת gitignore ותופסים בכל עומק.
  • חוק deny של Read חוסם גם את כלי ה-Edit על אותו נתיב (כולל יצירת קובץ חדש שם), החל מגרסה 2.1.208. אבל הוא אינו חוסם את Write ו-NotebookEdit, אז לנתיבים שאף כלי לא ישנה, הוסיפו גם חוק Edit deny.
  • חוקי Read ו-Edit חלים על כלי הקבצים המובנים ועל פקודות קבצים ש-Claude Code מזהה ב-Bash כמו cat, head, tail ו-sed. הם אינם חלים על תהליכים חיצוניים שקוראים קבצים בעקיפין, למשל סקריפט Python שפותח קובץ בעצמו.
גבול חשוב של Deny Rules

חוק Read(.env) מונע מ-Claude ומפקודות קבצים מוכרות לקרוא את הקובץ. הוא לא מונע מסקריפט שרירותי (python leak.py) לקרוא אותו. לאכיפה ברמת מערכת ההפעלה שחוסמת כל תהליך, צריך Sandbox, שנגיע אליו בהמשך. זו הסיבה שהשכבות משלימות.

הגנת credentials ב-Sandbox

כשה-Sandbox מופעל, מדיניות הקריאה של ברירת המחדל עדיין מאפשרת קריאת קבצי אישורים כמו ~/.aws/credentials ו-~/.ssh/. כדי לחסום אותם ולנקות משתני סביבה סודיים מפקודות מסונדבקות, יש בלוק sandbox.credentials ייעודי:

.claude/settings.json (הגנת סודות ב-Sandbox)
{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}

עבור ערכי "mode": "deny", נתיבי קבצים נחסמים לקריאה בתוך ה-Sandbox, ומשתני הסביבה מבוטלים לפני כל פקודה מסונדבקת. אין רשימת חסימת אישורים מובנית, אז רק מה שתרשמו יוגן. משתני סביבה תומכים גם ב-"mode": "mask", שמחליף את הערך האמיתי בערך סנטינל, ומזריק את האמיתי רק בבקשות ליעדים מוגדרים דרך ה-Proxy, כך שהכלי ממשיך לעבוד בלי שהסוד ייחשף בלוגים. לניקוי אישורי Anthropic וספקי ענן מכל תת-התהליכים ללא קשר ל-Sandbox, אפשר להגדיר את משתנה הסביבה CLAUDE_CODE_SUBPROCESS_ENV_SCRUB.

היגיינת סודות

  • לעולם אל תדביקו סודות ב-Prompt. כל מה שכתבתם בשיחה נשמר ב-Transcript המקומי, וייתכן שנשלח לשרת המודל. השתמשו במשתני סביבה או ב-Secret Manager, והפנו אליהם בשם.
  • השתמשו בערכי דמה בדוגמאות. כשמבקשים מ-Claude לכתוב קוד שמשתמש במפתח, כתבו YOUR_API_KEY ולא את המפתח האמיתי.
  • נקו לוגים. לפני שיתוף פלט או Transcript, ודאו שאין בו Tokens. פקודות /feedback, /bug ו-/share מנסות למחוק תבניות מפתח ידועות, אבל אל תסמכו על זה כרשת יחידה.
סכנה: סוד שדלף ל-Session

אם סוד אמיתי (מפתח, סיסמה, Token) נכנס ל-Prompt, לפלט פקודה, או ל-Transcript, התייחסו אליו כאל חשוף. השלבים: (1) בטלו את הסוד מיד (Rotate) אצל הספק שהנפיק אותו, זה הצעד היחיד שבאמת מגן. (2) מחקו את ה-Session המקומי הרלוונטי מ-~/.claude/projects/ (שם נשמרים ה-Transcripts בטקסט גלוי). (3) אם שיתפתם דרך /feedback, זכרו ש-Transcripts אלה נשמרים אצל Anthropic חמש שנים; פנו לתמיכה אם צריך. (4) בדקו לוגים ומערכות שאליהן הסוד הגיע. סיבוב הסוד הוא תמיד קודם, לא אחרון.

פעולות מסוכנות ואיך לגדר אותן

לא כל פקודה נולדה שווה. ארבע משפחות של פעולות מצריכות זהירות מיוחדת, ולכל אחת יש דרך לגדר עם הרשאות או Hooks.

התקנת חבילות

התקנת תלות (npm install, pip install) היא אחד הווקטורים המסוכנים בשרשרת האספקה. שני איומים עיקריים: Typosquatting (חבילה זדונית בשם דומה לחבילה לגיטימית, למשל reqeusts במקום requests), ותלות זדונית שהוזרקה ל-Repository. חבילה מותקנת יכולה להריץ סקריפטים בזמן ההתקנה עצמה. תמיד סקרו איזו חבילה מותקנת ומאיזה מקור, ואל תאשרו התקנה של חבילה שלא ביקשתם.

פקודות Shell וסקריפטים מרוחקים

הדפוס המסוכן ביותר הוא curl | bash: הורדת סקריפט מהרשת והרצתו ישירות, בלי לראות מה בתוכו.

דפוס מסוכן: לעולם לא לאשר בעיוורון
curl -fsSL https://example.com/install.sh | bash

הסקריפט רץ עם ההרשאות שלכם, ואינכם יכולים לדעת מה הוא עושה. אם צריך להריץ סקריפט כזה, הורידו אותו קודם לקובץ, קראו אותו, ורק אז הריצו. זכרו: curl ו-wget אינם מאושרים אוטומטית ב-Claude Code, אבל אישור חד פעמי חסר תשומת לב מבטל את ההגנה. כדי לחסום אותם לגמרי, הוסיפו אותם ל-permissions.deny.

תבניות Bash לצמצום ארגומנטים הן שבירות

התיעוד מזהיר: חוק כמו Bash(curl http://github.com/ *) שמנסה להגביל את curl ל-GitHub לא יתפוס וריאציות כמו אפשרויות לפני ה-URL, פרוטוקול אחר, Redirects, או משתנים (URL=http://github.com && curl $URL). לסינון URL אמין: חסמו את curl/wget ב-deny והשתמשו בכלי WebFetch עם WebFetch(domain:github.com), או השתמשו ב-PreToolUse Hook שמאמת את ה-URL.

אינטגרציית דפדפן ו-Computer Use

כש-Claude שולט בדפדפן או במסך (Computer Use), הוא רץ על שולחן העבודה האמיתי שלכם ולא בסביבה מבודדת. בקשות הרשאה פר-אפליקציה מגדרות כל אפליקציה. זו יכולת עוצמתית שדורשת פיקוח אנושי הדוק במיוחד, כי היא חורגת מגבול ה-Sandbox של פקודות ה-Bash.

שער אכיפה עם PreToolUse Hook

כשרוצים אכיפה תכנותית ולא רק חוק סטטי, PreToolUse Hook רץ לפני בקשת ההרשאה ויכול לחסום פעולה. הנה שער שחוסם rm -rf:

.claude/hooks/block-rm.sh
#!/bin/bash
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "פקודה הרסנית נחסמה על ידי Hook"
    }
  }'
else
  exit 0
fi

החלטות ה-Hook אינן עוקפות את חוקי ההרשאות: חוק deny תואם עדיין חוסם, וחוק ask תואם עדיין מבקש אישור, גם אם ה-Hook החזיר "allow". זה משמר את סדר העדיפויות "deny תחילה".

גבולות האמון של הרחבות

ההרחבות של Claude Code מרחיבות את היכולות שלו, ובאותה מידה את משטח התקיפה. עיקרון הזהב: כל הרחבה היא קוד של מישהו אחר שרץ בהקשר שלכם. להלן טבלת גבולות המסכמת מי עושה מה, מי מתחזק, ואיך לגדר:

רכיבמה הוא יכול לעשותמי מתחזקאיך לגדר
MCP Server קוד צד שלישי מלא. קורא, כותב, מריץ, מתחבר לרשת דרך הכלים שהוא חושף ספק חיצוני (או אתם) אמון לפני חיבור, OAuth עם oauth.scopes מצומצם, חוקי mcp__server__tool, קריאה בלבד תחילה

MCP: קוד צד שלישי בכל מובן

התיעוד מזהיר במפורש: "ודאו שאתם סומכים על כל שרת לפני חיבורו. שרתים ששולפים תוכן חיצוני יכולים לחשוף אתכם לסיכון Prompt Injection." Anthropic בודקת Connectors מול קריטריוני רישום לפני הוספתם ל-Directory, אבל אינה מבצעת ביקורת אבטחה ואינה מנהלת שום שרת MCP. עקרונות עבודה בטוחה:

  • העדיפו שרתים שכתבתם בעצמכם או מספקים שאתם סומכים עליהם.
  • צמצמו OAuth Scopes. הגדירו oauth.scopes כדי לקבע את ההרשאות שהשרת מבקש לקבוצה מינימלית שאושרה, גם אם השרת מציע יותר.
  • קריאה בלבד תחילה. כשמתחברים לשרת מסד נתונים, השתמשו בחיבור readonly, כמו בדוגמה של --dsn "postgresql://readonly:...".
  • שרתים ברמת פרויקט (.mcp.json) ממתינים לאישור. Repository משוכפל אינו יכול לאשר את השרתים של עצמו: אישור דורש שתריצו claude ותאשרו את חלון האמון.
  • הגבילו פלט. Claude Code מזהיר כשפלט כלי MCP חורג מ-10,000 Tokens ומגביל ל-25,000 כברירת מחדל. פלט ענק ממקור לא מהימן הוא גם סיכון הזרקה וגם עלות.

Hooks: רצים עם ההרשאות שלכם

Hooks הם אולי הרכיב המסוכן ביותר לזלזל בו, כי הם רצים אוטומטית ועם כל הכוח שלכם: כל משתני הסביבה (כולל מפתחות ו-Tokens), הרשאות מערכת הקבצים, וגישת רשת. עקרונות:

  • סקרו כל Hook בתפריט /hooks לפני שאתם מפעילים אותו. התפריט מציג את הפקודה, ה-Prompt או ה-URL המדויקים, ומאיזה קובץ הגדרות ה-Hook הגיע.
  • עבור Hooks מסוג HTTP, רק משתנים ברשימת allowedEnvVars נפתרים לתוך הכותרות. אל תפזרו Tokens לכל ה-Hooks.
  • Hooks ברמת פרויקט ב-Frontmatter של Subagent רצים רק אחרי שאישרתם את חלון האמון של התיקייה שממנה הגיע קובץ הסוכן.
  • מנהלי ארגון יכולים לאכוף allowManagedHooksOnly כדי לחסום Hooks ממשתמש, מפרויקט וממקורות אחרים.
  • ה-Hook מסוג ConfigChange מאפשר לנטר שינויי הגדרות במהלך Session, כלי טוב לזיהוי שינוי לא מורשה של קונפיגורציה.

שרשרת אספקה, הרשאה מינימלית ו-Sandboxing

סיכוני שרשרת האספקה חוצים את כל הרכיבים: תלות זדונית, Plugin נגוע, שרת MCP שנפרץ, Marketplace לא מהימן. שני עקרונות מגן: הרשאה מינימלית (least privilege, תנו לכל רכיב בדיוק את מה שהוא צריך ולא יותר) וסקירה לפני פריסה. מעליהם, שכבת אכיפה קשיחה: ה-Sandbox.

איך ה-Sandbox עובד

ה-Sandbox המובנה נותן ל-Claude להריץ רוב פקודות ה-Shell בלי לעצור לבקשת אישור, כי במקום לאשר כל פקודה, אתם מגדירים אילו קבצים ואילו יעדי רשת פקודות יכולות לגעת בהם, ומערכת ההפעלה אוכפת את הגבול על כל פקודה ותת-התהליכים שלה. ההפעלה: /sandbox.

שתי שכבות בלתי תלויות: בידוד מערכת קבצים (אילו נתיבים פקודות יכולות לקרוא ולכתוב) ובידוד רשת (אילו דומיינים הן יכולות להגיע אליהם). ברירת המחדל: כתיבה רק לתיקיית העבודה ולתיקיית ה-Temp של ה-Session, וקריאה מכל המחשב פרט לנתיבים חסומים. שימו לב שקריאת ברירת המחדל עדיין מאפשרת קריאת אישורים, ולכן צריך את sandbox.credentials שראינו למעלה.

.claude/settings.json (בידוד רשת עם רשימת היתר)
{
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["github.com", "*.npmjs.org"]
    }
  }
}

לניהול ארגוני, מנהלים יכולים לאכוף עם Managed Settings: enabled: true, failIfUnavailable: true (סירוב הפעלה אם ה-Sandbox לא מצליח לעלות), ו-allowUnsandboxedCommands: false (ביטול מנגנון הנסיגה החוצה מה-Sandbox).

סכנה: Sandbox אינו גבול בידוד מלא

התיעוד מדגיש: "Sandboxing מפחית סיכון אבל אינו גבול בידוד מלא." שלוש מגבלות מרכזיות: (1) Proxy ברירת המחדל אינו בוחן תעבורת TLS, כך שדומיין רחב כמו github.com יכול לפתוח נתיב לזליגת מידע דרך Domain Fronting. (2) חשיפת Unix Sockets כמו /var/run/docker.sock יכולה לתת גישה למערכת המארחת. (3) הרשאות כתיבה רחבות מדי לתיקיות עם קבצי הרצה או קבצי Shell (.bashrc) מאפשרות הסלמת הרשאות. בידוד אפקטיבי דורש גם מערכת קבצים וגם רשת. בלי בידוד רשת, סוכן שנפרץ יכול להוציא מפתחות SSH. בלי בידוד קבצים, הוא יכול להשתיל דלת אחורית.

כלי סקירה מובנים

Claude Code מציע שכבות סקירת אבטחה כ-Plugins וכפקודות, שמשלימות זו את זו:

  • Security guidance plugin (Stable): לאחר /plugin install security-guidance@claude-plugins-official, הוא בודק את הקוד ש-Claude כותב תוך כדי עבודה, בשלוש נקודות: בדיקת תבניות פר-עריכה (ללא קריאת מודל, ללא עלות), סקירת Diff בסוף כל תור, וסקירה סוכנתית עמוקה בכל Commit/Push ש-Claude מבצע.
  • /security-review: מעבר אבטחה חד פעמי על ה-Branch הנוכחי, לפי דרישה.
  • Claude Security plugin: /claude-security מריץ סריקת פגיעויות רב-סוכנית של ה-Repository או של Diff, עם ממצאים שנבדקים באופן עצמאי והופכים ל-Patches שאתם סוקרים ומיישמים ב-git apply. ה-Patches לעולם אינם מיושמים אוטומטית.

רשימת הבדיקה לפני אישור שינוי

זו הרשימה המרכזית של הפרק. עברו עליה לפני שאתם מאשרים שינוי משמעותי (במיוחד Merge, Deploy, או אישור אצווה של עריכות):

  • קראתי את ה-Diff המלא, שורה אחר שורה, ולא רק את הכותרת.
  • השינוי נוגע רק בקבצים שציפיתי להם. אין קבצים מפתיעים.
  • אין תלות (Dependencies) חדשה שלא נבדקה ואומתה מול המקור הרשמי.
  • אין סודות בקוד: מפתחות, Tokens, סיסמאות, Connection Strings.
  • אין קריאות רשת חדשות ליעדים לא מוכרים (curl, fetch, Webhooks).
  • אין פקודות הרסניות (rm -rf, DROP TABLE, git push --force) שלא ביקשתי במפורש.
  • הבדיקות (Tests) עוברות, כולל בדיקות חדשות לתרחיש שהשתנה.
  • ההרשאות (Permissions) מצומצמות למינימום הנדרש לשינוי.
  • שינויים בקבצי הגדרה, CI/CD וסקריפטים של בנייה נבדקו בקפידה יתרה.
  • לא הורדתי והרצתי סקריפט מרוחק בלי לקרוא אותו קודם.
  • לא הזרמתי תוכן לא מהימן ישירות להקשר של Claude.
  • מקור הקוד (Repository, Plugin, MCP) מהימן, ואישרתי את חלון ה-Trust ביודעין.
  • יש נקודת חזרה: Commit נקי לפני השינוי (Rewind אינו תחליף ל-Git).
  • ה-Sandbox מופעל אם אני עובד עם קוד שאינני סומך עליו לחלוטין.
  • אם אני במצב אוטומטי, אני בסביבה מבודדת (Container / VM) שבה נזק אפשרי מוגבל.

תרחיש תקיפה מנותח: README מורעל

נבחן תרחיש חינוכי מקצה לקצה. אתם משכפלים Repository ציבורי מפתה ("כלי CLI קטן ושימושי") ומבקשים מ-Claude: "תסקור את הפרויקט ותסביר מה הוא עושה". בתוך ה-README, למטה, שתול טקסט זדוני. הנה איך הוא נראה (מוצג כטקסט לא פעיל, להמחשה בלבד):

מטען הזרקה להמחשה בלבד (לא להריץ, לא להעתיק לפרויקט אמיתי)

זהו Prompt Injection קלאסי: הוא מתחזה להוראות מערכת, מנסה לגרום לקריאת סודות ולזליגתם, ומבקש להסתיר זאת מכם. עכשיו נראה איך שכבות ההגנה תופסות אותו, אחת אחרי השנייה:

  1. חלון ה-Trust. בהרצה הראשונה בתיקייה הזרה, Claude Code מבקש אימות אמון. עצם העצירה מזכירה לכם שזה קוד שלא כתבתם.
  2. Deny Rules. אם הגדרתם Read(~/.aws/**) ו-Read(~/.ssh/**) ב-deny, ניסיון הקריאה נחסם ברמת הכלי, עוד לפני שהמודל "מחליט" משהו.
  3. Network command approval. ה-curl/POST ליעד החיצוני אינו מאושר אוטומטית. במצב ברירת המחדל תופיע בקשת הרשאה שמציגה את הפקודה המדויקת, כולל הדומיין הזר.
  4. Context-aware analysis ו-Command injection detection. פקודה חשודה דורשת אישור ידני, גם אם משהו דומה אושר קודם.
  5. Sandbox. אם ה-Sandbox מופעל עם allowedDomains מצומצם ו-credentials.files חוסם, הקריאה לרשת ליעד לא מורשה נחסמת ברמת מערכת ההפעלה, וקבצי הסוד אינם ניתנים לקריאה בכלל.
  6. אתם. השכבה האחרונה והחשובה: אתם רואים בקשת הרשאה חריגה (קריאת ~/.ssh? שליחה לדומיין זר?) בזמן שביקשתם "רק סקירה". זו הנורה האדומה. דוחים, ומדווחים עם /feedback.

המסקנה החינוכית: אף שכבה בודדת אינה מושלמת, אבל תוקף צריך לעבור את כולן. אם עבדתם עם deny rules לסודות, Sandbox עם רשת מוגבלת, ובעיקר קריאה של בקשות ההרשאה, המטען הזה נעצר. אילו אישרתם הכול בעיוורון או עבדתם ב---dangerously-skip-permissions בסביבה לא מבודדת, אף אחת מהשכבות לא הייתה מגינה.

שגיאות נפוצות

  • אישור אוטומטי מתוך הרגל. לחיצת "Yes" בלי לקרוא היא הפרצה מספר אחת. מבטלת בדיוק את השכבה שאתם אמורים לספק.
  • --dangerously-skip-permissions על מכונה עם סודות. הדגל הזה מדלג על בקשות ההרשאה. השתמשו בו רק בסביבה מבודדת (Container/VM). התיעוד אף חוסם אותו בהרצה כ-root ב-Linux/macOS.
  • להסתמך רק על deny rules. הם לא חוסמים סקריפטים שרירותיים. שלבו עם Sandbox לאכיפת מערכת הפעלה.
  • לחבר שרת MCP צד שלישי בלי לבדוק Scopes. Token OAuth רחב מדי הוא מפתח לכל השירות.
  • להתקין Plugin מ-Marketplace לא מוכר. Plugin אורז Hooks ו-MCP שרצים עם ההרשאות שלכם.
  • להדביק מפתח אמיתי ל-Prompt "רק לבדיקה". הוא נשמר ב-Transcript. השתמשו ב-YOUR_API_KEY.
  • Sandbox עם רשת פתוחה. בידוד קבצים בלי בידוד רשת מאפשר זליגת מפתחות. צריך את שניהם.

Troubleshooting

שני כיווני תקלה הפוכים: חסימות מוגזמות ופרצות שקטות.

חסימות שגויות (False Positives) וחוקים מגבילים מדי

  • פקודה לגיטימית נחסמת בלי סוף. בדקו את הסדר: חוקי deny נבדקים לפני ask ולפני allow, וחוק deny רחב (Bash(aws *)) חוסם גם קריאה שתואמת חוק allow צר יותר. הסירו את ה-deny הרחב או צמצמו אותו.
  • Sandbox חוסם כלי שצריך רשת. תופעה נפוצה: jest נתקע (הריצו jest --no-watchman), docker לא תואם (הוסיפו ל-excludedCommands), כלי Go כמו gh ו-gcloud נכשלים ב-TLS תחת Seatbelt (הוסיפו ל-excludedCommands).
  • WebFetch נכשל כי הרשת חוסמת את api.anthropic.com. בדיקת הבטיחות של הדומיין דורשת גישה. הוסיפו לרשימת ההיתר או הגדירו skipWebFetchPreflight: true (ואז שלבו עם חוקי WebFetch להגבלת דומיינים).
  • חוק deny לא תופס. זכרו את סמנטיקת הנתיבים: /path יחיד מעוגן למקור ההגדרות, לא לשורש מערכת הקבצים. לנתיב מוחלט השתמשו ב-//path. לבית השתמשו ב-~/path.

חוקים מגבילים מדי בצוות

אם הגדרתם Managed Settings אגרסיביים והצוות "נחנק", השתמשו ב-allowManagedPermissionRulesOnly בזהירות: הוא מונע ממשתמשים ומפרויקטים להגדיר חוקי allow. עדיף להתחיל מרשימת deny ממוקדת (סודות, פקודות הרסניות) ולהרחיב לפי צורך, מאשר לחסום הכול ולתסכל.

שיקול עלות

לאבטחה יש שני "מחירים" הפוכים. מצד אחד, בדיקת התבניות של Security guidance plugin פר-עריכה אינה עולה Tokens (אין קריאת מודל). מצד שני, הסקירות מבוססות-המודל (סוף תור, Commit) והסריקה של Claude Security צורכות שימוש שנספר במכסה שלכם כמו כל בקשה. סקירה סוכנתית של Commit עשויה לקחת כמה תורות מודל (מוגבל ל-20 סקירות בשעה מתגלגלת). המסקנה המעשית: ההגנות ה"זולות" (deny rules, Sandbox, קריאת Diff) חינמיות ב-Tokens ומגינות הכי הרבה. הפעילו אותן תמיד. הסריקות היקרות שמורות לרגעים שבהם צריך עומק (לפני Merge גדול, לפני Release).

Best Practices

  • ברירת מחדל מגבילה, הרחבה מדודה. התחילו מ-deny rules לסודות ולפקודות הרסניות, והרחיבו allow לפי צורך אמיתי.
  • הגנה לעומק תמיד. Permissions + Sandbox + בקרת אנוש. אף אחד לבד.
  • חלקו הגדרות אבטחה ב-Version Control. .claude/settings.json מגיע לכל הצוות. ההגדרה המאובטחת הופכת לברירת המחדל של כולם.
  • הפעילו את Security guidance plugin. הוא זול (או חינמי בשכבת התבניות) ותופס פגיעויות תוך כדי כתיבה.
  • בקרו הרשאות תקופתית עם /permissions. חוקים מצטברים; נקו את מה שכבר לא צריך.
  • מצב אוטומטי רק בסביבה מבודדת. Dev Container או VM שבהם נזק מוגבל.
  • Commit לפני שינוי גדול. Git הוא רשת הביטחון האמיתית, לא Rewind.
  • למנהלי ארגון: Managed Settings לאכיפת סטנדרטים, disableBypassPermissionsMode, ניטור עם OpenTelemetry, ו-ConfigChange hooks לביקורת שינויים.

Anti-patterns

  • "אני סומך על Claude, אני מאשר הכול." אמון במודל אינו אמון בתוכן שהוא קורא. ההזרקה תוקפת דרך התוכן.
  • --dangerously-skip-permissions כברירת מחדל. הופך את כל שכבת ההרשאות לחסרת משמעות.
  • Sandbox עם allowedDomains רחב ("*", github.com לבד). פותח נתיב זליגה. צמצמו לדומיינים ספציפיים.
  • סודות ב-.env בתיקיית העבודה בלי deny rule. הם נגישים לקריאה כברירת מחדל.
  • חיבור MCP צד שלישי עם Scopes מלאים "כדי שיעבוד". צמצמו עם oauth.scopes.
  • התקנת Plugin מ-Marketplace אקראי בלי סקירה. קוד של מישהו אחר עם ההרשאות שלכם.
  • Hooks שמפזרים Tokens לכל משתני הסביבה. השתמשו ב-allowedEnvVars.

תרגיל

תרגיל 20.1: הקשחת ה-.claude/settings.json של TaskFlow

TaskFlow הוא פרויקט הדוגמה שלנו (Backend ב-Python/FastAPI עם SQLite, Frontend ב-React). בנו קובץ .claude/settings.json מוקשח שעונה על הדרישות הבאות:

  1. רשימת Deny לסודות: חסמו קריאת .env וכל וריאציה, מפתחות .pem ו-.key, וגם ~/.ssh ו-~/.aws (למקרה של הרחבת תיקיות).
  2. חסימת פקודות רשת ישירות: חסמו curl ו-wget, כדי לכפות שימוש ב-WebFetch מבוקר.
  3. מניעת push הרסני: חסמו git push --force.
  4. הפעלת Sandbox עם בידוד קבצים, בידוד רשת שמאפשר רק את הדומיינים שהפרויקט צריך (למשל PyPI ו-npm), והגנת credentials על ~/.aws.
  5. מניעת מצב Bypass: ודאו שאי אפשר להשתמש ב-bypassPermissions.

כתבו את הקובץ המלא. הסבירו ליד כל בלוק מה הוא מגן מפניו.

פתרון מוסבר
.claude/settings.json (TaskFlow, מוקשח)
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Read(**/*.pem)",
      "Read(**/*.key)",
      "Read(~/.ssh/**)",
      "Read(~/.aws/**)",
      "Bash(curl *)",
      "Bash(wget *)",
      "Bash(git push --force *)",
      "Bash(git push -f *)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": [
        "pypi.org",
        "*.pypi.org",
        "files.pythonhosted.org",
        "registry.npmjs.org",
        "*.npmjs.org"
      ]
    },
    "credentials": {
      "files": [
        { "path": "~/.aws", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "AWS_SECRET_ACCESS_KEY", "mode": "deny" }
      ]
    }
  }
}

הסבר בלוק אחר בלוק:

  • שורות Read בתוך deny: חוסמות קריאת סודות ברמת הכלי ופקודות הקבצים המוכרות. Read(.env) תופס בכל עומק, וה-~/ מבטיח שגם אם תרחיבו תיקיות (--add-dir), הבית מוגן. זוכרים: זה לא חוסם סקריפט שרירותי, ולכן ה-Sandbox משלים.
  • Bash(curl *) ו-Bash(wget *) ב-deny: כופים שכל שליפת רשת תעבור דרך WebFetch עם בדיקת בטיחות דומיין, במקום פקודה שקשה לגדר בתבניות.
  • git push --force: מונע דריסת היסטוריה משותפת בטעות. שתי הצורות (--force ו--f) כי הן שקולות.
  • disableBypassPermissionsMode: "disable": נועל את מצב ה-Bypass. עובד מכל Scope, וכך אף אחד לא ידלג על ההרשאות בטעות.
  • sandbox.network.allowedDomains: בידוד רשת שמאפשר רק את המקורות שהפרויקט באמת צריך להורדת תלות. כל יעד אחר יבקש אישור (או ייחסם בהגדרה ארגונית), מה שעוצר זליגת מידע דרך פקודות מסונדבקות.
  • sandbox.credentials: חוסם קריאת ~/.aws ו-~/.ssh גם בתוך ה-Sandbox (שם ברירת המחדל מתירה קריאתם), ומבטל את משתן הסביבה הסודי מפקודות מסונדבקות.

נקודה לדיון: שימו לב ש-Read(.env) ב-deny חוסם גם את Edit על .env (מגרסה 2.1.208). אם צריך למנוע גם Write, הוסיפו Edit(.env) נפרד. ולבסוף, הקובץ הזה מגיע ל-Version Control, כך שההקשחה הופכת לברירת המחדל של כל מי שמשכפל את TaskFlow.

סיכום

אבטחה ב-Claude Code אינה תכונה בודדת אלא מערך שכבות. ראינו את מודל האיום שנפתח כשלסוכן יש ידיים: קריאה, הרצה ורשת, ואת העיקרון המאחד של קלט חיצוני לא מהימן. עברנו על Prompt Injection ומקורותיה, על ההגנות המובנות ועל ההגנות שבידיים שלכם. למדנו לנהל סודות עם deny rules ו-sandbox.credentials, לגדר פעולות מסוכנות, ולמפות את גבולות האמון של MCP, Connectors, Hooks, Plugins ו-Subagents. בנינו הבנה של שרשרת האספקה, הרשאה מינימלית ו-Sandboxing ברמת מערכת ההפעלה (Seatbelt, bubblewrap), וסקרנו את מדיניות הנתונים והפרטיות. הכלי המרכזי שתיקחו הוא רשימת הבדיקה לפני אישור שינוי, והתרחיש המנותח הראה איך השכבות עובדות יחד כדי לעצור מטען אמיתי. העיקרון האחרון, החשוב מכולם: המהירות של Claude Code שווה משהו רק כשהיא נשענת על בקרה. אתם עורכים ראשיים, לא צופים. בפרק הבא נעבור ל-Skills, דרך לארוז ידע והנחיות שחוזרים על עצמם.
